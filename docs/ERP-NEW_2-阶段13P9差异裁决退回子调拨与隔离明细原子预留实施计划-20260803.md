# ERP-NEW_2 阶段 13P9：差异裁决退回子调拨与隔离明细原子预留实施计划

> 日期：2026-08-03
>
> 分支：`codex/erp-new-2-rebuild`
>
> 基线：`283df7e5 feat: compose adjudication reship effect owner`
>
> 范围：实现未接线退回效果所有者与专属隔离明细预留；不开放差异执行入口，不实现退回发货，不启动运行环境

## 1. 审计结论

退回来源不能调用普通 `InvTransferReservationService`。普通预留只在商品汇总库存上把 `available_quantity` 转为 `locked_quantity`，无法证明受损数量来自哪一条 V2 收货分配、受损派生批次、隔离库位或具体序列号。阶段 13P9 必须建立独立的隔离库存所有权模型，同时复用标准调拨的组织方向、物料快照、不可变修订和审批提交能力。

现有 V2 收货事实已经提供完整锚点：

1. `inv_transfer_shipment_receipt_allocation` 保存受损数量、源成本、隔离批次、隔离库位和隔离余额；
2. `inv_stock` 与 `inv_stock_balance_detail` 均满足 `current = available + locked + quarantine`；
3. 序列号收货审计保存原发货单件与当前隔离单件的唯一关系；
4. 阶段 13P7 已唯一推导反向调拨方向、类型、业务来源、库存来源和效果引用；
5. 标准 `saveDraft` 与提交封存链已拥有组织、物料、修订、审批、outbox 和状态日志语义，退回只替换库存预留所有者，不复制审批规则。

## 2. 固定方向和发起组织

退回子调拨始终反转父调拨方向：

| 父调拨类型 | 子调拨类型 | 子来源 | 子目标 | 标准发起组织 |
| --- | --- | --- | --- | --- |
| `warehouse` | `store_return` | 原目标门店 | 原来源仓库 | 原目标门店 |
| `store_return` | `warehouse` | 原目标仓库 | 原来源门店 | 原来源门店 |
| `cross_store` | `cross_store` | 原目标门店 | 原来源门店 | 原目标门店 |

由 `warehouse` 反转出的 `store_return` 使用固定系统原因 `DAMAGED_RECEIPT_RETURN`，原因正文只记录裁决动作 ID，不从客户端接收自由文本。

## 3. 专属隔离预留模型

新增两张惰性表：

- `inv_transfer_quarantine_reservation`：一条裁决动作、一张子调拨、一条明细和一个审批轮次只能有一条隔离预留；保存事项、裁决、动作、V2 收货分配、汇总库存、隔离余额、批次、库位、数量、成本、版本前后值和决定指纹。
- `inv_transfer_quarantine_reservation_serial`：序列号物料按 `receipt_serial_id` 与 `serial_id` 双唯一绑定具体隔离单件，保存 `quarantine -> quarantine_reserved` 状态证据。

两张表只服务 ERP-NEW_2 未来独立数据库迁移；当前不执行 SQL。隔离预留不写普通 `inv_transfer_reservation`，两种库存来源不可混用。

## 4. 原子数量变换

对汇总库存与目标隔离余额执行完全相同的守恒变换：

```text
current_after    = current_before
available_after  = available_before
locked_after     = locked_before + action_quantity
quarantine_after = quarantine_before - action_quantity
total_cost_after = total_cost_before
version_after    = version_before + 1
```

受损派生余额必须保持 `available_quantity = 0`，但允许已有其他退回动作形成的 `locked_quantity`。物理隔离余额不足、V2 分配累计处置超量、成本锚点漂移或版本冲突均失败关闭。

序列号动作数量必须为正整数；候选单件按 `receipt_serial_id, serial_id` 稳定排序，只选择本收货分配下仍为 `quarantine` 且未被受损写销或其他退回预留占用的单件。

## 5. 固定事务顺序

新增 `InvTransferReceiptDiscrepancyReturnEffectOwner`，`dispatch` 使用 `Propagation.MANDATORY`，只能由未来差异执行外层事务调用：

1. 校验请求、执行权限、当前登录身份和选择组织；
2. 锁定动作已有 P7 工作流关系，一致请求只返回原关系；
3. 锁定受损事项、裁决、退回动作、父调拨与 V2 收货分配；
4. 纯策略推导反向子调拨与系统返仓原因；
5. 调用标准 `saveDraft` 创建单明细草稿及不可变草稿修订；
6. 锁定回读草稿头和明细，验证业务来源、方向、物料和数量；
7. 按汇总库存、批次、库位、隔离余额、序列号顺序锁定全部库存事实；
8. 纯策略一次性验证全部事实并生成守恒变换；
9. 更新汇总库存和隔离余额，冻结序列号，追加隔离预留及单件绑定；
10. 复用标准审批提交封存逻辑，把草稿推进到 `submitted` 或 `approved`；
11. 锁定回读子调拨与隔离预留事实，生成 P7 工作流关系并条件追加；
12. 返回关系，供未来外层事务追加 dispatch 事件并推进动作状态。

关系、审批 outbox、状态日志或后续事件任一步失败时，上述草稿、修订、隔离冻结、预留与序列号状态必须由同一外层事务整体回滚。

## 6. 标准提交复用边界

`InvTransferServiceImpl` 仅把现有“库存已冻结之后”的审批提交逻辑提取为同类内部复用方法：

- 普通 `submitTransfer` 仍先调用普通可用库存预留，再进入同一提交封存逻辑；
- 退回效果所有者只能在来源业务为 `transfer_discrepancy_return`、草稿和唯一明细已精确核验、专属隔离预留已形成后调用；
- 不新增 Controller、HTTP、RPC、任务或消息入口；
- 不改变普通调拨现有行为、权限、审批或库存语义。

## 7. 验证

- 三种父调拨类型均唯一推导反向方向、类型和发起组织；
- 非 `damaged/return_to_source`、错误组织、错误锚点、数量金额漂移全部失败关闭；
- 汇总库存和隔离余额严格执行 `quarantine -> locked` 守恒；
- 批次动作拒绝序列号，序列号动作拒绝非整数、数量不足、重复或已占用单件；
- Mapper XML 可解析、方法全部绑定、锁序与条件 DML 完整；
- SQL 迁移只新增两张专属表，不复制到 Docker 初始化目录、不连接任何数据库；
- 效果所有者、专属 Mapper 和提交复用方法没有运行入口；
- 定向测试与 inventory 完整离线 Reactor 通过。

- 不实现隔离预留的发货消耗、审批拒绝释放或完成命令；
- 不执行 SQL，不连接 MySQL、Redis、Nacos 或任何数据库；
- 不启动 Docker、服务或中间件，不安装依赖；
- 不修改端口、配置、凭据或密钥；
- 不删除旧前端，不访问受保护原项目，不合并、不推送。
