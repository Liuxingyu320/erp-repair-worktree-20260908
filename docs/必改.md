# 多账号多店铺电脑端必改清单

来源报告：`docs/desktop-multi-account-store-audit-20260622.md`

## 筛选口径

本文件只放上线/验收前必须收口的问题。判定为“必改”的标准是：不改会造成主流程走不通、跨账号/跨店铺越权、成本/库存/工资/合同数据错误、敏感数据泄露、账号安全失控、审计证据无法追溯，或当前页面入口本身不可稳定使用。

原报告里的普通体验优化、文案提示、低风险导出确认、未交付模块残留表、纯视觉一致性和可后置的效率问题，不放入必改主清单。

## 必改明细

### 1. 成本字段读写权限必须统一到后端

必须改的原因：当前问题不是“页面展示不美观”，而是后端接口已经把成本价、采购价、库存总成本、毛利等字段返回给无成本权限角色；部分接口还允许无成本权限角色写入或改变成本字段。仅隐藏前端列没有意义。

必须改的内容：

- 商品列表、商品详情、供应商供货商品、采购商品选择、采购单详情、采购退货、库存列表、库存详情、库存汇总、库存流水、库存盘点详情、调拨详情、报表汇总、库存导出等接口都要在后端按 `inv:cost:view` 或独立“采购价/成本价”权限做字段级脱敏。
- 商品新增、编辑、导入必须在服务层校验成本写权限；无权限请求携带 `purchasePrice/costPrice` 时应拒绝或忽略，并记录审计。
- 库存调整要拆分“数量调整”和“成本影响”权限；无成本权限角色不能在不知情的情况下改变库存总成本。
- 销售出库必须保存原出库成本快照；销售退货入库要按原出库成本冲回，不能按当前库存成本或零成本。

涉及原报告编号：P1-01、P1-09、P1-24、P1-25、P1-26、P1-27、P1-28、P1-29、P1-30、P1-31、P1-32、P1-33、P2-77。

### 2. 账号密码、会话和权限撤销必须收口

必须改的原因：多账号多店铺系统最怕账号创建后不可控、弱密码长期可用、密码哈希进入前端、撤权后旧 token 继续使用。这些属于安全底线，不是体验优化。

必须改的内容：

- `sys.user.initPassword` 必须满足当前密码策略；新增、导入、注册、重置密码、个人改密必须共用同一套后端密码策略。
- 导入用户不能绕过密码策略创建 `123456` 这类弱初始密码账号。
- 首次登录/密码过期如果定义为强制策略，取消后不能继续进入系统。
- 用户详情、分配角色、个人中心、`getInfo` 等接口不得返回 BCrypt 密码哈希。
- 登录页“记住密码”不能保存可逆密码；共用电脑场景要避免串号。
- 修改角色、菜单、店铺授权、用户状态后，应刷新或吊销相关在线 token，不能等到 token 自然过期。
- 选择组织页取消登录必须清空 Vuex 角色、权限、用户信息和动态路由，不能让下一账号复用上一账号前端状态。

涉及原报告编号：P1-03、P1-11、P1-17、P2-07、P2-63、P2-86、P2-111、P2-113、P2-114、P2-115、P2-119、P2-125、P2-127、P2-132、P3-147。

### 3. 多店铺、多仓库授权边界必须以后端为准

必须改的原因：当前有多处只靠前端过滤或页面提示来表达组织边界，后端仍可被构造请求绕过。多店铺场景下这会直接造成跨店库存、跨仓采购、跨组织工资/合同/固定资产数据错位。

必须改的内容：

- 店铺授权页“组织范围”只能展示 `sys_user_shop` 显式授权；用户所属部门不能伪装成已授权门店。
- 店铺授权保存不能无确认清空全部授权；保存前后必须展示目标用户、授权差异和影响。
- 销售退货保存/提交必须后端校验原销售单属于当前门店。
- 采购退货保存/提交必须后端校验原采购单属于当前仓库。
- 库存盘点取消、删除草稿、库存调整、客户新增、薪资绑定、劳动合同发起等都要在服务层校验当前组织可写范围。
- 业务角色不应拥有部门组织树、菜单、角色、用户、店铺授权这类平台级写权限，除非产品明确把它定义为平台管理员。
- OA 路由也必须纳入组织选择守卫；管理员全局查看要显式显示“全局范围”，普通账号缺组织上下文时应跳转选择组织，不应在页面内报 500。

涉及原报告编号：P1-06、P1-12、P1-13、P2-01、P2-11、P2-60、P2-70、P2-72、P2-99、P2-100、P2-101、P2-102、P2-103、P2-116、P2-117、P2-121、P2-129、P2-133、P2-157、P2-159、P2-166。

### 4. 销售到发货到退货主流程必须跑通

必须改的原因：当前销售链路存在发货仓库候选为空、跨店发货组织类型冲突、销售单客户自由文本、无库存商品可提交、退货后端原单边界不校验等问题。这个链路是 ERP 核心业务，不能作为可后置体验项。

必须改的内容：

- 销售单客户字段改为客户主数据选择器，支持新建客户后回填；禁止仓库上下文新增门店客户。
- 销售制单时展示可用库存、可发仓库和缺货状态；零库存商品应禁选或进入明确预售/缺货状态。
- 发货通知可用仓库模型要重新定义，不能按“仓库必须是销售门店子节点”过滤。
- 仓库角色、门店角色、运营角色谁执行发货通知必须明确，并同步权限、菜单和后端校验。
- 跨店销售发货不能前端要求选择 `WAREHOUSE`，后端又自动生成要求来源为 `STORE` 的 `cross_store` 调拨。
- 发货通知部分发货后必须有关闭/取消剩余数量出口。
- 出库记录、库存流水、发货通知明细之间要有稳定关联，能从销售单追到每次发货和库存变化。
- 销售退货和采购退货都必须以原单为权威来源，后端校验归属、状态、已发/已收、已退和可退数量。

涉及原报告编号：P1-10、P1-12、P1-13、P2-04、P2-21、P2-22、P2-23、P2-28、P2-31、P2-32、P2-64、P2-65、P2-95、P2-164、P3-123、P3-124、P3-125。

### 5. 采购、商品、供应商主数据必须先治理

必须改的原因：采购链路依赖商品、供应商、采购价、分类和组织归属。当前不可采购商品会进入选择器，导入会自动在当前组织新建同名分类，供应商名称字符串被下游引用，供应商改名/停用不会保护采购链路。

必须改的内容：

- 采购商品选择器只展示主数据完整且可采购的商品；缺供应商、缺采购价、缺单位、缺编码的商品应禁选或明显标记。
- 商品导入规则要和页面规则一致，不能把待完善商品直接落入正式商品池。
- 商品分类、商品、供应商必须明确是集团共享还是仓库本地，列表可见范围、保存组织、导入匹配、编码生成使用同一口径。
- 采购单是否允许混选多个供应商必须定义清楚；如果不允许，前后端都要拦截。
- 供应商暂停/终止/停用后，采购制单不能继续只按商品上的供应商名称放行。
- 供应商改名时要保护或同步商品引用，避免采购链路按旧名称断开。

涉及原报告编号：P1-07、P2-18、P2-21、P2-22、P2-23、P2-66、P2-68、P2-105、P2-106、P2-109、P2-120、P2-24。

### 6. 库存、调拨和盘点的动作入口必须稳定

必须改的原因：库存调整、盘点确认、调拨发货/收货都会改变库存。当前部分入口存在上下文不匹配仍显示高危按钮、深链空白、部分发货批次不可收货、调拨审批只有通过没有驳回意见等问题。

必须改的内容：

- `/inventory/stock`、`/cangku/stock` 根据当前组织类型严格控制按钮、弹窗和提交接口。
- 仓库“可见库存”只读模式下不能打开库存调整。
- 可见库存范围和库存变动日志范围要一致，日志能解释同范围库存变化。
- 调拨应按发货批次状态显示收货入口，不能只按整单状态判断。
- 调拨审批电脑端要补齐后端已有的驳回和审批意见；如果短期只允许通过，就清理配置里的驳回语义。
- 调拨规则保存前要校验真实审批岗位、节点顺序、范围组织和候选审批人。
- 库存盘点确认前展示盈亏汇总，取消/删除草稿也做当前组织可写校验。
- 仓库和销售链路深链、刷新、菜单点击、首页跳转都要回归，不能出现 URL/面包屑已变但正文仍是首页或空白。

涉及原报告编号：P2-11、P2-14、P2-15、P2-25、P2-26、P2-27、P2-28、P2-29、P2-30、P2-40、P2-61、P2-94、P2-165、P3-119、P3-130、P3-131、P3-138。

### 7. 用户创建、导入、角色和店铺授权闭环必须可验收

必须改的原因：用户创建后如果不能稳定完成角色和店铺授权，就不是真正的多账号交付。当前新增、导入、授权、角色候选、配置状态都存在断点或误导。

必须改的内容：

- 用户列表必须真实返回并展示 `setupStatus/roleCount/shopScopeCount`，能筛出缺角色、缺组织授权、缺岗位的账号。
- 新增用户接口返回新用户 ID，前端用 ID 跳转店铺授权页。
- 用户导入不能只写基础账号，导入后要引导或批量配置角色、岗位、店铺/仓库授权。
- 角色分配候选必须展示部门、组织类型、已有角色和店铺/仓库授权摘要，避免店长角色选到仓库/集团/无部门用户。
- 店铺授权页搜索、重置、翻页后必须清空或校验当前目标用户；右侧面板和保存确认必须展示目标账号、昵称、用户 ID 和授权差异。
- 角色授权取消不能把账号变成无角色状态，除非有强确认和后端兜底。

涉及原报告编号：P1-02、P2-06、P2-36、P2-100、P2-112、P2-118、P2-129、P2-166、P3-183、P3-187、P3-188、P3-189。

### 8. 工资、考勤和薪资配置必须保护工资计算口径

必须改的原因：考勤和薪资直接影响工资。当前缺签退仍按正常工作日计算，工资配置覆盖薄弱，薪资绑定结束日期不可维护，员工薪资绑定可绕过门店关系。

必须改的内容：

- 考勤日期后端统一返回本地 `yyyy-MM-dd`，今日状态由后端返回，不靠前端截字符串判断。
- 缺签退记录必须进入异常/缺卡状态，工资计算前置校验不能把 `check_out_time/work_hours` 为空的 normal 记录当完整工作日。
- “我的考勤”和“全部考勤管理”权限拆开；全部视图和导出必须展示员工和组织。
- 工资计算前检查门店工资参数、员工薪资绑定、异常考勤、重复有效绑定。
- 员工薪资绑定保存接口校验员工与核算门店关系；保存失败不得先删除旧绑定。
- 薪资方案/档位删除必须预检员工和角色绑定影响。
- 员工薪资绑定结束日期要在前端可见、可维护，并参与冲突提示。

涉及原报告编号：P1-08、P2-12、P2-43、P2-52、P2-53、P2-54、P2-104、P2-107、P2-122、P2-157、P2-161、P2-168、P3-98、P3-151、P3-280。

### 9. 劳动合同证据链必须保护已签合同和身份字段

必须改的原因：劳动合同是正式证据。当前已签合同可直接作废，合同可挂到错误组织，hash 验证写事件且不按组织过滤，无效身份证/手机号也能签署。

必须改的内容：

- 已签合同不能走普通作废；必须拆成解除/终止/作废审批流程，要求原因、附件、审批人和事件链。
- 发起签约时校验员工归属、合同主体组织、身份证、手机号、员工姓名和企业章证据快照。
- 企业章配置在合同发送后要冻结快照，不能签署归档时使用被替换的新章。
- hash 验证按当前组织范围过滤，并明确这是会写事件的动作。
- 合同列表接口不要批量返回身份证、文件 URL、签署环境等详情字段；详情接口按权限读取。

涉及原报告编号：P1-34、P2-46、P2-47、P2-123、P2-124、P2-158、P2-163、P2-167。

### 10. 固定资产模块必须二选一：补齐上线条件或隐藏

必须改的原因：当前表、菜单、页面都像已上线，但只有 admin 授权、没有样例资产和额度数据，额度 GET 会写库，维修上报不校验配置表，删除配置会断历史关系。如果不交付，应隐藏；如果交付，必须补完整。

必须改的内容：

- 明确固定资产是否属于本次电脑端交付；不交付则隐藏菜单、移动端入口和相关按钮权限。
- 若交付，补角色矩阵、样例资产、额度初始化和空态引导，门店维修上报不能只授权超级管理员。
- GET 额度查询不能自动写入额度记录；初始化、重算、异常批准、确认上报要拆成明确写操作。
- 普通维修上报和异常批准都必须校验商品属于当前店铺启用固定资产配置。
- 固定资产配置不能物理删除已被维修单/额度流水引用的资产；应停用/退役并保留配置快照。
- 编辑资产所属店铺时必须同时重算原店铺和新店铺额度，或禁止编辑归属。
- 数量、资产金额、年度比例必须后端和数据库兜底校验。

涉及原报告编号：P1-05、P2-48、P2-49、P2-50、P2-51、P3-139、P3-140、P3-160、P3-164、P3-165。

### 11. 文件上传、公告和公开文件必须按安全边界重做

必须改的原因：劳动合同模板、企业章、公告富文本图片、通用上传都涉及文件上传和公开访问。当前权限树没有 `file:%`，文件 URL 可公开直连，富文本用 `v-html` 渲染，表单构建默认上传到外部演示站点。

必须改的内容：

- `file:upload/file:delete` 要进入权限树，并与劳动合同模板、企业章、业务附件维护权限联动。
- 合同模板、企业章等敏感文件不能默认落到公开白名单 URL；需要鉴权下载、文件元数据、删除审计和生命周期管理。
- 公告富文本后端过滤危险 HTML，前端渲染前做安全处理；公告图片上传和粘贴使用同一大小/类型校验和失败提示。
- 通用文件删除要检查真实删除结果，失败时不能静默成功。
- 表单构建上传组件默认地址不能指向第三方演示接口，生成代码前必须强制配置本系统上传接口或留空。

涉及原报告编号：P2-76、P2-88、P2-126、P3-148、P3-150、P3-256、P3-257、P3-278。

### 12. 日志、审计和运行态口径必须可追溯

必须改的原因：多账号多店铺问题最终都要靠日志、状态审计和稳定运行态口径追责。当前日志时区错、可直接清空、单据状态审计无入口，运行态 jar/源码/数据库和非运行态 schema 曾多次冲突。

必须改的内容：

- 登录日志、操作日志时间统一到系统时区，导出和页面一致。
- 日志详情、导出、删除/清空分层授权；敏感请求参数脱敏。
- 清空日志不能直接 `truncate` 正式表；必须有归档、二次确认、记录数、时间范围、hash 和操作者。
- 单据状态审计表、触发器、后端接口必须接入电脑端页面或单据详情时间线，并按组织范围过滤。
- 状态审计和库存流水要记录稳定用户 ID、昵称、角色摘要、当前组织、请求来源和 trace/request ID。
- 运行态 schema、jar、`target/classes`、前端 dev server、权限树版本要冻结；验收脚本输出 `sys_menu` checksum、数据库对象清单和核心表计数。
- `root@localhost` 定义的动态 DDL 存储过程要纳入迁移治理或清理，应用账号不能用 root 和 DDL 权限。

涉及原报告编号：P1-14、P1-15、P1-23、P2-09、P2-62、P2-71、P2-75、P2-90、P2-91、P2-108、P2-160、P3-146、P3-262、P3-264。

### 13. 系统工具和调度高危能力必须从业务角色收回

必须改的原因：代码生成、调度执行、系统工具、Swagger、表单构建这些能力不是普通业务账号能力。当前存在父菜单停用但子权限仍授给业务角色、隐藏副页可直连、定时任务停用仍可执行等风险。

必须改的内容：

- 系统工具若不交付，父菜单、子菜单、隐藏副路由、后端接口权限都要同步停用或收回。
- 代码生成导入、同步表结构、自定义路径、生成代码必须限制到平台管理员，并增加高危确认和差异预览。
- 表单构建若不交付，应停用；若交付，正则规则不能用 `eval`，上传地址不能默认外部接口。
- 定时任务停用后默认不能执行一次；执行一次应有独立权限、强确认和状态校验。
- 调度日志清空、导出、任务执行不能复用过宽权限，审计证据要独立保护。

涉及原报告编号：P2-13、P2-40、P2-96、P2-97、P2-108、P3-53、P3-110、P3-142、P3-233、P3-278。

## 建议执行顺序

1. 先修成本权限、账号密码安全、密码哈希泄露、文件公开访问、日志清空和 `@InnerAuth` 这类安全底线。
2. 再修多店铺/多仓库后端边界：销售退货、采购退货、库存盘点、薪资绑定、劳动合同、OA 组织守卫、店铺授权。

4. 再修用户创建/导入/授权闭环和工资考勤合同流程，保证新用户、多账号、多店铺能端到端验收。
5. 固定资产模块做产品决策：本期上线就补齐角色、样例、额度和校验；不上线就隐藏并写明不交付。
6. 最后处理 P3 里的体验、导出文案、空态、面包屑、列表效率和历史未交付模块。
