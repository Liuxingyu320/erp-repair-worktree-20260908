# 待办功能第四阶段详细实施方案（2026-07-13）

## 1. 阶段定位

第三阶段已经解决手机主操作、结构化确认、详情失败关闭、临时组织上下文、关键词统计、排序说明和桌面窄屏布局。本阶段不重复这些功能，重点把待办从“功能可用”推进到“可安全发布、可稳定联调、可按优先级快速处理”。

本阶段交付 5 个结果：

1. 从当前超大脏工作区中隔离出可审查、可提交、可回滚的待办发布范围。
2. 修复 `local` 模式下库存 Provider 无法调用系统服务的问题，并提供安全的本机原生启动、停止、状态和健康检查脚本。
3. 给库存、OA、系统三个 Provider 增加统一的 `priority` 服务端筛选契约，并在桌面、手机端提供快捷筛选。
4. 用真实权限角色、真实浏览器和 Provider 中断/恢复场景完成只读验收。
5. 在不提高现有性能阈值的前提下缩减 Element UI 首屏同步包，消除当前入口体积警告并保留安全余量。

全程使用 macOS 本机原生 Java、Node、MySQL、Redis 和浏览器进程；不使用虚拟机、Docker、Testcontainers、Android 模拟器或 iOS 模拟器。Git worktree 只是第二份源码检出目录，不是虚拟机，可以用于隔离当前脏工作区。

### 8.5 汇总语义

- `priority=urgent` 时，summary 的总数、分类数和 recent 都只统计紧急待办。
- summary 中的 `urgent/important/normal` 也基于同一过滤结果；因此选择 `urgent` 后 important/normal 为 0 是正确契约。
- 前端快捷筛选只显示“全部/紧急/重要/普通”标签，不在按钮上展示会随选择变化的分面计数，避免循环口径。
- `category` 仍不传入页面分类网格的 scoped summary，使分类网格能显示当前关键词、组织和优先级下的全部分类分布。

### 8.6 后端验收用例

每个 Provider 至少覆盖：

- 未传 priority 时返回完整结果。
- `urgent/important/normal` 分别只返回目标优先级。
- summary total 等于分类合计，也等于优先级合计。
- recent 不含其他优先级。
- 过滤发生在分页前，总数和页数正确。
- priority 与 category、keyword、scopeMode 同时使用时为 AND 关系。
- 空白参数规范化为 null。
- `high`、大小写错误和注入样式字符串被拒绝。
- 无权限类型不会因为 priority 参数重新出现。

### 9.2 请求和缓存

`todo.js` 中必须同时修改：

- `normalizeTodoQuery`：加入 priority。
- `buildTodoListCacheKey`：加入 priority，防止紧急缓存污染重要/普通结果。
- `refreshPage`：向每个 Provider 传 priority；`all` 转为空值。
- 页面 scoped summary 参数和 key：加入 priority。
- 全局 `refreshSummaries` 保持不带 priority，顶部汇总不受页面筛选影响。

Provider 降级时只能使用“来源、分类、范围、关键词、优先级、页码、页大小、组织”完全一致的缓存；不能跨优先级回退。

手机：
