## 1. 实际结果

阶段 12C2 已在外层持久化命令事务内建立只锁定、只校验的收货边界：

1. `InvTransferShipmentReceiptCreationService` 只声明 Gate 和窄化 Lock Gateway 两个业务依赖，不直接持有包含库存 mutation 的 Mapper。
2. Gate 和请求结构检查通过后，先锁发货批次和调拨单，再验证所选组织、目标仓库和收货方向。
3. Lock Gateway 按固定顺序锁定调拨明细、发货明细、来源分配、目标库存模式、物料策略、目标汇总库存、来源批次、来源及目标候选库位、本次请求涉及的已存在派生批次、目标余额和未分类发货序列号。
4. 所有集合参数在进入 Mapper 前去重并升序；来源分配必须完整覆盖每个发货明细，规划投影的分配集合必须与锁定分配完全一致。
5. 派生批次只按请求中正数合格/残损处置生成锁键；目标余额只按请求实际引用的正常/隔离库位生成锁键，避免无界笛卡尔组合。
6. 基础行全部锁定后，通过阶段 12B 同一个 `InvTransferShipmentReceiptPlanComposer` 重算权威规划，再执行阶段 12C2A 的纯请求策略。
7. 即使两个测试 Gate 都构造为 `true`、组织与请求校验全部成功，服务仍固定抛出“阶段12C3原子写入尚未接线”，不能返回成功结果。

外层 `InvTransferCommandService.createReceiptV2` 保持 `@Transactional(rollbackFor = Exception.class)`，内部 CreationService 继续使用 `Propagation.MANDATORY`。因此锁读取只能加入已存在的持久化命令事务，失败会回滚命令台账和全部行锁。

10. 来源库位及目标仓启用的 storage/quarantine `inv_warehouse_location`
11. 本次请求涉及的已存在目标派生 `inv_inventory_lot`
12. 本次请求涉及的已存在目标 `inv_stock_balance_detail`
13. 尚未分类的 `inv_inventory_serial`
14. 读取已锁行的收货规划投影，执行 Composer 与纯请求策略

锁 Mapper 查询全部使用稳定 `order by` 和 `for update`。目标库位查询同时锁住来源库位精确 ID 和目标仓当前启用的非虚拟 storage/quarantine 候选范围。
