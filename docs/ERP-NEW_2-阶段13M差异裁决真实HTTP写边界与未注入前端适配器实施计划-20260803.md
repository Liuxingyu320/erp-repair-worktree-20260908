# ERP-NEW_2 阶段 13M：差异裁决真实 HTTP 写边界与未注入前端适配器实施计划

## 1. 目标与范围

在阶段 13K 已完成 basis token 同事务消费、阶段 13L 已完成浏览器安全请求契约之后，建立可由未来运行时复用的真实 HTTP 协议边界：

- 后端在既有 `/transfer` Controller 下开放一次性 basis 签发和裁决计划提交两个精确 POST 入口；
- 前端在既有差异裁决 HTTP 文件中增加严格的 basis issuer 与 adjudication writer；
- 网络层强制同源路径、CSRF、当前组织、提交幂等请求 ID、严格 AjaxResult 数据解析和跨事项/组织响应拒绝；
- 默认 bootstrap、页面、功能码、菜单和 Mock Gateway 继续不注入该 Writer。

本阶段允许 HTTP 代码边界存在，但不启动服务、不连接数据库、不执行 DDL，也不执行库存、物流、财务或裁决计划写入。

## 2. 后端接口

### 2.1 签发 basis

`POST /transfer/discrepancies/{discrepancyCaseId}/adjudication-basis`

- 精确权限：`inv:transfer:discrepancy:adjudicate`；
- 从路径获取事项 ID，从现有组织请求头解析所选组织；
- 调用 `InvTransferReceiptDiscrepancyAdjudicationBasisIssueService.issue`；
- 响应设置 `Cache-Control: no-store`；
- 不接受 JSON 正文，不接受浏览器提供的事实指纹、事件 ID、用户或权限；
- 操作日志不保存请求或响应载荷，避免 bearer token 进入审计参数；
- 不标注 `@PersistentCommand`。

basis 签发是一项短时安全能力准备，不修改事项、库存、物流或财务状态。它无法在不保存原始 token 或引入可逆秘密的前提下重放相同成功响应，因此不能伪装成数据库持久化幂等业务命令。重复调用只会签发相互独立、固定 5 分钟有效、尚未消费的令牌；任何令牌都必须在裁决唯一事务中重新核验并一次性消费。

### 2.2 提交裁决计划

`POST /transfer/discrepancies/{discrepancyCaseId}/adjudications`

- 精确权限：`inv:transfer:discrepancy:adjudicate`；
- 标注 `@PersistentCommand` 和更新类业务审计，但审计不保存请求或响应载荷；
- `requestId` 只来自必填 `X-Request-Id`；
- 事项 ID 只来自路径，所选组织只来自请求上下文；
- JSON 正文使用阶段 13L DTO 并启用 Bean Validation；
- DTO 纯组装阶段 13K 命令，调用 `InvTransferReceiptDiscrepancyAdjudicationCreationService.create`；
- 响应设置 `Cache-Control: no-store`。

同一 `requestId` 的精确重放、令牌摘要锁定、事实恢复、权限和组织复核、裁决写入、事项推进与 token 消费继续只属于阶段 13K 的单一事务服务。Controller 不重写任何业务规则。

## 3. 前端 HTTP 适配器

在 `transfer-discrepancy-adjudication.http.ts` 中新增独立 Writer 接口：

- `issueDiscrepancyAdjudicationBasis(caseId, selectedOrganizationId, signal?)`；
- `submitDiscrepancyAdjudication(envelope, signal?)`。

约束：

- 路径事项 ID 和期望组织 ID 必须是 Java `Long` 范围内的规范正十进制字符串；
- 两个请求均为同源 POST，强制 CSRF 与组织上下文；
- basis 请求无正文，响应必须满足严格 5 分钟、服务端来源、事项和组织一致；
- 提交请求只发送信封的 `body`，路径、请求 ID 和组织保持独立权威来源；
- `ErpHttpClient` 增加只用于失败关闭的 `expectedOrganizationId` 选项，在设置组织头前比较当前组织，组织切换后不得发送陈旧信封；
- 创建结果必须为服务端来源、相同事项、固定计划状态和单调时间；
- token 不进入 URL、日志、持久化存储、Pinia、Mock fixture 或异常正文。

本阶段 Writer 保持独立导出，不加入 `TransferGateway`、providers、页面或 bootstrap，不改变功能码和路由可达性。

## 4. 测试

后端：

- 反射验证两个 POST 路径、精确权限、日志类型和 `@PersistentCommand` 的准确边界；
- 单元调用验证路径、组织、请求头和 DTO 到两个服务的精确传递；
- 两个敏感响应均为 `no-store`；
- basis 入口无请求正文，裁决入口正文必须 `@Validated`；
- 复跑 Bean Validation、服务事务、Controller 权限与幂等边界测试。

前端：

- basis POST 的路径、无正文、自动请求 ID、组织、CSRF、AbortSignal 与严格响应绑定；
- 裁决 POST 的精确正文、显式请求 ID、组织、CSRF 和响应事项绑定；
- 非法/超 Long 标识、跨事项、跨组织、未知字段和组织切换均在失败关闭路径覆盖；
- 源码 Gate 证明页面、bootstrap、providers 和 Mock Gateway 未注入 Writer，且 token 无持久化路径；
- 运行完整 `npm --prefix erp-ui-next run verify`。

后端运行 `./mvnw -pl erp-modules/erp-inventory -am -DskipITs test`，不运行数据库集成测试或迁移。

## 5. 风险与停止线

- basis 是 bearer capability，任何日志、URL、Mock、持久化或错误正文泄漏都必须阻止提交；
- 裁决提交不能退回客户端事实指纹或允许正文覆盖路径、组织、用户、权限、金额与执行状态；
- HTTP 边界通过只证明协议接线，不证明数据库 DDL 已执行、并发 SQL 已在真实 MySQL 验证或前端运行时已开放；
- 不启动 Docker、应用服务、MySQL、Redis 或 Nacos，不连接共享或生产资源；
- 不新增 `.env`、真实秘密、端口、依赖或锁文件；
- 不删除旧前端，不合并，不推送，不访问其他 worktree。

下一阶段才允许在仍可回滚的前端交互层编排“刷新权威事实 → 本地草案 → 二次确认 → 签发 basis → 立即提交 → 丢弃 token → 重载服务端计划”，并必须独立验证组织切换、双击、超时、取消和错误恢复。
