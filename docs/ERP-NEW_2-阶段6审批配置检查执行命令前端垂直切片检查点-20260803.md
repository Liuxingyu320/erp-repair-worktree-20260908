## 1. 本检查点结论

`erp-ui-next/` 的 `/approvals/validation` 已从只读批次审计扩展为受控的配置检查执行骨架。只有拥有 `approval:validation:run` 的管理员可按精确审批版本发起检查；列表与明细继续由 `approval:validation:list` 独立控制。

默认 Provider 只写入 ERP-NEW_2 自有可变 Mock。真实 HTTP Writer 保持未注入；本切片没有连接后端、服务、中间件或数据库。

## 2. 契约审计与纠偏

- 执行端点为 `POST /approval/validation/run`，规范请求体只有 `{ versionId, validationType }`。
- `versionId` 按 Java Long 正整数校验；检查类型只接受 `MANUAL`、`FULL` 或 `PUBLISH`。
- 旧页面的 `businessCode`、`scopeMode`、`anchorDeptId` 与 `businessSubtype` 不属于当前 Service 执行契约，新 Writer 不发送。
- Service 会在独立事务内新增检查批次和问题，返回 `{ run, issues }`；只校验版本、规则与模板存在，不限制版本状态。
- POST 必须发送 CSRF、显式省略组织头，并要求成功响应声明 `Cache-Control: no-store`。
- 当前后端没有业务请求标识、幂等注解或去重协议；HTTP `X-Request-Id` 只作相关性追踪，不能当作业务幂等键。

## 3. 权限、交互与错误恢复

- 执行权限与列表权限独立；无执行权限时没有写入口，同一会话权限下降会立即关闭对话框并清理命令状态。
- 对话框先说明新增审计批次但不修改、修复或发布规则，再要求精确版本与检查类型，最后展示目标、范围、写入结果与非幂等风险进行二次确认。
- 对话框打开后聚焦版本输入，二次确认聚焦标题；Tab 约束在对话框内，Escape 在安全阶段取消。
- 提交动作通过本地锁与父级状态共同阻止重复触发。
- 成功后刷新当前批次列表并打开服务端返回的新批次明细；替换读取失败时保留最近一次成功列表并准确提示。
- 结果不确定时不提供原地重试，只允许关闭并按该精确版本刷新批次，再由管理员决定是否重新执行。
