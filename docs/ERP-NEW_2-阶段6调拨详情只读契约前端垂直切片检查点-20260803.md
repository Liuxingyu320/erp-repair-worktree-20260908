## 1. 本检查点结论

新前端已冻结调拨详情的只读数据边界，并把它暴露为 `TransferGateway.loadDetail`。真实 HTTP reader 只允许正整数调拨标识，调用同源 `GET /api/inventory/transfer/{transferId}`，要求组织上下文，明确不发送 CSRF 写令牌；Mock Gateway 提供独立的内存详情投影。

本检查点只建立详情读取契约，不宣称已经接通真实后端、数据库、库存预留、审批运行时或发货/收货物理效果。

## 2. 详情契约

- `transfer-detail.contract.ts` 以浏览器字符串保留业务标识、版本和十进制数量；同时兼容后端 JSON 将 `BigDecimal` 序列化为数字的情况，并在浏览器边界重新规范化为字符串。
- 状态使用调拨命令已冻结的生命周期集合；调拨类型、时间格式、版本、组织/仓库标识、明细字段均经过 Zod 校验。
- 明细要求正数量；已发货和已收货数量不得为负、不得超过申请数量，且已收货不得超过已发货。明细的 `transferId`（若服务返回）必须与抬头一致，非空明细标识不得重复。
- 详情投影显式保留编辑/审核所需的抬头和金额字段，默认剥离后端返回的 `shipments`、`discrepancies`、审批扩展对象等未冻结字段，避免把复杂物理事实误当作详情契约。

## 3. HTTP 与 Gateway 边界

- `transfer-detail.http.ts` 在发出请求前拒绝 `mock-*`、路径穿越和非正整数标识，不会因非法输入触发 `fetch`。
- HTTP 请求使用组织必需、CSRF omit 的只读安全策略；成功响应仍需验证服务返回的 `transferId` 与请求路径完全一致。
- `TransferGateway`、不可用 Gateway 和 ERP-NEW_2 Mock Gateway 均已同步新增 `loadDetail`，未改变当前启动流程仍默认使用 Mock 的事实。
