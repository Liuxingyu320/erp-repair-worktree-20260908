4. `action` 只允许 `approve` 或 `reject`；操作者必须是任务受理人、候选用户或候选角色。

6. 不直接更新 `oa_purchase`，不删除或修改 `ACT_*`，不为迁移强行驳回无法判定的流程。

完成门：用于完整迁移的克隆 B 中，OA `submitted`、关联运行任务和采购运行实例均为 0。目标环境发布前还必须在目标库重新达到同一条件。

### 盘点 23 项治理

1. 对 21 张 `draft` 和 2 张 `invalidated` 分类为“有效待执行”“测试/重复”“已失效保留”“无法判定”。

3. 盘点人必须来自 `/inventory/stockCheck/counter-candidates` 的实际授权候选，不能从 `create_by` 或姓名猜测用户 ID。
4. 测试/重复项只能使用现有取消业务能力，并保留操作日志；`invalidated` 是否重盘由业务决定。
5. 无法判定项保留治理工单、责任人和期限，不把它伪装成已完成。

完成门：正式有效的活动盘点缺盘点人或截止时间为 0；保留异常都有工单和责任人。

## 6. 最终 Go/No-Go 标准

只有以下条件全部满足才能给出 Go：

1. thread 5738 并发 DDL 归属明确，482 表基线无后续漂移。
2. 目标库 OA `submitted`、关联运行任务和采购运行实例全部为 0。
3. 正式有效盘点缺责任人或截止时间为 0；保留异常有工单和负责人。
4. 克隆 B 两次 apply、两次 postflight、业务回滚和完整快照恢复全部通过。
5. 两个原生 MySQL 健康证测试实际执行且无跳过。
6. 六种真实角色无越权，汇总、列表、优先级和深链口径一致。
7. system、OA、inventory 均能单独中断和恢复，缓存不串组织或优先级。
8. Maven 专项、五服务干净打包、前端全量测试、生产构建、包体、审计和范围守卫全部通过。
9. 临时库、账号、fixture、开关、服务、端口、日志和敏感证据全部清理。
10. 目标库、维护窗口、快照和回退负责人已明确，验收报告给出可追溯证据。

任一 P0/P1 条件未满足即保持 No-Go；不得用“代码测试通过”替代业务数据、数据库演练或真实角色验收。
