# ERP-NEW_2 阶段 13C：收货差异确认事件唯一写事务实施计划

> 日期：2026-08-02
> 分支：`codex/erp-new-2-rebuild`
> 基线：`119f8654 feat: add bilateral discrepancy confirmation contract`
> 范围：未对外开放的确认事件锁、幂等回放、条件追加和唯一事务；不执行迁移、不增加 Controller、Gate、菜单、权限或前端写入口

## 1. 结果目标

阶段 13B 已定义双方确认同一事项版本与事实指纹的纯契约，但没有任何 DML。阶段 13C 将该契约落实为唯一原子追加事务，使后续开放接口前已经具备可审计、可幂等、不可单方关闭且不能信任客户端角色的服务端写边界。

本阶段仍不改变 `inv_transfer_receipt_discrepancy_case.status` 或 `case_version`，不形成裁决结果，不调用旧差异处理器，也不把新服务注入现有 Controller。

## 2. 固定锁序与事务所有权

唯一 `InvTransferReceiptDiscrepancyConfirmationCreationService` 使用一个 Spring 本地事务，固定顺序为：

1. 校验登录用户与当前选择组织。
2. 按 `discrepancy_case_id` 锁定 13A 事项单行；不存在立即拒绝。
3. 在同一事务中读取 13B 权威关系链与双方最新事件，并重算金额、指纹和当前确认投影。
4. 按 `request_id` 锁定既有确认事件；存在时只允许完全一致的同用户、同组织、同角色、同事项、同版本、同指纹、同决定与同说明回放。
5. 不存在时由 13B 纯策略生成准备事件，并执行一次受关系约束的 `insert ... select`。
6. 校验影响行数严格为 1 且生成键为正；否则异常传播并回滚。

不同事项复用同一全局 `request_id` 必须拒绝；相同请求回放不再插入事件。所有确认事务先锁事项再读幂等事件，避免同一事项的双方事件交错形成未经复核的状态。

## 3. 共享权威边界

把阶段 13B 查询服务中的金额、事实指纹、组织方向和事件投影验证抽取为纯共享解析器。只读服务和创建事务必须调用同一解析器，防止读写两套规则漂移。

解析结果包括：

- 通过关系链获取的不可变事项事实；
- 固定调出、调入组织；
- 当前事项版本和事实指纹；
- 双方最新事件及其是否匹配当前事实；
- 当前确认状态与是否可进入裁决。

## 4. 条件追加 SQL

确认写 Mapper 只允许三个动作：锁事项标识、按幂等标识锁事件、条件追加事件。追加 SQL 必须：

- 从当前事项连接收货、调拨单，重新核验事项版本、状态和指纹；
- 根据调拨方向重新计算 `source|target` 与组织标识，不接受客户端角色；
- 只接受 `confirmed|disputed`，质疑要求非空说明；
- 要求操作者、时间、请求标识、组织、角色与准备事件一致；
- 使用 `not exists` 防止已提交幂等标识重复插入，并由唯一索引兜底并发竞争；
- 不更新事项、确认历史、库存、发货、收货、台账或生命周期。

## 5. 响应与幂等语义

创建响应只返回事件标识、事项标识、服务端推导角色、决定、当前确认状态、是否已具备裁决前提、是否为幂等回放和服务端时间。相同请求回放返回已存在事件标识，并返回锁内重新计算的当前双方状态；不得把历史事件重新当作最新意见。

## 6. 验证与停止条件

定向测试覆盖锁序、完全一致回放、不同载荷复用请求标识、0 行条件写、缺失生成键、未授权组织、共享边界与 Mapper DML 白名单。随后运行库存模块、后端完整 Reactor、新前端完整校验和隔离审计。

若需要执行迁移、连接数据库、开放 Controller/Gate、授予权限、修改前端写入口、更新事项状态、进入独立裁决或接线旧差异处理器，立即停止并留待后续检查点。
