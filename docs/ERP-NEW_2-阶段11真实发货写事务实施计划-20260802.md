# ERP-NEW_2 阶段 11：真实发货写事务实施计划

> 日期：2026-08-02
> 基线：`e41feada feat: add authoritative shipment planning reader`
> 范围：只修改 ERP-NEW_2 隔离工作树；不启动服务、不连接数据库、不执行迁移

## 1. 目标

在阶段 10 的权威只读规划之上，新增一个独立、幂等、固定锁顺序、失败即整单回滚的 V2 发货写事务边界。该边界只能接受服务端建议的完整回传，必须在事务内重新锁定并重算同一规划，随后同时写入：

- 调拨发货单及发货明细；
- 调拨专属商品级预留及汇总库存；
- 批次库位明细余额及序列号状态；
- 汇总库存日志及不可变明细库存流水；
- 发货分配、序列号关联、调拨明细累计量和状态审计。

本阶段只交付“代码与迁移骨架 + 离线测试”，运行时保持硬关闭。迁移不执行，新前端不注入真实 Writer，V2 收货事务未完成前不得启用。

## 2. 审计结论

现有 `POST /transfer/deliver/{transferId}` 不能承载 V2 语义：

1. `InvDeliverRequest` 只有调拨明细 ID 与数量，没有 `planVersion`、封存修订、余额、批次、库位、序列号或证据。
2. 旧实现先生成发货单，再逐行锁预留和 `inv_stock`；它只扣减商品级汇总库存并写汇总日志。
3. `inv_transfer_shipment_detail` 没有分配事实；现有数量精度为两位、成本精度为两位，低于明细库存四位数量/六位成本。
4. `inv_stock_balance_detail`、`inv_inventory_serial`、`inv_stock_ledger_detail` 当前只有阶段 10 的读取路径，没有生产级写 Mapper。
5. 只读 `planVersion` 是乐观并发依据，不是授权令牌；客户端回传的余额、数量和序列号都不可信。
6. 现有幂等命令台账可以复用，但必须使用新的稳定命令类型和强结果对象，不能把 V2 请求混入 `TRANSFER_DELIVER` 历史指纹。
7. 旧收货路径只处理发货明细数量，不会移动批次、库位或序列号；V2 发货在对应收货事务落地前不能被运行时启用。

因此阶段 11 新增 `POST /transfer/{transferId}/shipments`，旧 `/deliver` 保持原 DTO、命令类型和行为不变。后续启用前再单独设置“V2 仓库排他路由”，禁止同一仓库同时走旧写链和 V2 写链。

## 3. 请求、响应与幂等

### 3.1 请求

请求头继续强制 `X-Request-Id`，正文只允许：

- `planVersion`：64 位小写 SHA-256；
- `sealedRevisionId`：正整数；
- `basis=server-recommendation`；
- 扁平分配列表：`transferDetailId/balanceId/lotId/locationId/quantity/serialIds`。

所有 ID、数量、列表唯一性和逐件序列号数量都做 Jakarta Validation 与服务层二次校验。正文不得提交仓库、物料、成本、批次号、库位编码、操作者或状态。

服务端按稳定顺序重新生成完整规划，并同时要求：

1. `planVersion` 与事务内规划完全一致；
2. `sealedRevisionId` 与最新已审批修订一致；
3. 客户端分配集合与服务端全部 `ready` 行完全一致；
4. 客户端没有增、删、拆分、合并、改量、换批次、换库位或换序列号。

任何差异返回“规划已变化，请重新获取”，不得部分采用客户端内容。实际扣减始终使用服务端重算对象。

### 3.2 幂等

- 新命令类型：`TRANSFER_SHIPMENT_CREATE_V2`。
- 资源键：`transfer:{transferId}`。
- 命令指纹继续覆盖用户、组织、资源和规范化请求正文。
- 成功结果使用强类型 `InvTransferShipmentCreationVo`，包含 `shipmentId/shipmentNo/transferId/status/planVersion/sealedRevisionId/createdTime`。
- 同一请求 ID、同一指纹重放同一结果；同一请求 ID 的任何语义变化必须拒绝。
- 发货单保存 `command_request_id` 唯一键，形成命令台账之外的第二道数据库约束。
- `shipment_no` 不再获取全局 `TS` 序列表锁，而由业务日期与 `SHA-256(X-Request-Id)` 的 128 位截断值确定性生成；不泄漏原请求 ID，唯一索引负责最终冲突拒绝。

## 4. 固定锁顺序

所有锁在第一次数量或状态变更前获取；批量 ID 必须升序，禁止循环中边锁边写：

0. `inv_transfer_command`：幂等命令行（现有 Executor 先插入；重放时 `FOR UPDATE`）。
1. `inv_transfer_order`：按单个 `transfer_id FOR UPDATE`。
2. `inv_transfer_revision`：最新修订 `FOR UPDATE`，再复核不可变哈希链与 `APPROVED` 状态。
3. `inv_transfer_detail`：同一调拨单全部明细按 `detail_id FOR UPDATE`。
4. `inv_warehouse_stock_mode`：来源仓模式行 `FOR UPDATE`。
5. `inv_item_fulfillment_policy`：涉及物料按 `item_type,item_id FOR UPDATE`。
6. `inv_transfer_reservation`：当前预留轮次按 `stock_id,reservation_id FOR UPDATE`。
7. `inv_stock`：涉及汇总库存按 `stock_id FOR UPDATE`。
8. `inv_stock_balance_detail`：涉及物料的全部明细余额按 `balance_id FOR UPDATE`，包括零余额行；所有授权的明细库存写入者必须先拥有第 7 级汇总库存锁，防止候选集幻读。
9. `inv_inventory_lot`：第 8 级余额引用的批次按 `lot_id FOR UPDATE`。
10. `inv_warehouse_location`：第 8 级余额引用的库位按 `location_id FOR UPDATE`。
11. `inv_inventory_serial`：第 8 级余额下的序列号按 `serial_id FOR UPDATE`，不能只锁客户端选择项。

阶段 11 不实现仓库模式切换写操作；未来模式切换、入库、销售出库和盘点的明细库存写入也必须遵守“模式 → 汇总库存 → 明细余额 → 批次 → 库位 → 序列号”的同一后缀顺序。不能证明遵守时，仓库不得切换 `dual/detail`。

## 5. 事务内重新规划

只读服务与写服务不得各自维护一套哈希算法。本阶段抽取纯 `InvTransferShipmentPlanComposer`：

- 只读服务负责组织范围、数据库读取和响应映射；
- 写服务负责固定顺序加锁和事务控制；
- Composer 负责标准化模式/策略、FEFO/FIFO/serial 计算、数量守恒、阻断项与 `shipment-plan-v1` 指纹；
- 两侧输入相同事实必须得到逐字相同的 `planVersion` 与分配序列。

写服务重算时仍要求 `dual + detail + reconcile passed`、最新已审批修订、可发状态、有效策略、合格活动批次、启用非虚拟库位、未过期、正数余额和序列号逐件一致。对账批次为空或发生变化必须拒绝。

## 6. 原子写入不变量

全部校验完成后才允许执行以下变更；任一 SQL 影响行数不等于期望值则抛错并回滚：

1. 插入 V2 发货单与逐调拨明细发货明细，保存写版本、请求 ID、规划版本、封存修订和对账批次快照。
2. 按服务端分配插入 `inv_transfer_shipment_allocation`，保存余额版本前后值、批次/库位、策略/跟踪方式、数量、单位成本和金额。
3. 对每个明细余额以 `balance_id + version` 乐观条件扣减 `current_quantity/available_quantity/total_cost`，不允许负数，`locked_quantity` 不变。
4. 序列号物料逐件把精确归属的 `available` 序列号更新为 `shipped`，并插入不可变发货序列号关联；lot 物料必须没有序列号。
5. 汇总库存按 `stock_id` 聚合扣减 `current_quantity/locked_quantity/total_cost`；`available_quantity` 不变，并逐调拨明细消耗其专属预留。
6. 每条调拨明细只写一条汇总 `transfer_out` 日志；每个余额分配写一条不可变 `inv_stock_ledger_detail`，通过 `summary_stock_log_id` 与 `shipment_allocation_id` 双向核验。
7. 明细流水 `request_id` 使用 `SHA-256(commandRequestId + allocationId)`，根请求另存 `command_request_id`，避免现有 100 字符列溢出且保证逐分配唯一。
8. 每条调拨明细：分配合计 = 本批发货量 = 预留消耗量 = 汇总库存数量变化 = 明细余额数量变化；序列号行还必须等于序列号条数。
9. 汇总库存成本变化 = 所有明细分配金额之和；发货明细成本保存六位精度加权单位成本，不允许退化到两位。
10. 最后更新调拨明细累计已发量、调拨单生命周期状态、状态日志和 OE 需求进度；不得在提交后发布外部消息。

数据库事务回滚是唯一业务回滚路径。代码不写补偿 SQL，不在异常分支删除或反向追加库存。

## 7. 加法迁移

新增 `sql/erp_inventory_transfer_shipment_v2_20260802.sql`，只允许加法/精度扩大，不执行数据迁移、不切换仓库模式、不写业务种子：

- 扩大 `inv_transfer_shipment_detail` 三个数量列为 `decimal(18,4)`、成本列为 `decimal(18,6)`；
- 为 `inv_transfer_shipment` 增加 `inventory_write_version/command_request_id/plan_version/sealed_revision_id/reconcile_batch` 与唯一/查询索引；历史行保持 `LEGACY`；
- 新建 `inv_transfer_shipment_allocation`；
- 新建 `inv_transfer_shipment_serial`；
- 为 `inv_stock_ledger_detail` 增加根命令 ID 和发货分配 ID及索引，保留现有唯一 `request_id`；
- 不复制到 `docker/mysql/db/`，不加入自动初始化，不执行 SQL。

迁移源码测试必须拒绝：`USE` 固定库名、远程连接、仓库模式更新、业务 `INSERT`、密码/密钥、删除/截断、原项目路径或 Docker 初始化目录修改。

## 8. 运行时硬关闭与收货隔离

新增双条件 Gate，默认值均为 `false`，仓库或配置文件不写启用值：

- `erp.inventory.transfer-shipment-v2.write-enabled`
- `erp.inventory.transfer-shipment-v2.receipt-boundary-ready`

V2 创建服务要求两个条件同时为真，否则在获取业务行锁前拒绝。阶段 11 不提供任何启用配置。

V2 发货单标记 `inventory_write_version=V2_DETAIL`。旧收货处理器遇到该值必须失败即关闭，防止只增加目标汇总库存却遗漏批次、库位和序列号迁移。阶段 12 的 V2 收货事务、隔离数据库并发测试、仓库排他路由与启用清单全部完成前，两个 Gate 不得设为真。

## 9. 前端边界

新前端只新增未注入的真实 Writer：

- 请求仍由现有已验证规划生成，增加封存修订 ID；
- Writer 使用同源 `/api/inventory/transfer/{id}/shipments`；
- `POST` 必须携带组织头、CSRF 和命令自身的 `X-Request-Id`；
- 响应必须经过 Zod 强校验并核对 `transferId/planVersion/sealedRevisionId`；
- 默认 `TransferGateway`、页面按钮和 Mock 模拟保持不变，不会发出真实 POST。

在不启动服务、不连接数据库、不安装依赖的前提下完成：

3. 固定 Mapper 锁 SQL 的 `ORDER BY ... FOR UPDATE`、所有更新的版本/非负条件和影响行数测试。
4. 汇总/明细/序列号/成本守恒、重复请求重放、不同指纹拒绝、任一步失败整单抛错的服务测试。

6. 旧收货拒绝 V2、旧发货 DTO 与命令类型不变的回归测试。
