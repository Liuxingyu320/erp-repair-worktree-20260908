# ERP-NEW_2 阶段 13P15：异步子调拨权威完成根事务骨架实施计划

> 日期：2026-08-03
>
> 分支：`codex/erp-new-2-rebuild`
>
> 基线：`7c91129e feat: add atomic return receipt skeleton`
>
> 范围：建立补发/退回子调拨的权威完成根事务；默认关闭、生产零调用，不触发发货或收货

## 1. 审计结论

阶段 13P7 已冻结异步裁决子调拨的不可变关系和完成证明，阶段 13P10 又把实际预留的全量消费与零释放纳入证明。阶段 13P12、P13、P14 已分别建立退回发货、退回收货规划和专属原子收货参与者，但仍存在一个明确缺口：

- P6 同步执行事务只接受责任台账、短缺损失和隔离写销，并在首个事件或效果 DML 前拒绝 `reship_workflow` 与 `return_workflow`；
- P7 Mapper 能锁定唯一关系和子调拨终态事实，却没有生产事务所有者调用完成策略；
- 当前没有事务把“关系不变、子调拨已收货、实际预留全量消费、纯 V2 发货/收货、零开放差异”与执行事件和三层状态推进原子绑定；
- P14 收货参与者不应自行推导裁决动作，也不能在没有锁定裁决根事实时独立更新裁决终态。

因此 P15 只建立完成根事务，不调用 P12/P14，不创建或修改子调拨业务事实。

## 2. 固定事务与锁序

新增独立双条件 Gate 和 `@Transactional(rollbackFor = Exception.class)` 根事务，固定顺序为：

1. Gate 首先校验，任一条件关闭时不得解析组织或访问 Mapper；
2. 校验 `complete` 命令、根请求 ID、登录用户和执行权限；
3. 解析当前组织可见范围；
4. 锁定差异事项主键并验证组织范围；
5. 锁定裁决边界和全部动作；
6. 锁定同请求已有执行事件；
7. 锁定动作唯一异步工作流关系；
8. 按关系锁定唯一子调拨及实时完成事实；
9. 用 P7 纯策略验证关系和完成证明；
10. 用 P6 执行纯策略准备 `complete` 事件与三层状态变换；
11. 交叉核验事项、裁决、动作、效果引用、效果类型、子调拨和工作流指纹；
12. 追加执行事件，条件推进动作、裁决计划和差异事项。

同一请求已有事件时，仍须重新验证不可变关系和子调拨终态，再执行 P6 幂等重放校验；不得重复任何 DML。

## 3. 权威完成条件

继续完全复用 P7/P10 既有纯策略，不在 Service 中自行判断完成：

```text
child.status = received
reservation.status = CONSUMED
reservation.consumed_quantity = reservation.reserved_quantity = action_quantity
reservation.released_quantity = 0
存在 V2_DETAIL 发货与收货
不存在旧发货和开放差异
```

关系必须同时证明动作、子调拨、效果引用、业务来源、方向、物料、数量、成本和库存来源未漂移。`reship` 与 `return` 共用完成事务，但其效果类型和工作流类型必须精确匹配，不能相互替代。

## 4. 关闭性与接线边界

- 新 Gate 的 `write-enabled` 和 `workflow-boundary-ready` 均默认 `false`；
- 新根事务在生产主代码中保持零调用点；
- 现有 `InvTransferReceiptDiscrepancyAdjudicationExecutionService` 继续硬关闭且不引用新事务；
- 现有 P6 同步事务不修改，仍拒绝异步动作；
- P12/P14 Gate 不启用，P15 不调用发货或收货参与者；
- 不新增 Controller、HTTP、权限路由、前端 Gateway、任务或消息消费者；
- 不新增 DDL、迁移或 Mapper SQL，复用 P6/P7 已有条件 DML 和锁定查询。
