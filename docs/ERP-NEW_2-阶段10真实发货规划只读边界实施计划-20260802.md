# ERP-NEW_2 阶段 10：真实发货规划只读边界实施计划

> 日期：2026-08-02
> 基线：`be860446 feat: scaffold transfer shipment planning`
> 范围：只修改 ERP-NEW_2 隔离工作树；不启动服务、不连接数据库、不执行迁移

## 1. 目标与结果

为阶段 9 的前端发货规划骨架建立真实、组织受控、只读且失败即关闭的后端边界。接口读取已审批调拨单、不可变审批修订、仓库库存模式、物料履约策略、批次库位余额和可用序列号，返回与新前端一致的强类型规划；前端新增真实 GET Reader，但默认启动组合仍保持隔离 Mock。

本阶段不改造或调用真实发货写事务。现有写入口只接受调拨明细与数量，无法承载批次、库位、序列号、计划版本和人工改选证据；在统一库存变动服务落地前继续保持关闭。

## 2. 权威条件

只有以下条件同时满足时，规划可以标记 `canCreateShipment=true`：

1. 调拨单属于当前选择组织可见范围，且当前组织对调出仓具有发货操作范围。
2. 调拨状态为 `approved/reserved/partial_delivered`。
3. 最新不可变业务修订存在、哈希链校验通过且状态为 `APPROVED`。
4. 调出仓库存模式为 `write_mode=dual`、`read_mode=detail`、`reconcile_status=passed`。
5. 只有具备启用履约策略的待发物料行可以形成建议；缺失策略的行保持阻断并从本批命令排除，不阻止其他合格行形成一次部分发货建议。
6. 可分配余额只来自启用库位、合格/让步且活动中的未过期批次，数量大于零。
7. FEFO/FIFO 依据完整；序列号物料的可用余额数量与可用序列号逐件一致。
8. 至少一条物料形成正数建议，且不存在全局阻断项。

仓库未达到权威模式时接口仍可返回业务抬头和逐行阻断，但不得查询或返回可执行明细余额建议。

## 3. 物料履约策略

现有物料主数据没有可证明的“序列号强制逐件”字段，因此新增独立、无样例数据的增量表 `inv_item_fulfillment_policy`：

- 业务键：`item_type + item_id`。
- `allocation_policy`：`FEFO/FIFO`，不得用现存批次数据猜测。
- `tracking_policy`：`lot/serial`。
- 启停状态、版本和审计字段。

迁移只创建结构和约束，不自动配置任何物料，不切换仓库模式，不写密码、密钥或业务样例。缺少策略的物料必须显示阻断。

## 4. 后端文件与步骤

1. 在 `sql/` 新增独立履约策略迁移及源码安全测试，不复制到 Docker 初始化目录、不执行 SQL。
2. 在 `domain/transfer/` 新增候选余额、序列号、库存模式、履约策略和纯分配规则；测试 FEFO、FIFO、部分建议、序列号一致性和数据异常。
3. 新增 `InvTransferShipmentPlanningMapper` 与 XML，批量读取策略、合格余额和可用序列号，避免逐物料 N+1 查询。
4. 新增单一强类型规划 VO，所有长整型 ID 序列化为字符串，数量序列化为规范十进制字符串。
5. 新增独立 `InvTransferShipmentPlanningService`，复用组织范围和不可变修订校验，不继续扩大巨型 `InvTransferServiceImpl`。
6. 在 `InvTransferController` 新增 `GET /transfer/{transferId}/shipment-planning`，仅允许发货权限并设置 `Cache-Control: no-store`。
7. 生成 SHA-256 `planVersion`，覆盖调拨行版本、封存哈希、模式/对账批次、策略、余额版本/数量和序列号 ID；后续写命令必须重新验证。

## 5. 前端文件与步骤

1. 收紧 `transfer-shipment.contract.ts`：分开分配策略与跟踪策略，支持已完成行和诚实的策略缺失阻断。
2. 库存权威对象增加写模式、对账状态和批次；可执行规划必须通过 `dual/detail/passed` 校验。
3. 新增 `transfer-shipment.http.ts` 与测试，只接受正整数真实路径，使用同源 `/api`、组织头、只读 GET 和运行时 Zod 校验。
4. 页面继续由 Gateway 读取；默认 Mock 不切换，真实 Reader 只作为后续隔离联调边界。

## 7. 风险与后续

- 规划读取不加行锁，因此 `planVersion` 只是乐观并发依据；后续写命令必须在固定锁顺序内重新读取并验证全部事实。
- `detail` 权威读不能证明 `dual` 写完整，必须同时要求最近对账通过；真实环境还需连续观察门槛。
- 本阶段只建立读取与计算边界，不证明数据库迁移已执行、数据已回填或真实仓库可切换。
- 人工改选、证据、拣货/复核任务、发货写入、在途批次和二维码仍是后续检查点。
