# 新增业务功能下一阶段持续优化方案

> 方案日期：2026-07-14  
> 项目基线：分支 `7月13号`，检查时 HEAD 为 `b694659dd2c1`  
> 关联文档：[新增业务功能优化实施结果](./新增业务功能优化实施结果-20260713.md)、[上线前剩余问题优化方案](./新增业务功能上线前剩余问题优化方案-20260713.md)  
> 方案定位：现有业务闭环不再重复建设；下一阶段先解决发布、真实数据库和真实角色验收，再进行可观测性、性能和结构优化。

## 1. 总体结论

健康证、我的团队、OE 超额自购与上报后补货、门店返仓、调拨差异、客户服务卡和受控附件已经完成代码闭环。下一阶段不建议继续增加新业务入口，推荐按以下顺序推进：

1. 固化本次发布范围，消除脏工作区和部署包不确定性。
2. 建立一个可重复执行、失败关闭的统一发布门禁。
3. 在 MySQL 5.7/8.0 完成迁移双执行、事务并发和备份恢复演练。
4. 用两门店、两仓库和真实角色完成接口与浏览器端到端验收。
5. 单店单仓灰度，接入告警和每日对账后再逐步全量开放。
6. 灰度稳定后拆分大页面和大服务，补充性能基线。

上线前完成阶段 0～3；阶段 4 是灰度门禁；阶段 5 不阻塞首次灰度，但应在继续扩展调拨和 OE 功能前完成。

## 3. 保持不变的业务边界

- OE 超额后只能提示同款购买参考，由员工自行购买且无需继续上报；不恢复异常批准，也不新增自购上报。
- 客户服务卡严格按当前门店隔离；同店员工可维护，不提供跨店搜索或共享。
- 店长团队接口返回完整手机号，但不全局关闭现有人事字段脱敏，也不返回工资、银行卡、完整证件号等字段。
- 门店要货和返仓继续复用调拨审批、发货、收货和差异流程，不建设第二套审核系统。
- 数据库迁移继续采用先加后减；回滚应用时不立即删除新增表、字段或历史业务事实。

## 4. 分阶段实施计划

### 阶段 0：发布范围与仓库卫生（P0，约 1 人日）

目标：从当前混合工作区得到一个内容明确、可复现的发布候选版本，同时不覆盖或丢弃使用人员的其他改动。

实施内容：

1. 建立版本级发布清单，记录候选提交、相关文件、8 个迁移、受影响表、功能开关、产物 SHA-256 和验证证据。
2. 把 4 组 `*Test.java -> *IT.java` 作为重命名成对核对，增加脚本断言旧类不存在、新类存在且只有类名相关差异。
3. 从版本库移除 `erp-ui/node_modules` 的绝对路径软链接，保留 `package-lock.json`，在干净目录使用 `npm ci` 安装依赖。
4. 将 `.codex-runs/`、临时 `.playwright-cli/page-*.yml` 等本地测试产物排除出发布范围；业务验收截图只保留明确选中的证据文件。
5. 在独立的干净发布工作区重建候选版本；当前工作区中的其他人事、合同、云盘和待办改动只做分类，不擅自删除或回退。

重点文件：

- `.gitignore`
- `erp-ui/node_modules`
- `erp-ui/package-lock.json`
- `scripts/verify-new-business-it-contract.sh`
- 建议新增 `scripts/verify-new-business-release-scope.sh`
- 建议新增 `docs/releases/20260714-new-business-release-manifest.md`

完成标准：

- 发布工作区 `git status --short` 为空，`git diff --check` 通过。
- 发布清单中的每个文件均能追溯到候选提交，不包含依赖目录、运行日志、临时截图或密钥文件。
- 4 个真实数据库测试重命名全部成对存在于候选提交中。

### 阶段 1：统一的失败关闭发布门禁（P0，约 1～2 人日）

目标：任何一项静态检查、单元测试、生产构建或真实数据库测试未执行/失败时，候选版本都不能被标为可发布。

实施内容：

1. 新增 `scripts/verify-new-business-release.sh`，顺序执行迁移、IT 契约、只读对账、权限准备、后端回归、前端回归和生产构建。
2. 在 `mvn -Pnew-business-mysql-it verify` 后解析 Failsafe 报告，明确断言 7 个指定 `*IT` 全部实际执行且 0 跳过；不能只检查文件存在。
3. 保留 Docker 不可用即失败的规则，并把 MySQL 5.7/8.0 结果、测试数量、开始/结束时间写入不含凭据的发布证据。
4. 先提供与平台无关的 Shell 门禁；确定实际 CI 平台后，再用极薄的 CI 配置调用同一脚本，避免本地和 CI 两套逻辑漂移。
5. 前端继续保留源码契约测试，但在发布结论中将其标为“契约回归”，不再表述为完整 UI 验收。

重点文件：

- `pom.xml`
- `scripts/verify-new-business-it-contract.sh`
- `scripts/verify-new-business-migrations.sh`
- `scripts/verify-new-business-readiness.sh`
- `scripts/verify-new-business-reconciliation.sh`
- 建议新增 `scripts/verify-new-business-release.sh`
- `erp-ui/package.json`

完成标准：

- Docker 关闭时统一门禁稳定失败；Docker 可用时 7 个 IT 全部执行、0 失败、0 错误、0 跳过。
- 后端四个业务模块、前端全量测试和生产构建均由同一门禁触发。
- 门禁生成一份可归档的机器可读摘要，且不包含数据库密码、AccessKey、Token 或客户数据。

### 阶段 2：数据库与生产部署契约（P0，约 2～3 人日）

目标：使“构建包、迁移清单、备份、应用发布、验证和代码回滚”成为同一个版本契约，不再依赖硬编码旧 SQL。

实施内容：

1. 为本次版本建立部署清单，至少包含 8 个 SQL 的顺序、SHA-256、影响表、备份表、验证语句和是否可重复执行。
2. 改造 `scripts/aliyun_ecs_deploy_helper.py`：移除固定数据库名和固定 20260701 SQL，改为显式参数传入版本清单；没有迁移确认参数时只发布代码，不执行数据库写入。
3. 数据库执行前先验证目标库名、版本、字符集、迁移 SHA 和备份文件；执行失败时保留现场并停止，不自动猜测后续动作。
4. `docker/copy.sh` 不再把所有 `sql/*.sql` 批量放入初始化目录；全新环境使用独立、固定顺序的 bootstrap 清单，日常增量迁移继续使用版本级清单。
5. 在可丢弃库分别完成 MySQL 5.7、8.0 的首次执行、第二次重复执行、服务启动、对账和备份恢复演练。
6. 生产迁移后仍保持 7 个功能开关为关闭，先做只读准备检查，再按灰度顺序开启。

本次需要纳入备份/核对的既有表至少包括：

- `inv_oe_item`
- `inv_transfer_order`
- `inv_transfer_detail`
- `inv_transfer_shipment`
- `inv_transfer_shipment_detail`
- `oa_fixed_asset_quota`
- `sys_config`
- `sys_menu`
- `sys_role_menu`

新增表可以保留为空表结构作为代码回滚兼容层，不在紧急回滚中直接删除。

重点文件：

- `scripts/aliyun_ecs_deploy_helper.py`
- `scripts/aliyun_apply_sql_helper.py`
- `scripts/new-business-migrations-20260713.list`
- `scripts/verify-new-business-migrations.sh`
- `docker/copy.sh`
- `docker/mysql/dockerfile`
- `docs/ALIYUN_ECS_DEPLOYMENT_RUNBOOK.md`

完成标准：

- 两个 MySQL 版本均可执行迁移两次，第二次无重复对象或菜单权限冲突。
- 发布助手只执行清单内且 SHA 匹配的 SQL，不能扫描并执行整个 `docker/mysql/db`。
- 每次数据库变更都有可定位的备份目录、迁移输出和只读验证结果。
- 应用回滚不依赖逆向删除表；关闭新入口后，在途审核、发件箱、收货和差异处理仍可继续闭环。

### 阶段 3：真实接口与浏览器端到端验收（P0，约 2～3 人日）

目标：补齐现有源码契约测试无法覆盖的登录、路由、上传、权限、门店上下文、并发和跨服务链路。

在专用测试库准备两门店、两仓库和以下角色：普通员工、店长、直属主管、人事、仓库员工、仓库负责人、管理员。测试数据不得复制真实客户照片、手机号或健康证附件。

| 场景 | 必须验证的结果 |
|---|---|
| 健康证 | 员工只能操作本人；人事可审核；续证只保留一个当前证件；附件 URL 不能绕过业务权限；员工档案与团队页到期日一致 |
| 我的团队 | 店长仅见当前门店，直属主管仅见直属员工；手机号完整；敏感人事字段不返回；切换门店后数据立即变化 |
| OE | 额度内提交产生一条维修单、一条额度事实和一条发件箱；并发临界额度最多合法请求成功；超额不写任何上报或补货记录，只显示同款自购参考 |
| OE 补货 | OA 失败可重试且库存幂等；仓库可见上报内容；多仓不能互相覆盖；调拨实发/实收正确回写需求 |
| 要货、返仓与差异 | 门店到仓库方向不可绕过；复用现有审批；部分收货、短少、残损、拒收和待质检均守恒；差异关闭后才完成调拨 |
| 客户服务卡 | 同店员工可新增、编辑、追加服务记录和看受控照片；另一门店列表、搜索、详情、照片及写接口全部拒绝；财务字段不出现在普通员工响应 |

实施建议：

- 后端增加真实 HTTP/API 集成测试，覆盖登录身份、请求头中的门店上下文和稳定错误码。
- 前端增加少量高价值浏览器测试，只覆盖上述六条关键链路；源码字符串测试继续作为快速回归层。
- 并发和迁移继续放在 Testcontainers/Failsafe，不把慢测试重新混入默认 Surefire。

完成标准：

- 六类业务链路全部有自动化证据和真实角色签字验收。
- 两门店、两仓库的负向越权用例全部通过，不能只验证正常流程。
- UAT 发现的问题修复后重新执行统一发布门禁，而不是只重测单个页面。

### 阶段 4：灰度、告警与日常对账（P1，约 1～2 人日）

目标：在问题影响单店单仓时即可发现、停用新入口和完成在途业务。

实施内容：

1. 将已有 Micrometer 指标接入实际监控平台，并为以下情况建立告警：发件箱 `DEAD > 0`、最老待投递超过 15 分钟、OE 需求超时未处理、调拨差异超过 24 小时未结、健康证提醒失败、客户卡跨店拒绝或乐观锁冲突异常升高。
2. 把 `scripts/new-business-daily-reconciliation.sql` 作为只读任务每日执行；异常明细进入运维工单，摘要用于趋势观察。
3. 功能开关建议按依赖顺序启用：健康证 → 我的团队；调拨差异 → 门店返仓；库存 OE 接收 → OA OE 上报；最后启用客户服务卡。
4. 第一批仅开放一个门店和一个仓库；稳定后加入第二门店验证隔离，再逐步全量。
5. 回滚时先关闭新建入口，再回滚前后端；不能停止在途审核、发件箱投递、调拨收货和差异处理。

完成标准：

- 灰度期间核心对账异常为 0，任何死信或数量不守恒都能在约定时间内告警。
- 每次开关变更均记录操作人、时间、范围和原因。
- 至少完成一次“关闭入口但在途业务继续完成”的演练。

### 阶段 5：结构与性能持续优化（P2，约 3～5 人日）

目标：降低后续修改调拨、额度和客户卡时的耦合，不改变已经验收的业务语义。

实施内容：

1. 将 `erp-ui/src/views/inventory/transfer/index.vue` 拆分为查询看板、申请表单、发货、收货、差异处理和详情轨迹组件；公共库存选择器独立复用。
2. 在现有收货、差异、OE 创建和方向策略已经分离的基础上，继续从 `InvTransferServiceImpl` 提取普通创建/提交、发货、查询投影和库存流水协作器。
3. 将 `OaFixedAssetServiceImpl` 按配置管理、额度计算和维修上报三个职责拆分，保持额度锁与发件箱同事务边界不变。
4. 将移动客户服务卡的照片、编辑表单和服务记录拆为组件，保留受控 Blob 释放、幂等键和乐观锁行为。
5. 使用接近生产数量级的数据，对健康证到期列表、客户卡搜索、OE 待处理列表、调拨工作台和差异列表保存 `EXPLAIN`、P95 响应时间与慢查询证据；只根据证据增加或调整索引。
6. 继续保持前端入口 1.5 MiB 强制预算，并新增关键异步分块预算，防止页面拆分后总体积反弹。

完成标准：

- 页面拆分后六类真实业务 E2E 与现有契约测试全部通过。
- 核心服务的事务边界、锁顺序和幂等键不因拆分改变。
- 性能优化有前后对比数据，不以单纯增加索引或减少代码行数作为完成标准。

## 7. 风险与回滚原则

- 当前工作区的混合改动属于最高发布风险；实施阶段 0 时只分类和复制，不能用重置、清理或覆盖方式处理使用人员的其他改动。
- 数据库迁移与代码发布必须分开记录。应用回滚成功不代表数据库已回滚，新增表和字段默认保留以兼容旧代码。
- OE 的 OA 开关必须最后开启、最先关闭；库存内部幂等接收和在途发件箱不能随入口开关停止。
- 门店返仓依赖差异处理，必须先启用并验证差异能力，再开放返仓入口。
- 客户照片、健康证附件和完整手机号只用于授权业务页面；测试和发布证据不得保存真实敏感数据。

## 8. 推荐执行顺序

下一轮实施从阶段 0 开始，先完成发布范围清单、测试重命名固化和 `node_modules` 仓库修正；随后立即建设统一门禁和部署清单。未完成阶段 0～3 前，不建议继续扩展新的业务需求，也不应将当前版本标记为生产可全量上线。
