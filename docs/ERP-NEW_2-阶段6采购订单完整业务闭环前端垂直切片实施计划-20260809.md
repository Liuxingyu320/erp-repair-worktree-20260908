## 目标

在全新前端 `erp-ui-next/` 内把现有采购订单只读工作台扩展为桌面与移动端完整业务闭环，并同步收紧现有后端读写契约。切片覆盖列表、详情、新建、草稿编辑、保存、保存并提交、按 ID 提交已保存草稿、分批收货、逐行质检、取消、草稿物理删除、收货与质检追溯以及导出；所有数据和命令都必须严格限定在当前已选仓库。

本切片不启动 Docker、服务或数据库，不安装依赖，不访问受保护原项目，也不删除旧前端。浏览器端到端、真实文件上传、真实并发与独立非 Docker 运行环境联调保留到对应运行环境可安全启动后执行。

## 已确认的业务与安全边界

- 列表：`inv:purchase:list`；详情与完整收货轨迹：`inv:purchase:query`。
- 新建、编辑及采购专用供应商/物料目录：`inv:purchase:add`。
- 保存并提交必须同时要求 `inv:purchase:add` 与 `inv:purchase:submit`；提交已保存草稿只接受路径 ID，并只要求 `inv:purchase:submit`，不得借提交权限改写草稿内容。
- 收货：`inv:purchase:receive`；逐行质检：`inv:purchase:qc`；取消和删除草稿：`inv:purchase:remove`；导出：`inv:purchase:export`。
- 采购订单只能在仓库上下文执行。公司、集团、门店上下文不得发送列表、详情或命令请求。
- 列表、我的列表、详情、目录、收货批次和所有命令必须精确限定 `shop_dept_id = 当前仓库`，不得隐式扩展到子组织。
- 新建/编辑命令仅接受物料类型、物料标识、数量和允许覆盖的进价；商品编码、名称、规格、单位、供应商、金额、已收数量、仓库及申请人快照均由服务端重算或覆盖。
- 每条采购数量必须为正、最多 4 位小数；进价非负并受精度限制；最多 200 行且同类物料不得重复。
- 收货按采购明细 ID 和正数量执行，收货仓库固定为当前仓库；一张订单存在待检批次时不得继续收货。
- 质检按待检收货批次逐行执行。合格和让步接收数量在现有后端中直接完成库存入账；拒收数量回滚可收货额度。因此本切片不展示虚假的独立“上架”按钮，`pending_putaway` 仅作为后端兼容投影保留。
- 质检缺陷级别只允许约定枚举，备注和原因限长，附件最多 5 个且只能使用受信任的本地上传 URL。
- 所有认证、授权和业务响应必须声明 `Cache-Control: no-store`；前端缺失该响应头时失败关闭。
- 组织在请求发送前发生变化时阻止请求；响应包含其他仓库数据时拒绝使用。
- 金额和数量在前端使用十进制字符串与 `decimal.js`，不得以 JavaScript 二进制浮点数作为业务权威值。
- 用户界面遵循高频 ERP 工作台的克制动效：键盘、筛选、逐行录入和表格更新即时；只对低频确认层、按钮状态及焦点使用可中断的短时 `transform`、`opacity`、颜色或阴影过渡，并完整支持 `prefers-reduced-motion`。

## 后端实施任务

### 任务 1：控制器契约和缓存边界

新增 `InvPurchaseControllerTest`，先锁定：

1. 所有读写响应均设置 `no-store`。
2. 保存并提交的 AND 权限、按 ID 提交草稿的单一权限及幂等切面。
3. 四类采购专用目录端点只依赖采购新增权限，不要求用户额外拥有主数据列表权限。
4. 详情权限可读取完整收货批次轨迹；待检端点仍只允许质检权限。

### 任务 2：服务、DTO 和 MyBatis 并发加固

修改采购服务、保存 DTO、采购单/明细映射、收货批次/质检附件映射及对应测试：

1. 列表和“我的”查询强制精确仓库；“我的”额外按当前用户过滤。
2. 保存草稿锁定既有单据，锁后重新校验仓库与 `draft` 状态；服务端强制清空客户端传入的仓库并把已收数量置零。
3. 保存、提交、收货、质检、取消和删除检查所有关键数据库受影响行数；并发状态变化返回明确业务错误。
4. 保存并提交与按 ID 提交均在同一事务中锁定并重新校验草稿状态。
5. 收货和质检锁后再次校验单据存在、精确仓库和状态；质检校验批次、逐行数量、缺陷字段及附件安全。
6. 新增完整收货批次查询，装配收货明细、质检记录及附件，形成不可伪造的服务端追溯投影。
7. 新增采购专用供应商、商品、OE 和礼盒目录端点；沿用服务端主数据可见范围和启用状态，避免前端依赖额外权限。
