# ERP-NEW_2 阶段 13A：收货差异事项不可变骨架实施计划

> 日期：2026-08-02
> 分支：`codex/erp-new-2-rebuild`
> 基线：`70e8c441 feat: add authoritative transfer receipt confirmation`
> 范围：V2 收货事务内的不可变差异事项、加法迁移源码和离线测试；不启用 Gate，不接线旧差异处理器，不启动或连接任何运行环境

## 1. 结果目标

阶段 12 已把每次 V2 收货的合格、残损和显式短缺保存为不可变收货事实，但残损和短缺尚没有可供双方确认与独立角色裁决的 V2 专属事项标识。阶段 13A 在同一个收货事务中，为每个存在残损或短缺的收货分配分别创建一条不可变差异事项：同一分配同时存在两类差异时必须生成两条，不能把不同物理语义合并。

本阶段只建立未来裁决的可信事实根。它不实现补发、退回、报损、责任调整或运输损耗核销，不允许旧 `inv_transfer_discrepancy` 处理器读取或改写 V2 事项，也不增加任何默认可执行的真实写入口。

## 2. 数据模型

新增独立加法迁移 `sql/erp_inventory_transfer_discrepancy_v2_20260802.sql`，仅创建 `inv_transfer_receipt_discrepancy_case`：

- 一条记录严格关联一个 `receipt_allocation_id` 和一个 `discrepancy_type=damaged|shortage`；二者唯一。
- 保存 receipt、shipment、transfer、来源 shipment allocation 的不可变归属。
- 保存差异数量、来源批次成本、六位小数损失金额、说明与证据引用快照。
- 保存 64 位事实指纹，供后续双方确认和裁决拒绝陈旧事实。
- 初始状态固定为 `awaiting_confirmation`，`case_version=0`；本阶段没有状态更新 SQL。
- 迁移只位于仓库 `sql/`，不得复制到 Docker 初始化目录，不执行、不插入业务种子、不启用配置。

后续双方确认、质疑、独立裁决和物理库存处置使用新的加法表与独立检查点实现；13A 不提前固化未确认的裁决状态机。

## 3. 纯计划与守恒

扩展 `InvTransferShipmentReceiptPreparedMutation`：

1. 增加 `DiscrepancyCase` 列表，全部在第一条 DML 前由纯 Planner 构造。
2. `damaged_quantity > 0` 生成 damaged 事项，金额等于 `source_cost_price × damaged_quantity`。
3. `shortage_quantity > 0` 生成 shortage 事项，金额等于 `source_cost_price × shortage_quantity`。
4. 列表按 `shipmentAllocationId` 和 `damaged → shortage` 稳定排序；输入分配顺序不得改变结果。
5. 事实指纹覆盖收货规划版本、来源分配、类型、数量、成本、说明和证据；相同事实稳定、任一事实变化都必须变化。
6. 无残损/短缺时列表必须为空；任何缺少说明、证据、正数量、精确金额或合法指纹的事项必须在第一条 DML 前拒绝。

## 4. 原子持久化顺序

在现有唯一 `InvTransferShipmentReceiptMutationExecutor` 中：

1. 先写收货头和目标库存事实；
2. 写不可变收货分配并取得 `receipt_allocation_id`；
3. 立即逐条写差异事项并校验单行影响数和正生成键；
4. 再继续序列号、累计量、台账和生命周期写入。

事项 SQL 使用 `insert ... select` 从刚写入的不可变收货分配复制归属、数量、成本、说明和证据，同时要求 receipt、shipment、allocation、类型、数量与金额完全一致。任何 0 行、多行、生成键缺失或唯一冲突都向外层唯一事务所有者传播，使整次收货回滚。
