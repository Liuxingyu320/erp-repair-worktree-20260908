# ERP-NEW_2 阶段 12C2：收货事务内权威校验实施计划

> 日期：2026-08-02
> 基线：`737ea218 feat: add guarded transfer receipt persistence skeleton`
> 范围：只修改 ERP-NEW_2 隔离工作树；不使用 Docker、不启动服务、不连接数据库、不执行迁移

## 1. 目标与非目标

12C2 让 V2 收货写边界在事务内完成固定锁序、权威规划重算、请求规范化和全部业务校验，但仍不调用任何库存或审计 mutation。完成后，即使测试构造两个 Gate 为 `true`，服务也只能锁定、校验并最终明确拒绝“原子写入尚未接线”。

本检查点不插入收货头，不更新来源分配累计，不补建目标库存/批次/余额，不移动序列号，不更新调拨生命周期，不接前端 Writer。上述写入只允许在 12C3 单独检查点实施。

## 2. 先统一多次部分收货规划

阶段 12B 的临时规则“发货明细存在历史累计即阻断”必须被逐来源权威进度替代：

- `InvTransferReceiptPlanningAllocationFact` 增加累计合格、累计残损、累计显式短缺和 `receiptVersion`；
- 规划查询读取 12C1 新列；序列号查询排除已经写入 V2 收货序列号审计的已分类序列号；
- 当前剩余为 `allocated - accepted - damaged - shortage`；四项必须非负且精度不超过四位；
- 同一发货明细的所有分配合计等于已发数量，累计合格合计等于 `shipment_detail.received_quantity`；
- 单条分配剩余为零且无阻断时状态为 `complete`，不再要求序列号仍处于来源位置；仍有剩余时状态为 `ready`，只返回尚未分类且当前仍为来源位置 `shipped` 的序列号；
- `receiptPlanVersion` 加入三类累计和 `receiptVersion`，任何收货进度变化都会使旧页面版本失效。

迁移为序列号处置审计增加 `(shipment_id, shipment_serial_id)` 唯一键，保证同一发货序列事实只能被一个普通收货批次分类。后续差异裁决使用独立边界，不通过第二个普通收货批次覆盖历史。

## 3. 纯请求校验策略

新增不依赖 Spring/Mapper 的纯策略，输入客户端请求和权威 `Composition`，输出不可变规范化命令：

1. `receiptPlanVersion` 必须逐字匹配，`basis` 必须为 `server-recommendation`；
2. 请求分配 ID 唯一且必须来自状态为 `ready` 的服务端分配；
3. 每条合格、残损、短缺数量非负、最多四位小数，合计必须大于零且不超过当前剩余；
4. 合格数量大于零时必须选择服务端正常库位，等于零时不得夹带合格库位；残损及隔离库位同理；
5. 残损或短缺大于零时，差异说明和附件引用均不能为空；
6. lot 跟踪不得提交序列号；serial 跟踪的三类数量必须为整数并分别等于对应 ID 数，ID 在当前剩余序列号集合内且全请求唯一；
7. `finalizeShipment=true` 当且仅当提交后整个发货批次剩余为零；未出现在请求中的 ready 分配保持在途；
8. 规范化结果按来源分配 ID 和序列号 ID 排序，备注/说明去除首尾空白，生成稳定 `requestFingerprint` SHA-256 供业务幂等使用。

策略测试覆盖：陈旧规划、重复/越界分配、数量超限、错误库位、缺差异证据、lot/serial 混用、序列号重复/越界、部分收货、完成标志和稳定指纹。

## 4. 只锁定事务协调器

新增只暴露 `select...ForUpdate` 的 Lock Gateway；`InvTransferShipmentReceiptCreationService` 不能直接持有包含 mutation 方法的 Mapper。

调用顺序：

1. Gate；请求和基础标识防御式校验；
2. 发货批次、调拨单；组织范围与收货方向；
3. 调拨明细、发货明细、来源分配；
4. 目标模式；
5. 全部物料策略；
6. 全部目标汇总库存；
7. 全部来源批次；
8. 全部来源及目标候选库位；
9. 请求涉及的已存在派生批次；
10. 请求涉及的已存在目标余额；
11. 发货序列号；
12. 在已锁事实内调用与 GET 相同的 Composer，再运行纯请求策略；
13. 无论校验成功与否都不调用 mutation；全部成功后仍抛出“12C3 原子写入尚未接线”。

集合在 Gateway 前先去重升序。锁顺序测试使用 Mockito `InOrder`；mutation 方法使用 `verify(..., never())` 或通过类型隔离证明不可达。

## 6. 验证与停止条件

运行定向测试、库存完整离线 Reactor、`erp-ui-next npm run verify` 和 `git diff --check`。静态审计必须证明运行配置没有 Gate=true、CreationService 没有 mutation Mapper 字段、没有数据库连接串/秘密/共享服务/受保护路径和符号链接。

如果逐来源累计与发货明细累计无法守恒、已分类序列号仍出现在剩余计划、GET 和事务重算使用不同指纹输入、任何 mutation 在 12C2 可达，或需要触碰受保护原项目，则立即停止。
