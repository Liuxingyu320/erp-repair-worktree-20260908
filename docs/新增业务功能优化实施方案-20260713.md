# 新增业务功能优化实施方案

> 方案日期：2026-07-13  
> 文档状态：已结合当前项目代码、表结构、权限、移动端、统一待办和库存流程完成技术细化  
> 需求依据：[新增业务需求确认总结](./新增业务需求确认总结-20260713.md)  
> 关联计划：[仓库管理优化实施计划](./仓库管理优化实施计划-20260713.md)  
> 实施约束：兼容当前 Java 17、Spring Cloud 微服务、Vue 2、MyBatis 和 MySQL 5.7；数据库迁移先加后减，不直接删除历史数据或旧业务关联。

## 1. 优化后的建设结论

本次五项需求可以继续建设，但不能按“直接在现有页面加几个字段”的方式实施。结合当前项目，推荐采用以下方案：

1. 健康证建立独立历史表，员工档案和“我的团队”只读取当前证件投影，不把健康证到期日重复写入 `sys_user_profile`。
2. OE 额度内上报成功后，OA 通过可靠发件箱把补货事件交给库存服务；库存服务先生成补货需求，再由仓库选择来源仓并生成现有调拨单，不在上报事务中直接扣库存。
3. OE 超额路径彻底取消“异常批准后继续上报”，保留同款购买参考；同时修复当前额度校验的并发风险。
4. 旧 `inv_customer` 继续作为客户主键和销售单关联，不再作为员工使用的客户管理页面；新增客户服务卡、服务记录和变更日志，并提供不含信用额度等字段的安全接口。
5. 门店返仓作为 `store_return` 调拨类型加入现有调拨模块，复用审批、待办、发货、收货和流水，但需要补齐当前实际上尚未完成的“调拨收货差异处理”。
6. 店长查看员工使用独立的“我的团队”接口和精简 DTO，手机号在此接口完整返回；不能给店长开放现有完整人事详情，也不能全局关闭手机号脱敏。

最终业务链路为：

| 业务 | 权威模块 | 复用能力 | 新增核心能力 |
|---|---|---|---|
| 健康证 | `erp-system` | 员工档案、数据范围、统一待办、站内通知 | 健康证历史、审核、到期投影、提醒扫描 |
| 我的团队 | `erp-system` | 员工、部门、直属主管、门店授权 | 团队专用数据范围和安全返回模型 |
| OE 上报 | `erp-oa` | 固定资产配置、额度、上报、图片 | 并发额度保护、同款参考、可靠补货事件 |
| OE 补货 | `erp-inventory` | OE 主数据、库存、调拨、统一待办 | 补货需求、仓库处理台、上报与调拨关联 |
| 门店返仓 | `erp-inventory` | 调拨审批、发货、收货、库存流水 | 返仓方向、返仓原因、货况、真实差异处理 |
| 客户服务卡 | `erp-inventory` | 客户 ID、门店隔离、销售单关联 | 服务资料、服务记录、修改审计、安全 DTO |
| 受控附件 | `erp-file` | 云盘空间、节点权限、审计下载 | 业务记录保存受控节点 ID，而非长期裸 URL |

## 2. 当前项目核对结果

### 2.1 可以直接复用的基础

- 员工主档已经有 `direct_supervisor_user_id`、合同日期、门店/部门和岗位关系。
- `HrEmployeeAccessService` 已使用 `@DataScope` 作为人事数据范围边界。
- 系统待办已有合同到期、资料不完整等人事类型，前端已有统一待办路由解析。
- 系统通知已有 `(user_id, business_key)` 幂等约束，可避免重复提醒。
- OA 固定资产上报已经按门店选择 OE、计算额度并写额度流水。
- 库存通用物料模型已经支持 `product`、`oe`、`gift`，采购和库存也能识别 OE。
- 调拨已经具有审批实例、审批轨迹、部分发货、按发货批次收货、统一待办和库存流水。
- 客户已经按门店范围查询，销售单已经保存 `customer_id` 和客户名称快照。
- 文件模块已有带空间权限、操作日志和受控读取的云盘能力。

### 2.2 必须先处理的项目现状风险

#### 风险一：OE 额度存在并发超用窗口

当前 `OaFixedAssetServiceImpl.submitRepair` 先汇总已用额度，再插入上报和流水，但没有锁定“门店 + 年度”额度行。两个员工同时提交时，可能都读取到相同可用额度并同时成功。

处理要求：

- 新增 `selectQuotaForUpdate(shopDeptId, quotaYear)`；
- 新年度额度行不存在时先安全创建；并发插入命中唯一键后重新读取并加锁；
- 单条和批量上报都先锁额度行，再重新计算已用额度；
- 上报、额度流水、补货发件箱必须处于同一个本地事务；
- 并发测试必须证明最多只有合法额度内的请求成功。

#### 风险二：现有“异常批准”不符合新口径

当前固定资产配置页仍有“异常批准”按钮和 `oa:fixedAsset:config:approve` 权限，后端也能生成 `special_extra` 流水。现有已用额度汇总又只统计 `normal_submit` 和 `advance_future_months`，`special_extra` 不会进入常规已用额度计算。

处理要求：

- 新版本隐藏并撤销“固定资产异常批准”菜单权限；
- 后端停止创建新的异常维修上报，不能只依赖前端隐藏；
- 历史 `pending_confirm` 记录保留只读并提供一次性处置清单；
- 超额后唯一业务结果为“上报失败、无补货、员工按同款参考自行购买、无需再上报”。

#### 风险三：调拨的差异状态目前不是完整流程

项目虽然已有 `discrepancy` 状态和页面文案，但 `receiveTransferShipment` 当前要求每条明细必须按本次发货数量全量收货，数量不同会直接报错，尚未生成差异单、责任处理和最终结案。

处理要求：

- 门店返仓上线前补齐真实差异记录；
- 实收少于实发、残损、拒收均不能伪装成正常完成；
- 差异处理后再决定入合格库存、待质检库存、退回来源或核销。

#### 风险四：现有客户列表会返回财务字段

当前 `/customer/list` 返回 `InvCustomer`，其中包含信用额度、已用额度和账期。如果直接把原权限授予所有门店员工，会把不需要的财务字段一并开放。

处理要求：

- 客户服务卡使用新 DTO 和新权限；
- 销售选择客户改用精简 `/customer/options`；
- 原客户列表只作为兼容接口保留，不授予普通员工。

#### 风险五：现有人事详情不能直接给店长

当前 `HrEmployeeProfileVo` 包含大量人事字段，即使多数已脱敏，也超出店长日常管理需要；当前列表和详情手机号均会脱敏。

处理要求：

- 新增团队专用 DTO，只声明允许返回的字段；
- 只在团队 DTO 的 `phoneNumber` 返回完整手机号；
- 不修改 `HrSensitiveFieldMasker`，不改变现有人事页面和导出的脱敏规则。

## 3. 总体技术边界

### 3.1 模块职责

1. `erp-system` 只管理员工、健康证、团队权限、提醒和通知。
2. `erp-oa` 负责判断 OE 上报是否成功，并可靠发布“成功上报”事实。
3. `erp-inventory` 负责补货需求、来源仓选择、调拨和库存变化。
4. `erp-file` 负责附件内容和访问权限，业务表只保存受控节点标识及必要快照。
5. `erp-ui` 负责桌面和移动端交互，但任何门店范围、额度、审批、发货和收货限制都必须由后端再次校验。

### 3.2 跨服务一致性

项目当前没有库存共享 API，但已经有“系统模块本地发件箱 → Feign 内部接口 → OA 幂等接收”的成熟实现。OE 补货沿用同样模式：

1. OA 在成功上报事务中原子写入上报、额度流水和补货发件箱。
2. 定时分发器领取发件箱事件，不在远程调用期间持有原业务事务。
3. 库存内部接口以 `repair_id` 幂等创建补货需求。
4. 成功后 OA 发件箱记录库存需求 ID；超时、限流和服务不可用进入退避重试。
5. 载荷非法或永久性 4xx 进入 `DEAD`，生成管理员待办并允许人工修复后重投。

不建议采用“OA 上报成功后同步调用库存并直接生成调拨单”，原因是来源仓尚未确定，且库存服务短暂故障会让业务结果不一致。

### 3.3 数据迁移原则

- 所有首版迁移只新增表、字段、索引和权限，不删除旧列、旧接口或历史数据。
- 菜单和角色授权通过稳定权限字符串查找，不依赖固定菜单 ID。
- SQL 必须兼容 MySQL 5.7，不依赖 MySQL 8 专属语法。
- 回填脚本先输出 dry-run 数量、异常样本和预期变更，再由人工确认正式执行。
- 新旧页面至少兼容一个正式版本；使用量归零后再讨论删除旧实现。

## 4. 员工健康证方案

### 4.1 数据模型

计划新增 `hr_employee_health_certificate`：

| 字段 | 说明 |
|---|---|
| `certificate_id` | 健康证记录 ID |
| `user_id` | 绑定员工 ID |
| `dept_id_snapshot` | 提交时所属组织快照，仅用于历史展示，不作为授权依据 |
| `certificate_no` | 健康证编号 |
| `issued_date` | 办理日期 |
| `valid_from` | 有效期开始日 |
| `expires_on` | 到期日 |
| `issuer_name` | 发证机构 |
| `attachment_node_id` | 受控云盘节点 ID |
| `review_status` | `DRAFT/PENDING_REVIEW/APPROVED/REJECTED` |
| `current_flag` | 当前已审核证件为 `Y`，历史行保存 `NULL` |
| `reviewed_by_user_id/name/time` | 审核快照 |
| `rejection_reason` | 驳回原因 |
| `version` | 乐观锁版本 |
| 审计字段 | 创建人、创建时间、修改人、修改时间、逻辑删除标记 |

约束和计算规则：

- 唯一索引 `(user_id, current_flag)`，利用历史行 `NULL` 保证每名员工最多一条当前证件；
- 审核通过时锁定员工档案行，先把旧当前记录改为历史，再把新记录设为当前；
- `VALID/EXPIRING/EXPIRED/NOT_SUBMITTED` 是查询时根据当前记录、审核状态和日期计算的展示状态，不由使用人员手填；
- `sys_user_profile.health_status` 继续表示员工健康状况，不改作健康证状态；
- 不在 `sys_user_profile` 冗余保存健康证到期日，避免续证时产生双份权威数据。

### 4.2 接口与权限

计划新增接口：

| 接口 | 用途 | 建议权限 |
|---|---|---|
| `GET /hr/health-certificate/me` | 员工查看本人当前证件和历史 | 登录用户本人 |
| `POST /hr/health-certificate/me/draft` | 保存本人草稿 | `hr:healthCertificate:self:edit` |
| `POST /hr/health-certificate/me/submit` | 提交本人证件审核 | `hr:healthCertificate:self:submit` |
| `GET /hr/health-certificate/list` | 人事按状态和到期日查询 | `hr:healthCertificate:list` |
| `GET /hr/health-certificate/employee/{userId}` | 管理范围内查看员工历史 | `hr:healthCertificate:query` |
| `POST /hr/health-certificate/{id}/review` | 人事审核或驳回 | `hr:healthCertificate:review` |

所有写接口增加 `@IdempotentSubmit` 和不记录附件内容的操作日志。员工本人接口用登录用户 ID，不接受前端传任意 `userId`。

健康证附件不能只依赖云盘空间本身的可见范围。业务下载/预览接口应先按“本人、当前管理范围、人事权限”校验健康证记录，再通过文件服务读取内容；响应不返回长期公开地址，也不允许知道 `nodeId` 后绕过健康证权限直接下载。

### 4.3 员工档案投影

员工列表、详情和团队页增加以下只读字段：

- `healthCertificateStatus`；
- `healthCertificateIssuedDate`；
- `healthCertificateExpiresOn`；
- `healthCertificateDaysRemaining`；
- `healthCertificateAttachmentPresent`。

列表查询采用一次批量投影查询，不允许逐员工查询证件造成 N+1。员工详情点击状态后再加载历史记录。

### 4.4 到期提醒

- 新增 `HR_HEALTH_CERT_DUE` 待办类型并接入 `todoRouteResolver.js`；
- 配置项建议为 `todo.health-certificate.warning-days=30,15,7`；
- 每日按 Asia/Shanghai 扫描，复用 `HrContractRenewalScanner` 的批处理、可配置和时钟测试方式；
- 员工本人、当前门店内拥有提醒权限的店长、人事人员分别生成通知；
- 幂等键建议为 `HR_HEALTH_CERT:{certificateId}:{expiresOn}:{threshold}`；
- 已过期后保留风险待办，但同一提醒节点不重复发送推送。

### 4.5 页面

- 员工档案列表增加证件状态、到期日筛选和到期标记；
- 员工档案详情增加“当前健康证”摘要及“查看历史”；
- 新增员工本人上传页面，桌面和移动端共用状态规则；
- 人事增加待审核、即将到期、已过期三个快捷视图；
- 附件预览通过鉴权接口读取，不把永久公开 URL 写入页面模型。

## 5. “我的团队”方案

### 5.1 数据范围

团队查询必须同时满足：

1. 使用人员已选择且有权访问当前门店；
2. 目标员工当前组织属于该门店范围；
3. 店长权限可查看该门店在职员工；其他主管权限只查看 `direct_supervisor_user_id = 当前用户` 的员工；
4. 多门店人员每次只查询当前选择门店，不把多个门店混合展示；
5. 调店、离职或主管关系生效后，下一次查询立即按当前权威关系变化。

建议拆分权限：

- `hr:team:list`：进入团队页面；
- `hr:team:store`：查看当前门店员工，授予店长角色；
- `hr:team:direct`：查看本人直属员工，按实际管理岗位授予；
- `hr:team:healthCertificate`：查看证件日期和受控附件状态。

角色只决定能力，数据范围仍由服务端门店授权和组织关系计算，不能在代码中只判断角色名称 `dz`。

### 5.2 专用返回模型

计划新增 `HrTeamMemberVo`，只返回：

- 员工 ID、工号、姓名、头像；
- 完整手机号 `phoneNumber`；
- 当前门店、岗位、直属主管；
- 在职状态、入职日期；
- 健康证状态、办理日期、到期日期；
- 合同到期日期和提醒级别；
- 档案完整度。

明确不得声明工资、银行卡、身份证完整号码、住址、户籍、紧急联系人和其他完整人事档案字段。接口响应增加 `Cache-Control: no-store`，操作日志不保存响应体，不提供普通团队导出。

### 5.3 页面与接口

- 新增 `GET /hr/team/list` 和 `GET /hr/team/{userId}`；
- 详情仍返回团队精简 DTO，不跳到现有 `/hr/employee/{userId}` 完整详情；
- 桌面新增“我的团队”，移动端新增 `/mobile/hr/team`；
- 默认只显示在职员工，可切换“待离职”；
- 支持姓名、工号、岗位、健康证状态搜索，搜索条件仍受同一数据范围限制。

## 6. 调拨管理与门店返仓方案

### 6.1 类型与方向策略

计划新增集中常量/策略 `InvTransferTypes`，替换服务和页面中分散的字符串判断：

| 类型值 | 页面名称 | 发起组织 | 来源 | 目标 | 默认物料 |
|---|---|---|---|---|---|
| `warehouse` | 门店要货 | 门店 | 仓库 | 当前门店 | 商品、礼盒、OE |
| `store_return` | 门店返仓 | 门店 | 当前门店 | 目标仓库 | 商品、礼盒、OE |
| `cross_store` | 异店调货 | 按现有规则 | 门店 | 门店 | 保持现有商品、礼盒范围 |

现有数据库值 `warehouse` 不改名，避免破坏历史调拨、审批规则和移动端；只把显示名称统一为“门店要货”。

`InvTransferOrder` 当前固定使用“发货仓库不能为空、目标门店不能为空”的校验文案，需要改为中性的“来源组织、目标组织”，再由类型策略返回准确业务错误。

### 6.2 返仓字段

主单计划增加：

- `return_reason_code`：`OVERSTOCK/NEAR_EXPIRY/WRONG_DELIVERY/DAMAGED/STORE_CLOSURE/OTHER`；
- `return_reason_text`：其他原因说明；
- `attachment_node_ids` 或独立附件关系；
- `source_business_type/source_business_id`：预留 OE 补货等来源业务关联；
- `version`：并发状态更新保护。

明细计划增加：

- `goods_condition`：`NORMAL/DAMAGED/PENDING_QC`；
- `condition_note`；
- 批次/库位启用后关联现有 `lot_id`、`source_location_id`，不再新建另一套文本批次权威数据。

### 6.3 状态与操作方

门店返仓状态沿用当前调拨主状态：

`draft → submitted → approved → partial_delivered/delivered → partial_received/discrepancy → received/closed`

方向规则：

- 门店是来源方，只能由当前来源门店发货；
- 仓库是目标方，只能由目标仓库收货和验收；
- 审批候选人继续由现有审批规则和四级负责人链计算；
- `InvTodoMapper.xml` 按来源组织生成发货待办、按目标组织生成收货待办；
- 后端按类型和组织双重校验，页面按钮规则仅用于交互提示。

现有库存流水和发货批次还需要做一次方向中性化：

- `addTargetStockAndLog` 当前把所有调拨入库的 `business_type` 固定写成 `cross_store_transfer`，应按实际类型改为 `warehouse_replenishment/store_return/cross_store_transfer/oe_replenishment`，历史流水不重写；
- `inv_transfer_shipment.warehouse_id/warehouse_dept_id` 当前默认来源一定是仓库，门店返仓时语义不成立；首版增加 `source_location_dept_id` 并从旧字段回填，代码优先读新字段，旧字段保留一个兼容周期；
- 统计和对账使用稳定的调拨类型及来源业务字段，不能再根据中文备注推断业务方向。

### 6.4 OE 调拨兼容

当前 `InventoryItemResolver` 能解析 OE，但 `InvTransferServiceImpl.resolveTransferItem` 会明确抛出“OE不能用于调拨流程”，桌面和移动调拨也只允许商品、礼盒。

处理要求：

- 移除全局 OE 禁止，改为由调拨类型策略决定允许的物料类型；
- 门店要货、门店返仓允许 OE，异店调货本期保持原范围；
- 调拨明细、发货批次、库存和流水继续使用 `item_type + item_id`；
- 对历史只有 `product_id` 的明细保持兼容读取。

### 6.5 差异处理

计划新增调拨差异主表和明细表，记录：

- 调拨、发货批次、调拨明细；
- 实发量、实收量、短少量、拒收量、残损量；
- 差异类型、图片、说明、责任方；
- 处理决定：补发、退回来源、按实收结案、进入待质检、核销；
- 处理人、处理时间和状态日志。

收货时只把实际验收并确认进入目标组织的数量增加到库存。存在差异时主单进入 `discrepancy`，不能提前归档。差异处理接口必须幂等，并验证处理后所有数量对平。

### 6.6 与仓库批次方案的关系

- 当前汇总库存模式下先完成方向、审批、发货、收货和差异闭环；
- 批次/库位模式开启后，受批次管理的商品返仓必须选择来源批次和库位；
- 正常品进入可用或待上架库存，残损品进入隔离/残损状态，待质检品生成仓库任务；
- 不在返仓功能中重复建设批次、效期和库位表，直接依赖既有仓库阶段 3 模型。

## 7. OE 上报、购买参考与仓库补货方案

### 7.1 超额前后端契约

建议增加上报预校验接口，并保留最终事务校验：

- `POST /fixedAsset/repair/precheck` 返回本次占用额度、锁前可用额度、是否允许上报和同款购买参考；
- 真正提交时锁额度行并重新计算，预校验通过不代表可以绕过最终并发校验；
- 超额使用稳定错误码 `FIXED_ASSET_QUOTA_EXCEEDED`，页面不得通过匹配中文错误字符串判断；
- 超额响应/参考接口返回当前选择 OE 的编码、名称、描述、订货单位、图片和购买链接；
- 失败后不插入维修单、不写额度流水、不写补货发件箱。

### 7.2 同款购买参考

`inv_oe_item` 当前已有编码、名称、产品描述、订货单位、供应商和图片，计划增加：

- `purchase_reference_url`；
- `purchase_reference_note`；
- `purchase_reference_updated_by/time`。

安全与数据要求：

- 只允许 `https` 链接，并按配置的可信域名白名单校验；
- 前端使用新窗口时增加 `noopener/noreferrer`；
- 不接受通用商城首页，链接必须对应同款或明确采购页面；
- 上线前输出所有启用固定资产 OE 的参考信息完整度清单；
- 活跃固定资产缺少编码、图片或购买参考时不得通过上线验收。

### 7.3 可靠补货事件

OA 计划新增 `oa_fixed_asset_replenishment_outbox`，关键字段包括：

- `outbox_id`、`repair_id`、`event_version`；
- `payload_json`；
- `status=PENDING/SENDING/RETRY/SENT/DEAD`；
- `retry_count`、`next_retry_time`、`last_error_code`；
- `target_demand_id`、`version` 和审计时间。

`repair_id` 建唯一索引，确保一条成功上报只发布一次业务事实。批量上报为每条维修记录分别产生事件，单条失败时整个批量事务回滚。

现有 `oa_fixed_asset_repair.image_urls` 在兼容期继续可读；新写入逐步改为受控附件关系或节点 ID，发件箱只传业务附件引用和必要快照，不复制公开文件地址作为新的长期权威字段。

计划新增 `erp-api-inventory`：

- 在 `ServiceNameConstants` 增加 `INVENTORY_SERVICE`；
- 定义 `RemoteOeReplenishmentService` 和事件 DTO；
- 库存内部接口使用 `@InnerAuth`；
- 接收端以来源服务、`repair_id` 和事件版本做幂等校验。

### 7.4 库存补货需求

库存计划新增：

1. `inv_oe_replenishment_demand`：保存上报门店、OE 快照、上报量、计划量、已发量、已收量、故障和图片快照、处理状态。
2. `inv_oe_replenishment_transfer`：关联一个需求和一个或多个调拨单，支持不同仓库分批补货。

建议状态：

- `PENDING`：待仓库处理；
- `PREPARING`：已选择来源仓/正在备货；
- `TRANSFER_CREATED`：已生成调拨；
- `PARTIAL_SHIPPED`、`SHIPPED`；
- `PARTIAL_RECEIVED`、`COMPLETED`；
- `OUT_OF_STOCK`：缺货待采购；
- `CLOSED`：人工关闭并有原因。

仓库操作：

1. 打开待补货需求，查看上报门店、同款 OE、数量、图片和当前各仓库存；
2. 选择来源仓和本次补货数量；
3. 生成 `warehouse` 类型调拨单，物料固定为该 OE；
4. 使用现有调拨审批、发货、收货和差异处理；
5. 根据调拨实际发货/收货数量回写需求汇总状态。

仓库无库存时标记 `OUT_OF_STOCK` 并进入采购/补货处理，不允许直接标记完成。替代型号本期不自动支持；确需替代时关闭原需求并按有审计的新流程处理。

### 7.5 待办与页面

- 新增 `INV_OE_REPLENISHMENT` 待办类型和仓库处理权限；
- 桌面在库存/仓库管理下新增“OE 补货需求”；
- 移动端增加仓库待补货列表和详情，生成调拨可先跳转现有调拨表单；
- OA 上报详情显示补货状态和关联调拨；库存需求详情可返回原 OA 上报摘要，但不能依赖跨库直接联表。

## 8. 客户服务卡方案

### 8.1 兼容策略

保留 `inv_customer` 作为客户核心身份：

- `customer_id` 继续被销售单引用；
- 客户名称、编码、联系电话、所属门店和状态继续作为核心字段；
- 旧信用额度、已用额度、账期等列暂不删除，但不进入服务卡 DTO；
- 旧“客户管理”菜单隐藏或重定向到“客户服务卡”；
- 原接口至少保留一个版本，供历史客户端和回滚使用。

### 8.2 数据模型

计划新增一对一 `inv_customer_service_profile`：

- `customer_id` 唯一关联客户主表；
- `photo_node_id`；
- `tea_preferences`；
- `preference_tags`；
- `brewing_service_preferences`；
- `cautions`，用于忌口、过敏和注意事项；
- `budget_min`、`budget_max`；
- `last_visit_date`；
- `version` 和审计字段。

计划新增一对多 `inv_customer_service_record`：

- 服务日期、服务人员、人数（可空）；
- 本次茶饮/器具偏好、注意事项、服务备注；
- 可选消费金额快照；
- 创建人用户 ID、姓名、所属门店和时间；
- 默认追加记录，不允许普通员工物理删除。

计划新增 `inv_customer_service_change_log`：

- 客户 ID、请求幂等键、变更字段；
- 变更前后摘要；
- 操作人、操作门店、时间和来源端；
- 对敏感备注只保存必要审计摘要，不把整张客户卡复制到普通系统日志。

### 8.3 安全接口

建议接口：

| 接口 | 返回范围 | 建议权限 |
|---|---|---|
| `GET /customer/options` | ID、名称、电话、状态 | `inv:customer:option` |
| `GET /customer/service-card/list` | 服务卡列表 DTO | `inv:customerCard:list` |
| `GET /customer/service-card/{id}` | 本门店服务卡详情 | `inv:customerCard:query` |
| `POST /customer/service-card` | 新建客户和服务卡 | `inv:customerCard:add` |
| `PUT /customer/service-card/{id}` | 乐观锁更新 | `inv:customerCard:edit` |
| `POST /customer/service-card/{id}/records` | 追加服务记录 | `inv:customerCard:record:add` |
| `POST /customer/service-card/{id}/archive` | 停用/归档 | `inv:customerCard:archive` |

不向普通员工提供物理删除和旧财务字段导出。所有列表、详情、更新、归档和服务记录接口都要使用当前选择门店，并在按 ID 查询后再次校验所属门店。

权限迁移应把客户服务卡的查看、新增、编辑和追加服务记录授予现有门店员工角色及对应入职角色模板，但不能同时授予旧 `inv:customer:export`、财务字段或物理删除权限。以后新增门店岗位时也必须通过同一角色模板同步服务卡基础权限。

客户照片和服务附件沿用与健康证相同的“先校验业务门店范围，再读取受控文件”方式，不能把云盘节点 ID 当作无需二次鉴权的公开资源。

### 8.4 旧功能替换

- 桌面旧客户页面替换为卡片式客户服务卡；
- 销售单客户选择从 `/customer/list` 迁到 `/customer/options`；
- 移动端客户实体选择器和快速新建改用新接口；
- 快速新建仍返回 `customerId`，保证销售单现有提交流程不变；
- 不修改历史销售单的客户名称快照，不因客户后续改名重写历史单据。

### 8.5 门店隔离

- 非管理员也必须先选择门店；
- 拥有多个门店权限时只查询当前门店；
- 客户手机号搜索也只能在当前门店范围内；
- 通过其他门店客户 ID 请求详情、更新、归档或添加服务记录统一返回无权访问/记录不存在；
- 管理员跨店管理仍应明确选择目标门店，不默认返回所有门店客户混合列表。

### 12.3 必须覆盖的后端场景

健康证与团队：

- 两次续证保留历史且只有一条当前记录；
- 审核并发不会产生两条当前证件；
- 30/15/7 天通知幂等；
- 店长能看到完整手机号，但序列化结果不含工资、银行卡和完整证件号码；
- 其他门店员工 ID 直查被拒绝；
- 调店和离职生效后访问范围立即变化。

OE：

- 两个并发上报不能同时超用额度；
- 超额不产生维修单、流水或发件箱；
- 额度内上报三项数据同事务成功或全部回滚；
- 发件箱重复投递只产生一个补货需求；
- 库存服务停机后恢复能继续重试，不丢需求；
- 一个需求可关联多次部分调拨并正确汇总实发、实收。

调拨返仓：

- 门店只能作为返仓来源，仓库只能作为目标；
- 返仓审批与现有审批规则一致；
- 非来源方不能发货，非目标方不能收货；
- OE 能在允许的调拨类型中正常出入库；
- 短收、残损和拒收进入差异，不提前完成；
- 差异处理前后库存、明细、发货批次和流水对平。

客户服务卡：

- 新建服务卡同时产生可供销售使用的 `customerId`；
- 旧销售单仍能显示客户快照；
- 普通员工接口响应不含信用额度、已用额度和账期；
- 其他门店列表、搜索、详情、更新、归档和服务记录全部拒绝；
- 乐观锁冲突不覆盖他人刚完成的修改；
- 修改日志能追溯操作人和变更摘要。

## 13. 发布、灰度与回滚

### 13.1 功能开关

建议配置：

- `feature.hr.health-certificate.enabled`；
- `feature.hr.team.enabled`；
- `feature.oa.oe-replenishment.enabled`；
- `feature.inventory.store-return.enabled`；
- `feature.inventory.customer-service-card.enabled`。

开关只控制新入口和新单创建。已经生成的证件审核、发件箱、补货需求、返仓调拨和差异单必须继续可处理，不能因关闭入口留下永久在途数据。

### 13.2 灰度顺序

1. 管理员和测试门店；
2. 一个门店 + 一个仓库验证健康证、团队、返仓和 OE 补货；
3. 两个门店验证客户隔离和跨店越权；
4. 扩大到全部店长和仓库人员；
5. 观察一个完整提醒周期和库存对账周期后全量启用。

### 13.3 回滚

- 健康证：关闭新写入口，保留历史表和只读投影；不把数据回填到普通健康状况字段。
- 我的团队：关闭菜单和权限，不修改原人事脱敏逻辑。
- OE：停止分发时让发件箱保持可重试；已创建调拨继续走完，不删除补货需求。
- 门店返仓：隐藏新建类型，但已提交单继续按原状态处理；不得通过回滚代码跳过库存对账。
- 客户服务卡：临时恢复旧页面时继续读取原 `inv_customer`；新增服务资料保留，不反向覆盖历史销售单。
- 数据库：首版不删旧列，因此应用回滚不要求破坏性逆迁移。

## 14. 运行监控与对账

建议新增指标和管理员视图：

- 健康证待审核数、即将到期数、已过期数、提醒失败数；
- OE 发件箱 `PENDING/RETRY/DEAD` 数量和最老等待时间；
- 补货需求待处理、缺货、超时和已完成数量；
- 返仓在途、差异、待质检和超时数量；
- 客户服务卡跨店拒绝次数、乐观锁冲突数、旧接口调用量；
- 每日核对 OE 成功上报数 = 已发送事件数 + 可解释的待重试/死信数；
- 每日核对返仓来源扣减、目标增加、在途和差异数量。

任何对账异常只生成管理员待办和报告，不自动修改库存或客户数据。

## 15. 最终验收清单

### 健康证与团队

- [ ] 员工档案列表和详情能直接看到当前健康证到期日。
- [ ] 续证不覆盖历史，当前证件唯一。
- [ ] 提醒节点不重复发送。
- [ ] 店长只看到当前门店/管理范围内员工。
- [ ] 团队页面手机号完整显示，其他敏感字段不返回。

### OE

- [ ] 额度并发校验不会超用。
- [ ] 超额上报原子失败且不能走异常批准绕过。
- [ ] 超额页面保留同款 OE 编码、图片、规格说明和购买链接。
- [ ] 成功上报最终必有一个可追踪的库存补货需求。
- [ ] 仓库能生成 OE 调拨，门店收货后补货闭环完成。

### 调拨返仓

- [ ] 同一调拨入口支持门店要货、门店返仓、异店调货。
- [ ] 门店返仓复用现有审批和统一待办。
- [ ] 来源门店发货、目标仓库收货的权限和方向不可绕过。
- [ ] 商品、礼盒、OE 的库存和流水正确。
- [ ] 短少、残损、拒收有真实差异单和处理记录。

### 客户服务卡

- [ ] 旧客户菜单被服务卡替换，历史客户 ID 和销售单关系不丢失。
- [ ] 当前门店员工可以共同新增和编辑服务卡。
- [ ] 普通员工看不到信用额度、账期等旧财务字段。
- [ ] 不同门店无法通过列表、搜索、ID 直查或写接口访问彼此客户。
- [ ] 每次修改都有操作人、时间和变更摘要。

## 16. 推荐批准范围

建议一次评审确认整体架构，但分阶段批准上线：

1. 立即批准阶段 0，先修复 OE 额度并发和异常批准口径。
2. 批准健康证与“我的团队”作为独立版本，不等待库存改造。
3. 调拨返仓和差异处理一起验收，不能只增加 `store_return` 类型后提前上线。
4. OE 补货必须依赖调拨 OE 支持和可靠发件箱，不能用手工库存调整代替。
5. 客户服务卡上线前必须先完成安全 DTO 和销售选择接口迁移，不能把旧客户完整接口直接授予全店员工。

以上方案能够在不破坏当前销售、员工档案、调拨审批和历史数据的前提下，完成用户确认的五项业务目标，并把当前项目中已经发现的额度、权限和库存一致性风险一并封住。
