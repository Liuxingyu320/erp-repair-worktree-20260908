# 系统管理功能检查与优化方案

检查日期：2026-07-13  
检查范围：系统管理目录及其直接相关的用户、权限、组织、薪资、审批配置与审计日志链路  
运行方式：本机直接运行前后端服务、浏览器实测、代码静态检查、数据库只读核验、专项自动化测试；未使用虚拟机或容器  

## 1. 结论

系统管理功能目前“主流程可用、基础框架一致”，用户、角色、菜单、部门、岗位、薪资方案和调拨审批配置都能完成日常管理。现有权限指令、后端数据范围检查、公告 HTML 清洗、组织授权的未保存提醒、薪资与调拨审批预览等能力，说明系统已经具备较好的管理后台基础。

但本轮发现 5 项应优先处理的高风险边界，以及一批会明显降低管理员效率的体验问题。最需要先处理的是：

1. 非法角色数据范围值会让数据权限过滤“失效放开”，而不是“拒绝访问”。
2. 当前初始密码长度为 6 位，与系统 8～20 位密码策略冲突；批量导入路径还能绕过策略直接创建弱密码账户。
3. 任意已登录用户可按参数 ID 或参数键读取系统参数，初始密码等配置没有管理员查询边界。
4. 操作日志只排除了密码字段，现存日志包含未脱敏手机号模式；日志详情还可以直接复制请求与响应。
5. 操作日志和登录日志的“清空”直接执行 `TRUNCATE TABLE`，并且与普通删除共用权限，审计证据可被一次性销毁。

建议先完成 P0 安全边界修复，再做列表效率、角色配置、日志可信度和复杂配置防误操作。不要先投入大规模视觉改版；当前最重要的是把权限、密码和审计链路收紧。

## 2. 检查方法与覆盖面

本轮采用五层检查：

1. 信息架构：核对系统管理菜单、动态路由、按钮权限与页面之间的关系。
2. 真实页面：以 1280×720 视口逐页检查组织选择、列表、搜索、弹窗、空状态、横向滚动和关键操作。
3. 前后端边界：核对 Controller 权限、参数校验、Service 防护、Mapper 写入与数据权限切面。
4. 数据状态：只读核验角色数据范围、密码配置、日志数量、敏感字段模式和数据库时间。
5. 自动化回归：运行系统管理、组织授权、用户资料、公告安全、调拨审批规则等专项测试。

覆盖页面共 19 个状态，见第 6 节证据索引。

## 3. 做得较好的部分

- 页面整体采用统一的查询区、操作区、表格、状态标签和分页结构，学习成本较低。
- 用户编辑中的公司、门店、职级等派生字段使用只读展示并提供说明，减少了直接改错主数据的概率。
- 组织授权页面已经有未保存离开确认，并会保留当前管理员范围之外的授权，避免“看不见即删除”。
- 薪资配置按“方案—档位—员工绑定”分层，主列表可读性良好，关键操作列固定在右侧。
- 调拨审批配置明确提示固定审批链、禁止自审和缺人向上收敛规则，并提供候选人预览，是复杂规则配置中值得保留的设计。
- 公告 HTML 安全、角色/用户数据范围边界和组织上下文已有专项测试基础。

## 4. P0：先修复的高风险问题

### P0-01 角色数据范围异常值会导致权限过滤失效

风险：高。具备 `system:role:edit` 的账户如果提交 `1`～`5` 以外的 `dataScope`，数据库可以保存该值；数据权限切面无法识别时仍把该值加入已处理条件，最终既不追加过滤 SQL，也不执行兜底的 `dept_id = 0`，形成 fail-open。

证据：

- `SysRoleController.dataScope` 使用 `@RequestBody`，没有 `@Validated`。
- `SysRole.dataScope` 没有枚举校验。
- `SysRoleMapper.xml` 对任意非空 `dataScope` 直接写入。
- `DataScopeAspect` 仅处理 1～5，未知值仍执行 `conditions.add(dataScope)`；只有 `conditions` 为空时才拒绝全部数据。
- 当前数据库 12 个有效角色中，2 个为范围 1、10 个为范围 4，当前非法值为 0。也就是说当前数据尚未被污染，但代码边界可被触发。

方案：

- API、Service、Mapper 三层统一枚举校验，只允许 `1`～`5`。
- 数据库增加 `CHECK (data_scope in ('1','2','3','4','5'))` 或等效约束。
- 数据权限切面对 `null`、空值和未知值一律追加拒绝条件并记录安全告警。
- 将数据范围修改从通用 `system:role:edit` 拆成 `system:role:dataScope`。

验收：任何非法或空数据范围请求返回 400；无论脏数据从何处进入，最终查询必须收敛为“无数据”，不能放开全量。

### P0-02 初始密码与密码策略冲突，导入路径绕过校验

风险：高。数据库中的初始密码长度为 6，而后端和前端都要求 8～20 位。手工新增用户会自动带入该初始密码，用户不修改时会与策略冲突；批量导入则直接加密写入初始密码，没有调用密码策略校验。

证据：

- `UserConstants.PASSWORD_MIN_LENGTH = 8`、`PASSWORD_MAX_LENGTH = 20`。
- `SysUserServiceImpl.importUser` 直接读取 `sys.user.initPassword`、加密并插入。
- 用户新增页读取同一参数并预填到表单。
- 当前配置：初始密码长度 6；开启“初始密码修改提醒”，密码有效期为 0 天。提醒不是强制改密。

方案：

- 首选“激活链接/一次性随机密码”，不要为所有新账户设置相同固定密码。
- 手工新增、批量导入、重置密码、接口同步必须调用同一密码策略服务。
- 首次登录必须完成改密后才能进入业务系统；服务端保存首次登录改密状态，不能只做前端提醒。
- 参数列表不再展示密码明文；历史默认密码应立即轮换。

验收：所有创建入口使用同一规则；导入 1000 个用户不能生成相同弱密码；未改初始密码的账户不能进入业务页面。

### P0-03 系统参数读取权限过宽

风险：高。`GET /config/{configId}` 和 `GET /config/configKey/{configKey}` 只要求登录，不要求 `system:config:query`。任何登录账户如果知道或猜到键名，都可能读取任意系统参数。

方案：

- 管理端参数详情必须要求 `system:config:query`。
- 新增独立的“公开运行参数”接口，只允许后端维护的白名单键，不能让前端自行传入任意键。
- 密码、令牌、密钥、黑名单等敏感项不放在通用参数中心；列表和日志统一掩码。
- 为参数查询增加“普通用户不可枚举/不可越权读取”的负向测试。

验收：普通登录账户读取任意非白名单键或 ID 返回 403；公开白名单参数仍能支持登录页和普通业务页面。

### P0-04 操作日志缺少敏感字段脱敏

风险：高。日志切面只排除密码相关字段，手机号、证件号、银行卡号、令牌等请求和响应可能原样进入数据库。当前 339 条操作日志中，26 条请求包含手机号字段名，22 条包含 11 位数字模式，未发现脱敏标记。报告不展示具体号码。

方案：

- 日志采集改为结构化字段白名单，默认不保存完整请求和响应。
- 增加统一敏感字段识别和脱敏：手机号、证件号、银行卡、地址、邮箱、token、cookie、authorization 等。
- 日志详情单独设置 `system:operlog:detail` 权限；复制按钮也受该权限控制。
- 规定保存期限和归档策略，并对历史日志执行一次离线脱敏或受控清理。

验收：新增用户、导入用户、修改资料后，数据库与导出文件均不出现完整手机号或令牌；普通日志查看者看不到详情原文。

### P0-05 “清空日志”可一次性销毁全部审计证据

风险：高。操作日志和登录日志的清空 Mapper 都执行 `TRUNCATE TABLE`；页面使用与单条删除相同的 `remove` 权限，只做一次通用确认。

方案：

- 正常管理页面移除 `TRUNCATE` 清空能力，改为按保留期归档/清理。
- 如业务确实需要清理，使用独立 `clean` 权限、输入确认词、二次审批和不可修改的外部归档。
- 清理操作本身写入独立审计通道，不能与被清理的表位于同一证据边界。

验收：拥有普通删除权限的管理员无法清空全部日志；任何清理都可追溯到申请人、审批人、范围、时间和归档位置。

## 5. P1～P3：体验与治理优化

### P1-01 修正日志时间慢 8 小时

数据库时间和宿主机均为 Asia/Shanghai，但登录日志和操作日志页面显示值恰好慢 8 小时。当前日志实体的 `@JsonFormat` 没有显式时区，运行时序列化结果与预期不一致。

方案：统一使用 `Instant/OffsetDateTime` 加明确时区契约，或至少在日志字段上显式指定 `timezone = "GMT+8"`；前端显示“北京时间”；增加 JSON 序列化回归测试。

验收：同一条记录在数据库、API、页面和导出文件中的时间差不超过 1 秒。

### P1-02 重做用户列表的默认信息密度

用户列表默认显示约 14 个业务列，1280 宽度下出现严重横向滚动，右侧操作不固定；筛选项也一次性全部铺开。工具栏虽然支持列偏好持久化，但用户页没有传 `storageKey`，刷新后会丢失设置；手机号默认显示也不符合最小披露原则。

方案：

- 默认只显示账号、姓名、主部门、门店、岗位、员工状态、账号状态、配置状态和固定操作列。
- 其余字段放入“更多列”；手机号默认隐藏。
- 传入稳定 `storageKey`，按用户保存列、排序、筛选和分页偏好。
- 将低频筛选放入“更多筛选”抽屉，提供“门店人员 / 总部人员 / 待完善资料”等保存视图。

验收：1280 宽度下核心列和操作无需页面级横向滚动；刷新后列配置与保存视图保持不变。

### P1-03 将新增用户改为可完成、可复核的分步配置

当前新增用户弹窗有 5 个页签但只有一个最终提交，归属部门没有前端必填规则，角色和岗位也可能遗漏；隐藏页签的错误不容易被发现。“直属主管”使用自由文本，容易产生同名或拼写错误。初始密码还以固定值预填。

方案：按“账号 → 组织/岗位 → 角色/数据范围 → 资料 → 复核”组织；页签显示完成状态和错误数；提交失败自动跳到第一个错误页签；直属主管改为用户选择器；底部操作区固定；新增完成后给出待办清单。

### P1-04 把角色菜单权限与数据范围放在同一个创建流程

新增角色只配置菜单权限，数据范围要到列表“更多”中二次设置；角色创建后默认数据范围为“本部门及以下”，管理员容易误以为创建已经完成。

方案：新增/复制角色时同时确认菜单权限、数据范围、适用组织和高风险能力；提供权限模板、有效权限预览、差异对比；列表直接展示数据范围和已授权用户数；数据范围修改使用独立权限。

### P1-05 修正解锁操作语义

当前账户解锁使用 GET 请求修改 Redis，选择任意一条登录日志都可点击“解锁”，即使用户并未锁定也会返回成功。

方案：改为 POST/DELETE 动作；先查询实际锁定状态，只对锁定账户启用按钮；返回操作前后状态并记录审计。

### P1-06 让组织授权更容易看懂当前对象和变更影响

现有页面的未保存保护做得好，但 19:5 分栏使右侧用户区过窄，树默认展开较密，选中对象主要依赖行高亮，保存成功提示仍使用“店铺配置”旧称。

方案：分栏可拖拽或把用户列表放入抽屉；顶部固定展示“当前用户”卡片；显示直接授权、继承授权、不可编辑授权数量；保存前展示新增/移除差异；统一名称为“组织数据范围”。

### P2-01 菜单、部门排序增加防误操作和冲突保护

当前支持批量保存排序并在无变更时提示，这是优点；但按钮无法直观看出脏数据数量，也没有撤销、版本校验或并发冲突提示。大树依靠手填数字排序，成本较高。

方案：同级拖拽排序、显示“已修改 N 项”、撤销、离开保护、乐观锁版本；部门树增加路径搜索、按需展开和依赖预览。

### P2-02 参数中心改为类型化配置

当前参数名、键和值在窄列中大量截断，所有值都按普通文本处理，缺少布尔、数字范围、枚举、密码和 JSON 等类型控制。

方案：按安全、账户、界面、业务分组；为每类参数提供专用控件、范围校验、默认值、影响说明、变更差异和回滚；敏感值只允许重置，不允许回显。

### P2-03 薪资配置增加影响预览和版本治理

薪资方案主页健康，分层清楚；但档位明细和员工绑定列很多，仍依赖横向滚动，方案状态/生效日期变化的影响范围不够直观。

方案：固定关键列、提供薪资组成侧栏、显示受影响员工数量、版本号和生效时间线；修改前预览“新增/变更/失效”的员工清单；生效后的方案使用新版本而不是原地覆盖。

### P2-04 调拨审批规则增加冲突与命中解释

候选人预览和审批链说明是强项；不足是 1100px 弹窗在 1280×720 下超出首屏，列表横向滚动明显，优先级是裸数字，管理员难以判断规则之间是否覆盖或冲突。

方案：改为抽屉或分步编辑；底部确认区固定；优先级显示“最高/较高/兜底”等解释；保存前运行规则冲突检查；提供“用一张模拟调拨单测试命中规则”的沙盒，不写业务数据。

### P2-05 空状态、无障碍和快捷操作

- 公告空状态只显示“暂无数据”，应增加“发布第一条公告”及帮助说明。
- 工具栏圆形图标依赖 tooltip，没有 `aria-label`；状态开关也缺少包含行对象名称的可访问标签。
- 小号按钮和浅色文字需要补足键盘焦点、44×44 触达区域和颜色对比。
- 危险操作统一使用动作名称、对象数量和影响范围，不再使用泛化确认文案。

### P3 技术治理

前端仍为 Vue 2.6.12 + Element UI 2.15.14。Vue 2 已进入停止维护状态，建议在 P0/P1 稳定后规划 Vue 3/Element Plus 或兼容迁移，先抽取表格视图、权限按钮、危险确认、配置表单和可访问性基础组件，避免边修边复制。
