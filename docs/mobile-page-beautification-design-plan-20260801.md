# ERP 手机端页面美化设计方案（2026-08-01）

> 依据：[ERP 手机端页面与控件全量台账](./mobile-page-control-inventory-20260801.md)
> 方案形式：仅文字设计方案，不含线框图、视觉稿或页面实现。
> 设计范围：58 个手机业务路由、8 个公共入口/状态页、20 种页面实现、37 个移动 Vue 页面/共享组件。

## 1. 方案结论

本轮建议采用一套“**稳健运营型移动视觉**”：以暖白、浅灰作为页面底色，以现有深茶绿作为唯一品牌主色，蓝色只承担信息提示语义，橙、绿、红分别承担待处理、成功、异常状态。

改造重点不是给 58 个路由分别换皮，而是先统一 20 种页面实现，尤其是承载 38 个路由的通用业务模板。设计顺序应为：

1. 先统一状态语义、页面骨架和设计令牌；
2. 再统一列表、详情、表单、弹层和底部操作栏；
3. 最后处理页面级视觉润色与专属业务差异。

最终应达到以下效果：

- 登录、工作台、个人中心和业务页面不再出现蓝色玻璃态与茶绿色双体系；
- 页面从“卡片堆叠”转为清晰的任务层级，首屏优先显示当前组织、待处理事项和主操作；
- 302 个按钮、137 个字段、36 个弹层和 101 个状态区遵循同一视觉和交互规则；
- 云盘、报销、签约、入职等长流程的主操作固定可见，异常后能明确恢复；
- 58 个业务路由继续保留现有路由、接口、权限、组织限制和业务动作。

## 2. 目标与边界

### 2.1 设计目标

- **统一感**：所有移动页面像同一款产品，而不是不同模块拼接。
- **任务感**：用户进入页面后，能立即看见“当前在哪里、有什么状态、下一步做什么”。
- **效率感**：减少说明卡、装饰卡和重复提示，让搜索、筛选、列表和主操作更早出现。
- **可信感**：会话失效、无权限、未选组织、空数据和网络错误互不混淆。
- **可达性**：单手操作、软键盘、安全区、文字放大、读屏和焦点行为具备统一基线。

### 2.2 本轮不改变

- 不新增或删除业务路由；
- 不改变后端接口、数据映射、审批规则和权限判断；
- 不把 PC 表格功能机械搬到手机端；
- 不在本方案中设计暗色模式；
- 不生成插图、背景图、图标资产或视觉稿；
- 不把导航重构、扫码能力和推送体系强行并入纯视觉改造，可作为后续产品阶段单独立项。

## 3. 现状判断

### 3.1 页面与控件规模

| 对象 | 规模 | 对设计方案的影响 |
|---|---:|---|
| 手机业务路由 | 58 | 用作最终路由验收矩阵 |
| 公共入口/状态页 | 8 | 单独使用安全入口与恢复骨架 |
| 页面实现 | 20 种 | 应作为实际设计对象 |
| 通用业务模板路由 | 38 | 占业务路由约 66%，是最高杠杆改造点 |
| 按钮 | 302 | 必须统一层级、尺寸、禁用和反馈 |
| 输入/选择字段 | 137 | 必须统一标签、校验、键盘与错误定位 |
| 弹窗/抽屉 | 36 | 必须统一宿主、滚动、焦点和底部动作 |
| 状态反馈区域 | 101 | 必须先建立互斥状态模型 |
| 非语义点击节点 | 16 | 纳入 P0 可访问性整改 |

### 3.2 八类真实截图的主要问题

| 页面 | 可见问题 | 美化重点 |
|---|---|---|
| 登录 | 写实背景、玻璃卡片、蓝青渐变按钮与业务端风格割裂；验证码拥挤；弱文字对比不足 | 改为暖中性入口壳，统一深茶绿主按钮，重新分配验证码区域，扩大“记住账号”点击区 |
| 个人中心 | 卡片、按钮、页签层层堆叠；返回方式与其他页不一致；底栏遮挡内容 | 收敛为身份摘要、常用入口、资料设置三段，统一页头与安全区 |
| 店铺工作台 | 组织选择重复；多个告警占满首屏；卡片内继续套卡片 | 未选组织时只显示一个门控状态；已选择后优先显示待办、快捷入口和核心指标 |
| 库存 | 无权限、会话失效和切换组织同时出现，原因与恢复动作冲突 | 先修正状态语义，再压缩介绍区，使用快捷筛选加筛选抽屉 |
| 报销 | “先拍发票”方向正确，但引导卡偏高；草稿与提交不在首屏；刷新图标容易引起丢失数据担忧 | 保留发票优先，压缩引导，显示自动保存状态，固定草稿与提交操作 |
| 云盘 | 会话失效和空文件夹同时出现；空白容器过大；关键文件动作不可见 | 阻断状态互斥；正常空目录提供上传与新建文件夹；工具栏和文件列表连续呈现 |
| 我的签约 | 同一认证错误被拆成两张红色错误卡；重复刷新；页签选中态弱 | 同源错误合并为一个恢复状态；增强页签选中和数量层级 |
| 新建入职 | 步骤只有数字；首步同时出现“下一步”和“创建入职”；底部导航与任务操作叠加 | 步骤增加短标签；仅最后一步显示创建；办理流程隐藏全局底栏并使用任务操作栏 |

### 3.3 现有样式基础与冲突

当前已经存在一套较适合作为主干的移动令牌：`erp-ui/src/views/mobile/styles/mobileSystem.scss`，它由 `erp-ui/src/assets/styles/index.scss` 全局导入，已有暖灰页面、白色表面、深茶绿主色、安全区、动态视口、44/48px 控件、68px 底部导航、弹层、焦点环和减少动效规则。

同时仍存在两份蓝色体系的历史样式：

- `erp-ui/src/assets/styles/mobile-system.scss`：包含蓝色主色、玻璃模糊、背景图片和较重阴影；
- `erp-ui/src/views/styles/mobileSystem.scss`：包含另一套蓝色基础变量和页面间距。

当前未发现上述两份历史样式被正式入口导入，但它们仍可能被误用。组件内部也存在“旧玻璃规则在前、扁平覆盖规则在后”的级联债务：工作台顶栏仍有内联渐变，确认弹窗重新引入茶绿到蓝色渐变，个人中心、库存、人事和云盘各自维护不同宽度、标题、圆角与阴影；`glass-*` 类名虽已被部分扁平化，仍会误导后续维护。

37 个手机 Vue 文件中，共享基础类的实际接入率仍然偏低。实施时应把第一份深茶绿令牌文件确立为唯一来源，先让共享组件真正消费令牌，再对另外两份完成引用审计和退役，避免只增加一层新的覆盖样式。

## 4. 视觉方向：稳健运营型

### 4.1 设计关键词

**清晰、克制、可信、高效、可恢复。**

视觉上避免大面积背景图、重度玻璃模糊、彩色渐变、卡片套卡片和无业务意义的悬浮装饰。页面层级主要依靠字号、对齐、间距、细分隔线和少量底色完成。

### 4.2 色彩规范

| 角色 | 建议值 | 使用规则 |
|---|---|---|
| 页面底色 | `#F4F5F2` | 所有业务页面统一暖灰底 |
| 主表面 | `#FFFFFF` | 页头、面板、列表、弹层 |
| 次表面 | `#F8F8F5` | 分组区、只读区、轻提示背景 |
| 主文字 | `#17211D` | 标题、正文、关键数字 |
| 次文字 | `#66736D` | 说明、元信息；在白底上满足正文对比要求 |
| 弱文字 | `#8A948F` | 仅用于非关键信息和大字号，不用于关键正文 |
| 分隔线 | `#DDE2DE` | 连续列表、面板边界 |
| 强分隔线 | `#CBD3CE` | 输入框、选中前边界 |
| 品牌主色 | `#0B6B53` | 唯一主操作、当前导航、焦点 |
| 品牌深色 | `#075441` | 按下态和高对比强调 |
| 品牌浅色 | `#E7F2ED` | 次按钮、选中底板、轻提示 |
| 信息蓝 | `#2866B1` / `#EDF4FD` | 处理中、同步中、普通信息，不再作为品牌色 |
| 待处理橙 | `#A76505` / `#FFF3DC` | 待审批、待补充、临期、风险提醒 |
| 成功绿 | `#147A50` / `#E8F4ED` | 已完成、已通过、上传成功 |
| 异常红 | `#C4322B` / `#FFF0EE` | 驳回、失败、危险操作、阻断错误 |

规则：状态始终同时包含文字，必要时再加图标；不能只通过颜色区分。品牌主色表达“可以做什么”，状态色表达“现在是什么”。

### 4.3 字体层级

| 层级 | 字号/行高 | 字重 | 用途 |
|---|---|---|---|
| 强调标题 | 28/36 | 700 | 工作台问候、关键结果 |
| 页面标题 | 24/32 | 700 | 顶部主标题 |
| 区块标题 | 17/24 | 700 | 待办、筛选结果、分组标题 |
| 主要正文 | 15/22 | 400–600 | 列表主信息、表单内容 |
| 标签/辅助 | 13/18 | 500–600 | 字段标签、元信息、辅助说明 |
| 小型元信息 | 12/18 | 400–600 | 时间、来源；不得承载关键动作 |
| 关键数字 | 24/30 | 700 | 金额、数量、待办数 |

输入框文字固定为 16px，避免 iOS 聚焦自动放大。字体栈继续使用 `Inter, PingFang SC, Microsoft YaHei, system-ui, sans-serif`。默认字重只使用 400、500、600、700，停止把 800/900 用作常规标题和按钮字重。

### 4.4 间距、圆角与表面

- 使用 4px 基础网格，常用间距为 4、8、12、16、20、24、32；
- 页面左右间距默认 16px，320px 宽屏可收紧到 14px；
- 内容容器最大宽度统一为 480px，居中显示；独立预览器可按内容需要放宽；
- 区块间距 20px，面板内边距 16px，连续列表行上下内边距 12px；
- 控件圆角 12px，面板圆角 16px，小标签圆角 8px；仅状态徽标可使用全圆角；
- 普通面板依靠 1px 边框区分，不使用常驻大阴影；
- 阴影仅用于底部抽屉、模态弹层和确有层级需要的浮层；
- 页面内不允许卡片继续嵌套卡片，最多保持“页面—面板—连续行”三级结构。

### 4.5 图标与动效

- 统一使用现有图标库的一套线性图标，不混用 emoji、字符图标和不同描边粗细；
- 常规图标 20–24px，图标按钮触控区至少 44×44px；
- 图标按钮必须有可读名称；首次出现的专业动作优先使用“图标 + 文字”；
- 页面反馈动效控制在 120–240ms，以透明度、颜色和轻微位移为主；
- 移动端不设计依赖 hover 的反馈，不使用明显缩放或弹跳；
- 遵循 `prefers-reduced-motion`，关闭非必要动效。

## 5. 全局页面骨架

全站只保留六类页面骨架，所有路由按业务差异填充内容，不再各自设计页头、状态区和底栏。

### 5.1 安全入口骨架

适用：登录、注册、强制改密、资料补全、选择店铺/仓库、401、404、锁屏。

- 顶部只保留系统标识、页面标题和必要说明；取消表单背后的全屏写实背景与玻璃穿透；
- 表单采用单列结构，字段标签常驻，错误紧跟字段；
- 主按钮全宽 48px 高，辅助入口位于按钮下方；
- 验证码输入与图片按约 2:1 分配，图片可点刷新并提供可读标签；
- 会话或提交失败后保留非敏感字段，密码按安全策略处理；
- 401、404、锁屏只显示一个主要恢复动作，不同时给出互相矛盾的返回入口。

### 5.2 工作台骨架

适用：店铺、仓库、进销存、人事工作台及“我的”。

页面顺序固定为：

1. 页头：标题、当前组织、通知/刷新；
2. 阻断状态或单条局部告警；
3. 今日待办/优先处理；
4. 高频入口，首屏最多 4 个，总数最多 8 个；
5. 关键指标或最近处理；
6. 全局底部导航。

未选择组织时，页面只显示一个“选择组织后继续”的门控状态，不再同时展示空待办、不可确认和多个解释卡。部分数据源失败时，保留成功内容，只在相关区块顶部显示可展开的局部告警。

### 5.3 业务列表骨架

适用：38 个通用业务模板路由及员工、客户、合同等列表页。

- 页头：返回/标题、当前组织、刷新或单一新建动作；
- 页面说明压缩为标题下的一行辅助文字，不再使用大面积 Hero 卡；
- 第一行使用搜索，第二行使用 3–5 个高频状态筛选和“更多筛选”；
- 完整筛选进入底部抽屉，底部固定“重置”和“查看结果 N”；
- 列表使用一个连续面板，业务对象以行或轻卡片呈现，不模拟 PC 横向表格；
- 每行最多呈现：主对象、单号/人员、一个关键数值、状态、两行元信息和进入详情提示；
- 返回列表后恢复搜索条件、筛选、分页和滚动位置；
- 有创建权限时，主操作放在页头或安全区上方的固定操作栏，不再把多个“快捷处理”卡放在列表之后。

### 5.4 详情与办理骨架

- 顶部显示业务对象、单号、当前状态和组织；
- 仅在有风险时展示风险条；
- 正文按“摘要—明细—附件—流程轨迹”分组；
- 简单查看使用底部抽屉，复杂编辑、行项目和文档办理使用全屏页；
- 页面底部固定一个主操作，次操作最多两个，危险操作收进“更多”；
- 按钮使用业务动词，如“确认收货”“提交报销”，不使用泛化的“确定”；
- 提交中禁用重复点击，服务端未确认前不预先显示最终成功；
- 数据被他人更新时，显示冲突提示、禁用旧动作并保留用户尚未提交的文字。

### 5.5 分步表单骨架

- 顶部显示“第 1/4 步 + 当前步骤名 + 细进度条”，不只显示无文字的圆点；
- 每步只展示一个主题，字段按逻辑分组；
- 底部任务操作栏固定显示“上一步”和“下一步”，仅最后一步出现最终提交；
- 进入办理/编辑流程后隐藏全局底部导航，避免双底栏；
- 字段校验失败时先显示错误摘要，再滚动并聚焦首个错误字段；
- 显示自动保存/草稿状态，离开、切后台、会话变化时明确说明是否已保存；
- 软键盘打开后，当前字段、错误文字和主操作仍可达。

### 5.6 文件与文档骨架

适用：云盘、合同预览、签约阅读与发票预览。

- 工具区固定展示当前位置、搜索/页码和必要操作；
- 文件列表、预览主体和操作栏各自只有一个滚动责任；
- 上传任务显示逐文件进度、成功、失败和单文件重试；
- 预览失败不丢失列表位置，可返回继续处理；
- 阅读确认、签署、拒签、验收等动作位于安全区上方的任务操作栏；
- 文件状态在列表、详情、预览和操作抽屉中使用同一文案与颜色。

## 6. 共享组件规范

| 组件 | 设计责任 | 现有基础/建议 |
|---|---|---|
| `MobilePageShell` | 动态视口、安全区、单一滚动区、页头与底栏关系 | 由现有 `.mobile-system-page`、`.mobile-system-scroll` 收敛 |
| `MobileTopbar` | 返回、标题、组织、刷新/单一主动作 | 替换各页面自定义页头和内联渐变 |
| `MobileContextSwitcher` | 显示当前店铺/仓库/组织及切换入口 | 工作台、列表、详情、提交确认保持一致 |
| `MobileFilterBar/Drawer` | 快捷筛选、完整筛选、结果数与重置 | 取代多排筛选按钮和页面内散落字段 |
| `MobileBusinessRow` | 移动列表对象、状态、关键数据和元信息 | 通用模板优先接入 |
| `MobileStatusChip` | 草稿、待处理、处理中、完成、驳回、异常 | 统一颜色、文字和图标规则 |
| `MobileDataState` | 加载、空、无结果、会话、权限、组织、网络、局部失败 | 合并 101 个重复状态区域 |
| `MobileDetailSheet` | 摘要、明细、附件、轨迹、底部动作 | 保留现有组件，收敛视觉与滚动规则 |
| `MobileFormSheet` | 字段、校验、草稿、键盘避让和提交 | 保留现有组件，统一字段密度与错误行为 |
| `MobileActionDialog` | 短业务动作与确认 | 每次只处理一个清晰动作 |
| `MobileLineItemsEditor` | 商品/费用明细增删改 | 长明细使用独立滚动体，固定合计与提交 |
| `MobileEntityPicker` | 人员、组织、商品、客户/供应商选择 | 搜索常驻，结果独立滚动，关闭后恢复焦点 |
| `MobileBottomActionBar` | 一个主操作、最多两个次操作、安全区 | 办理页隐藏全局底栏后使用 |
| `MobileUploadQueue` | 拍照、文件、识别与逐项重试 | 报销、健康证、云盘和入职资料复用 |
| `MobileTimeline` | 审批、签署、流转和操作记录 | 时间、处理人、结果和意见顺序一致 |

现有 `feature/components/mobileSheet.scss` 已具备遮罩、单一内部滚动区、固定底部操作、键盘与安全区适配，可提升为全局共享的 Sheet/Form 基础，避免多个 SFC 重复 scoped 引入。实施期间可保留 `glass-card` 等旧类名作为兼容别名，但其视觉效果应先变为不透明表面；待页面迁移完成后再统一重命名。

## 7. 页面家族美化方案

**注册、强制改密、资料补全**

### 7.2 工作台与“我的”（5 路由）

- 当前组织只出现一次，并固定在页头可见；
- 待办优先于统计卡，首屏最多展示 3 个高优先任务和 4 个快捷入口；
- 多来源失败收敛为一条局部告警，不用多个错误卡挤压业务内容；
- 指标使用连续面板和分隔线，减少浮卡和阴影；
- “我的”按身份摘要、个人事项、常用服务、账户与安全分组，退出登录放在页面底部危险区。

### 7.3 通用业务模板（38 路由）

通用模板应成为全站视觉母版，统一 `feature/index.vue` 及其详情、表单、动作、确认、行项目和实体选择组件。

**列表首页**

- 删除大面积功能介绍卡，把说明压缩到标题下方；
- 搜索和高频状态筛选前置，列表在首屏尽早出现；
- 列表从独立浮卡改为一个连续面板，状态位固定在右上/右侧；

- 资料类页面突出名称、编码、启停状态；单据类页面突出单号、组织、数量/金额、等待时长；日志类页面突出时间、对象、结果和来源。

**详情与表单**

- 详情按摘要、明细、附件、轨迹分组；
- 长单号、名称和备注允许换行，不出现横向滚动；
- 表单底部主操作固定，草稿型业务统一编辑、提交、删除语义；
- 删除、强制退出、重置等危险动作使用独立确认，不与主操作并排强调；
- 系统管理页面采用移动目录和只读摘要，不缩放 PC 表格；复杂授权或高风险编辑可提示转 PC 处理。

### 7.4 待办、采购审批与通知

- 状态分段器显示待审批、待执行、退回、风险等核心分类；

- 通知卡显示业务类型、标题、摘要、时间、未读状态和可访问深链；无权限时不泄露业务内容。

### 7.5 费用报销

- 保留“先拍发票，自动生成报销内容”的任务方向，但把说明压缩为紧凑启动区；

### 7.6 企业云盘

- 页头显示空间名称和返回，空间选择器压缩为一行；

- 文件夹和文件使用紧凑列表行，主信息包含名称、类型/大小、更新时间和验收状态；

- 待验收、已验收、退回、审核人和验收记录贯穿列表、详情、预览与操作记录。

### 7.7 人事、入职与资料完整度

**入职列表与详情**

- 卡片突出员工、岗位/组织、预计入职日、资料完整度和当前责任人；
- 详情顶部显示生命周期状态，下面依次为人员摘要、资料缺失、任职信息、合同/社保资料和办理轨迹；

**入职四步表单**

- 步骤名称固定为短标签，例如基础、任职、资料、确认；

- 办理流程隐藏全局“我的”底栏，避免双操作区。

- 合同列表统一状态、到期时间、预览和下载入口；

### 7.9 客户服务卡与资产报修

- 客户卡片突出客户名称、车辆/服务对象、最近服务时间和状态；记录与照片作为详情分组，不在列表堆叠；
- 快速新建客户继续复用弹层，但字段和错误行为与通用表单一致；
- 资产报修使用服务单状态时间线，突出报修对象、故障摘要、处理人、预计时间和确认动作。

### 7.10 系统管理与监控（14 路由）

- 不适合手机完成的复杂编辑给出明确的 PC 处理说明，而不是展示不可用按钮。

## 8. 状态与反馈体系

### 8.1 页面级状态优先级

阻断状态必须互斥，优先级为：

1. 会话失效；
2. 无权限；
3. 未选择或组织不匹配；
4. 页面级网络/服务错误；
5. 加载中；
6. 查询无结果或真正空数据；
7. 正常内容。

局部数据源失败可以和已成功内容共存，但只能出现在对应区块，不能升级为多个全页错误卡。

### 8.2 状态文案与恢复动作

| 状态 | 标题方向 | 唯一主要动作 |
|---|---|---|
| 加载中 | 正在加载业务内容 | 无；使用与内容结构一致的骨架 |
| 真正空数据 | 还没有相关记录 | 有权限时新建或返回 |
| 查询无结果 | 没有符合当前条件的记录 | 清除筛选 |
| 会话失效 | 登录状态已过期 | 重新登录 |
| 无权限 | 你没有查看此内容的权限 | 返回有效入口/联系管理员 |
| 未选组织 | 选择店铺或仓库后继续 | 选择组织 |
| 组织不匹配 | 请切换到适用组织后继续 | 切换组织 |
| 网络失败 | 暂时无法加载数据 | 重试，并显示上次更新时间 |
| 局部失败 | 部分数据暂不可用，其他结果已显示 | 仅重试失败来源 |
| 功能关闭 | 该功能当前未开放 | 查看说明或返回 |
| 数据已变化 | 该任务已被他人处理 | 加载最新状态 |
| 提交失败 | 本次提交未完成，已保留填写内容 | 重试或返回修改 |

### 8.3 业务状态统一

- 草稿、停用、关闭：中性灰；
- 待审批、待补充、临期、待确认：橙色；
- 处理中、识别中、同步中、进行中：信息蓝；
- 已完成、已通过、已付款、已验收：成功绿；
- 驳回、失败、异常、退回：异常红；
- 每个状态都使用统一词汇，不在不同模块混用“正常/成功/已完成”等近义词表达同一阶段。

## 9. 导航、底栏与安全区

- 一级页面可显示全局底部导航；详情、编辑、审批、签署、预览和分步表单进入后隐藏全局底栏；
- 任务型页面改用 `MobileBottomActionBar`，高度包含底部安全区；
- 本轮保持现有路由和导航逻辑，不强制改变一级入口数量；共享底栏组件应支持后续 2–5 个入口调整；
- 顶部栏高度至少 56px 并叠加顶部安全区，底部导航基准高度 68px 并叠加底部安全区；
- 页面滚动区底部内边距必须包含底栏、键盘遮挡和至少 16px 呼吸空间；
- Android 返回顺序为：关闭当前弹层、返回详情、返回保留状态的列表、再处理退出。

## 10. 技术落地边界

### 10.1 单一设计令牌来源

- 以 `erp-ui/src/views/mobile/styles/mobileSystem.scss` 为唯一移动令牌源；

### 10.2 共享实现优先

建议按以下顺序落地：

1. 设计令牌、状态模型、页头、底栏和操作栏；

6. 其余公共状态页与全量视觉回归。

### 10.3 迁移规则

- 先建立兼容样式，再逐页迁移，不一次性重写业务逻辑；
- 每迁移一个共享组件，立即验证其所有消费页面；
- 保留权限、路由竞态、数据映射、草稿恢复和幂等提交逻辑；

- 继续使用现有 Vue 2、SCSS 和 Element UI，不为页面美化引入第二套 UI 框架；
- 内联样式和局部硬编码逐步替换为令牌；
- 删除遗留样式前必须确认没有独立入口、原生壳或延迟加载页面引用。

## 14. 设计评审时需要确认的三项决策

1. 确认“暖白 + 深茶绿”的稳健运营型视觉为唯一方向，蓝色不再承担品牌主色；
2. 确认通用业务模板和状态组件优先于逐页装饰性美化；
3. 确认办理/编辑流程隐藏全局底栏，并使用固定任务操作栏。

这三项确认后，即可按 P0 → P1 → P2 → P3 顺序进入实施，不需要再为每个路由重新定义一套视觉规则。
