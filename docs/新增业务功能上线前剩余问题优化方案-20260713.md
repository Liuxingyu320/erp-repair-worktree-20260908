# 新增业务功能上线前剩余问题优化方案

> 方案日期：2026-07-13  
> 方案状态：阶段 0～7 代码实施完成，本机回归与静态发布门禁通过；待真实 MySQL、生产数据准备、部署和角色验收  
> 当前基线：[新增业务功能优化实施结果](./新增业务功能优化实施结果-20260713.md)  
> 本方案范围：针对健康证、我的团队、OE 上报与补货、门店返仓、调拨差异、客户服务卡及受控附件做上线前加固，不扩展为整个 ERP 的全面重构。

## 1. 项目核对后的结论

下表保留为本方案实施前的项目基线。其中发布契约、动态开关、多仓一致性、权限/主数据检查、运行监控、移动闭环和结构优化已完成代码实施；真实 MySQL 5.7/8.0、生产数据完整度和真实角色仍必须在发布环境验收，因此仍不适合直接无灰度全量上线。

本次项目核对发现：

| 优先级 | 当前事实 | 风险 |
|---|---|---|
| P0 | 8 份新增迁移中，只有健康证脚本在 `docker/mysql/db/` 有字节一致镜像，另外 7 份缺失 | 发布包和根目录 SQL 不一致，新环境可能缺表、字段或权限 |
| P0 | 7 个 `feature.*.enabled` 已写入 SQL，但代码没有读取它们 | 管理员以为关闭了功能，实际上接口仍可新建业务 |
| P0 | 主 Docker 环境为 MySQL 5.7，`docker-compose.ecs-host.yml` 使用 MySQL 8.0 | 只验证一个版本不能代表当前两个部署入口 |
| P0 | 4 个 Testcontainers 事务测试需要 Docker，1 个健康证原生 MySQL 测试需要环境变量；当前机器未完成这些测试 | 额度锁、唯一当前证件、迁移重复执行和事务回滚仍缺真实数据库证据 |
| P0 | OE 需求支持多仓分批调拨，但 `markOutOfStock` 和 `close` 仍修改需求全局状态及单一 `sourceWarehouseDeptId` | 仓库 B 可能覆盖仓库 A 已建立的处理关系，造成错误缺货或关闭状态 |
| P0 | 8 份脚本没有统一迁移清单或全局迁移锁，菜单 ID 使用 `MAX(menu_id)+1` | 并行或重复发布时存在菜单 ID 竞争和脚本顺序漂移风险 |
| P1 | 客户服务卡权限迁移依赖固定角色键及历史菜单权限 | 自定义门店角色、新增岗位或直属主管可能没有获得预期能力 |
| P1 | 移动端客户卡可以新增、编辑、看照片和历史，但没有“追加服务记录”动作 | 一线员工移动服务场景仍需回到桌面端 |
| P1 | 客户服务卡变更日志已写库，但没有受控查询接口和管理端查看入口 | 出现争议时只能由技术人员直接查库 |
| P1 | OE 发件箱只有死信查看，业务链路没有低基数指标和积压告警 | `PENDING/RETRY` 长时间积压可能不能及时发现 |
| P2 | Vue 生产构建成功，但入口约 1.68 MiB，完整引入 Element UI | 首屏仍有体积告警，移动网络体验可继续优化 |
| P2 | `InvTransferServiceImpl`、移动端通用 feature 页面继续扩大 | 后续修改调拨或移动功能时回归范围过大 |

## 2. 可选优化路径

### 路径 A：最小上线

只复制 SQL、人工执行迁移并做一次手工验收。

- 优点：最快，约 2～3 人日。
- 缺点：功能开关仍不可信，多仓状态和真实数据库事务风险未解决，出现问题后缺乏监控和安全回滚入口。
- 结论：不建议用于正式全量发布。

### 路径 B：生产加固后灰度上线

先完成 P0，再完成必要 P1，保留当前业务架构，不引入新的数据库迁移框架或工作流平台。

- 优点：复用现有 `sys_config`、`RemoteConfigService`、调拨、统一待办、Actuator 和云盘能力；改动集中，能在当前技术栈内闭环。
- 缺点：需要补充数据库环境和真实角色验收，约 9～13 人日。
- 结论：推荐采用。

### 路径 C：平台化重构

统一 Flyway/Liquibase、建设独立功能开关服务、统一权限模板、拆分调拨领域服务并升级前端组件体系。

- 优点：长期治理能力最好。
- 缺点：至少 18～25 人日，变更面明显超过本次业务上线范围，反而提高当前发布风险。
- 结论：只选择其中的迁移规范、权限模板和服务拆分作为 P2 演进，不阻塞本次上线。

## 3. 推荐架构决策

### 3.1 功能开关复用现有系统参数能力

项目已经存在：

- `ISysConfigService` 和 Redis 参数缓存；
- `/config/inner/configKey/{configKey}` 内部接口；
- `RemoteConfigService` 及 OA、库存模块的现有使用方式；
- 云盘 `drive.enabled` 的菜单、权限和登录能力返回范例。

因此本次不再建立第二套开关中心，推荐继续使用现有 7 个 `sys_config` 键：

- `feature.hr.health-certificate.enabled`
- `feature.hr.team.enabled`
- `feature.oa.oe-replenishment.enabled`
- `feature.inventory.oe-replenishment.enabled`
- `feature.inventory.store-return.enabled`
- `feature.inventory.transfer-discrepancy.enabled`
- `feature.inventory.customer-service-card.enabled`

开关规则必须统一：

1. 迁移默认值从 `true` 改为 `false`，完成数据库、服务和数据准备后再通过系统参数接口启用。
2. system 模块直接读取 `ISysConfigService`；OA 和 inventory 通过 `RemoteConfigService` 读取。
3. 新建入口读取失败时按关闭处理，返回稳定错误码 `FEATURE_DISABLED` 或 `FEATURE_CONFIG_UNAVAILABLE`，不能猜测中文错误。
4. 开关只阻止新业务进入，不能阻止已经存在的审核、发件箱投递、调拨发货、收货、差异处理和客户历史读取。
5. OA 发件箱分发器和库存内部幂等接收接口不得因关闭入口而停止，否则会把在途业务留死。
6. 管理员修改开关必须通过系统配置服务，使 Redis 缓存同步更新；服务运行期间不直接执行 SQL 修改开关。
7. 登录信息返回 `businessFeatures` 能力映射；桌面动态菜单、移动固定路由和直接 URL 访问同时校验，后端仍是最终边界。

典型关闭行为：

| 功能 | 关闭后禁止 | 关闭后仍允许 |
|---|---|---|
| 健康证 | 新草稿、新提交 | 查看历史、审核已提交记录、附件鉴权 |
| 我的团队 | 团队入口和查询 | 原人事模块按原权限使用 |
| OA OE 补货 | 新 OE 上报及预检成功 | 已写入发件箱继续分发 |
| 库存 OE 补货 | 新人工处理入口可隐藏 | 内部接收在途事件、已建调拨继续闭环 |
| 门店返仓 | 新建 `store_return` | 已提交返仓继续审批、发货和收货 |
| 调拨差异 | 新单只允许全量正常收货 | 已产生差异必须继续处理 |
| 客户服务卡 | 新建和编辑入口 | 管理员按权限只读查询既有资料和审计 |

### 3.2 数据库迁移继续使用项目现有双份脚本约定

本次上线前不临时引入 Flyway。约定调整为：

- `sql/` 是唯一编辑源；
- `docker/mysql/db/` 是字节一致的发布镜像；
- `docker/mysql/seed/` 只保留新环境基础快照，不承担已有数据库升级；
- 已有数据库一律通过显式的一次性迁移命令升级，不能依赖 MySQL 初始化目录；
- 一个版本使用一份有序迁移清单，禁止人工临时调整执行顺序；
- 迁移运行器先获取版本级 MySQL 命名锁，再顺序执行，避免 `MAX(menu_id)+1` 并发竞争；
- DDL 存在隐式提交，发布前必须备份并逐脚本记录结果，不能宣称 8 份脚本整体事务回滚。

推荐执行顺序调整为先补基础调拨能力、再接跨服务生产者：

1. `erp_hr_health_certificate_20260713.sql`
2. `erp_hr_team_permission_20260713.sql`
3. `erp_inventory_oe_purchase_reference_20260713.sql`
4. `erp_inventory_store_return_20260713.sql`
5. `erp_inventory_transfer_discrepancy_20260713.sql`
6. `erp_inventory_oe_replenishment_20260713.sql`
7. `erp_oa_fixed_asset_replenishment_outbox_20260713.sql`
8. `erp_inventory_customer_service_card_20260713.sql`

所有代码必须在 8 份迁移全部完成后启动，不能在第 6 或第 7 步之间启动 OA 服务。

### 3.3 测试分为快速回归和强制发布门禁

当前 Testcontainers 用例混在默认测试生命周期中，导致无 Docker 的本地开发无法完成全量测试，但真正发布又不能简单跳过。

推荐拆分：

- 默认 `mvn test`：执行不依赖容器的快速单元、Mapper 和契约测试；
- `new-business-mysql-it` 发布 Profile：通过 Failsafe 执行 `*IT`，Docker 或指定测试库不可用时必须失败；
- 迁移脚本同时在 MySQL 5.7 和 MySQL 8.0 执行两次；
- 业务事务测试以 MySQL 5.7 为权威，MySQL 8.0 用于保证 ECS 当前环境兼容；
- 测试数据库必须是可丢弃环境，禁止使用业务库。

这样不会用“跳过测试”换取绿色结果，也不会让普通代码回归被本机 Docker 状态长期阻塞。

### 阶段 2：修复 OE 多仓状态边界（P0，1～2 人日）

#### 当前问题

`InvOeReplenishmentServiceImpl` 的 `createTransfer` 已通过需求行锁、版本号和已关联数量支持多次调拨；但 `markOutOfStock` 可由任意有权仓库把整张需求改为 `OUT_OF_STOCK`，`close` 又依赖单一来源仓字段，与多仓模型不完全一致。

#### 优化规则

1. `createTransfer`、`markOutOfStock` 和 `close` 均先 `selectByIdForUpdate`，再校验版本。
2. 已存在非终态关联调拨、实发量、实收量或未结差异时，禁止把需求改成全局缺货或关闭。
3. `sourceWarehouseDeptId` 只作为最近/首次处理展示字段，不再作为多仓授权权威；权威关系读取 `inv_oe_replenishment_transfer`。
4. 仓库缺货首版记录为“当前仓处理结果”；只有没有任何有效调拨时才能改变需求全局状态。
5. 关闭从普通 `handle` 权限拆成 `inv:oeReplenishment:close`，只授予仓库负责人和管理员，并强制填写原因。
6. 需求状态由关联调拨实发、实收和差异状态重新汇总，不能由页面直接指定完成。
7. 后续如需完整记录多个仓库的缺货尝试，再增加 `inv_oe_replenishment_warehouse_action`，不在 P0 强行扩表。

#### 修改范围

- `erp-modules/erp-inventory/src/main/java/com/erp/inventory/service/impl/InvOeReplenishmentServiceImpl.java`
- `erp-modules/erp-inventory/src/main/resources/mapper/inventory/InvOeReplenishmentDemandMapper.xml`
- `erp-modules/erp-inventory/src/main/resources/mapper/inventory/InvOeReplenishmentTransferMapper.xml`
- `sql/erp_inventory_oe_replenishment_20260713.sql`
- `erp-ui/src/views/inventory/oeReplenishment/index.vue`
- `erp-ui/src/views/mobile/inventory/oeReplenishment/index.vue`
- `erp-modules/erp-inventory/src/test/java/com/erp/inventory/service/impl/InvOeReplenishmentServiceImplTest.java`

#### 验收门槛

- 仓库 A 创建调拨后，仓库 B 不能把需求误改为全局缺货或关闭；
- A、B 两仓可在剩余数量内分别创建调拨，总计划量不超需求；
- 两个仓并发操作只有满足版本和剩余数量的事务成功；
- 任何关联调拨存在未结差异时需求不能完成或关闭；
- 状态汇总与调拨实际实发、实收完全一致。

新增或扩展：

- OA：额度行锁并发、超额零副作用、维修单/流水/发件箱同事务、发件箱唯一和领取恢复；
- inventory：8 份迁移依赖、事件幂等、多仓计划量、返仓方向、短收/拒收/残损和客户跨店 SQL；

目标命令：


#### 必须通过的故障场景

- 库存服务停机后 OA 发件箱进入重试，恢复后只创建一个需求；
- 远端永久 4xx 进入死信，429/超时继续退避；
- `SENDING` 超时记录可被下一轮安全接管；
- 两个并发 OE 上报不能同时超额成功；
- 两个健康证审核不能产生两条当前证件；
- 客户 ID、健康证 ID、差异 ID 的跨门店/跨范围直查全部拒绝；
- 每份迁移在 5.7 和 8.0 连续执行两次后数据一致。

### 阶段 4：权限、基础数据和角色验收（P0/P1，1～2 人日）

#### 权限准备

新增只读脚本 `scripts/new-business-permission-readiness.sql`，输出：

- 当前门店在职员工中缺少客户卡查看、新增、编辑或服务记录权限的人员；
- 当前直属主管中缺少 `hr:team:direct` 的人员；
- 店长中缺少 `hr:team:store` 或健康证提醒权限的人员；
- 仓库人员中缺少 OE 补货、调拨发货、返仓收货或差异处理权限的人员；
- 意外拥有客户归档、OE 关闭或死信重投高风险权限的普通角色。

短期以审计结果补齐现有角色；P1 再建立通用业务能力模板，在角色新增/修改和入职岗位配置变更时自动同步，避免继续维护固定角色键名单。

#### OE 数据准备

- `inventory.oe.purchase-reference.allowed-hosts` 配置可信域名；
- 所有启用固定资产 OE 必须有编码、名称、图片、规格/说明和购买参考；
- 链接必须为 HTTPS 且指向具体同款页面；
- 完整度查询结果不为 0 时，不启用 OA OE 新上报开关。

#### 真实角色矩阵

至少准备：员工 A/B、店长 A/B、人事、直属主管、仓库 A/B、管理员。

必须验证：

- 店长 A 只能看到门店 A 员工，手机号完整，响应不含工资、银行卡和完整证件号码；
- 门店 A 员工不能读取或修改门店 B 客户卡；
- 员工只能提交本人健康证；
- 仓库只能以当前已授权仓库处理 OE 需求和返仓收货；
- 只知道 `nodeId` 不能绕过健康证或客户卡业务权限读取附件；
- 管理员切换门店后仍必须显式带当前门店上下文，不能混合返回所有客户。

- 客户卡跨店拒绝、乐观锁冲突和旧客户接口调用量。

每日只读对账：

```text
额度内成功 OE 上报数
  = SENT 发件箱数
  + 可解释的 PENDING/RETRY/SENDING/DEAD 数

每个补货需求计划量
  >= 关联调拨计划量
  >= 实发量
  >= 实收量

返仓实发量
  = 实收合格量 + 差异待处理量 + 已完成处理量
```

对账异常只告警和生成管理员待办，不自动改库存或客户数据。

## 6. 回滚原则

- 首先关闭“新建入口”，不是停止在途处理器；
- OA 发件箱继续分发，库存继续处理已接收需求和已创建调拨；
- 门店返仓只隐藏新建，已提交单继续审批、发货、收货和差异闭环；
- 健康证不再接收新提交，但已提交记录继续审核；
- 客户服务卡关闭编辑后保留资料和日志，不回写或删除旧客户、历史销售单；
- 数据库首版只增不删，应用回滚不执行破坏性逆迁移；
- 如果对账不平，停止扩大灰度并人工定位，不用脚本自动补库存。
