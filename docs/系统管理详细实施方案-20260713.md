# 系统管理详细实施方案

> 编制日期：2026-07-13  
> 依据文档：`docs/系统管理功能检查与优化方案-20260713.md`  
> 方案状态：R0～R5 已完成首轮实现与自动化验收；尚未提交、部署生产  
> 实施约束：不使用虚拟机、Docker、Testcontainers；仅使用本机 JDK、Node.js、MySQL、Redis 和隔离测试库

## 1. 结论与推荐执行方式

本项目的系统管理功能不是简单的页面美化问题，当前最需要先解决的是权限边界、凭据生命周期和审计数据治理。推荐按“安全止血 → 账号闭环 → 审计治理 → 高频体验 → 配置防错”的顺序分 5 个发布批次实施，总投入约 31～40 人日。若配置 1 名后端、1 名前端、1 名兼职测试，预计 6～7 周；若 2 名后端和 1 名前端并行，预计 4～5 周。

必须先完成的 P0 工作：

1. 数据范围遇到非法值时由当前可能放行改为拒绝访问，并在角色写入入口做三层校验。
2. 停止把初始密码配置下发到浏览器；导入、创建、重置统一进入一次性凭据流程。
3. 配置查询接口从“登录即可读”收紧为明确权限；内部服务调用保持 `@InnerAuth`。
4. 操作日志默认脱敏，列表不再返回请求参数和响应正文。
5. 下线两类日志的 `TRUNCATE` 清空入口，改为受控归档与分批清理。
6. 修复审计时间少 8 小时和使用 GET 解锁账号的问题。

本次不建议顺手做 Vue 3、微服务拆分、全库字段重命名或薪资引擎重写。这些变化风险大且与当前目标没有直接依赖，应另立专项。

## 2. 项目基线与实施前提

### 2.1 技术基线

| 项目 | 当前情况 | 实施要求 |
|---|---|---|
| 后端 | Java 17，Spring Boot 4.0.3，Spring Cloud 2025.1.0；本机 Maven 3.9.14 当前实际运行在 Java 25.0.2 | 编译、单测、发布都先设置 `JAVA_HOME` 并确认 Maven 实际切到 JDK 17，不能把 Java 25 下的结果作为发布依据 |
| 前端 | Vue 2、Vue CLI 4 | 使用 `.nvmrc` 指定的 Node 22；`package.json` 要求 `>=22 <25`，不得用当前本机 Node 25 作为发布验证结果 |
| 数据库 | 本机审计环境为 MySQL 8.0.45 | 新增 SQL 保持项目现有 MySQL 5.7 兼容要求，不使用 8.0 专属排序规则、窗口函数、真正依赖 CHECK 约束等能力 |
| 缓存 | Redis | 账号锁定、会话凭据状态验证需覆盖 Redis 正常和不可用场景 |
| 迁移 | `sql/` 与 `docker/mysql/db/` 双份脚本 | 两份脚本内容必须一致；虽然目录名含 docker，本方案不启动容器，只保持项目发布包结构兼容 |
| 工作区 | 已存在大量其他功能的未提交修改 | 系统管理实施必须按工作包隔离提交，禁止覆盖或格式化无关文件 |

### 2.2 已确认的数据现状

| 数据项 | 当前值 | 对方案的影响 |
|---|---:|---|
| 活跃角色 | 12 | 角色权限迁移可逐个核对，不允许把新增高危权限自动发给所有角色 |
| 活跃用户 | 155 | 账号迁移必须支持在线用户和灰度发布 |
| 活跃且 `pwd_update_date IS NULL` 的用户 | 152 | 不能把 `pwd_update_date IS NULL` 直接解释为“首次登录必须改密”，否则几乎所有用户会被锁住 |
| `sys_oper_log` 记录 | 339 | 可在上线前完成敏感字段扫描；存量日志不自动改写，先封住新增泄漏 |
| `sys_logininfor` 记录 | 1415 | 清理方案必须保留可验证的归档清单，不能再无痕清空 |
| `sys.user.initPassword` 长度 | 6 | 与后端 8～20 位规则冲突，需在 P0 中修正并在应用启动/使用时校验 |

### 2.3 现有能力应复用

- `HrOnboardingConfirmationService` 已有 `SecureRandom` 一次性密码生成逻辑，应抽取为公共凭据服务，不再写第二套弱随机实现。
- `RightToolbar` 已支持 `storageKey`，用户列表列偏好可以直接复用。
- 菜单、部门排序页面已有“仅提交变化项”的思路，应保留并补充标准 DTO、撤销和离开提醒。
- 调拨规则已有 `/transfer/rule/preview`、候选人预览及校验 DTO/VO，应扩展现有模型，不建立平行规则引擎。
- 项目已有系统管理前端回归测试和后端服务测试，应在其上增量扩充。

## 3. 范围与非目标

### 3.1 本期范围

- 用户、角色、部门、岗位、菜单、参数配置。
- 操作日志、登录日志、账号锁定与解锁。
- 门店/组织授权页面的易用性。
- 薪资方案配置的影响预览。
- 调拨审批规则的冲突检查与模拟。
- 以上功能涉及的权限、接口、数据库迁移、前端交互、测试和上线观测。

### 3.2 本期非目标

- 不升级 Vue 3，不替换 Element UI，不进行全站视觉重构。
- 不改变现有组织数据权限的业务含义，只修复非法值放行和操作体验。
- 不重做薪资计算引擎，不改变历史工资结果。
- 不将日志接入新的外部 SIEM 或数据仓库；本期先实现可归档、可校验、可追踪。
- 不引入虚拟机、容器或新的基础设施依赖。

## 4. 实施原则

1. **权限失败即关闭**：未知数据范围、缺少作用域、校验异常都不能退化成全量访问。
2. **密码状态显式建模**：使用 `must_change_password` 表示强制改密，`pwd_update_date` 只记录时间，不再承担状态推断。
3. **敏感数据最少返回**：列表只返回展示所需字段；密码和日志正文只在明确场景、明确权限下短暂出现。
4. **高危操作可确认、可审计、可回滚**：解锁、清理、批量授权和薪资配置变更必须展示影响范围。
5. **迁移幂等且兼容 MySQL 5.7**：先做数据预检，再增量迁移；权限菜单使用稳定权限字符串，不在方案阶段猜测菜单 ID。
6. **前端渐进拆分**：先从 1000 行以上页面抽出对话框和筛选器，不在安全修复阶段更换框架。
7. **小批次发布**：每个发布批次都有独立开关、回滚条件和验收记录，不能把所有变化一次上线。

## 6. R0：实施基线、数据预检与发布护栏

### 6.1 任务

1. 固定发布工具链：JDK 17、Node 22、项目当前 Maven；在构建日志打印实际 Java/Node 版本。
2. 建立独立本机测试库，例如 `erp_system_mgmt_test`，从结构备份初始化，不连接生产写库。
3. 导出以下只读预检结果并由负责人签字：
   - 非法或空 `sys_role.data_scope`；
   - 角色到菜单权限的现有映射；
   - `pwd_update_date` 为空的用户量；
   - 初始密码配置是否满足当前策略；
   - 操作日志中手机号、身份证、银行卡、令牌等命中量；
   - 两类日志表的行数、最早/最晚时间和占用空间。
4. 新建实施脚本时同步维护：
   - `sql/erp_system_management_hardening_20260713.sql`（新增）；
   - 该迁移仅保留在 `sql/`，不得进入自动 Docker 初始化目录；
   - `sql/erp_system_management_hardening_rollback_20260713.sql`（新增，仅处理可逆结构和权限变更）。
5. 所有工作包独立提交，禁止批量格式化仓库；每次提交前检查 `git diff --name-only`，只包含本工作包文件。

### 6.2 验收

- 本机基线测试可重复执行，测试库可重复初始化。
- 两份正向 SQL 校验和一致，脚本重复执行不会产生重复权限或重复数据。
- 回滚脚本明确区分“可回滚结构”和“不可恢复的业务数据变化”；不允许把删除数据伪装成可回滚。

## 7. R1：权限边界与配置读取收口

### 7.1 数据范围 fail-close

#### 后端修改

1. 在 `erp-common/erp-common-core/src/main/java/com/erp/common/core/constant/Constants.java` 增加数据范围合法值集合或 `isValidDataScope` 方法，只接受 `1`～`5`。
2. 在 `erp-api/erp-api-system/src/main/java/com/erp/system/api/domain/SysRole.java` 对 `dataScope` 增加枚举校验；新增/编辑 DTO 若后续拆分，也必须复用同一校验器。
3. 在 `SysRoleController` 的新增、编辑、`PUT /role/dataScope` 入口启用参数校验。
4. 在 `SysRoleServiceImpl.insertRole`、`updateRole`、`authDataScope` 再做一次服务层校验，防止内部调用绕过 Controller。
5. 修改 `DataScopeAspect`：
   - 非法、空值或无法识别的数据范围必须追加永假条件，例如 `<deptAlias>.<deptField> = 0`；
   - 记录角色 ID、用户 ID 和非法值，但不记录个人隐私字段；
   - 多角色场景中只要存在合法范围，按合法范围求并集；非法角色本身不得扩大范围；
   - 管理员豁免逻辑保持当前语义，并为豁免单独测试。
6. `SysRoleMapper.xml` 继续只负责持久化，不依赖数据库 CHECK 作为唯一防线；MySQL 5.7 下 CHECK 不能作为可靠约束。

#### 权限拆分

- 将 `PUT /role/dataScope` 从 `system:role:edit` 拆为 `system:role:dataScope`。
- SQL 按权限字符串查找父菜单和已有记录，再分配经评审的未占用 `menu_id`；实施时先查 `MAX(menu_id)` 和目标权限是否存在，不在方案中硬编码未知 ID。
- 只给当前确实负责组织权限的角色授权；不得把新权限复制给所有拥有角色编辑权限的角色。

#### 测试

- 扩充 `DataScopeAspectTest`：覆盖 `null`、空字符串、`0`、`6`、混合合法/非法角色、管理员、禁用角色。
- 扩充 `SysRoleControllerDataScopeTest`：覆盖参数校验、无权限、定制部门为空、越权部门 ID。
- 新增 `SysRoleServiceImpl` 数据范围测试：证明内部调用也无法写入非法值。
- 集成验证：普通角色查询用户、部门和业务数据时，非法范围返回 0 条或明确错误，绝不能返回全量。

### 7.2 配置读取边界

1. 将 `GET /config/{configId}` 与 `GET /config/configKey/{configKey}` 从 `@RequiresLogin` 调整为 `@RequiresPermissions("system:config:query")`。
2. 保留 `GET /config/inner/configKey/{configKey}` 的 `@InnerAuth`，不影响服务间读取。
3. 删除用户页面读取 `sys.user.initPassword` 的调用，不再需要面向普通登录用户的公共配置读取接口。
4. 修改 `SysControllerAuthBoundaryTest`，明确断言两个外部读取接口必须有查询权限、内部接口必须有内部鉴权。
5. 配置详情响应对敏感配置只返回 `configured=true/false`，不返回原值；在 R5 类型化之前，先由代码中的敏感键注册表控制。

### 7.3 R1 上线门槛

- 人工构造非法 `data_scope` 后，所有受数据范围保护的查询均不能看到额外数据。
- 无 `system:config:query` 的已登录用户访问配置 ID 和配置键均返回 403。
- 内部 Feign 配置读取仍正常。
- 新权限只出现在经评审角色中，迁移前后角色权限差异清单可核对。

### 7.4 回滚

- 应用代码可回滚至上一版本，但不回滚已修正的非法 `data_scope` 数据。
- 新权限菜单可停用，不立即物理删除，避免角色关联残留。
- 若前端尚未同步，配置读取收口不会影响用户页，因为 R1 同时删除该调用。

## 8. R2：账号与凭据生命周期闭环

### 8.1 先处理兼容风险

在完整流程上线前，先完成以下 P0 止血：

1. 将 `sys.user.initPassword` 修改为满足 8～20 位及项目复杂度要求的值。
2. `SysUserServiceImpl.importUser` 在开启事务、写入任何用户前验证配置密码；不合法则整批拒绝，不允许导入一半。
3. 用户新增页面取消初始密码明文预填和配置键读取。
4. 导入、重置、创建接口的操作日志禁止保存密码请求与密码响应。

### 8.2 数据模型

在 `sys_user` 新增：

```sql
must_change_password char(1) NOT NULL DEFAULT '0' COMMENT '是否必须修改密码（0否 1是）'
```

迁移规则：

- 所有存量用户统一回填 `0`，包括 152 个 `pwd_update_date IS NULL` 的活跃用户，避免发布后被误锁。
- 新建、管理员重置、导入和入职确认产生的一次性凭据设置为 `1`。
- 用户本人成功修改密码后设置为 `0`，并同步更新 `pwd_update_date`。
- `pwd_update_date` 继续用于密码年龄和审计，不再推断首次登录状态。
- 新字段使用项目兼容字符集/排序规则，不使用本机 MySQL 8 的 `utf8mb4_0900_ai_ci`。

涉及文件：

- `erp-api/erp-api-system/src/main/java/com/erp/system/api/domain/SysUser.java`
- `erp-modules/erp-system/src/main/resources/mapper/system/SysUserMapper.xml`
- `erp-modules/erp-system/src/main/java/com/erp/system/service/impl/SysUserServiceImpl.java`
- `erp-modules/erp-system/src/main/java/com/erp/system/controller/SysProfileController.java`

### 8.3 公共凭据服务

新增 `TemporaryPasswordGenerator` 和 `UserCredentialProvisioningService`（建议放在 `erp-system` 的 `service/credential` 包）：

- 从 `HrOnboardingConfirmationService` 抽取现有 `SecureRandom` 生成逻辑。
- 默认生成 16 位，至少包含大小写字母、数字和当前策略要求的特殊字符。
- 生成后仍调用统一密码策略校验；策略改变时，生成器测试必须立即失败而不是生成弱密码。
- 明文只存在于当前方法返回对象中，不写数据库、不进缓存、不进日志、不进入异常消息。
- 数据库只保存加密结果。
- 创建、导入、重置和入职确认都调用同一服务。

### 8.4 首次登录强制改密

1. 在 `erp-common-security` 新增语义明确的豁免注解，例如 `@AllowPasswordChangeRequired`。
2. 在 `PreAuthorizeAspect` 或统一安全拦截层读取登录用户的 `mustChangePassword` 状态；状态为 `1` 时仅允许：
   - `GET /user/getInfo`；
   - 用户本人修改密码接口；
   - 登出和必要的会话续期。
3. 不使用 URL 字符串散落判断；所有豁免点必须通过注解和单测可枚举。
4. 用户修改密码成功后，在同一事务更新字段，并同步刷新令牌缓存中的用户对象。
5. 前端登录成功后优先判断 `mustChangePassword`，直接进入改密页；该流程不得依赖先选择门店。

### 8.5 创建、重置与导入交互

#### 单个创建和重置

- 默认使用“系统生成一次性密码”；允许有权限的管理员选择“手工设置”，手工密码仍需满足同一策略。
- 成功响应使用专门结果 DTO，只返回一次临时密码；对话框明确提示复制后即不再显示。
- 响应设置 `Cache-Control: no-store`，接口 `@Log(isSaveResponseData = false)`。
- 管理员遗失临时密码时只能重新执行重置，服务端不能找回原密码。

#### 批量导入

分两步实施：

1. R2 首次发布保留兼容导入，但导入前验证共享临时密码并强制所有导入用户改密。
2. 随后切换为每个账号生成不同的一次性密码，并将“用户名 + 临时密码”作为本次请求的一次性结果文件流返回给导入管理员：
   - 不把明文写入数据库、Redis、磁盘临时文件或操作日志；
   - 响应禁止缓存，下载后前端不保留副本；
   - 请求重试不能重放旧密码；管理员丢失文件后只能批量重置；
   - 导入结果同时包含成功、失败原因，但失败行不生成账号和密码；
   - 超大批次设置明确上限，建议每批 500 人。

### 8.6 前端修改

- `erp-ui/src/views/system/user/index.vue`：移除 `getConfigKey('sys.user.initPassword')` 和默认密码预填。
- `erp-ui/src/api/system/user.js`：适配一次性凭据响应、强制改密状态和导入结果流。
- `erp-ui/src/views/system/user/profile/resetPwd.vue`：支持强制改密模式，隐藏取消入口并说明原因。
- `erp-ui/src/permission.js` 或当前路由守卫：强制改密状态下只开放改密路由。
- 创建/重置成功对话框增加复制状态、关闭前确认和“不会再次显示”提示。

### 8.7 测试与验收

- 密码生成器 10,000 次属性测试：长度、字符集、策略符合、无空值；不以“绝对不重复”作为错误承诺，但应验证没有明显固定输出。
- 存量迁移后 155 个活跃用户不被强制改密。
- 新建、重置、导入、入职四条路径均设置 `must_change_password=1`。
- 用户本人改密后字段为 `0`、更新时间非空、缓存中的状态立即一致。
- 强制改密用户访问业务接口返回明确错误，仍可查看本人信息、改密和退出。
- 日志与网络响应检查中，除本次一次性结果外不能出现密码明文；该结果响应也不能被操作日志持久化。
- 前端补充/扩充 `authSecurityHardening.test.js`、`passwordResetShopSelection.test.js` 和用户管理测试。

### 8.8 回滚

- `must_change_password` 字段至少保留一个版本，不在应用回滚时立即删除；旧版本会忽略该字段。
- 通过配置开关 `sys.security.mustChangePassword.enabled` 控制拦截器，默认在迁移与应用同时完成后开启。
- 回滚只关闭新拦截，不把已重置的新密码恢复成旧密码。

## 9. R3：日志、时间与账号操作治理

### 9.1 统一日志脱敏

在 `erp-common/erp-common-log` 新增 `SensitiveLogSanitizer`：

- 对 Map、Java Bean、JSON、集合递归处理，设置最大深度、集合长度和字符串长度。
- 键名标准化后匹配：`password`、`oldPassword`、`newPassword`、`phone`、`phonenumber`、`mobile`、`idNumber`、`bankAccount`、`token`、`authorization`、`cookie`、`secret`、`accessToken`、`refreshToken` 等。
- 密码、令牌、Cookie、密钥直接删除或固定替换；手机号、证件号、银行卡按保留首尾规则掩码。
- 脱敏发生在 Fastjson2 序列化前；序列化失败只写摘要，不回退到未脱敏原对象。
- `LogAspect` 的 `excludeParamNames` 继续生效，但作为接口级补充，不是唯一防线。
- 默认不保存完整响应；只有确认无敏感信息的接口才显式开启。

测试至少覆盖嵌套对象、数组、大小写变化、别名键、超长字符串、循环引用、文件上传和异常对象。

### 9.2 操作日志列表/详情分离

1. 修改 `SysOperLogMapper.xml` 列表查询，只返回时间、模块、业务类型、操作人、状态、耗时、地址等摘要，不返回 `oper_param`、`json_result`、完整异常正文。
2. 新增 `GET /operlog/{operId}`，权限为 `system:operlog:detail`；详情仍经过展示层脱敏。
3. 默认导出也不包含请求和响应正文。若未来确需敏感导出，另设独立权限和审批，不复用普通导出权限。
4. `erp-ui/src/views/system/operlog/detail.vue` 点击详情时再请求数据；没有详情权限时不展示复制按钮。
5. 详情查看本身写入审计记录，防止“审计人员查看敏感审计”成为盲区。

### 9.3 清理与保留策略

#### 立即措施

- 下线 `DELETE /operlog/clean` 与 `DELETE /logininfor/clean` 的页面入口。
- 停止调用 Mapper 中的 `TRUNCATE`；接口可先返回“功能已停用”，一轮兼容期后再删除。
- 单条/批量删除继续受原权限控制，但默认不授予普通管理员。

#### 正式保留机制

新增 `sys_audit_archive_batch`（名称可在数据库评审时确认），记录：批次 ID、日志类型、截止时间、条数、校验和、归档位置、申请人、审批人、状态、开始/完成时间和失败原因。

清理流程：

1. 生成待归档范围和数量预览。
2. 导出归档文件并计算校验和。
3. 复核归档文件可读且行数一致。
4. 以小批次 `DELETE ... WHERE id IN (...)` 清理，每批建议 1,000～5,000 行，避免长事务。
5. 写入完成记录；失败可从最后成功主键继续。

配置 `sys.audit.retention.enabled` 初始为 `false`；生产确认归档位置、保留期限和责任人后再开启调度。若没有可靠归档存储，本期只停用清空，不自动删历史记录。

### 9.4 时区修复

1. 在应用配置中明确 `spring.jackson.time-zone: Asia/Shanghai`。
2. 对 `SysOperLog.operTime`、`SysLogininfor.accessTime` 增加明确时区序列化配置，避免依赖系统默认时区。
3. 检查 `ApplicationConfig` 当前配置的是 legacy Jackson 还是 Spring Boot 4 实际使用的 HTTP `ObjectMapper`；以注入到 MVC 的真实对象为测试对象。
4. 测试数据库时间、接口 JSON、Excel 导出和页面显示四处一致；不要在前端再人工加 8 小时。

### 9.5 解锁接口语义

- 新增 `GET /logininfor/lock-state?userName=...`，只读返回是否锁定、剩余时长和可否解锁。
- 将写操作改为 `POST /logininfor/{userName}/unlock`，保留 `system:logininfor:unlock`，增加 `@IdempotentSubmit`。
- 校验目标用户存在且当前管理员有权管理该用户；返回解锁前后状态。
- 旧 `GET /unlock/{userName}` 保留一个版本但不在前端使用，记录弃用告警，下一版本删除。
- 前端只有在真实锁定时启用“解锁”，成功后刷新状态，不再把“接口调用成功”误当作“原本已锁定”。

### 9.6 R3 验收

- 使用包含手机号、身份证、银行卡、令牌和密码的测试请求，数据库操作日志中不出现完整值。
- 无详情权限用户从列表、详情、导出均无法获得请求/响应正文。
- 清空按钮不可见，直接调用旧接口也不会执行 `TRUNCATE`。
- 同一条日志的数据库、API、Excel、浏览器显示时间一致，误差仅允许格式精度差异。
- 解锁写操作只接受 POST；重复请求结果稳定且有审计记录。

## 13. 数据库迁移设计

### 13.1 正向脚本顺序

1. 预检：非法数据范围、重复权限字符串、目标字段是否存在、目标菜单 ID 是否占用。
2. 新增 `sys_user.must_change_password`，仅在字段不存在时执行。
3. 明确回填全部存量用户为 `0`。
4. 新增 `system:role:dataScope`、`system:operlog:detail` 等权限菜单，使用幂等插入。
5. 修正 `sys.user.initPassword` 为合规值；真实密码通过发布密钥管理流程注入，脚本库中不提交生产明文。
6. 可选新增 `sys_audit_archive_batch`；若归档位置尚未确定，只建表、不开调度。
7. R5 再增加配置元数据字段、`sys_salary_scheme.version` 和 `sys_salary_scheme_revision`，避免与 P0 迁移绑在同一批。
8. 薪资版本迁移先把存量方案版本回填为 `1`，再为每个现有方案生成一条基线修订；条数和方案数必须一致后才能开启乐观锁。
9. 执行后校验字段、默认值、权限映射、用户数量、角色数量及薪资基线修订数量。

### 13.2 SQL 约束

- 兼容 MySQL 5.7，使用 `utf8mb4_general_ci` 或项目基线排序规则。
- 不把 CHECK 当作数据范围合法性的唯一保障；主要依靠应用校验和 fail-close。
- 不在数据库脚本中生成或保存生产密码明文。
- 每段迁移输出可核对结果；失败立即停止，不继续执行后续 DML。
- 正向脚本在 `sql/` 和 `docker/mysql/db/` 保持字节级一致。

### 13.3 回滚边界

- 新增列、表和菜单可以在确认没有新版本数据依赖后回滚；默认采用“停用而不删除”。
- 已生成、已修改的密码不可恢复为旧密码。
- 已脱敏的新日志不补回原文。
- 已归档后删除的日志只能从经校验归档恢复，不能靠回滚 SQL 凭空恢复。

## 16. 发布、观测与回滚策略

### 16.1 发布顺序

1. 备份目标表结构与权限映射，生成预检报告。
2. 部署向后兼容的数据库增量字段和权限菜单。
3. 发布后端，但敏感新流程先由配置开关关闭。
4. 发布前端，确认不再读取初始密码、使用新解锁和日志详情接口。
5. 小范围管理员账号开启新流程，观察 1 个工作日。
6. 开启全量强制改密拦截和日志列表瘦身。
7. 清理/归档调度必须最后单独开启，且需人工审批。

### 16.2 需要监控的指标

- 非法数据范围被拒绝次数及涉及角色。
- 配置接口 403 数量及调用来源。
- 新建/导入/重置账号数量、首次改密成功率和失败原因。
- 日志脱敏命中量、序列化失败量、详情查看量。
- 解锁请求量、真实锁定命中率和重复请求量。
- 用户创建表单完成率、平均耗时、首个错误步骤分布。
- 薪资预览与保存影响人数不一致次数。
- 调拨规则阻断/警告数量。

任何监控日志本身也必须经过脱敏。

### 16.3 自动停止/回滚条件

- 普通用户出现任何全量数据越权：立即回滚应用并停用相关角色。
- 存量用户被大面积误判强制改密：关闭 `sys.security.mustChangePassword.enabled`，保留字段和新密码。
- 日志写入失败率或接口 P95 延迟明显上升：关闭响应正文采集，保留请求摘要脱敏。
- 归档数量、校验和或恢复抽查不一致：停止删除任务，不继续下一批。
- 前端新用户流程完成率显著下降：切回旧表单入口，但保留后端安全校验。

## 17. 验收矩阵

| 验收域 | 必须达到的结果 | 证据 |
|---|---|---|
| 数据权限 | 非法范围永不放大访问，写入口全部拒绝非法值 | 单测、集成测试、测试库故障注入截图/日志 |
| 配置安全 | 普通登录用户不能读任意配置，敏感值不回显 | 权限矩阵和接口测试 |
| 密码闭环 | 四条账号路径统一一次性凭据；存量用户不误锁 | 数据迁移核对、端到端录像/截图、日志扫描 |
| 日志隐私 | 新增操作日志无完整密码、令牌、手机号、证件和银行卡 | 自动化脱敏测试及数据库抽样 |
| 日志保留 | 无 TRUNCATE；归档后才允许分批清理 | 接口/SQL 审查、归档批次记录 |
| 时间一致 | DB、API、Excel、页面均为 Asia/Shanghai | 同一记录四处对照 |
| 账号解锁 | GET 只读、POST 修改、重复请求幂等 | 接口测试和审计记录 |
| 用户体验 | 创建成功率 100%，中位耗时下降 30% | 任务测试记录 |
| 角色配置 | 创建时完成数据范围，默认仅本人 | 前后端测试和数据库关系核对 |
| 配置防错 | 类型、范围和敏感属性在后端统一校验 | 单测及表单校验记录 |
| 薪资/规则 | 保存前可见影响和冲突，预览与执行一致 | 服务测试与业务验收 |
| 构建 | JDK 17 全量测试、Node 22 测试及生产构建通过 | CI/本机构建日志 |

## 18. 人员分工与评审节点

建议角色：

- 后端负责人：数据权限、账号凭据、日志治理、数据库迁移。
- 前端负责人：用户/角色/日志/配置交互和路由守卫。
- 测试负责人：权限矩阵、迁移验证、端到端与回归。
- 系统业务负责人：确认角色权限、日志保留期限、薪资影响口径和调拨规则语义。
- 发布负责人：脚本执行、配置开关、监控与回滚。

必须评审的四个检查点：

1. R0 结束：确认数据现状、权限映射和迁移脚本。
2. R1 结束：用非法数据范围做红队式验证后才能进入凭据改造。
3. R2/R3 上线前：确认一次性密码不会进入日志，确认不存在 TRUNCATE 路径。
4. R4/R5 上线前：用真实业务角色完成任务测试，确认体验提升没有削弱权限。

## 19. 完成定义

一个工作包只有同时满足以下条件才能标记完成：

- 代码、SQL、接口文档、权限菜单和前端在同一工作包中闭环。
- 目标模块测试和全量回归通过，工具链版本记录正确。
- 正向迁移重复执行无副作用，回滚边界经过演练。
- 新增权限已由业务负责人逐角色确认。
- 日志和网络响应完成敏感信息扫描。
- 关键行为有监控，异常时有明确开关或回滚方案。
- 方案对应的验收证据已归档，且未触碰工作区无关修改。

完成以上 5 个发布批次后，系统管理会从“功能基本齐全但边界和流程不够稳”提升为：权限默认安全、账号生命周期闭环、日志可治理、高频操作更清晰、配置变更有预览和防错能力。此时再评估 Vue 3 升级或更大范围的设计系统改造，风险和返工都会明显更低。
