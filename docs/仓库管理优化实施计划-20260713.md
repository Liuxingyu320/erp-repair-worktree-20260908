# 仓库管理优化实施计划

> 计划日期：2026-07-13
> 状态：阶段 0～2 已实施；阶段 3 已完成架构门和安全迁移资料，尚未切换生产权威读写
> 依据：[仓库管理功能检查与优化方案](./仓库管理功能检查与优化方案-20260713.md)
> 约束：不使用虚拟机、Docker、Testcontainers；数据库集成测试使用本机独立 MySQL 测试库，不接触业务库。

## 1. 目标

按“先安全、再正确、后提效、最后扩展”的顺序，把当前仓库模块从可运行的仓库进销存提升为：

1. 审批不能被状态字段绕过。
2. 收货、质检、退货、盘点的状态和数量一致。
3. 桌面端和移动端关键作业少输入、不遮挡、不误导。
4. 库存可以按批次、效期、库位和序列号追溯。
5. 报表使用可解释、可下钻、可对账的经营口径。
6. 每次上线都有数据预检、自动化验证、灰度和回滚方案。

## 2. 实施边界

### 本计划包含

- 调拨审批与发货完整性。
- 采购收货、行级质检、采购退货。
- 移动端采购业务阶段和统一待办。
- 盘点术语、范围、盲盘、复盘和移动作业。
- 批次、效期、库位、序列号和库存明细余额。
- 库存报表口径、下钻与性能。
- 历史异常数据核对、修复和日常对账。
- 桌面端、移动端易用性与基础无障碍改进。

### 本计划暂不包含

- 自动化立体库、输送线、电子秤、打印机等硬件集成。
- 供应链预测、自动采购和复杂补货算法。
- 多币种成本核算和完整财务总账改造。
- 与第三方物流平台的正式承运接口。

这些能力可以在批次和作业任务模型稳定后另立项目。

## 3. 实施原则

1. **P0 单独发布**：审批发货阻断不等待其他功能完成。
2. **后端先守住边界**：页面隐藏动作不能替代接口校验。
3. **迁移先加后减**：先增加新表/字段和双轨核对，不在同一版本删除旧结构。
4. **所有修复脚本先 dry-run**：先输出数量和样本，评审后才允许写入。
5. **库存写入单入口**：收货、发货、退货、盘点、调整最终走同一个库存变动服务，避免各模块各自改余额。
6. **每阶段可回滚**：功能开关、兼容接口、幂等 SQL、数据快照和对账结果必须齐全。
7. **不污染现有改动**：仓库优化只修改明确列出的库存相关文件，不覆盖仓库中 OA、合同、云盘等现有工作。

## 6. 阶段 1：业务正确性和高频易用性

- `draft`：草稿；
- `pending_receive`：待收货；

## 7. 阶段 2：收货批次与行级质检

### 2.1 先建立明确的数据对象

本阶段不直接改造全部库存余额，先把收货和质检事实记录正确：

- 收货批次主表：采购单、仓库、供应商批次、到货时间、状态。
- 收货批次明细：采购明细、收货数量、待检数量、已检数量。
- 质检记录：收货批次明细、抽检量、合格量、不合格量、让步量、缺陷、结论、人员和时间。
- 质检附件：图片/文件、上传人和关联质检记录。

表名和字段在开发前形成一页数据模型评审文档，确认后再写迁移；不先在现有聚合库存行上堆临时字段。

### 2.2 API 兼容策略

1. 保留当前收货和质检 URL，逐步把 `Map<String,String>` 替换为有校验的 DTO。
2. 旧客户端只传整单结果时，在兼容期明确映射到一个收货批次；新客户端传批次和行级结果。
3. 兼容期至少一个正式版本，服务端记录旧调用来源；旧客户端使用量归零后再移除兼容逻辑。

**现有主要修改点**

- `InvReceiveRequest.java`
- `InvReceiveItem.java`
- 计划新增行级质检 DTO。
- `InvInboundRecord.java`
- `InvPurchaseController.java`
- `InvPurchaseServiceImpl.java`
- 入库记录 Mapper 及 XML。
- `erp-ui/src/views/inventory/purchase/index.vue`
- 移动采购详情和质检页面。

### 2.3 质检交互

1. 默认不选择质检结果。
2. 每行展示收货量、已检量、本次检验量、合格/不合格/让步量。
3. 数量必须满足：本次检验量 = 合格 + 不合格 + 让步。
4. 拒收和让步必须选择原因；让步接收根据权限决定是否需要额外审批。
5. 支持照片、附件、缺陷等级和备注。
6. 移动端不提供无明细确认的“一键质检通过”。

**阶段 2 验收**

- 同一采购单两次收货可分别质检，结果互不覆盖。
- 同一批次多行可分别合格、拒收和让步。
- 质检结果数量与待检数量严格对平。
- 拒收只回退对应批次和明细，不影响历史已合格库存。
- 旧客户端在兼容期仍可工作并有调用审计。

## 8. 阶段 3：批次、库位、序列号与仓库作业

### 3.1 架构决策门

开发前新增并评审：

- `docs/architecture/warehouse-lot-location-design.md`（计划新增）

推荐采用渐进式两层模型：

1. 新增“批次/库位明细余额”作为追溯事实。
2. 现有 `inv_stock` 暂时保留为仓库级汇总，供旧页面和报表兼容使用。
3. 所有库存写入通过统一变动服务，在同一事务内更新明细余额、汇总余额和不可变流水。
4. 每日校验 `明细余额合计 = inv_stock 汇总余额`。
5. 稳定至少一个版本后，再决定是否废弃 `inv_stock` 上的批次/库位附加字段；本阶段不删除旧列。

这样可以降低一次性改写采购、销售、调拨、退货、盘点全部代码的风险。

### 3.2 计划新增的数据能力

- 仓库库区/库位主数据。
- 库存批次：供应批次、生产日期、到期日期、质检状态。
- 批次/库位库存余额。
- 序列号状态和所在库位。
- 库存流水关联批次、库位、序列号和作业任务。
- 上架、移库、拣货、复核和发货作业任务。

### 3.3 迁移策略

1. 只读预检现有 200 条库存和全部流水。
2. 新表、索引和外键采用增量迁移，不删除旧唯一键。
3. 为旧库存生成“历史批次”和“未分配库位”，保证数量不丢失。
4. 开启双写但旧读，连续对账无差异后切换新读。
5. 先在主仓库灰度，其他仓库仍走旧汇总模式。
6. 主仓库稳定后逐仓启用；每个仓库启用前输出库存对账签字单。
7. 最后才调整旧唯一键和旧字段，不与首次切换同版本执行。

**计划新增 SQL**

- `sql/erp_inventory_lot_location_schema_20260713.sql`
- `sql/erp_inventory_lot_location_backfill_20260713.sql`
- `sql/erp_inventory_lot_location_reconcile_20260713.sql`
- `sql/erp_inventory_lot_location_rollback_20260713.sql`

### 3.4 作业体验

1. 收货后生成待上架任务，扫码确认批次和库位。
2. 出库按 FEFO 或指定策略分配批次，扫码拣货和复核。
3. 调拨发货记录来源批次/库位，目标仓收货后重新上架。
4. 采购退货必须选择原入库批次和出库库位。
5. 盘点按库位、批次、序列号生成任务，支持盲盘和复盘。
6. 移动端支持草稿自动保存、重复扫码提示和网络恢复续传。

**阶段 3 验收**

- 同一商品同一仓库可存在两个批次、两个效期和两个库位。
- FEFO 能优先分配最近到期且质检合格的库存。
- 任一出库可追溯采购来源、质检结果、批次和库位。
- 明细余额、汇总余额和流水三者持续对平。
- 关闭新模式后旧汇总页面仍可读，不影响紧急作业。

## 9. 阶段 4：报表、性能和持续治理

### 4.1 正式毛利

1. 毛利口径改为“已确认销售净收入 - 对应出库成本”。
2. 处理销售退货、取消、折扣和成本冲销。
3. 报表展示口径版本、数据截止时间和币种。
4. 指标可下钻到销售单、出库流水和成本批次。
5. 用固定样本逐笔对平，不以页面数字看起来合理作为验收。

### 4.2 性能

1. 减少库存报表多个标量子查询的重复扫描。
2. 建立日结事实或预聚合表，长时间范围报表走异步任务。
3. 对库存列表、待办、移动工作台和报表建立 P95 基线。
4. 使用本机生成的脱敏测试数据验证 10 万库存余额、100 万流水；不使用虚拟机。

### 4.3 数据治理

## 11. 发布、灰度和回滚

### 每次发布前

1. 生成业务库只读预检报告。
2. 备份受影响表并记录行数、校验值和备份位置。
3. 自动化、真实 MySQL 集成和视觉验收全部通过。
4. SQL 在本机同版本 MySQL 完成 dry-run。
5. 确认回滚应用版本、反向配置和数据恢复步骤。

### 灰度顺序

1. 管理员测试账号。
2. 主仓库单一班次。
3. 主仓库全部班次。
4. 其他仓库逐个启用。

### 回滚原则

- P0 审批硬校验不允许因使用不便而回滚为可绕过状态，只能修复真实审批数据。
- 数据库迁移首版只新增，不立即删列删表。
- 批次/库位模式通过配置切回旧汇总读取时，双写和对账仍保留，防止新数据丢失。
- 发生余额差异立即停止新模式写入，保存现场，使用流水重算；禁止直接手改余额掩盖问题。
