# 待办功能复检与二期优化方案（2026-07-13）

## 结论

当前待办主链路已经可用，上一轮修复的精确跳转、组织同步、页面缓存保护、异常态重试和汇总范围参数在本轮复检中均通过。现阶段没有发现会立即写错业务数据的已确认 P0 缺陷，但仍有 4 类应优先处理的 P1 问题：审批入口防误触不足、移动端统计无法与总数对账、组织范围语义不够直观、无障碍标签/焦点/对比度不达标。

建议先完成“详情先行 + 明确动作”的审批改造，再处理统计和范围语义；这些改动对使用者的安全感和理解成本提升最大。

## 范围与约束

- 覆盖首页入口、顶部待办、桌面待办中心、移动待办中心、组织切换、来源/分类/关键词筛选、分页、精确跳转、服务部分不可用和恢复。
- 使用本机原生前后端进程与内置浏览器完成检查；未使用虚拟机、Docker 或其他虚拟化环境。
- 只打开详情和确认层，没有点击任何最终“确定/通过/驳回”，未写入业务数据。
- 结合真实页面、可访问性树、代码和自动化测试判断；没有把一次性、不可稳定复现的浏览器状态当作已确认产品缺陷。

## 问题与优化方案

### P1-01 审批入口应先看详情，再选择动作

**现象**

- 桌面从待办进入调拨审批后，直接打开“调拨审批”框，并默认选中“通过”；框内只有单号、决定和意见，用户看不到调出/调入组织、商品、数量、金额、备注和审批链。
- 移动端先打开完整详情，随后立即自动打开“审批通过”动作层；动作层覆盖详情，用户还没有完成核对就进入确认阶段。
- 代码依据：`erp-ui/src/views/inventory/transfer/index.vue` 的待办动作直接调用 `openTransferApproval`；`erp-ui/src/views/mobile/feature/index.vue` 的 `handleLoadedTodoFocus` 在打开详情后继续调用 `handleDetailAction`。

**用户影响**

虽然仍需点击最终确定才会写入，但默认“通过”与缺少决策依据会放大习惯性确认和误批风险，移动端尤为明显。

**方案**

1. 待办精确跳转只打开目标详情，不自动进入任何会写数据的动作层。
2. 在详情内固定展示决策摘要：单号、调出/调入组织、商品种数、总数量、参考金额（按权限）、申请人、提交时间、备注、当前审批节点和风险提示。
3. 用户在详情内显式点击“通过”或“驳回”后再打开对应动作层；动作层标题、按钮和确认文案必须与所选动作一致。
4. 驳回继续强制填写原因；通过意见是否必填沿用现有业务规则，不在入口阶段预填决定。
5. 对审批、删除、发货、收货等写操作增加 `detailFirst/requiresReview` 元数据，只对明确安全的查看类动作允许直接执行。

**验收**

- 从桌面和移动待办点击审批事项后，第一屏只出现目标详情。
- 在用户显式选择动作前，页面不存在已选中的通过/驳回决定，也不显示最终确认按钮。
- 确认层至少重复展示单号、组织、数量和动作影响；取消后仍停留在详情。

### P1-02 移动端统计必须与总数对得上

**现象**

实测总数为 48，卡片只显示审批 18、执行 26、风险 0，三项合计 44；切换“退回修改”后可看到缺失的 4 条。当前模板只渲染审批、执行、风险。

**用户影响**

使用者会怀疑总数或分类统计错误，也无法从摘要快速发现退回事项。

**方案**

- 将移动摘要改为 2×3 的可点击统计网格：总数、审批、执行、退回、风险、个人；每个数字使用同一批提供方、同一组织范围和同一健康状态。
- 点击统计直接切换分类，并同步 URL；未知来源时数字继续使用 `?` 或 `n+`，不显示虚假精确值。
- 分类按钮也显示数量，作为统计与列表之间的第二层校验。

**验收**

- 六个分类的和与总数一致；存在未知提供方时，摘要和列表都明确为不完整。
- 320、360、390、430、480px 宽度下无裁切，统计项可用键盘和屏幕阅读器识别。

### P1-03 “当前组织”需要把跨组织审批说清楚

**现象**

在 Test Store 的“当前组织”范围下，列表会出现北京柏悦等其他组织的本人审批。页面底部虽有说明，但范围控件、列表标题和顶部徽标仍只呈现“当前组织/我的待办”，用户很难在扫描时理解口径。

**用户影响**

容易误以为组织上下文切错、列表串数据，或误把顶部徽标与“全部授权组织”列表直接比较。

**方案**

1. 将单一范围标签拆成两段可见说明：`组织执行范围：Test Store`、`本人审批：全部有权审批的组织`。
2. 顶部弹层增加范围行，例如 `执行范围：Test Store · 审批含跨组织`；从“全部授权组织”页面返回时也不让徽标看起来像该页面总数。
3. 中期可把范围拆成“执行事项组织范围”和“本人审批范围”两个独立筛选；本期先保持后端规则不变，只修正可见语义。

**验收**

- 任意数字旁都能在同一视区看到其范围，不依赖阅读长说明。
- 选择“当前组织”时出现跨组织审批不会被误解为组织串数据；顶部徽标和列表范围差异有明确解释。

### P1-04 补齐无障碍标签、焦点与颜色对比度

**现象**

- 桌面“来源”选择器在可访问性树中的名称是“请选择”，关键词框主要依赖占位符，表单文字标签未稳定关联控件。
- 移动搜索输入显式设置 `outline: 0`，父容器没有 `:focus-within`，键盘焦点不可见。
- 桌面元信息 `#94a3b8` 对白色对比度约 2.56:1，“去处理”蓝色 `#409eff` 约 2.78:1；移动元信息 `#758692` 约 3.76:1、帮助文字 `#70818e` 约 4.02:1，均低于普通小字 4.5:1 的目标。

**方案**

- 给桌面来源、范围、关键词补明确的 `id/for` 或 `aria-label`；移动搜索补可见或屏幕阅读器标签。
- 移动搜索容器增加 `:focus-within`；所有交互控件统一 `:focus-visible`，不只依赖颜色变化。
- 桌面优先复用现有主题色 `#4f46e5`，移动复用 `--mobile-color-primary`、`--mobile-color-muted`，避免在待办页继续硬编码更浅的颜色。
- 自动化增加可访问名称、焦点样式和对比度断言，再用键盘完整走一遍筛选、打开详情、取消动作和返回。

**验收**

- Tab 顺序符合视觉顺序，每个焦点清晰可见；所有输入、选择器和按钮有稳定可访问名称。
- 普通文字对比度不低于 4.5:1，大字和非文字焦点/边界不低于 3:1。

### P2-01 常驻显示活动筛选和“一键重置”

当前只有空结果时才出现“清除筛选”。当来源、分类、范围和关键词同时生效且仍有结果时，用户必须逐项恢复。

建议在桌面查询按钮旁和移动筛选卡底部常驻“重置”；同时显示活动筛选标签，可单独移除关键词或来源。重置后回到该组织的默认范围并同步 URL。

### P2-02 移动分类导航不应依赖用户猜测横向滚动

390px 下“个人”只露出一部分。建议优先改为两行网格或允许换行；若保留横向滚动，增加末端渐隐/滚动提示，并让选中项始终完整可见。与 P1-02 的 2×3 统计网格合并设计可减少重复导航。

### P2-03 统一业务详情时间格式

调拨详情和审批进度仍显示 `2026-07-...T...`。`erp-ui/src/views/mobile/feature/featureMapper.js` 已有日期与时间格式化函数，可补一个本地化日期时间函数，并在调拨、OA、审批节点等详情字段统一复用。

验收目标：统一显示 `YYYY-MM-DD HH:mm`，明确使用本地时区；无效值回退为 `-`，不展示 `Invalid Date`。

### P2-04 移动分页只保留一种主触发方式

页面同时有“加载更多”按钮和接近底部自动加载；代码虽用 `loadingMore` 防止同一时刻并发，但在页面高度变化后仍可能连续触发多页，降低用户对流量和当前位置的掌控。

建议二选一：优先保留显式“加载更多”；若需要无限滚动，则使用单独的 IntersectionObserver 哨兵、节流和每次只推进一页，并保留“已加载 n/总数”反馈。

### P2-05 动作名称应反映下一步

列表统一写“去处理”，无法预判点击后是查看、审批、执行还是补资料。建议按类别和动作能力显示“查看审批”“执行发货”“补充资料”“查看风险”，并在无写权限或事项已处理时退化为“查看详情”。

## 回滚与兼容性
