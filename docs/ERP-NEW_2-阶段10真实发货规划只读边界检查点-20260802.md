# ERP-NEW_2 阶段 10：真实发货规划只读边界检查点

## 1. 本检查点结论

阶段 9 的发货规划页面现已具备一个真实、组织受控、只读且失败即关闭的后端读取边界。后端核验调拨状态、来源仓发货范围和最新不可变审批版本，再按仓库库存模式决定是否允许读取批次库位明细；只有 `dual + detail + reconcile passed` 同时成立时才批量读取合格余额和可用序列号并形成建议。

本检查点没有接入真实发货写事务。新前端真实 Reader 只发送 GET；默认应用组合仍使用隔离 Mock；页面“接受建议”仍只在浏览器内组装非持久化命令演练，不调用现有 `/deliver` 写入口。

## 2. 权威读取与失败即关闭

- 入口为 `GET /transfer/{transferId}/shipment-planning`，要求 `inv:transfer:deliver` 权限并设置 `Cache-Control: no-store`。
- 真实路径只接受正整数调拨 ID，并要求同源 API、当前组织头；GET 明确不携带 CSRF。
- 调拨单必须处于 `approved/reserved/partial_delivered`，来源仓必须在当前组织可操作范围内。
- 最新不可变业务修订必须存在、哈希链通过既有服务校验，并且最新状态为 `APPROVED`。
- 仓库模式不是 `dual/detail/passed` 时，不查询批次余额或序列号，只返回保守枚举和逐项阻断原因。
- 未知仓库模式值降级为 `legacy/legacy/not_run`，不会把未来值或脏值误当权威状态，也不会向前端泄漏不可解析枚举。
- 明细查询仅包含启用的非虚拟库位、合格/让步且活动中的未过期批次，以及正数可用余额；SQL 不加锁、不写表、不使用字符串拼接。

## 3. 履约策略与建议算法

- 新增独立增量表 `inv_item_fulfillment_policy`，业务键为 `item_type + item_id`，只表达 `FEFO/FIFO` 分配策略和 `lot/serial` 跟踪策略。
- 迁移默认停用且没有样例数据、仓库模式切换、密码、密钥或业务种子；本检查点未执行迁移。
- 缺失、停用、归属不一致或未知的履约策略都保持行级阻断，不根据现有批次或序列号猜测。
- FEFO 按有效期、入库时间和余额 ID 稳定排序；FIFO 按入库时间和余额 ID 稳定排序。
- 序列号物料要求可用余额为整数，并与可用序列号逐件一致；返回客户端的序列号标签仅保留末四位。
- 允许库存不足时形成正数的部分建议；允许跳过缺失策略的阻断行和已完成行，只把 `ready` 行装入本批 Mock 命令。
- SHA-256 `planVersion` 覆盖调拨版本/状态、审批修订哈希、仓库模式/对账批次、策略 ID/版本/状态、数量、余额版本、批次/库位和所选序列号 ID。

## 4. 后端结构

- 新增独立 `InvTransferShipmentPlanningService`，不继续扩大既有巨型调拨服务。
- 新增只读 Mapper，一次批量读取策略、一次批量读取候选余额、一次批量读取可用序列号，避免逐行 N+1。
- 新增纯 `InvTransferShipmentAllocationPolicy`，不依赖 Spring 或数据库即可测试数量守恒、排序和序列号一致性。
- 响应 VO 把长整型 ID 和十进制数量显式转换为字符串，避免 JavaScript 精度和浮点守恒问题。
- 整个读取在只读事务中执行但不获取行锁；后续真实写命令必须用固定锁顺序重新读取并验证计划全部事实，不能只信任 `planVersion`。

## 5. 新前端边界

- `transfer-shipment.contract.ts` 已把排序策略与序列号跟踪拆开，删除伪 `SERIAL` 排序策略。
- 契约支持 `ready/blocked/complete` 三种行状态；只有 `ready` 行允许携带正数分配，`blocked` 行必须说明原因，`complete` 行必须没有剩余量。
- `canCreateShipment=true` 必须至少存在一条 `ready` 行、没有全局阻断，并且库存权威状态为 `dual/detail/passed`。
- 新增 `transfer-shipment.http.ts`，对真实响应做完整 Zod 校验并再次核对响应调拨 ID。
- 页面可诚实展示缺失策略、服务端只读来源和 Mock 来源，不会因可空策略崩溃；真实读取结果也不会把 Mock 演练描述成持久化发货。
- 启动组合未切到真实 Reader，因本轮未启动隔离服务和数据库；这避免把未执行迁移或未回填的数据误当可用环境。
