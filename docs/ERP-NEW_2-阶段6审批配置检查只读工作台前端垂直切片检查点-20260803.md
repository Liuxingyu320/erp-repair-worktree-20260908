## 1. 本检查点结论

`erp-ui-next/` 已新增 `/approvals/validation` 审批配置检查只读工作台，使用 `approval.validation.view` 与 `approval:validation:list` 双重门禁。页面提供管理员跨组织的检查批次列表、精确目标筛选、服务端分页、当前页状态摘要，以及同一只读权限下的问题明细。

本切片没有执行 `POST /approval/validation/run`，也没有提供规则修复、版本发布、编辑、导出或任何写操作入口。真实 HTTP Reader 仍未注入应用运行时。

## 2. 契约审计与纠偏

- 列表端点：`GET /approval/validation/runs`；明细端点：`GET /approval/validation/runs/{id}`。
- 列表只发送后端实际消费的 `templateId`、`ruleId`、`ruleVersionId`、`validationType` 和 `runStatus`，并使用标准分页参数。
- 旧 `ValidationPanel.vue` 会发送后端不消费的 `businessCode` 和 `status`；新 Reader 没有复制该偏差。
- 旧页面执行检查发送 `businessCode`、`scopeMode`、`anchorDeptId` 和 `businessSubtype`，但当前 Controller DTO 要求非空 `versionId`，可选 `validationType`；本切片拒绝臆测兼容，完全不实现执行检查 POST。
- 检查类型固定为 `PUBLISH`、`FULL`、`MANUAL`；批次状态固定为 `RUNNING`、`PASSED`、`FAILED`；问题级别固定为 `ERROR`、`WARNING`。
- 契约校验 Java Long、非负安全整数、本地日期时间、状态与计数不变量，并校验明细问题数量、级别合计和 `runId` 与批次一致。
- 批次快照、内部操作人和用户 ID，以及问题内部目标 ID、问题快照与审计字段均不进入页面模型。

## 3. 权限、数据范围与缓存

- 列表和明细都只需要 `approval:validation:list`；执行检查单独需要 `approval:validation:run`，未被本切片引入。
- 当前 Controller 与 Mapper 没有当前组织过滤，页面明确标注“管理员跨组织只读”；Reader 不发送组织头，也不发送 CSRF。
- 两个成功响应都必须声明 `Cache-Control: no-store`，缺失时 Reader 失败关闭。
- 当前后端没有该响应头证据，因此真实 Reader 保持未注入，这是生产接线阻断项。
- 默认 Provider 只注入 ERP-NEW_2 自有脱敏 Mock，不读取真实或共享业务数据。
