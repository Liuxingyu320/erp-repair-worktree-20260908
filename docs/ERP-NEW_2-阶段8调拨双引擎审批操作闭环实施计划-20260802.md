# ERP-NEW_2 阶段 8：调拨双引擎审批操作闭环实施计划

> 日期：2026-08-02
> 基线：`187be8f9 feat: expose transfer revision history`
> 范围：只修改 ERP-NEW_2 隔离工作树；不启动服务或连接数据库

## 1. 结果与范围

在 `erp-ui-next/` 建立可从统一待办深链进入的调拨审批任务页。页面必须以服务端验证过的不可变修订作为商品、数量、组织、原因和凭证上下文，支持旧库存审批与统一审批两种执行引擎，并通过同源、组织、CSRF、请求标识和运行时响应契约保护真实写操作。

本检查点不把默认应用从隔离 Mock 切换到真实后端，也不启动任何服务。Mock 页面用于浏览器内交互验证；真实 HTTP 适配器及契约测试用于冻结未来联调边界。

## 2. 重要约束

1. 旧审批引擎只允许 `approve/reject`，调用 `/inventory/transfer/approve`。
2. 统一审批引擎允许 `approve/return/reject`，调用 `/approval/tasks/{taskId}/{action}`。
3. 所有审批写请求必须携带同一个安全请求标识到 HTTP 头和需要它的业务体，要求组织上下文与 CSRF，且不自动重试。
4. 拒绝或退回必须填写有意义的原因；通过意见可选，但统一限制长度。
5. 路由中的 `transferId/taskId/instanceId` 必须先由运行时契约验证；真实 HTTP 只接受正整数，Mock 只在隔离 Gateway 内接受固定测试标识。
6. 页面不得从可变主单重新拼接审批业务内容；业务上下文来自最新封存修订，并要求状态仍为 `SUBMITTED`。
7. 待办深链、路由、功能标识和权限统一使用 `inventory.transfer.approve` / `inventory:transfer:approve`。
8. 默认 Mock 决策明确返回 `persisted: false`，不得暗示已经改变审批、库存或数据库。

## 4. 执行步骤

1. 收紧旧审批请求：验证正 ID、动作白名单、意见长度，并要求驳回原因；保持服务层校验以覆盖非 HTTP 调用。
2. 定义双引擎路由、审批上下文、审批轨迹子集和决策结果的 Zod 契约；组合阶段 7 的强类型修订历史。
3. 实现真实 HTTP 适配器：分别读取旧审批轨迹或统一审批实例详情，验证任务/实例/业务归属，再向对应引擎提交决策。
4. 扩展 Gateway 和 Mock fixture；审批 Mock 必须保持非持久化并记录可断言的输入。
5. 注册审批深链、路由、功能和权限；让现有审批待办由“后续原型”变为可进入任务页。
6. 实现移动优先审批页：单一下一步、封存哈希、商品数量、审批节点、原因输入、二次确认和明确成功/失败反馈。
7. 添加领域、HTTP、深链和页面测试，覆盖错误引擎动作、路径注入、实例归属错配、CSRF/组织/请求标识、拒绝原因和 Mock 非持久化。
8. 运行前端完整 `npm --prefix erp-ui-next run verify`，以及 Java 17 + 隔离 Maven repository 的库存模块离线 reactor 测试。
9. 记录阶段检查点，执行受保护路径/旧前端引用/共享资源扫描，精确暂存并提交；不推送。

## 5. 兼容性与风险

- 统一审批实例详情属于参与者可见接口；前端只解析任务页需要的白名单字段，不展示候选人内部记录、回调发件箱或原始快照 JSON。
- 页面加载后任务可能被他人处理；提交时以后端锁、候选人和当前节点校验为准，冲突必须提示刷新，不做客户端假成功。
- 旧审批与统一审批的拒绝语义不同：旧引擎由规则决定回草稿或关闭；统一引擎区分 `return` 与 `reject`。界面必须按引擎显示准确文案。
- 正式 OpenAPI 生成仍需隔离服务可用后完成；本阶段的手写运行时契约不冒充生成类型。

## 6. 验证标准

- 任一非法路由标识、未知引擎、任务/实例/调拨归属不一致都在写请求前失败。
- 真实写适配器同时证明 CSRF、组织头、同源路径和请求标识。
- 页面测试证明审批上下文来自封存版本，拒绝/退回原因必填，通过后显示非持久化 Mock 说明。
- 前端完整门禁和后端相关离线 reactor 均为 0 失败。
- Git 提交中没有受保护原项目路径、真实秘密、共享服务配置、旧前端源码引用或生成构建产物。
