# ERP-NEW_2 阶段 13M：差异裁决真实 HTTP 写边界与未注入前端适配器检查点

## 1. 检查点结论

阶段 13M 已把阶段 13J–13L 的一次性 basis、安全命令和传输契约接入真实 HTTP 协议代码，同时继续把前端页面和默认运行时保持在关闭状态。

新增后端入口：

- `POST /transfer/discrepancies/{discrepancyCaseId}/adjudication-basis`；
- `POST /transfer/discrepancies/{discrepancyCaseId}/adjudications`。

新增前端能力：

- 同源 basis issuer；
- 同源 adjudication writer；
- 通用 `expectedOrganizationId` 失败关闭检查，组织切换后的陈旧请求在 `fetch` 前被阻断。

本阶段没有把 Writer 加入 `TransferGateway`、providers、Mock、页面或 bootstrap，因此当前应用运行时仍不能触发真实签发或裁决写入。

## 2. 后端边界

两个入口均只接受精确权限 `inv:transfer:discrepancy:adjudicate`，从路径获取事项 ID并从现有请求上下文解析所选组织，响应均设置 `Cache-Control: no-store`。

### 2.1 basis 签发

- 使用 POST 且无请求正文；
- 只调用阶段 13J 的签发事务服务；
- 操作日志类型为 `OTHER`，没有允许进入审计摘要的请求字段，中央日志实现也不序列化任意响应；
- 不标注 `@PersistentCommand`。

不使用 `@PersistentCommand` 是刻意的安全语义：要重放同一签发成功响应就必须保存原始 bearer token、保存可逆密文或确定性派生 token，这会破坏不透明令牌边界。重复签发只能产生相互独立、5 分钟后失效且未消费的能力，不修改事项、库存、物流或财务状态。

### 2.2 裁决提交

- JSON 正文必须通过阶段 13L Bean Validation；
- `X-Request-Id` 必填且不在正文重复；
- 事项只来自路径，组织只来自请求上下文；
- 标注 `@PersistentCommand` 和更新类业务审计，但不保存请求或响应载荷；
- 仅调用 `InvTransferReceiptDiscrepancyAdjudicationCreationService.create`。

浏览器不提供事实指纹、确认事件 ID、决定指纹、金额、执行状态、裁决主键、用户或权限。令牌锁定、当前事实恢复、权限/组织复核、裁决头与动作写入、事项推进、最后消费以及精确重放继续全部属于阶段 13K 单一事务。

## 3. 前端网络边界

`transfer-discrepancy-adjudication.http.ts` 现在提供独立 Reader 和 Writer：

- 路径事项和期望组织在网络前限制为 Java `Long` 范围内的规范正整数；
- basis POST 无正文，自动携带请求 ID、CSRF 和组织头；
- basis 响应必须是严格服务端来源、精确 5 分钟有效期，并与请求事项及组织一致；
- 裁决 POST 只发送信封 `body`，显式复用信封的 `requestId`，路径与组织保持独立权威来源；
- 创建结果必须与提交事项及动作数量一致；
- 未知内部字段、跨事项、跨组织、超 Long 标识和陈旧组织信封全部失败关闭。

`ErpHttpClient` 的 `expectedOrganizationId` 只做客户端提交前一致性校验，不把期望组织作为新请求字段发送。它与当前会话组织不一致时返回 `ORGANIZATION_CONTEXT_CHANGED`，并且不会调用 `fetch`。
