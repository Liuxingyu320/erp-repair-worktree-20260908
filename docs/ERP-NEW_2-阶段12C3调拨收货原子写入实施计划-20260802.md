# ERP-NEW_2 阶段 12C3：调拨收货原子写入实施计划

> 日期：2026-08-02
> 分支：`codex/erp-new-2-rebuild`
> 基线：`3ae369ff feat: add transfer receipt lock validation boundary`
> 范围：仅 ERP-NEW_2 隔离工作树；不使用 Docker、不启动服务、不连接数据库、不执行迁移

## 1. 结果与范围

本阶段把 12C2 已完成的固定锁序和权威请求校验扩展成单事务原子写入边界。一次成功收货必须同时产生不可变收货审计、合格/残损目标库存、来源分配进度、序列号处置、明细累计和单据生命周期；任一插入、条件更新或唯一约束失败都必须抛出异常，由外层 `InvTransferCommandService` 事务整体回滚，禁止部分成功或捕获后继续。

12C3 只完成源码与离线测试。两个收货 Gate 继续默认 `false`；前端 Writer 仍不注入，按钮仍不接线。真实迁移、并发、死锁与回滚验证留给 ERP-NEW_2 专属非 Docker 数据库检查点。

## 2. 已确认假设

- 请求已经由 `InvTransferShipmentReceiptRequestPolicy` 规范化为不可变、按 allocation ID 排序的命令，并绑定事务内重算的 `receiptPlanVersion`。
- `remaining = allocated - accepted_received - damaged_received - shortage_reported`；本次三类数量之和大于零且不超过剩余量。
- 合格与残损成本固定使用来源分配 `cost_price × quantity`，保留六位小数；短缺只写审计，不增加任何目标库存。
- `inv_transfer_shipment_detail.received_quantity` 和 `inv_transfer_detail.received_quantity` 只累计合格量。
- 合格增加目标汇总/明细的 `current + available`；残损增加 `current + quarantine`；两类处置使用各自的派生批次、余额与流水。
- 合格 serial 移至目标正常库位并改为 `available`；残损 serial 移至隔离库位并改为 `quarantine`；短缺 serial 仅写不移动的差异审计。
- 任一残损或短缺使发货批次和调拨单进入 `discrepancy`；无差异且仍有剩余为 `partial_received`；全部合格完成才为 `received`。
- 缺失目标行通过唯一键解决并发竞态；插入唯一冲突不重查、不吞掉，整笔回滚后由调用方以新事务重试。

## 3. 代码结构与文件

### 3.1 锁定边界

- 新增 `domain/transfer/InvTransferShipmentReceiptLockedBoundary.java`，只暴露复制后的 header、权威 Composition、来源分配/明细、目标模式、目标汇总、来源/派生批次、目标库位/余额和 serial 映射。
- 修改 `service/impl/InvTransferShipmentReceiptLockGateway.java`，`lockAndCompose` 返回完整边界；所有集合先去重、排序、校验归属，再构造不可变快照。
- 扩展 Lock Gateway 测试，证明返回边界与已锁事实一致，且缺失目标行只表现为“待创建”，不能绕过来源事实校验。

### 3.2 纯 Prepared Mutation

- 新增 `domain/transfer/InvTransferShipmentReceiptPreparedMutation.java`，保存收货头草稿、逐 allocation 处置、目标汇总聚合、派生批次/余额需求、serial 动作、明细累计与最终生命周期。
- 新增 `domain/transfer/InvTransferShipmentReceiptMutationPlanner.java`，输入 request ID、锁定边界、Validated Command 与操作者，输出确定性 Prepared Mutation；不得注入 Spring 或 Mapper。
- 规划器必须重复证明每个 allocation 的数量守恒、来源成本守恒、目标库位类型、serial 集合和生命周期；生成确定性的 receipt no、lot no 与流水 request ID。
- 添加纯单元测试覆盖多 allocation 聚合、合格/残损分流、短缺零库存、serial 三分类、全部完成/部分/差异状态及输入顺序无关性。

### 3.3 窄持久化执行器

- 扩展 `InvTransferShipmentReceiptPersistenceMapper.java` 及 XML：仅增加收货专用 insert、带归属/版本/守恒谓词的 update 和生成键记录。
- 新增必要的收货写记录类，字段与 `erp_inventory_transfer_receipt_v2_20260802.sql` 一一对应，不复用可任意更新业务行的宽 Mapper。
- 新增 `service/impl/InvTransferShipmentReceiptMutationExecutor.java`，它是唯一允许调用收货 mutation 的组件；每个单行操作都要求影响行数恰为 1，生成键必须为正数。
- 修改 `InvTransferShipmentReceiptCreationService.java`：固定执行 Gate → header 锁 → 组织/方向校验 → 完整锁边界 → Request Policy → Mutation Planner → Mutation Executor → 强类型结果；方法继续要求 `Propagation.MANDATORY`。

## 4. 固定写入顺序

所有读取锁完成且 Prepared Mutation 已完全生成后，执行器按下列顺序写入：

1. 插入不可变收货头并取得 `receipt_id`。
2. 按物料键创建缺失目标汇总库存；已存在行按旧版本条件更新，新建行用本次总量初始化。
3. 按目标仓、物料、来源批次、处置创建缺失派生批次并取得 `lot_id`。
4. 按派生批次、目标库位创建缺失明细余额；已存在余额按旧版本条件更新，新建余额用本次处置量初始化。
5. 按物料键写汇总库存日志并取得 `summary_stock_log_id`，供后续明细台账建立可核验关联。
6. 按 allocation ID 插入不可变收货分配审计，记录来源/目标 ID、数量、成本及版本前后值。
7. 按 serial ID 条件移动合格/残损 serial；短缺 serial 不做位置更新；随后插入全部 serial 处置审计。
8. 按 allocation ID 条件累计合格、残损、短缺及 `receipt_version`。
9. 按 shipment detail ID 和 transfer detail ID 条件累计合格数量，禁止写入残损或短缺。
10. 按 allocation ID、处置顺序写 accepted/damaged 明细库存台账；短缺不写库存台账。
11. 更新发货批次/调拨单状态并写状态审计；所有状态更新带旧状态、归属及调拨单版本谓词。
12. 用数据库生成 ID、固定计划版本、本次分类总量和写入前确定的创建时间装配 `InvTransferShipmentReceiptCreationVo`。

执行器不得在循环中临时发现新锁键或重新规划，也不得在写入后做可导致“审计缺失但库存已变”的非事务外部调用。

## 5. SQL 硬约束

- 目标汇总和余额更新必须约束 ID、仓库、维度、旧版本、非负数量、非负成本和写前 `current = available + locked + quarantine`。
- allocation 累计必须约束 shipment 归属、旧 `receipt_version`、三类 delta 非负且累计不超过 `allocated_quantity`。
- serial 更新必须同时匹配 serial ID、来源仓/余额/批次/库位和旧状态 `shipped`。
- shipment/transfer detail 更新必须匹配业务归属、旧累计值，并保证新累计不超过已发/调拨数量。
- 生命周期更新必须匹配 shipment/transfer 归属、允许的旧状态和调拨单旧版本。
- 收货头 `command_request_id`、派生批次维度、目标余额维度、收货分配、收货 serial 和处置流水唯一键冲突均直接失败。

## 7. 风险与停止条件

遇到以下任一情况立即停止该实现路径：需要访问受保护原项目；需要连接任何现有服务或数据库；现有唯一键无法保证目标建行；锁边界不能提供完整来源事实；需要复用无版本宽更新；短缺会改变库存位置；旧差异处理器会接管 V2；或必须打开 Gate 才能验证源码。

真实数据库阶段还必须单独验证 MySQL 5.7 的执行计划、gap/next-key 锁、唯一冲突、死锁重试和故障回滚；在此之前，12C3 源码完成不构成上线授权。
