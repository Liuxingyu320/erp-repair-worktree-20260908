# ERP-NEW_2 阶段 6：审批配置检查只读工作台前端垂直切片实施计划

> 日期：2026-08-03
> 基线：`1d05c9b2 feat: add approval definition catalog skeleton`
> 状态：本只读垂直切片已完成；不代表执行检查、规则修复或统一审批闭环迁移完成

## 1. 目标与范围

在 `erp-ui-next/` 内新增 `/approvals/validation` 审批配置检查只读工作台，覆盖拥有配置检查列表权限的管理员查看检查批次、按模板/规则/版本 ID、检查类型和结果筛选、服务端分页、当前页状态摘要，并按相同只读权限查看一个批次的问题明细。

本切片只实现：

- `GET /approval/validation/runs`；
- `GET /approval/validation/runs/{id}`；
- 权限 `approval:validation:list`；
- 明确的管理员跨组织只读语义，请求不发送组织头；
- 精确目标 ID、检查类型和检查结果筛选；
- 服务端总记录数，以及当前页检查中、通过、未通过、错误和警告数量；
- 问题级别、稳定问题编码、范围、业务子类型、节点、说明和修复建议的只读明细；
- ERP-NEW_2 隔离 Mock 默认运行时和未注入的真实只读 HTTP Reader；
- 桌面表格、移动卡片、加载、错误、空状态和最近成功筛选语义。

以下能力明确留待后续独立切片：`POST /approval/validation/run`、规则/版本编辑、发布、停用、修复命令、导出、真实运行时注入和旧审批管理页面下线。

## 2. 审计结论与硬边界

### 2.1 当前后端契约

- 检查批次列表与明细都要求 `approval:validation:list`；执行检查单独要求 `approval:validation:run`；
- 列表 Mapper 实际只支持 `templateId`、`ruleId`、`ruleVersionId`、`validationType` 和 `runStatus`；
- 检查类型闭集来自表结构与调用路径：`PUBLISH`、`FULL`、`MANUAL`；结果闭集为 `RUNNING`、`PASSED`、`FAILED`；问题级别闭集为 `ERROR`、`WARNING`；
- 明细响应结构为 `{ run, issues }`，问题按错误优先、问题 ID 排序。

### 2.2 旧页面契约偏差

- 旧 `ValidationPanel.vue` 发送 `businessCode` 与 `status`，但 `ApprovalValidationRun`/Mapper 不消费这两个属性；
- 旧页面执行检查发送 `businessCode`、`scopeMode`、`anchorDeptId` 和 `businessSubtype`，当前 Controller DTO 实际要求非空 `versionId`，可选 `validationType`；
- 新工作台不得复制这些无效参数或把旧 UI 行为当作已冻结契约；执行检查 POST 本切片完全不实现。

### 2.3 跨组织与敏感投影

- 列表和明细没有当前组织数据范围条件，属于审批管理员系统级审计视图；新 Reader 显式省略组织头；
- 批次模型只保留目标 ID、类型、结果、问题计数、发起人显示名和起止时间；发起人用户 ID、范围 JSON、内部操作人、更新时间和备注全部丢弃；
- 问题模型只保留显示所需范围、节点、编码、说明和建议；内部模板/规则/版本 ID、问题快照、内部操作人、创建时间和备注全部丢弃；
- 列表和明细成功响应必须显式声明 `Cache-Control: no-store`，否则 Reader 失败关闭。当前端点没有该响应头证据，因此仍是生产注入阻断项。

## 3. 设计与动效决策

这是高频 ERP/SaaS 审计工作台，采用 Emil Kowalski 为主、Jakub Krehel 为辅：

- 使用“管理员跨组织范围 → 服务端总量/当前页健康 → 精确筛选 → 批次列表 → 选中批次问题”的层级；
- 批次事实与查看问题能力在桌面和移动端保持等价；
- 搜索、键盘提交、分页、列表替换和明细切换不播放动画；
- 只允许按钮按压的 140ms 可中断 `transform` 过渡；
- `prefers-reduced-motion: reduce` 下关闭所有非必要过渡；
- 21st.dev 与 UI Prompt Library 仅用于后台审计层级，Motion Primitives 仅用于失败时保留最近成功状态；不复制外部代码、素材、品牌或付费提示词；
- 不新增 React、Tailwind、Motion、GSAP、远程字体或外部组件依赖。

## 6. 验证标准

- 不安全 Long、未知类型/状态/级别、负数、无效时间、计数不一致和非法完成状态全部失败关闭；
- 列表只发送后端实际消费的筛选参数，不发送旧页面的 `businessCode`、`status`、`scopeMode`、`anchorDeptId`、`businessSubtype` 或 `params`；
- 列表与明细不发送组织头或 CSRF，并都强制响应 `no-store`；
- 默认隔离 Mock 提供多个 ERP-NEW_2 模拟目标与问题，不读取任何真实或共享业务数据；
- 页面明确区分服务端总记录、当前页批次数与当前页问题计数；
- 筛选成功后才更新已应用条件，失败时保留最近成功标签；明细失败不清空批次列表；
- 页面只有真实可执行的“查看问题”只读动作，没有执行检查、编辑、发布、修复、导出或新建伪入口；
- 功能开关和列表权限同时满足才可见且可访问；
- 完整前端验证、迁移生成器、确定性哈希和隔离扫描通过；
- 旧 `erp-ui/`、受保护原项目、Docker、服务、数据库、依赖和真实配置保持零改动。

## 7. 停止线

发现以下任一情况立即停止：

- 需要读取或修改受保护原项目、连接数据库、启动服务或安装依赖；
- 需要修改旧 `erp-ui/`、注入真实 Reader 或把当前组织头误当作管理员数据范围；
- 需要执行检查、规则修复或发布命令而没有独立命令契约；
- 需要扩大普通用户权限或不能证明跨组织检查记录仅由管理员权限控制；
- 不能证明全部文件、运行目录和测试只位于 ERP-NEW_2 隔离工作树。
