## 1. 使用者最终应看到什么

日常列表、通知、弹窗和详情按场景回答：**谁／什么事／哪个门店或公司／当前到哪一步／发生或截止时间／接下来做什么**。已有信息由系统自动带出；只显示这次办事需要的内容，不把所有字段堆到一张卡片。

| 场景 | 目标表现（姓名和内容均为示例） |
|---|---|
| 合同待发送消息 | 张三 · 测试门店｜入职合同待发送；劳动合同等 4 份已准备好，进入该人员批量合同入口核对发送 |
| 员工首次签名后 | 张三已完成首次签名，接下来由经办人完成公司资料/最终文件准备；不能提前叫全部完成 |
| 合同全部完成消息 | 张三 · 测试门店｜入职签约已完成；明确哪一期、哪份文件，可查看归档 |
| 截止提醒 | 明确年月日时分，区分首次签署/最终确认；“签约超时”与“原劳动合同到期”分开 |
| 新任务还没有签约包 | 仍能显示员工姓名、账号/工号、门店、负责人；不等文件生成后才知道是谁 |
| 角色和店铺配置 | 页头明确正在配哪个角色/哪些人，保存摘要列出新增和移除的店名，正常操作不用抄 ID |
| 请假、补卡审批 | 员工、门店、日期、假种/拟补时间、原因、当前处理人，直接处理准确申请 |
| 历史记录 | 姓名优先，原账号/单号辅助；缺信息说明缺什么，不用“系统”或随便一个当前姓名填空 |
| 回收站 | 同名文件可由原目录和删除人区分，显示真实预计清理日期，不一律写“30天后” |

消息摘要不放身份证、住址、银行卡、工资或未授权内部文件；需要这些内容时进入有权限的详情。正常业务单号、SKU、套餐代号可保留作辅助。不同字段的 A/B 不作全局替换，按社保、薪酬版本、套餐路由各自实际定义解释。

## 2. 已确定规则

- **人事管理 → 批量处理入职合同是唯一员工合同发布位置。** OA 任务、签约包、消息、手机入口只能查看/定位办理对象，发布操作统一回这里；合同模板发布仍是配置功能。
- 保留 Excel 导入及合同 Excel 工资来源。首次当前合同录得晚与真正历史补签分开；历史补签不能覆盖已存在的后续现行工资。
- 姓名、手机号、证件、工作归属不通过“随便覆盖全部字段”同步；按已有员工主数据与匹配规则办理。已签文件和冻结快照不随主档编辑改写。
- 普通调岗不触发工资文件；只有具备工资权限、实际选择并改变工资时，沿用现有调薪流程。
- 常见九类假种和已有规则配置继续使用；系统代换算，员工不研究地区规则；不编造统一假期天数、工资或余额。
- 保留跨页批量选择、复制上周、已有排班保护、停用角色可查看/移除、不新增停用角色等既有能力。
- 保存失败保留输入；结果不明核对原请求，不重复发起。后端数据校验和上下文隔离由系统承担，避免增加人工确认。
- 对 L01 离职签署接续先验证真实可达路径，不为了方便恢复离职人员全部业务权限。只有确有未定业务取舍时，主窗口一次问一个具体问题；其他包继续实施。

## 5. 关键实施设计

### 5.1 姓名和中文标签

人员/操作者查询批量补齐姓名、账号、组织摘要，避免列表每一行都额外请求一次用户接口。事件有当时快照则优先使用；只剩 ID 时通过已授权关联解析；只有历史账号且身份无法确认时保留原账号并说明，不猜人。不要改写旧 createBy/updateBy 等审计原值。

用“字段键＋原值”生成中文标签，避免一个 A/B 在不同业务下被错误翻译。合法历史中文保留；未知状态显示可理解的“状态待核对”，原代号放辅助信息。未填写、加载失败、无权限、已停用/删除分别表达。正常流程里的设置选择提供中文名称；高级技术日志、权限字符和 JSON 可保留在折叠详情。

### 5.2 签约消息的完整链路

共用签约上下文包含：对象 ID（内部关联）、员工姓名/账号或工号、办理时门店、中文场景、文件摘要与份数、业务包号、对应文件版本、事件时间、签署期限、当前负责方、下一步入口。已生成包优先取对应版本快照；未生成包使用有效业务事件/员工资料。不能直接加一个不存在或未赋值的 task.employeeName 就结束。

12 个事件/收件人分支全部改：补资料、草稿待发送、员工待签、首次签名、最终件确认、初签提醒、最终确认提醒、完成发 HR、完成发员工、拒签、超时发 HR、超时发员工。初签与全部完成的现有正确状态顺序必须保留。提醒实现受配置控制，本轮不擅自开启线上提醒。

站内列表、搜索、详情、手机与推送使用同一份安全摘要来源。手机不能处理的操作提供只读详情和明确接续入口；没有权限/关联失效要说明原因，不能点完仅变已读且原地无提示。变已读不等于业务处理完成。

### 5.3 历史消息也要可读、可搜索

仅改新模板不满足用户现有消息问题。新数据保存上下文版本；旧数据按 routeType＋taskId/packageId 及对应业务版本进行确定性补全。优先事件当时快照，不能用今天的门店/期限冒充历史。可以采用受权限控制的读时显示投影或可回滚批处理；姓名搜索应覆盖补全后的字段，不只在浏览器临时拼文本。

不重发旧消息、不改变已读状态/创建时间/业务去重键，保留原文。无法准确关联时显示历史信息未完整记录和有效编号。先在隔离测试库验证补全、重跑和回滚；真实历史数据补全属于后续上线步骤，不在本轮直接执行。

### 5.4 合同与人员资料

按现有字段注册表列出每个导入字段的主档归属、当前/历史规则和回写时点，形成可查字段映射。普通 Excel、HR 行编辑、员工补资料经办人确认最终使用同一规则。工资写入、合同生成、发送是不同完成步骤，页面分别反馈且自动刷新相关档案；失败可从原批次继续。

现行合同与正在办理的续签同时可见，不把待签当已完成，也不因展示改动随意调整既有工资生效/停号时点。保留原合同、签约任务与档案变更来源的连接。健康证恢复/审批显示当前对象、原因、重试时间和正在等谁。

### 5.5 角色与管理店铺一次配置

账号配置面板合并基本资料、角色、所属组织、可管店铺；可从人事人员或角色成员页进入同一个配置能力。复用岗位入职配置作为可见默认方案，用户可修改，不让人再手动维护第二份配置。角色配置页头固定角色名；每个弹窗固定本次人员和范围。

批量选择人后应用同一角色/范围，预览显示具体增删门店名称及数量；保留已有多店额外授权和权限范围外的保留项，不默默删除或增加。返回逐人成功、失败和待核对结果，失败只重试原失败部分。岗位/角色停用后，原关联名称仍可见，新增选项仍仅列可用项。审批规则用组织树、人员/岗位名称选择，不要求抄数据库编号。

### 5.6 日常考勤与 OA

查询、预检、确认、写入使用固定的同一对象范围。选员工/选记录的操作与后端能力一起实现；“整店处理”是明确动作，不能借前端筛选让人误以为只处理当前人。切店/切日期后旧结果不得写回新页面。重算用一次包含门店、日期、人员和覆盖数量的明确确认。

假种的未设置数值在组件中保持未设置，不被最小值夹成 1；只有用户开启对应规则后才产生阈值。小时/天的换算复用已有配置。请假、补卡从列表直接找到人和对应待办；审批“下一条”仅打开下一张，不自动审批。采购“以此再申请”生成全新可编辑草稿，不继承旧单号与审批状态。

## 6. 验证与 Codex/Grok 复查循环

1. 实施窗口按 ledger 更新每条状态、修改文件、验证命令和证据，允许合修但每个入口都交代；不能只写“已覆盖”。旧证明问题的探针保留，修复验收另写正确行为断言。
2. 每包先运行相关测试；Java 明确使用项目 JDK 17，前端依赖沿 lock。真实数据写入测试使用可识别的隔离数据库，不使用现有 1025/8080 服务当新代码证据。现有 Docker 未启动，可准备隔离验证环境；做不到的层次如实留待验证。
3. 汇总前运行受影响模块编译/测试与前端构建，修复本轮引入的失败。无需为改一行标签反复跑全仓测试；消息组装、人员回写、权限批量、范围变更和历史补全必须有有意义的行为检查。
4. 浏览器验收覆盖电脑和手机尺寸：两个同名员工、两个店、同人多份合同、未生成包、已停用原关联、未知状态、旧消息、长姓名、无权限、请求失败/切换对象。字段清楚、摘要和详情一致、处理入口准确。截图或页面测试夹具是 UI 证据；不能拿它冒充真实数据库/生产/锁屏设备验收。
5. 实施窗口提交本轮候选版本和清单，暂不回合原目录。主窗口冻结候选提交、diff、源码哈希和测试日志，先做 Codex 独立复查，再把同一版本交给本机 Grok 只读审查。Grok 只能读取相关源码和合成验证材料，不修改代码、不读取密钥/真实人事资料、不外发通知。
6. 任一审查发现有效问题，主窗口记录具体场景、文件位置、期望结果和复测方式，发回指定实施窗口。该项状态改为 returned，修好后重新冻结版本；相关场景及共用能力再次复核。不能把上一版的通过意见用于新版。
7. Grok 结论若仅审了报告、不曾查源码，记为材料审阅，不能算独立源码复核。Grok 不可用时明确保留待复核，不伪称联合通过；其余 Codex 验证继续。
8. 全部条目明确为通过、合并验证通过或有证据的不适用；不能将条件未验证算通过。确需用户业务选择的项单独提出，其余继续。通过后再安全回合本轮变更到原项目，处理期间的新差异，不覆盖原有工作。部署和真实数据回填仍单列为后续事项。

每次退回/复查记录在 ledger.reviews，至少包括轮次、候选提交/哈希、Codex结果、Grok结果、未通过ID、实施窗口回复及复测证据。用户无需在两个窗口来回搬运问题。进度未变化时不反复通知，只报告阶段完成、新失败或确实需要用户决定的事项。
