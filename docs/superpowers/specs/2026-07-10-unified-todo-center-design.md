# ERP 统一待办中心设计

## 1. 文档状态

- 日期：2026-07-10
- 状态：已完成业务设计确认
- 适用端：电脑端、手机端
- 目标分支：`6月13号`

## 2. 背景

当前项目已有“我的待办”、调拨审批、盘点审批、手机库存工作台和通知公告等入口，但这些入口彼此独立：

- 电脑端 `/oa/todo` 实际只显示 OA 采购审批。
- 调拨审批和盘点审批分别隐藏在各自业务页面中。
- 手机端采购、调拨和盘点审批使用三个不同入口。
- 首页“我的待办”是静态入口，没有本人真实未处理数量。
- 库存工作台仅统计部分收发货和调拨审批，未覆盖盘点、OA、人事和个人签署事项。
- 公告的“已读”和业务任务的“已处理”语义不同，不能共用一个数字。

因此，用户无法在登录后立即判断自己是否有审批、收发货、重盘、签署或管理提醒，容易造成流程滞留。

## 3. 目标与非目标

### 3.1 目标

1. 为每个登录用户提供统一、准确、可跳转的业务待办中心。
2. 在电脑顶部、电脑首页、统一待办页和手机工作台显示一致的未处理数量。
3. 待办仅在业务处理完成后消除，打开查看不会清除。
4. 所有数据必须同时满足业务状态、用户权限、候选审批人和组织范围。
5. 支持部分业务服务失败时的降级，不得把总数错误清零。
6. 保留现有业务页面和审批入口，逐步统一数据源，不破坏原流程。

### 3.2 非目标

第一期不实现以下能力：

- WebSocket、短信、微信或邮件实时推送。
- 催办、转办、委托、加签和待办 SLA 管理后台。
- 普通业务草稿提醒。
- 缺少排班、休息日和请假依据的未打卡提醒。
- 尚无预警阈值和处理闭环的库存临期/过期提醒。
- 尚无完整确认流程的工资月度待计算提醒。
- 固定资产“异常批准”伪审批；当前流程是管理员直接创建已批准记录。
- 将系统公告混入业务待办总数。

## 4. 核心决策

### 4.1 聚合方式

采用“领域模块实时提供标准化待办，前端统一聚合”的方式：

- 库存模块负责库存审批、收发货、退货、重盘和库存风险。
- OA 模块负责采购审批、固定资产确认和员工签署。
- 系统/人事模块负责人事资料、入离职、合同到期和账号安全提醒。
- 前端使用独立 Todo Store 并行加载各模块汇总和列表。

不采用前端直接猜测业务状态，也不在第一期建立永久待办事件表。这样可以让业务表继续成为唯一事实来源，避免业务已处理但待办记录未关闭。

### 4.2 待办与消息分离

- 业务待办：按“是否仍需处理”计算，处理完成后消除。
- 通知公告：按“是否已读”计算，阅读后消除未读标记。
- 电脑顶部显示两个独立图标和两个独立数字。
- 手机端统一待办入口与通知公告入口保持分离。

公告“全部已读”后必须重新读取后端未读数，不能只处理当前展示的五条后在前端直接清零。

## 5. 总体架构

```text
库存待办 Provider ─┐
OA 待办 Provider  ─┼─> Vuex Todo Store ─> 电脑顶部角标 / 电脑首页 / 统一待办页
人事待办 Provider ─┘                  └> 手机工作台 / 手机统一待办页

通知公告接口 ─────────────────────────> 独立公告角标与公告页面
```

每个 Provider 提供两类只读接口：

1. 汇总接口：返回总数、分类数量、优先级数量和最近待办。
2. 列表接口：按分类、当前组织/全部授权组织、关键字和分页条件返回待办。

Provider 自己负责权限与范围判断。前端只能进一步隐藏无路由项，不能以隐藏按钮代替后端鉴权。

## 6. 统一待办数据契约

每条待办至少包含：

| 字段 | 含义 |
|---|---|
| `todoKey` | `来源类型:业务ID:当前动作`，全局唯一 |
| `source` | `inventory`、`oa` 或 `system` |
| `type` | 稳定的待办类型编码 |
| `category` | `approval`、`execution`、`returned`、`risk`、`personal` |
| `businessId` | 业务主键 |
| `businessNo` | 单号或可识别编号 |
| `title` | 面向用户的待办标题 |
| `summary` | 组织、申请人、商品数量等简要说明 |
| `status` | 原业务状态 |
| `priority` | `urgent`、`important`、`normal` |
| `createdTime` | 待办产生时间 |
| `waitingSeconds` | 已停留秒数，由后端计算 |
| `deptId`、`deptName` | 归属组织 |
| `scopeMode` | `all_authorized` 或 `current_org` |
| `routeType` | 前端路由解析使用的稳定类型 |
| `routeParams` | 业务 ID、筛选状态等跳转参数 |
| `requiredPermission` | 跳转和操作所需权限，用于前端校验与诊断 |

前端不得使用 `status=submitted` 直接判断业务类型，因为采购审批、采购收货、销售发货和退货确认都可能使用相同状态但含义不同。

## 7. 第一期待办范围

### 7.1 审批类

| 类型编码 | 触发条件 | 责任人 |
|---|---|---|
| `OA_PURCHASE_APPROVAL` | OA 采购为审批中且当前 Flowable 任务属于本人 | 实际任务候选人，具备 OA 待办权限 |
| `INV_TRANSFER_APPROVAL` | 调拨为待审批、审批实例运行中、当前节点任务待处理 | 当前节点实际候选人，具备调拨审批权限 |
| `INV_STOCK_CHECK_APPROVAL` | 盘点为 `pending_approval`、当前实例和任务运行中 | 运营总监候选人，具备盘点审批权限 |

管理员账号也必须满足真实候选人条件，不得因为是管理员而看到无法处理的审批。

### 7.2 库存业务执行类

| 类型编码 | 触发条件 | 责任权限 |
|---|---|---|
| `INV_PURCHASE_QC` | 采购已提交且质检状态待检 | 当前仓库 `inv:purchase:qc` |
| `INV_PURCHASE_RECEIVE` | 采购已提交、有剩余数量且不处于待质检 | 当前仓库 `inv:purchase:receive` |
| `INV_SALES_NOTICE_CREATE` | 销售已提交、仍有未发数量且无有效发货通知 | 销售组织 `inv:deliveryNotice:add` |
| `INV_DELIVERY_EXECUTE` | 发货通知为待发货/发货中且有剩余数量 | 发货仓库 `inv:deliveryNotice:deliver` |
| `INV_TRANSFER_DELIVER` | 调拨为已通过/已锁库/部分发货 | 调出组织 `inv:transfer:deliver` |
| `INV_TRANSFER_RECEIVE` | 调拨批次为待收货 | 调入组织 `inv:transfer:receive` |
| `INV_PURCHASE_RETURN_CONFIRM` | 采购退货已提交 | 当前仓库 `inv:purchaseReturn:confirm` |
| `INV_SALES_RETURN_CONFIRM` | 销售退货已提交 | 所属组织 `inv:salesReturn:confirm` |

待质检采购单不能同时计入待收货。调拨审批看调入或调出组织，发货只看调出组织，收货只看调入组织。

### 7.3 退回修改与重盘类

| 类型编码 | 触发条件 | 责任人 |
|---|---|---|
| `OA_PURCHASE_RETURNED` | OA 采购已驳回 | 原申请人本人 |
| `INV_TRANSFER_RETURNED` | 调拨审批驳回后退回草稿，且存在最近驳回实例 | 原创建人本人 |
| `INV_STOCK_CHECK_RETURNED` | 盘点为 `rejected` | 原提交人本人 |
| `INV_STOCK_CHECK_RESTART` | 盘点为 `invalidated` | 原提交人本人，具备重盘权限 |

普通新草稿不进入待办。第一期必须同时提供明确的退出路径：OA 采购驳回后允许原申请人重新提交或关闭申请，关闭后进入 `cancelled` 终态；调拨和盘点退回后复用现有重新提交与取消能力。不得上线只能产生、无法消除的退回待办。

### 7.4 OA 与个人事项

| 类型编码 | 触发条件 | 责任人 |
|---|---|---|
| `OA_FIXED_ASSET_REPAIR_CONFIRM` | 维修记录为 `pending_confirm` | 当前门店具备确认权限的共享处理池 |
| `OA_LABOR_CONTRACT_SIGN` | 劳动合同为 `pending_sign` | 合同绑定员工本人 |
| `OA_SIGN_PACKAGE_SIGN` | 签约包为 `pending_sign` 或 `part_viewed` | 签约包绑定员工本人 |

`part_viewed` 只表示部分阅读，不能视为签署完成。共享池任务由任一授权人完成后，对其他授权人同步消除。

### 7.5 人事与账号管理提醒

| 类型编码 | 触发条件 | 责任人 |
|---|---|---|
| `HR_PROFILE_INCOMPLETE` | 关键员工资料存在缺失 | 同时具备查看、编辑权限且在组织范围内的人事人员 |
| `HR_ONBOARDING_CONFIRM` | 员工状态为待入职 | 具备入职查看、员工编辑权限的人事人员 |
| `HR_CONTRACT_DUE` | 未离职员工合同在 0–30 天内到期 | 合同/人事管理员，按组织范围 |
| `HR_OFFBOARD_ACCOUNT` | 员工待离职/已离职但账号仍启用 | 人事和具备用户状态编辑权限的管理员 |

高数量的人事事项按组织汇总显示，点击进入已筛选的人员明细。总数必须由后端统计，不能继续使用当前页十条数据计算。

### 7.6 库存风险提醒

| 类型编码 | 触发条件 | 责任人 |
|---|---|---|
| `INV_LOW_STOCK` | 可用库存小于等于安全库存 | 有库存查看权限，且具备补货、采购或库存调整能力的人员 |
| `INV_OUT_OF_STOCK` | 可用库存小于等于零 | 与低库存相同，但优先级为紧急 |

低库存和缺货按“组织 + 严重程度”汇总，点击进入库存预警明细。缺货属于低库存子集，总数不得重复相加。

## 8. 组织范围与权限规则

1. 审批类默认使用“全部授权组织”，但必须匹配本人实际候选任务。
2. 收货、发货、质检、退货、重盘和库存风险默认使用“当前组织”。
3. 统一页面允许在“当前组织”和“全部授权组织”之间切换。
4. 每条待办展示归属组织，防止跨店仓误操作。
5. 没有处理权限的用户不能仅因为具有列表查看权限而收到待办。
6. 权限或候选人变化后，下一次刷新必须立即移除不再属于本人的事项。
7. 前端跳转前再次检查当前路由可见性；路由已不可用时刷新待办并提示权限已变化。

## 9. 分类、优先级与生命周期

### 9.1 页面分类

- 全部
- 待审批
- 待执行
- 退回修改
- 风险提醒
- 个人事项

### 9.2 默认优先级

- 紧急：缺货、合同 7 天内到期、离职账号仍启用、超过 24 小时未处理的审批。
- 重要：普通审批、员工待签、退货确认、库存变化需重盘。
- 普通：收货、发货、质检、资料补充、待入职和低库存。

阈值通过系统配置维护，默认审批升级时限 24 小时、合同预警 30 天、紧急合同 7 天。

### 9.3 消除规则

- 打开待办不改变待办状态。
- 业务状态进入完成、取消、关闭、签署完成等终态后，下一次刷新消除。
- 共享任务由任一授权人处理后，对所有候选人消除。
- 业务被驳回时，审批人待办消除，同时为原申请人生成退回修改待办。
- Provider 失败时保留上一次成功数据并标注为可能过期，不能清零。

## 10. 前端页面设计

### 10.1 电脑端

- 顶部公告铃铛旁新增待办图标，显示未处理总数；超过 99 显示 `99+`。
- 首页“审批流转”卡片显示真实总数和审批、执行、风险三个小计。
- 首页“今日建议”改为最近的高优先级真实待办。
- 新增 `/workbench/todo` 统一页面。
- 旧 `/oa/todo` 保留，跳转统一页面并预选采购审批来源。

### 10.2 手机端

- 工作台顶部增加真实待办角标和入口。
- 新增 `/mobile/todo` 统一页面。
- 不增加第六个底部导航项。
- 公告继续从通知公告入口进入，使用独立未读数。

### 10.3 待办行交互

每条待办展示类型、标题、单号、组织、状态、产生时间、停留时长、优先级和“去处理”按钮。

统一列表只负责发现和跳转，不在同一页面拼装采购、调拨、盘点、收货等不同业务表单。点击后进入原业务详情，业务处理仍使用原服务和原权限。

电脑端通过统一 `todoRouteResolver` 根据待办类型、组织类型和当前可见菜单解析实际路径，避免在组件中散落门店/仓库路径别名。手机端复用既有业务路由和筛选参数。

## 11. 前端状态管理与刷新

新增独立 Vuex Todo Store，保存：

- 总数和各分类数量。
- 各来源最近待办。
- 当前组织和查询范围。
- 各 Provider 的加载、失败和最后成功时间。
- 当前请求锁和下次刷新时间。

刷新时机：

1. 登录并加载完用户权限后。
2. 选择或切换组织后。
3. 每 60 秒自动刷新。
4. 页面从后台恢复可见时立即刷新。
5. 审批、收货、发货、质检、重盘、退货确认、签署等操作成功后。
6. 退出登录时停止定时器并清空状态。

页面隐藏时暂停轮询。上一请求未完成时不得再次发起同类刷新。

汇总接口只返回分类数量和最近少量待办；统一页面按来源和分类调用分页列表。高数量风险项采用汇总行，避免一次性加载全部低库存商品或员工资料。

## 12. 错误处理与降级

- 使用 `Promise.allSettled` 或等价机制并行加载 Provider。
- 单个 Provider 失败时显示“部分待办加载失败”和失败来源。
- 失败来源保留上一次成功数量，并标注更新时间；没有历史数据时显示未知，不显示零。
- 业务处理时若待办已被他人处理，提示“事项已处理”，刷新后移除。
- 跳转目标不存在或权限变化时，不打开空白页，提示后立即刷新。
- 后端列表必须稳定排序：优先级、产生时间、业务 ID。

## 13. 实施顺序

为降低跨模块改造风险，按以下批次实施并在同一次统一待办功能中交付：

1. 建立统一数据契约、Todo Store、电脑/手机入口和路由解析器。
2. 接入库存审批、质检、收发货、退货、重盘和库存风险。
3. 接入 OA 采购审批、固定资产确认、劳动合同和签约包。
4. 接入人事资料、待入职、合同到期和离职账号提醒。
5. 将现有首页、手机工作台和旧待办入口切换到统一数据源。
6. 修复公告“全部已读”错误清零问题并完成全端回归。

## 14. 测试策略

### 14.1 后端

- 每个待办类型测试触发状态和终止状态。
- 测试功能权限、数据范围、候选审批人和本人归属。
- 测试共享任务被任一用户处理后对其他用户消除。
- 测试驳回审批转换为原申请人退回待办。
- 测试待质检采购不重复计入待收货。
- 测试缺货不与低库存重复计数。
- 测试管理员不绕过真实候选人规则。
- 测试人事统计基于完整数据集而非当前分页。

### 14.2 前端

- 测试三类 Provider 汇总、去重、排序和分类。
- 测试单个 Provider 失败时保留其他来源及历史数据。
- 测试登录、组织切换、60 秒轮询、后台恢复和业务完成刷新。
- 测试电脑顶部、电脑首页、待办页和手机工作台数量一致。
- 测试门店/仓库路由解析和权限变化降级。
- 测试公告未读数与业务待办数互不影响。

### 14.3 端到端

- OA 采购、调拨和盘点审批的通过与驳回。
- 采购质检/收货、销售发货、调拨发货/收货和退货确认。
- 盘点失效重盘和驳回重提。
- 固定资产维修确认、劳动合同签署和签约包签署。
- 人事资料补齐、确认入职、合同到期处理和离职账号停用。

## 15. 验收标准

1. 同一账号在电脑顶部、电脑首页、统一待办页和手机工作台看到的总数一致。
2. 用户只能看到自己有权处理且在其组织范围内的事项。
3. 业务处理成功后，相关待办在立即刷新中消失。
4. 驳回事项转为原申请人可处理的退回待办。
5. 当前组织变化时，组织型待办随之变化，跨组织本人审批仍可查看。
6. 任一 Provider 故障不影响其他 Provider，也不会将总数错误清零。
7. 每一种待办均能在电脑端和手机端跳转到正确业务详情。
8. 公告未读数和业务未处理数分别显示、分别清除。
9. 现有采购、调拨、盘点和手机工作台入口保持可用。

## 16. 已知现状修正项

实施时必须同时修正以下问题：

1. 现有手机工作台待审批数只统计调拨，漏掉盘点和 OA 采购。
