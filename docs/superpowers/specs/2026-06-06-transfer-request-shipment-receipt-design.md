# 调拨要货、分批发货与分批收货设计

日期：2026-06-06

## 背景

当前调拨管理已经有调拨单、审批、处理中列表和记录列表，但现有流程更接近“创建调拨时同时指定调出方和调入方”。本轮业务口径调整为门店向仓库要货：门店只提出要货需求，上级只审批是否允许，仓库管理员按审批后的单据发货，门店按每次发货确认收货，确认后才进入门店可售库存。

组织结构需要依赖部门管理中的部门类型来区分公司、店铺和仓库。仓库是集中存放大量货物的地方；店铺不是仓库，只保存马上要售卖的商品库存。仓库管理用于维护仓库主数据，进销存管理用于门店业务流转。

## 目标

- 门店发起要货时只选择要货仓库和商品明细，不手填目标门店。
- 系统根据当前选择的门店上下文确定要货门店。
- 上级审批只负责通过或驳回，不指定发货仓库。
- 审批通过后，由对应仓库管理员处理发货。
- 仓库管理员可以一次全部发货，也可以多次部分发货。
- 门店必须对每次发货确认收货，确认后才增加门店可售库存。
- 最终调拨记录列表整合为一条主记录，进入详情后能看到每次发货和每次收货。
- 未发完、已发未收、部分收货的主单继续留在调拨处理中。

## 非目标

- 不把每次部分发货拆成独立调拨主单。
- 不让审批人在审批时分配发货仓库。
- 不取消门店收货确认。
- 不把店铺当作仓库主数据处理。
- 不重做部门管理，只使用现有部门类型作为判断基础。
- 不重做仓库管理页面，只补足调拨流程对仓库主数据的使用规则。

## 方案比较

### 方案一：每次部分发货生成独立调拨单

这个方案实现简单，但列表会出现多张来源相同的调拨单，不符合“最后整合为一条，详情里看两次发货”的业务要求。后续追踪总需求、剩余数量和审批状态也会变复杂。

### 方案二：主调拨单加发货批次和收货批次

主调拨单保存门店要货总需求；每次仓库发货生成一条发货批次；门店对每条发货批次确认收货。列表最终只展示一条主单，详情展示批次明细。这个方案最符合当前业务口径。

### 方案三：只在明细行上累计发货和收货数量

这个方案表结构少，但无法清楚追溯“第一次发了多少、第二次发了多少、每次谁收货、什么时候收货”。不适合后续审计和问题追踪。

推荐采用方案二。

## 组织与权限语义

- 公司或上级组织：用于管理下属店铺、仓库和审批权限。
- 店铺：用于销售和门店可售库存，不等同于仓库。
- 仓库：集中存储货物，由仓库管理员负责发货。
- 发起要货的人必须在当前门店上下文内有权限。
- 选择要货仓库时，只能选择当前用户可见或业务允许的仓库。
- 上级审批人必须来自审批规则候选人，并遵守当前审批快照。
- 仓库管理员只能看到和操作自己有权限的仓库待发货单。
- 门店人员只能确认自己门店相关的收货批次。

权限校验需要同时关注门店上下文、仓库权限和部门类型，不能只按门店或只按仓库单独判断。

## 主流程

### 1. 门店发起要货

门店用户进入调拨管理，当前门店由系统上下文确定。用户选择要货仓库，填写商品和数量，保存草稿或提交审批。

提交后主单进入“审核中”。主单需要保存：

- 要货门店 ID 和名称。
- 要货仓库 ID 和名称。
- 总要货数量。
- 明细商品、数量。
- 状态、审批实例和提交信息。

### 2. 上级审批

审批人只做通过或驳回。

- 通过：主单进入“待发货”或等价处理中状态。
- 驳回：按审批规则进入草稿、已驳回或关闭。
- 审批时不选择发货仓库，因为发货仓库已经是门店发起时选择的要货仓库。

### 3. 仓库管理员发货

仓库管理员在调拨处理中看到自己仓库下已审批待发货的要货单。发货时可以选择全部剩余数量，也可以填写部分数量。

每次发货生成一个发货批次，记录：

- 发货批次号。
- 主调拨单 ID。
- 仓库 ID。
- 发货人和发货时间。
- 每个商品本次发货数量。
- 本次发货状态：待收货、已收货、部分收货、异常。

发货时扣减仓库库存，但不增加门店可售库存。主单仍留在处理中。

### 4. 门店确认收货

门店人员对每个待收货发货批次确认收货。一次发货对应一次收货确认。

确认收货后：

- 增加门店可售库存。
- 写入门店入库流水。
- 更新发货批次为已收货。
- 更新主单累计已收货数量。

如果发货批次支持差异收货，差异部分需要单独状态；本期可以先要求本次收货数量等于本次发货数量，后续再扩展差异处理。

### 5. 完成与记录

主单只有在“总发货数量等于要货数量，并且所有发货批次都已收货”后，才进入调拨记录。

记录列表显示一条整合后的主调拨记录。点击详情后展示：

- 主单基础信息。
- 要货明细和总数量。
- 每次发货批次。
- 每次收货确认信息。
- 状态流转日志。

未发完、发了未收、部分批次未收的主单继续留在调拨处理中。

## 状态设计

建议主单状态：

| 状态 | 含义 |
| --- | --- |
| `draft` | 草稿 |
| `submitted` | 审核中 |
| `approved` | 已审批，待仓库发货 |
| `partial_delivered` | 已部分发货 |
| `delivered` | 已全部发货，但仍有批次待收货 |
| `partial_received` | 已部分收货 |
| `received` | 全部发货且全部收货，进入记录 |
| `rejected` | 已驳回 |
| `closed` | 已关闭 |
| `cancelled` | 已取消 |

发货批次状态：

| 状态 | 含义 |
| --- | --- |
| `pending_receive` | 已发货，待门店收货 |
| `received` | 门店已确认收货 |
| `abnormal` | 收货异常或差异待处理 |

## 数据模型

保留 `inv_transfer_order` 作为主调拨单。现有 `from_dept_id` / `to_dept_id` 语义需要调整或通过新字段明确：

- 要货门店：店铺部门 ID。
- 要货仓库：仓库部门 ID 或仓库主数据 ID。
- 当前字段若继续复用，必须在代码和页面中统一命名，避免“发货方/目标方”与实际业务含义冲突。

新增或补齐发货批次表：

- `shipment_id`
- `transfer_id`
- `shipment_no`
- `warehouse_id`
- `warehouse_dept_id`
- `status`
- `shipped_by`
- `shipped_time`
- `received_by`
- `received_time`
- `remark`

新增或补齐发货批次明细表：

- `shipment_detail_id`
- `shipment_id`
- `transfer_id`
- `transfer_detail_id`
- `product_id`
- `product_name`
- `planned_quantity`
- `shipped_quantity`
- `received_quantity`

主单明细保留总需求数量，并增加或维护累计字段：

- `requested_quantity`
- `delivered_quantity`
- `received_quantity`

## 页面设计

### 调拨处理中

列表按状态区分处理中单据：

- 草稿。
- 审核中。
- 待发货。
- 部分发货。
- 待收货。
- 部分收货。

按钮按角色和状态显示：

- 门店发起人：保存、提交、取消、查看。
- 审批人：审批通过、驳回。
- 仓库管理员：发货、查看发货历史。
- 门店收货人：确认收货。

### 发起要货弹窗

字段：

- 要货仓库。
- 商品明细。
- 数量。
- 备注。

不显示目标门店选择。当前门店只作为上下文展示或隐藏字段。

### 发货弹窗

展示剩余待发数量。仓库管理员可选择：

- 全部发货。
- 部分发货，逐行输入本次发货数量。

本次发货数量不能超过剩余待发数量，也不能超过仓库可用库存。

### 收货弹窗

按发货批次收货。门店确认后增加门店可售库存。

### 调拨记录

只展示最终完成或归档的主单。详情内展示发货批次和收货批次。

## 后端设计

- 调整保存和提交逻辑：发起时只校验当前门店和所选仓库，不再要求用户选择目标门店。
- 审批逻辑保留快照模式，审批通过只推进主单状态，不分配仓库。
- 增加发货接口：按主单和明细生成发货批次，扣减仓库库存，更新累计发货数量。
- 增加收货接口：按发货批次确认收货，增加门店库存，更新累计收货数量。
- 调整列表查询：处理中包含未完成主单，记录只包含全部完成或归档主单。
- 调整详情接口：返回主单、要货明细、发货批次、批次明细和状态日志。
- 校验部门类型：发起方必须是店铺上下文，要货仓库必须是仓库类型。

## 错误处理

- 未选择门店上下文：提示先选择店铺。
- 所选要货仓库不是仓库类型：拒绝提交。
- 用户无权访问当前门店：拒绝保存和提交。
- 仓库管理员无权访问该仓库：拒绝发货。
- 门店用户无权访问该门店：拒绝收货。
- 发货数量超过剩余数量：拒绝发货。
- 仓库可用库存不足：拒绝发货。
- 收货批次不是待收货状态：拒绝收货。
- 主单状态不允许当前动作：按状态守卫拒绝。

- 后端单测：提交要货不需要手填目标门店。
- 后端单测：审批通过不修改发货仓库，只推进状态。
- 后端单测：部分发货生成发货批次并扣减仓库库存。
- 后端单测：未发完主单继续留在处理中。
- 后端单测：门店确认收货后才增加门店库存。
- 后端单测：两次发货和两次收货后主单进入记录，详情能看到两个批次。
- 权限测试：无仓库权限不能发货，无门店权限不能收货。
- 前端构建：`npm --prefix erp-ui run build:prod`。
- 后端编译或目标测试：`mvn -pl erp-modules/erp-inventory -am test`，必要时先跑目标测试。
- 浏览器验证：调拨处理中、审批、分批发货、分批收货、调拨记录详情。

## 影响范围

- 调拨管理页面。
- 调拨记录页面。
- 调拨 API。
- 调拨主单、明细、状态日志。
- 新增发货批次和批次明细。
- 库存扣减和门店入库流水。
- 部门类型和仓库权限校验。

## 风险与缓解

- 现有字段命名和新业务语义冲突：实现时统一页面文案和后端注释，必要时新增字段避免误用。
- 部门类型数据不完整：实现前检查部门类型字典和现有部门数据，缺失时补 SQL 或校验提示。
- 部分发货导致状态复杂：主单状态只表达总体进度，批次状态表达每次发货和收货。
- 仓库库存与门店库存混用：发货只扣仓库库存，收货才加门店库存。
- 记录列表重复：记录列表按主单展示，批次只在详情展示。
