# 调拨审批进度双端可见设计

## 背景

店铺用户从调拨管理提交要货单后，目前只能看到主单处于“审核中”，无法知道审批已经到哪一级、当前有哪些候选审批人、最终由谁处理，也无法回看驳回原因和历史审批轮次。

审批数据实际上已经写入 `inv_transfer_approval_instance`、`inv_transfer_approval_task` 和 `inv_transfer_status_log`。电脑端调拨详情却只加载主单、明细和发货批次；现有“流程轨迹”也是按主单状态推算的固定业务阶段，不是真实审批轨迹。手机端复用同一个调拨详情接口，因此存在相同缺口。

## 目标

- 发送者在电脑端和手机端都能看到当前审批到哪一级。
- 审批中显示当前节点的候选审批人安全展示名；同级多人时显示全部候选人，并明确通过规则。
- 审批完成或驳回后显示实际处理人、动作、时间和意见。
- 驳回后重新提交时保留全部历史审批轮次。
- 电脑端和手机端共用同一个后端审批轨迹读模型，不维护两套业务逻辑。
- 列表直接提供当前审批摘要，详情提供完整轨迹，同时避免逐行查询造成 N+1。
- 审批轨迹继承调拨详情的数据范围，不能扩大跨店铺可见范围。

## 非目标

- 本次不修改调拨审批人匹配规则、节点推进顺序或驳回策略。
- 本次不把审批、发货、收货和库存流水合并成完整业务审计中心。
- 本次不新增手机端专用审批进度路由，也不复制 `/mobile` 后端接口。
- 本次不要求只有原始发送者本人可见。可见范围与调拨详情一致：具备详情权限且组织范围命中该单的用户都可查看，其中包括发送者。
- 本次不把原始规则快照、用户 ID、任务 ID或岗位编码暴露给前端。

## 已确认产品口径

1. 审批中必须显示“候选审批人”，不能把尚未处理的候选人称为“实际审批人”。
2. 当前节点有多人候选时，详情显示全部安全展示名；列表显示前两人并附总人数，电脑端可悬浮查看全部姓名。
3. 节点处理完成后显示“实际审批人”。
4. 手机端和电脑端的节点状态、人员、时间和意见必须来自同一个后端响应，前端不解析 `rule_snapshot`。
5. 发送者不需要 `inv:transfer:approve` 权限即可查看审批进度。
6. 现有“流程轨迹”改名为“业务履约进度”，与新增的“审批进度”区分。

## 方案选择

### 方案一：只扩展现有调拨详情

把当前审批节点直接嵌入 `GET /inventory/transfer/{transferId}`。改动较少，但列表仍看不到进度，完整历史会让普通详情响应越来越重，审批轨迹也难以独立处理加载失败和权限审计。

### 方案二：列表摘要加独立审批轨迹接口

列表批量附加轻量 `approvalSummary`，详情并行请求独立审批轨迹接口。该方案边界清晰，可复用现有库存盘点 `/approval-track` 模式，并支持电脑端、手机端和调拨记录页共用。

本设计采用方案二。

### 方案三：完整业务事件时间线

把提交、审批、发货、收货、取消和库存变化全部合并为一条事件线。审计能力最完整，但超出“发送者看到审批到哪里”的当前目标，留待后续业务审计中心统一建设。

## 总体架构

后端增加两个只读输出层次：

1. **审批摘要**：随调拨处理中列表和调拨记录列表返回，只描述最新有效轮次的当前结论。
2. **审批轨迹**：通过独立接口返回所有审批轮次、节点状态和处理结果。

前端使用方式：

- 电脑端调拨处理中列表、手机端补货/调拨列表读取审批摘要。
- 电脑端调拨详情、调拨记录详情以及手机端调拨详情读取完整审批轨迹。
- 电脑端详情接口和审批轨迹接口并行加载。轨迹失败时不阻止主单、明细和发货批次展示。
- 手机端详情继续使用现有通用详情 Sheet，在调拨明细之前插入“审批进度”区块。

## 后端读模型

### 审批摘要

调拨列表行增加非持久化字段 `approvalSummary`，建议结构为：

```json
{
  "state": "in_progress",
  "roundNo": 2,
  "currentNodeOrder": 2,
  "totalNodeCount": 4,
  "currentNodeName": "三级负责人",
  "currentCandidateDisplayNames": ["张三", "李四"],
  "currentCandidateCount": 2,
  "completedNodeCount": 1,
  "summaryText": "待三级负责人审批"
}
```

列表服务先完成原有分页和组织范围过滤，再按当前页 `transferId` 集合批量查询最新实例与当前任务并装配摘要。禁止为每一行单独查询审批任务。

摘要状态包括：

- `not_started`：尚未提交审批。
- `in_progress`：当前存在有效审批节点。
- `approved`：审批已通过。
- `rejected`：最近一轮已驳回。
- `auto_approved`：历史兼容数据由系统自动通过且没有人工任务。
- `cancelled`：调拨单取消，审批已终止。
- `partial`：审批实例或任务数据残缺，只能返回部分轨迹。

不返回线性百分比。多节点、或签和会签模式下，百分比容易误导；列表使用“已完成节点数 / 总节点数”。

### 审批轨迹接口

新增：

```text
GET /inventory/transfer/{transferId}/approval-track
```

建议返回：

```json
{
  "transferId": 123,
  "orderNo": "TF202607100001",
  "documentStatus": "submitted",
  "state": "in_progress",
  "traceCompleteness": "complete",
  "summaryText": "当前第 2/4 级，等待三级负责人审批",
  "currentNode": {
    "nodeOrder": 2,
    "nodeName": "三级负责人",
    "candidateDisplayNames": ["张三", "李四"],
    "candidateCount": 2,
    "approvalModeText": "任一人通过即可"
  },
  "rounds": [
    {
      "roundNo": 1,
      "status": "rejected",
      "submittedAt": "2026-07-10T09:00:00+08:00",
      "finishedAt": "2026-07-10T09:20:00+08:00",
      "nodes": []
    },
    {
      "roundNo": 2,
      "status": "in_progress",
      "submittedAt": "2026-07-10T10:00:00+08:00",
      "finishedAt": null,
      "nodes": [
        {
          "nodeOrder": 1,
          "nodeName": "四级负责人",
          "postName": "店长",
          "state": "approved",
          "candidateDisplayNames": ["王店长"],
          "candidateCount": 1,
          "approvalModeText": "任一人通过即可",
          "decision": "approve",
          "actualApproverDisplayName": "王店长",
          "handledAt": "2026-07-10T10:05:00+08:00",

```

响应不包含：

- `candidateUserIds`
- `approverId`
- `taskId`
- `ruleId`
- `postCode`
- 原始 `ruleSnapshot`
- 手机号、邮箱或原始登录账号

### 轮次与节点归一化

按调拨单查询全部审批实例，按实例创建时间和实例 ID升序生成 `roundNo`。不要求新增轮次字段或修改历史数据。

节点状态由后端结合主单状态、实例状态、`currentNodeOrder` 和任务状态计算，前端不得直接展示数据库原始 `pending`：

- `approved`：节点已经完成。
- `current`：运行实例的当前节点。
- `waiting`：运行实例中尚未轮到的后续节点。
- `rejected`：该节点执行了驳回。
- `terminated`：实例已经驳回、关闭或主单已取消，遗留待处理任务无需继续审批。
- `auto_approved`：实例自动通过且没有人工任务。
- `partial`：快照、实例或任务关系不完整。

历史实例中残留的 `pending` 任务不能显示成“正在等待某人审批”。主单已取消时，以取消状态为最高优先级，全部未完成节点显示“审批已终止”。

### 多人候选和审批模式

候选审批人是提交时的任务快照。详情显示全部安全展示名，同时显示后端生成的审批模式文案：

- `any_one`：任一人通过即可。
- `all_posts`：配置岗位全部通过。
- `quorum`：达到配置人数后通过。
- `all_nodes`：所有有效节点依次完成。

展示层只反映审批引擎实际实例和任务状态，不在本功能中改变审批模式算法。若历史配置无法由现有任务表达，返回 `traceCompleteness=partial` 和“审批配置数据异常”，不能伪造已完成进度。

### 自动通过与状态日志

补充状态日志只读查询，识别历史 `auto_approve` 记录并返回自动通过原因和时间。当前审批创建路径通常会产生人工任务，但旧数据和兼容分支仍必须正确显示“系统自动通过”。

## 人员展示与隐私

发送者需要看到具体是谁在处理，但页面展示的是员工安全展示名，不是原始登录标识。

- 当前候选人通过任务中的候选用户 ID在服务端批量解析 `nick_name` 或员工展示名。
- 实际审批人通过 `approverId` 批量解析安全展示名。
- 新产生的任务继续保存候选人展示名快照，保证基本历史可读性。
- 旧任务只有登录账号快照时，优先使用用户 ID解析当前安全展示名；无法解析时显示“姓名未配置”，不直接返回手机号式账号或邮箱。
- 审批意见按纯文本返回和渲染，去除控制字符，并遵守数据库字段长度限制。

## 权限与数据范围

审批轨迹属于调拨详情的一部分，不要求 `inv:transfer:approve`，也不依赖数据库中尚未统一授权的孤立 `inv:transfer:approval:track` 权限。

接口权限沿用：

- `inv:transfer:query`
- 或 `inv:transfer:records:query`

同时必须满足组织范围：当前所选店铺或仓库必须先通过当前用户的可选组织校验，再命中调拨单的调出部门、调入部门、调出仓库或调入仓库之一。

现有调拨详情的 `assertAndGetScopedTransfer` 在检查目标部门前没有先验证请求头中的所选组织确实属于当前用户。实施本功能时必须先把它改为使用 `resolveAndValidateShopDept` 或等价的统一安全校验，并让详情、审批轨迹共用同一授权入口，避免伪造组织请求头扩大可见范围。

店铺发送角色若当前只有 `inv:transfer:list/submit` 而没有 `inv:transfer:query`，上线前必须补齐查询权限。验收时要用真实发送角色验证，而不能只用管理员账号。

审批轨迹响应应设置为不可公开缓存；日志中不得打印候选人 ID列表或完整审批意见。

## 电脑端设计

### 调拨处理中列表

保留主单状态和“当前责任”列，在状态下增加第二行审批摘要：

- `审核中` / `待三级负责人审批`
- `审核中` / `等待张三、李四处理`
- `待发货` / `审批已通过`
- `草稿` / `上轮已驳回，待修改后重新提交`
- `已取消` / `审批已终止`

多人候选时列表最多直接展示两人，完整姓名通过悬浮提示提供。列表摘要必须换行或截断，不能挤压操作列。

### 调拨详情

在主单基本信息之后、要货明细之前增加“审批进度”：

1. 顶部结论条显示轮次、当前级别和当前节点。
2. 使用纵向时间线展示节点。
3. 已完成节点显示实际审批人、时间和意见。
4. 当前节点显示全部候选审批人及审批模式。
5. 后续节点显示“等待前置节点完成”。
6. 历史轮次默认折叠，最新轮次默认展开。
7. 轨迹加载失败时显示独立错误态和重试按钮，不关闭详情弹窗。

新增可复用的 `TransferApprovalProgress` 组件，同时供调拨处理中详情和调拨记录详情使用。

现有固定五阶段区域改名为“业务履约进度”，继续用于提交、审批、发货、收货和归档的高层业务状态，不再承担具体审批人展示。

### 调拨记录

终态记录详情同样加载全部审批轮次，保证已完成、已驳回、已关闭和已取消单据可以回看实际处理人及意见。

## 手机端设计

不新增路由。发送者继续从“补货申请”或“调拨处理”列表进入现有详情 Sheet；`/mobile/transfer-approval` 继续作为审批人待办入口。

### 列表卡片

审核中单据增加一行短摘要：

- `审批中 · 三级负责人 · 张三等2人`
- `审批已通过`
- `上轮已驳回`

### 详情 Sheet

“审批进度”放在调拨明细之前，采用纵向布局：

- 当前节点使用文字和图标双重强调，并设置 `aria-current="step"`。
- 候选人姓名和意见放在可换行区域，状态徽标只放短文本。
- 详情展示全部候选人，不因列表摘要截断而省略。
- 审批进度加载失败时保留主单内容，提供单独重试。
- 发送者没有审批权限时只能查看，不出现通过或驳回按钮。

小屏至少验证 320×568、360×640 和 390px 宽度。长节点名、多人姓名和长意见必须使用 `overflow-wrap:anywhere`，不得产生横向滚动；交互目标保持至少 44px。

## 错误处理与兼容性

- 草稿且没有实例：显示“尚未提交审批”。
- 运行实例缺少当前任务：显示“审批数据异常，请联系管理员”，不猜测审批人。
- 实例、任务或快照关系不完整：返回 `traceCompleteness=partial`，已确认的历史仍可展示。
- 轨迹接口返回 403：页面显示“无权查看该调拨单审批进度”，不得把它解释成“暂无审批记录”。
- 网络失败：保留主单详情并允许单独重试轨迹。
- 快速切换不同调拨单：取消旧请求或核对 `transferId`，不能把上一单轨迹显示到下一单。
- 已取消单据存在运行实例或待处理任务：展示层统一归为“审批已终止”。底层取消实例和清理幽灵待办属于审批一致性修复，可在实施时一并补齐，但不能阻塞只读轨迹正确显示。

## 测试策略

### 后端

- 草稿无实例返回 `not_started`。
- 多级审批正确返回已完成、当前和后续节点。
- 当前多人候选返回全部安全展示名和正确人数。
- 实际通过和驳回返回操作人、动作、时间和意见。
- 驳回回草稿后重新提交生成多轮历史，最新轮次为当前轮次。
- 自动通过且无人工任务返回 `auto_approved`。
- 已结束实例中的残留 `pending` 返回 `terminated`，不是 `current`。
- 主单取消优先于运行实例状态。
- 缺失实例、孤儿任务、损坏快照返回 `partial`。
- 当前页审批摘要使用批量查询，不产生每单一次查询。
- 伪造所选组织、越权店铺和不匹配调入/调出范围均被拒绝。
- DTO不包含用户 ID、任务 ID、岗位编码和原始规则快照。
- 手机号式账号和邮箱不会作为人员展示名下发。

### 电脑端

- 列表显示当前节点摘要，非审批状态保留正确业务责任人。
- 详情按真实节点渲染通过、当前、等待、驳回、终止和自动通过。
- 多轮审批最新展开、历史折叠。
- 轨迹失败不影响主单和发货批次展示。
- 调拨处理中页与调拨记录页使用同一组件。
- 列表不会逐行请求审批轨迹。

### 手机端

- `replenishment`、`transfer`、`transferApproval` 和 `transferRecords` 详情都能映射审批轨迹。
- 发送者详情只读，审批人待办仍保留原有动作。
- 审批区块排在调拨明细之前。
- 姓名、节点和意见在小屏正确换行，状态不只靠颜色表达。
- 加载、无数据、无权限、部分数据和网络失败分别显示明确状态。

### 真实角色验收

至少使用以下账号类型完成端到端验证：

1. 店铺普通发送者：提交后能在电脑和手机看到当前审批节点和候选人。
2. 当前节点候选审批人：处理前后发送者页面及时反映实际审批人和时间。
3. 同店铺有详情权限但不是发送者的用户：按详情范围看到同一轨迹。
4. 其他店铺用户：无法通过直接 URL 或伪造组织请求头查看轨迹。
5. 管理员：可以在明确组织上下文中查看，但不能绕过轨迹数据一致性检查。

## 验收标准

- 店铺发送者在电脑端和手机端无需审批权限即可看到审批到哪一级。
- 当前节点展示全部候选审批人安全展示名，并准确区分候选人与实际处理人。
- 审批通过、驳回、重新提交、自动通过和取消场景均有正确文案和轨迹。
- 调拨记录能够回看历史审批轮次、实际审批人、时间和意见。
- 两端使用同一后端轨迹响应，节点状态不由前端猜测。
- 列表摘要批量加载，详情轨迹独立加载且失败不影响主单。
- 调拨详情和审批轨迹均先校验用户的真实组织授权，不存在伪造所选店铺越权读取。
- 响应不包含内部 ID、原始规则 JSON或手机号式登录标识。
- 自动化测试和真实角色双端验收全部通过后才能上线。
