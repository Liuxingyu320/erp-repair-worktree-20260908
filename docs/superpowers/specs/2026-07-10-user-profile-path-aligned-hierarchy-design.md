# 用户档案组织层级真实路径对齐设计

## 背景

用户档案当前已经能够根据归属部门实时派生所属公司、1–3 级部门、4 级门店和部门主管，但现有算法存在两个与真实组织数据不一致的问题：

- 它从公司向下依次填充 1、2、3 级部门，无法保证门店直接上级固定显示为 3 级部门。
- 它把路径中距离用户最近的 `COMPANY` 节点当作所属公司；现有员工导入逻辑会把“浙江区域”“浙江一区”等中间节点也标记为 `COMPANY`，因此不能只依赖中间节点类型判断层级。

真实路径示例为：

```text
金英灵韵集团 → 金英灵韵 → 浙江区域 → 浙江一区 → 杭州柏悦
```

期望派生结果为：

| 字段 | 结果 |
| --- | --- |
| 所属公司 | 金英灵韵 |
| 1 级部门 | 空 |
| 2 级部门 | 浙江区域 |
| 3 级部门 | 浙江一区 |
| 4 级门店 | 杭州柏悦 |
| 部门主管 | 浙江区域节点配置的负责人 |

前端把空值显示为 `-`，后端不把横线作为数据返回或保存。

## 目标

- 以 `sys_dept` 的真实父子路径为主要依据，不根据部门名称猜测层级。
- 门店路径从门店向上倒排，保证门店直接上级落在 3 级部门。
- 非门店路径继续从所属公司向下正向排列。
- 所属公司和部门主管按管理路径位置识别，不受中间节点错误标记为 `COMPANY` 的影响。
- 列表、详情、导出和编辑预览继续复用同一套派生算法。
- 不迁移现有组织类型，不改变审批、库存、权限或员工导入对组织树的使用。

## 方案比较

### 方案一：真实路径锚点匹配

以路径中的 `GROUP`、其下第一个业务节点和最近的 `STORE` 为锚点，再按相对位置映射部门层级。中间节点即使标记为 `COMPANY`，也按其在路径中的位置作为部门层处理。

优点是直接兼容当前数据，不需要迁移组织类型，计算结果与用户看到的真实路径一致。缺点是必须严格校验父子路径。

### 方案二：先清洗组织类型

把区域、分区等中间节点统一迁移为普通部门类型，再继续按节点类型计算。

该方案的数据语义更整洁，但会影响现有组织授权、审批、库存和导入逻辑，迁移风险超出本次用户档案优化范围。

### 方案三：节点类型优先、路径位置兜底

正常时按类型计算，类型冲突时再按位置回退。

该方案兼容面较广，但同一条路径可能因类型变化产生不同结果，规则难以解释和测试。

### 结论

采用方案一。真实父子路径是本功能的唯一层级依据；节点类型只用于识别 `GROUP`、`STORE` 和 `WAREHOUSE` 等结构锚点，不再用“最近的 `COMPANY`”判断所属公司。

## 路径解析

### 构造路径

1. 根据用户的 `deptId` 获取当前归属部门。
2. 根据 `ancestors` 按从根到当前节点的顺序加载所有祖先。
3. 校验路径中每个节点存在、启用，且其 `parentId` 等于前一个节点的 `deptId`。
4. 任一校验失败时停止组织字段派生，返回“组织结构待修复”警告。

本文所称“有效业务节点”是路径中类型不为 `GROUP`、`STORE` 或 `WAREHOUSE` 的有效节点。`COMPANY` 类型可以成为有效业务节点：`GROUP` 后的第一个此类节点作为所属公司；它之后的同类型节点则按真实路径位置作为部门层节点。

### 识别所属公司

1. 在路径中定位距离当前节点最近且能够包住当前业务路径的 `GROUP` 节点。
2. 取该 `GROUP` 之后沿当前路径的第一个有效业务节点作为所属公司；如果 `GROUP` 后直接连接 `STORE` 或 `WAREHOUSE`，不把它误认成公司。
3. 不再向下搜索“最近的 `COMPANY`”，因此“浙江区域”“浙江一区”即使被标记为 `COMPANY`，也不会覆盖“金英灵韵”。
4. 路径中没有 `GROUP` 或 `GROUP` 后没有业务节点时，所属公司及部门层级留空，并返回“无法识别所属公司”警告。

`GROUP` 自身不占用所属公司或部门层级。

### 识别门店

从当前节点向上查找最近的有效 `STORE` 节点，将其作为 4 级门店。当前节点位于门店下属节点时，同样使用该祖先门店。

如果路径中没有 `STORE`，该用户按非门店人员规则处理，不把普通叶子节点按名称猜测为门店，也不因缺少门店单独报错。

`WAREHOUSE` 不作为门店或普通部门层级。

## 层级映射

### 门店人员：从门店向上倒排

取所属公司与门店之间的所有有效业务节点。除了已经确定的所属公司外，即使这些节点的 `deptType` 是 `COMPANY`，仍按普通部门层参与映射。

从门店父节点开始向上排列：

- 最近的节点映射为 3 级部门。
- 再上一级映射为 2 级部门。
- 再上一级映射为 1 级部门。
- 层级不足时从 1 级方向留空，不把后续层级向前移动。

示例：

```text
公司 → 浙江区域 → 浙江一区 → 杭州柏悦
```

映射为 1 级空、2 级浙江区域、3 级浙江一区、4 级杭州柏悦。

当公司与门店之间超过三个部门节点时，仍显示距离门店最近的三个节点，保证门店直接上级始终是 3 级部门；同时返回“组织层级超过系统定义”警告，但不阻断用户查询或保存。

### 非门店人员：从公司向下正排

路径中没有 `STORE` 时，取所属公司之后到当前归属部门之间的有效业务节点：

- 第一个节点映射为 1 级部门。
- 第二个节点映射为 2 级部门。
- 第三个节点映射为 3 级部门。
- 不填写 4 级门店。

超过三个部门节点时显示前三个节点，并返回“组织层级超过系统定义”警告。

## 部门主管

部门主管表示“所属公司向下一级的最高部门负责人”，不表示距离员工最近的负责人。

计算规则为：

1. 从所属公司开始，取沿当前用户路径向下的第一个部门层节点。
2. 直接读取该节点的 `leader` 作为部门主管。
3. 不继续向门店方向寻找其他负责人，也不回退使用公司负责人。
4. 如果公司下面没有部门层节点，或该节点未配置 `leader`，部门主管留空并返回“未配置部门负责人”警告。

在示例路径中，无论“浙江区域”最终显示为 1 级还是 2 级部门，部门主管始终取浙江区域节点配置的负责人。

## 数据流与组件边界

现有用户档案派生服务继续作为唯一实现位置，但内部职责拆分为三个独立步骤：

- 路径解析器：加载并验证真实祖先路径。
- 组织锚点与层级映射器：识别所属公司、门店及 1–3 级部门。
- 部门主管解析器：识别公司下一级部门并读取其负责人。

编辑页面在归属部门变化后继续调用只读预览接口。用户列表、用户详情和导出在返回前继续调用同一派生服务。前端不复制路径算法，只展示后端结果和警告。

自动字段继续保持只读且不写入 `sys_user_profile` 的冗余列。组织改名、移动用户或调整负责人后，下次读取自动反映最新组织数据。

## 异常处理

| 场景 | 结果 |
| --- | --- |
| 归属部门不存在、停用或路径断裂 | 组织派生字段留空，提示“组织结构待修复” |
| 无法定位集团或所属公司 | 组织派生字段留空，提示“无法识别所属公司” |
| 无门店节点 | 按非门店规则计算，不提示门店异常 |
| 部门层级超过三个 | 按已确认方向显示三个节点，提示“组织层级超过系统定义” |
| 公司下一级部门或其负责人缺失 | 部门主管留空，提示“未配置部门负责人” |
| 快速切换归属部门 | 前端丢弃过期预览响应，只采用最后一次请求结果 |

警告只用于提示组织管理员，不阻断正常查询。保存时对所选归属部门不存在、停用或越权的情况继续使用现有校验阻断请求。

## 测试设计

### 核心路径

- `金英灵韵集团 → 金英灵韵 → 浙江区域 → 浙江一区 → 杭州柏悦` 输出所属公司“金英灵韵”、1 级空、2 级“浙江区域”、3 级“浙江一区”、门店“杭州柏悦”。
- “浙江区域”和“浙江一区”均标记为 `COMPANY` 时，结果保持不变。
- 公司与门店之间分别有零个、一个、两个和三个部门节点时，从 3 级方向正确对齐。
- 公司与门店之间超过三个部门节点时，输出最近三个节点并返回层级告警。
- 用户归属门店下属节点时，仍使用最近的祖先 `STORE` 作为门店。

### 非门店路径

- 公司直属用户不生成部门层级或门店。
- 公司下区域、分区等非门店用户按公司向下顺序填入 1–3 级部门。
- 普通叶子节点不按名称误判为门店。

### 部门主管

- 门店路径固定取所属公司下第一个部门节点的 `leader`。
- 中间更近的节点和门店即使配置了 `leader`，也不会覆盖部门主管。
- 公司下一级部门缺失或未配置负责人时返回对应警告。

### 一致性与边界

- 列表、详情、导出和预览对同一用户输出相同结果。
- 组织改名、移动用户或修改负责人后，无需修改档案即可得到新结果。
- 伪造请求中的所属公司、部门层级、门店或部门主管仍不会写入数据库。
- 停用节点、错误 `ancestors`、错误 `parentId` 和缺失集团分别返回预期警告。
- 前端空值显示 `-`，提交载荷不包含作为数据的横线。

## 验收标准

- 真实示例路径得到已确认的六个组织字段结果。
- 门店直接上级始终显示在 3 级部门。
- 中间节点错误标记为 `COMPANY` 不影响所属公司识别。
- 非门店用户保持公司向下正向排列。
- 部门主管固定取公司下一级部门负责人。
- 超层级、路径异常和负责人缺失均有明确且稳定的警告。
- 现有审批、库存、权限、员工导入和组织类型数据不发生变化。

## 非目标

- 本次不批量修改 `sys_dept.dept_type`。
- 不修改员工导入脚本对组织节点的创建方式。
- 不改变审批、库存或数据权限对组织树的解释。
- 不根据节点名称中的“区域”“门店”等文字猜测类型或层级。
- 不新增组织层级配置表或删除用户档案历史冗余列。
