# 统一待办 OA 采购审批导航修复设计

## 背景

统一待办中心 `/workbench/todo` 负责聚合和分发，业务页面负责实际处理。当前 `OA_PURCHASE_APPROVAL` 指向依赖后台菜单注册的 `/oa/todo`；后台菜单移除旧待办入口后，导航预检无法确认该路由，因而返回 `route_missing`。OA 页面本身已经具备 `process=1`、`purchaseId` 聚焦模式，但缺少不依赖菜单的固定处理路由。

## 架构原则

- `/workbench/todo` 是唯一统一待办发现入口。
- 每种待办通过路由矩阵声明桌面/移动处理路由、组织约束和固定参数。
- 处理路由必须由前端固定注册或由已授权动态路由注册，不能依赖已废弃菜单。
- 业务页面消费标准参数 `todoType`、`businessId`，并可消费业务专用 ID 与处理模式。
- 业务处理完成后使统一待办缓存失效并刷新摘要。

## 实现方案

新增固定隐藏路由 `/oa/todo/process`，复用现有 OA 审批组件。将 `OA_PURCHASE_APPROVAL` 的桌面处理契约改为该路由，并继续生成 `process=1`、`purchaseId`、`todoType`、`businessId`。普通访问旧 `/oa/todo` 仍跳往统一待办；处理路由则进入聚焦审批模式。

OA 审批成功后调用 `todo/invalidateAfterMutation`，清理统一待办列表缓存并刷新摘要，再重新加载 OA 当前列表。刷新失败不覆盖已经成功的审批结果。

通用移动业务页统一消费 `todoBusinessFocus` 契约：按业务 ID 查询并匹配精确行，重新读取详情后再判断动作和调拨 shipment，只打开目标业务页已经暴露的动作。详情读取失败、目标消失或动作不可用时统一报告“事项已处理”并刷新待办，不回退到第一行或其他 shipment。桌面固定资产确认同样复用共享聚焦 mixin，并在写操作前重新读取精确详情。

## 防重复与错误语义

统一待办页面保留单一 `openTodo` 入口，按钮阻止事件冒泡。导航器对一次调用只执行一次失败报告；路由缺失、权限变化和组织不符继续保留独立原因。处理中的按钮状态防止重复提交审批。

## 测试

1. 路由契约：OA 采购审批解析为固定 `/oa/todo/process`，并携带标准参数。
2. 注册契约：固定路由集合始终包含 OA 处理路由，不依赖后台菜单。
3. 页面契约：普通模式跳统一待办，处理模式聚焦对应采购单。
4. 完成契约：审批成功后使统一待办失效并刷新，同时重新加载业务列表。
5. 导航失败：单次调用只显示一次错误并刷新一次摘要。
6. 运行统一待办相关测试、完整前端测试和生产构建。
7. 通用移动页覆盖精确行、详情后 shipment 校验、退回调拨编辑动作及同步异常隔离。

## 非目标

- 不恢复旧 OA 待办作为第二个发现入口。
- 不修改 OA 审批后端接口。
- 不改造统一待办视觉样式。
- 不处理仓库已有的 jar、推送、数据库脚本或 Git 引用改动。
