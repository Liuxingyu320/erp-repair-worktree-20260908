# 手机端分阶段全量整改设计

日期：2026-07-10
状态：方案已确认，待书面评审

## 1. 背景与决策

2026-07-10 手机端综合审计确认：当前登录、组织选择、门店/仓库工作台及主要业务列表基本可用，但存在跨路由页面状态错乱、公告存储型 XSS、前端私钥文件、客户为空时无法继续销售开单、测试数据污染、个人资料功能不完整及多项移动体验问题。

本设计依据以下审计结果：

- `docs/mobile-audit-20260710.md`
- `docs/mobile-security-best-practices-report-20260710.md`
- `docs/audit-screenshots/mobile-audit-20260710/`

方案选择为 **B：分阶段全量整改**。所有确认的问题都进入整改范围，但按风险拆成独立发布批次，每批可单独验证、灰度和回滚。

用户明确不需要扫码能力。因此本设计不接入摄像头、扫码插件、条码识别或扫码枪适配；现有无实现能力的“扫码”按钮与占位提示将移除，商品继续通过名称、编码或条码文本搜索选择。

## 2. 目标

- 消除手机端路由切换卡死、地址与页面不一致、跨模块状态串用的问题。
- 修复公告 XSS 和前端私钥两个高风险发布阻断项。
- 让无客户资料的新门店可以在手机端完成销售开单。
- 补齐手机端个人资料与修改密码流程，不再跳转桌面页面。
- 清理或隔离 QA 数据，并建立测试数据不会再次污染业务环境的机制。
- 优化首屏信息层级、表单操作区、空状态、组织切换语义与移动端可访问性。
- 分阶段完成认证 Cookie、重复提交缓存和安全响应头加固。
- 建立覆盖路由、权限、真实写流程、移动视口和安全门禁的发布标准。

## 3. 非目标

- 不实现任何扫码功能；不把扫码作为验收或发布门槛。
- 不在本轮重写整个移动端或桌面端 ERP。
- 不在功能整改版本中同步完成 Vue 3 全量迁移；Vue 2 升级作为后续独立工程。
- 不改变现有门店、仓库和公司组织模型。
- 不绕过后端现有的组织范围和业务权限校验。
- 不自动删除无法确认归属的生产数据；生产数据删除必须经过清单评审和单独执行确认。
- 不以 CSP 代替输入净化，也不以客户端校验代替服务端授权。

## 5. 总体架构

整改保持现有 Vue 2、移动路由定义、业务 API 和后端权限体系，围绕五个明确边界实施：

1. **路由生命周期边界**：路由变化负责关闭临时界面、重建功能状态、启动新请求，不直接移动组件 DOM。
2. **功能状态边界**：标题、搜索字段、查询条件、分页、列表和操作配置全部由当前 `featureKey` 决定。
3. **业务补救边界**：客户选择器负责“选择或快速创建”，销售表单只接收最终客户值并保存草稿状态。
4. **安全边界**：富文本、凭证、重复提交信息和响应头由各自独立模块处理，禁止在通用页面中散落临时补丁。
5. **发布边界**：R1-R4 每阶段独立构建、测试、灰度和回滚；前一阶段未通过门禁时不得继续生产发布。

## 6. R1：流程稳定与高风险安全修复

### 6.1 弹层所有权与滚动锁定

`mobileOverlayStack.js` 不再接收或移动 DOM 元素。弹层节点始终留在 `MobileFeaturePage` 及其子组件的 Vue 管理树内，通过已有遮罩层和 `position: fixed` 覆盖视口。

该工具只保留以下职责：

- 记录弹层锁的引用计数或唯一标识。
- 第一个弹层打开时保存滚动位置并锁定 `body`。
- 最后一个弹层关闭时恢复 body 样式和滚动位置。
- 页面销毁、路由离开和异常清理时提供幂等的全量释放。

禁止继续使用 `document.body.appendChild` 对 Vue 管理节点重新挂载。重复释放和异常销毁不得抛错，也不得遗留 `mobile-overlay-open` 等 body class。

### 6.2 路由状态重建

`MobileFeaturePage` 把一次路由变化视为原子切换：

1. 如果表单有未保存内容，先执行现有离开确认。
2. 确认离开后关闭表单、详情、选择器和确认弹层。
3. 清理上一个功能的查询、分页、选中项、加载状态和错误状态。
4. 从目标路由重新计算 `featureKey` 和完整功能配置。
5. 使用新配置生成默认查询和搜索控件。
6. 启动新功能的数据请求。

每次数据加载生成递增的请求版本号。响应只在“版本号与 `featureKey` 都仍匹配”时写回页面；旧路由的迟到响应直接丢弃，避免销售结果覆盖库存页面。

移动功能页的组件 key 使用标准化后的移动路由身份；仅对 `/mobile/*` 功能页生效，不让桌面路由无条件重挂载。该 key 是隔离保护，不替代正确的状态清理。

### 6.3 路由异常处理

- 路由切换失败时显示“页面切换失败，请重试”，不保留“新 URL + 旧页面”的假成功状态。
- 加载失败保留当前路由和搜索条件，提供明确重试操作。
- 未保存表单在网络失败或业务校验失败时保持原值。
- 所有路由回归测试同时监听未处理 Promise、Vue error handler 和浏览器 console error。

### 6.4 公告富文本净化

公告采用双层防护：

- `SysNoticeServiceImpl` 在新增和修改公告前调用统一的服务端富文本净化器。
- 允许的内容限定为业务排版所需标签和安全属性；脚本标签、事件属性、危险协议、iframe、object 和外部执行内容全部删除。
- 历史公告在读取展示时仍走净化，避免只保护新数据。
- `HeaderNotice/DetailView.vue` 在唯一 `v-html` 入口使用经过审计的前端净化封装。
- 净化器异常时按纯文本展示，不回退到原始 HTML。

测试至少覆盖 `<script>`、`onerror`、`javascript:` URL、SVG 事件、畸形标签、允许的列表/链接/加粗格式和历史脏数据。

### 6.5 私钥与密码安全门禁

- 删除 `erp-ui/src/utils/jsencrypt.js`，不得复制或记录其中的私钥内容。
- 保留并加强 `authSecurityHardening.test.js`，禁止前端目录出现私钥、`setPrivateKey` 或可逆保存密码的实现。
- CI 增加秘密扫描；测试命中时阻止合并和生产构建。
- 密码只通过 TLS 传输给服务端并使用服务端密码哈希，不设计“前端持有私钥”的替代方案。

### 6.6 重复提交保护

现有 `sessionStorage` 完整负载缓存改为页面内存中的短期请求指纹：

- 指纹包含 method、规范化 URL、不可逆 payload 摘要和时间。
- 不保存原始负载，不写 localStorage、sessionStorage 或 Cookie。
- 请求结束或窗口过期后清除。
- 登录、解锁、修改密码、上传文件和明确标记的敏感接口强制跳过通用指纹缓存，使用按钮 loading 或接口幂等机制。
- 页面刷新后丢失指纹是可接受行为；服务端关键写操作仍需依赖业务幂等和事务约束。

## 7. R2：核心业务完整性

### 7.1 销售表单内快速新建客户

客户选择器空状态根据权限显示不同动作：

- 拥有 `inv:customer:add`：显示“新建客户”。
- 只有查询权限：提示“当前门店暂无客户，请联系有权限人员新增”，并保留表单草稿。
- 请求失败：显示失败原因和“重新加载”，不把失败误报为无数据。

快速新建客户采用独立轻量表单，复用现有客户新增 API 和服务端校验。首版字段为客户名称、联系人、联系电话；客户编码等字段继续服从现有服务端默认值或既有必填规则，不另造第二套客户模型。

数据流如下：

1. 销售表单把当前草稿保留在父组件状态。
2. 客户选择器打开快速新建层。
3. 创建成功后把新客户插入选择项并自动选中。
4. 关闭选择器，销售商品、数量、价格、日期和备注保持不变。
5. 创建失败时保留客户输入和销售草稿，允许修正或重试。

### 7.2 移除无实现的扫码入口

- 从 `MobileEntityPicker.vue` 和 `MobileLineItemsEditor.vue` 移除“扫码”按钮、环境不支持提示及无效处理函数。
- 保留商品名称、商品编码和条码文本搜索。
- 不新增摄像头权限、原生插件、浏览器媒体能力或扫码测试。

### 7.3 手机端个人资料

手机端新增资料编辑、头像上传和修改密码入口，复用：

- `getUserProfile`
- `updateUserProfile`
- `uploadAvatar`
- `updateUserPwd`

资料编辑只允许修改现有后端允许的本人字段，不提供角色、部门、门店权限等管理能力。手机号和邮箱沿用服务端唯一性与格式校验；头像上传沿用文件类型和大小限制。

`passwordResetReminder.js` 根据移动视口返回 `/mobile/profile?mode=reset-password`。强制修改密码时直接打开移动密码表单；成功后清理提醒状态，失败时保留当前页面和错误信息。

### 7.4 组织选择语义

手机端按钮“进入工作台”的行为固定为：

- 选择门店后进入门店工作台。
- 选择仓库后进入仓库工作台。
- 不因来源页面的 `redirect` 返回个人资料或其他二级页。

如果业务需要“切换后返回原页面”，必须使用文案明确的另一入口“切换并返回”，不复用“进入工作台”按钮。失效、桌面端或无权限 redirect 一律回退到对应手机工作台。

### 7.5 QA 数据治理

上线前先运行只读审计，按可识别前缀、创建账号、创建时间、测试运行 ID、关联业务单据和组织范围生成清单。

处理顺序：

1. 导出清单和关联关系并备份。
2. 能确认的测试租户或测试组织数据先隔离。
3. 经过评审的数据使用事务化脚本按依赖顺序清理。
4. 无法确认归属的数据保留并标记，不自动删除。
5. 清理后复跑审计和业务数量校验。

后续自动化测试必须使用独立数据库、独立租户或明确测试组织，并给每次运行写入唯一 run ID；测试结束执行清理，清理失败触发告警。生产环境测试默认禁止真实写入，确需验证时使用专门白名单数据并限时回收。

## 8. R3：移动体验与可访问性

### 8.1 首屏信息层级

- 工作页面优先展示当前待办、关键筛选和第一条业务数据。
- 高频快捷动作最多保留 4 个。
- 导出、退货入口、配置等低频动作进入“更多”。
- 390×844 首屏应能看到至少一条列表记录或清晰空状态；320×568 不要求完整记录，但必须能看到列表标题和状态。
- 空状态必须区分“确实无数据、筛选无结果、加载失败、无权限”，并给出对应动作。

### 8.2 表单操作区

- “保存并提交”或当前业务的最终动作作为唯一主按钮。
- “保存草稿”作为次按钮。
- “取消”使用弱按钮或文字动作。
- 底部操作区含安全区总高度目标不超过 112px。
- 错误摘要显示在操作区上方，并可将焦点移动到第一个错误字段。
- 键盘弹起时操作区不得遮挡当前输入框和最后一个字段。

### 8.3 语义与键盘操作

- 可打开详情的列表卡改为真实 `button` 或 `a`；内部存在独立操作时使用合理的嵌套结构，禁止交互控件嵌套。
- 所有表单字段使用可见 `label` 或等价 ARIA 关联，必填状态对读屏可感知。
- 弹层打开后焦点进入弹层，Tab 不逃逸；关闭后回到触发控件。
- 加载、保存成功和错误消息使用合适的 `aria-live`，避免只靠颜色表达状态。
- 登录验证码刷新改为按钮，图片提供用途说明；账号使用 `autocomplete="username"`，密码使用 `current-password` 或 `new-password`。

### 8.4 视觉和响应式

- 正文和次级文字达到可读对比度，重要状态不使用过浅灰色。
- 减少 12px 密集正文；允许系统字体放大后自然换行。
- 触控目标保持至少约 44×44px。
- 英雄卡和组织说明在 320px、390px 下不发生信息重叠。
- 保持现有无横向滚动的优点，并覆盖 iPhone 安全区。

## 9. R4：认证与部署安全

### 9.1 HttpOnly Cookie 迁移

认证迁移必须使用兼容灰度，不直接一次切断现有 Bearer Token：

1. 后端登录成功时可在功能开关下同时设置 `Secure; HttpOnly; SameSite=Lax; Path=/` 会话 Cookie。
2. 网关在灰度期同时接受新 Cookie 和现有 Authorization Header，并记录使用比例和失败原因。
3. Web、Android WebView 和 iOS WebView 均验证登录、刷新、退出、过期、切换组织和冷启动。
4. 状态变更请求增加 Origin/Referer 校验，并按部署形态补充 CSRF Token；验证通过前不关闭旧模式。
5. 前端切换到 Cookie 模式后不再保存或读取原始访问令牌。
6. 灰度稳定后关闭 Header 模式，退出登录由后端清除 Cookie。

若原生壳的域名或 Cookie 策略不兼容，R4 不得带病强制上线，应保留旧模式并先解决同源和 Cookie 持久化问题。

### 9.2 安全响应头

生产边缘实际响应先做基线检查，避免仓库配置与线上代理不一致。随后分两步发布：

- 第一步：加入 `Content-Security-Policy-Report-Only`，收集真实脚本、样式、图片、API、WebSocket 和字体来源。
- 第二步：修正违规来源后启用强制 CSP，并同时设置 `X-Content-Type-Options`、`Referrer-Policy`、`Permissions-Policy` 和 `frame-ancestors`。

HSTS 只在确认整个域名及子域均稳定使用 HTTPS 后启用。CSP 不允许为了快速通过而无限期保留宽泛通配符或不必要的脚本例外。

## 10. 错误处理原则

- **路由错误**：不允许 URL 与可见模块不一致；回退到稳定页面并提示重试。
- **并发请求**：旧请求不得覆盖新路由；按钮和分页需要防重复触发。
- **表单错误**：业务校验错误显示在字段旁和顶部摘要，草稿不丢失。
- **权限错误**：说明缺少的业务能力，隐藏不可执行动作，但不把权限错误显示成“暂无数据”。
- **网络错误**：保留用户输入和筛选条件，提供重试；禁止自动重复提交写请求。
- **安全净化错误**：富文本降级为纯文本，绝不展示未经处理的原始 HTML。
- **数据清理错误**：事务回滚，保留审计日志和备份，不继续处理后续批次。
- **认证灰度错误**：按开关回退旧模式并记录指标，不要求用户清除浏览器数据自救。

## 11. 测试设计

### 11.1 自动化测试

- 单元测试：overlay 锁幂等、feature 状态重置、迟到响应丢弃、redirect 规范化、请求指纹、权限分支和富文本净化。
- 组件测试：客户空状态、快速新建并回填、资料编辑、移动密码表单、表单 footer、语义标签和验证码刷新。
- 后端测试：公告新增/修改/历史读取净化，客户新增权限，认证 Cookie 生命周期、CSRF/Origin 校验和退出清理。
- 安全测试：私钥/密码持久化门禁、XSS payload、敏感 payload 不进入浏览器存储、安全响应头。
- 浏览器回归：390×844 与 320×568 的主流程和截图对比。

### 11.2 必测路由场景

核心 P0 回归固定为：

```text
销售 → 新建 → 添加商品 → 取消 → 放弃修改
→ 库存 → 销售退货 → 出库 → 采购
```

连续执行 50 次跨模块切换，必须满足：

- URL、标题、搜索字段、快捷动作和列表内容属于同一 `featureKey`。
- 无 `insertBefore`、Vue patch、未处理 Promise 或 console error。
- body 不遗留滚动锁和弹层 class。
- 迟到请求不改变当前页面。

### 11.3 角色与环境

- 门店普通用户、门店有客户新增权限用户、仓库用户、管理员和无业务权限用户。
- Web 手机浏览器、Android WebView、iOS WebView。
- 正常网络、慢速网络、请求超时、接口 401/403/500、系统返回键、键盘顶起和字体放大。
- 所有会写数据的自动化用例只在隔离测试数据源运行。

## 12. 发布顺序、门禁与回滚

| 发布 | 内容 | 预计人日 | 回滚单位 |
| --- | --- | ---: | --- |
| R1 | 路由稳定、公告净化、私钥清除、内存防重复 | 3～5 | 前端包 + system 服务 |
| R2 | 客户补建、移除扫码入口、个人资料、组织跳转、QA 治理 | 4～7 | 前端包 + 数据治理脚本 |
| R3 | 首屏、表单操作区、无障碍和响应式 | 3～5 | 前端包 |

预计总量为 14～25 人日。前后端与测试并行时，主要整改约需 2～3 周；R1 可以先独立发布。

每阶段上线前必须满足：

- `npm run build:prod` 通过。
- 前端测试全部通过，当前安全测试从 87 项中 1 项失败恢复为全绿，并包含新增回归。
- 生产依赖保持 0 个中危、高危和严重漏洞。
- 对应阶段的浏览器和服务端测试通过。
- 手机路由矩阵没有未处理异常和状态串页。
- 320×568、390×844 截图回归通过。

回滚时只回滚当前发布单元，不回滚已经确认的数据修复。数据清理脚本必须同时提供备份与恢复方案；认证和安全头通过配置开关回退。
