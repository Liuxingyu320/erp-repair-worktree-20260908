# 统一待办稳定性与易用性整改设计

## 1. 文档状态

- 日期：2026-07-13
- 状态：设计已确认，待实施计划
- 适用端：电脑端、手机端
- 运行约束：仅使用本机进程完成构建与验证，不使用虚拟机

## 2. 背景与目标

统一待办已经具备三类 Provider 聚合、部分失败降级、统一跳转和电脑/手机入口，但本次源码、测试和真实界面审计确认了以下问题：

1. 最新源码构建出的系统服务无法启动，系统 Provider 因而长期未知。
2. 多处仍调用已不存在的 `todo/refresh` Vuex action。
3. 顶部存在两个含义相近但目的地不同的业务待办入口。
4. 公告“全部已读”在请求完成前直接清空本地未读数。
5. 电脑端组织范围保护弱于手机端。
6. `returned` 分类被显示成具有终态含义的“已驳回”。
7. 手机统一待办在来源未知时仍展示精确分类数量。
8. 筛选恢复、空状态、键盘操作和手机触控尺寸仍可改善。

本次整改目标是恢复运行稳定性，统一待办入口、刷新和降级语义，并用有限的交互优化减少用户重复操作。整改不改变各业务模块对待办事实、权限或候选人的判定。

## 3. 范围与非目标

### 3.1 本次范围

- 修复系统服务中 APNs、FCM 推送客户端的 Spring 构造器注入。
- 清除所有 `todo/refresh` 调用，按调用语义切换到现有 Todo Store action。
- 让 HeaderTodo 成为电脑端唯一业务待办入口。
- 恢复公告全部已读的权威刷新流程。
- 统一电脑端与手机端的有效组织上下文判断。
- 统一退回类待办文案和未知数量表达。
- 将统一待办筛选同步到 URL，并提供清除筛选能力。
- 补齐待办行/卡片的键盘语义和手机端最小触控尺寸。
- 为上述行为增加回归测试，并完成真实界面回归。

### 3.2 非目标

- 不新增永久待办表，不修改 Provider 的业务事实来源。
- 不增加批量审批、催办、转办、委托、SLA 或保存视图。
- 不把公告、个人消息计入业务待办数量。
- 不重做统一待办视觉系统，不改变业务处理表单。
- 不顺带修复完整前端基线中与统一待办无关的失败项。

## 4. 核心设计决策

### 4.1 单一入口和单一刷新责任

- `HeaderTodo` 是电脑端唯一业务待办入口，进入 `/workbench/todo`。
- `HeaderNotice` 只负责通知公告和个人消息，不读取待办数量，也不触发待办刷新。
- Todo Store 的 `start` action 继续独占 60 秒轮询、页面恢复和组织切换刷新。
- 普通读取使用 `todo/refreshSummaries`。
- 业务写操作成功后使用 `todo/invalidateAfterMutation`，先清理列表缓存再刷新摘要。

这样可以消除重复入口、重复轮询和调用不存在 action 的风险，同时保持现有 Provider 聚合边界不变。

### 4.2 系统服务构造器注入

`ApnsPushDeliveryClient` 和 `FirebasePushDeliveryClient` 都保留生产构造器及包级测试构造器。生产构造器必须显式标记为 Spring 注入构造器，使组件扫描不会尝试查找默认构造器。

新增轻量 Spring BeanFactory/上下文测试，同时实例化两个组件，防止只修复 APNs 后由 FCM 在下一次启动时继续阻断服务。现有网关注入单元测试保持不变。

### 4.3 组织上下文规则

组织型待办的“当前组织”只接受同时具备有效 `deptId`，且类型为 `STORE` 或 `WAREHOUSE` 的上下文。

- 在 `shopContext` 提供可接收上下文快照的纯判断函数，并让现有 `hasSelectedInventoryDeptContext()` 复用它；删除手机页面内部的重复判断。
- 电脑端和手机端初始化时都执行相同的范围归一化。
- 没有有效上下文时默认使用 `all_authorized`，并禁用“当前组织”。
- 组织变化后重新归一化范围并从第一页加载。
- URL 中传入无效的 `scope=current_org` 时也必须回退，不能绕过保护。

### 4.4 未知与缓存语义

Provider 失败时继续使用现有 fail-closed 规则：有精确缓存则标记缓存，无缓存则标记未知，不把未知换算成零。

手机统一待办分类数量采用项目内 MobileWorkbenchShell 已有规则：

- 已知来源全部成功：显示精确数字。
- 任一选中来源未知：已知部分大于零显示 `N+`，否则显示 `?`。
- 任一选中来源仍在加载：已知部分大于零显示 `N+`，否则显示 `…`。

总数、分类数、状态提示必须使用同一组选中来源计算。分类数不能继续直接读取全部 Provider 的聚合 getter，而应从当前选中 Provider 的 summary 汇总，避免来源筛选与数字不一致，也避免页面同时出现“来源未知”和精确零。

## 5. 组件与交互设计

### 5.1 顶部待办与通知

- 删除 HeaderNotice 内的“业务待办”按钮、待办 getter、待办路由判断和待办轮询。
- HeaderNotice 的定时刷新只更新个人消息未读数；公告在首次挂载、打开公告浮层和读状态变更后读取权威数据。
- 保留 HeaderTodo 的未知来源健康提示和最近五条待办。
- HeaderTodo 及统一页面中的 `returned` 显示为“退回修改”。

公告全部已读流程为：

1. 加载或提交期间阻止重复点击。
2. 调用无参数 `markNoticeReadAll()`。
3. 请求成功后重新调用 `loadNoticeTop()` 获取权威列表和未读数。
4. 任一步失败都保留当前列表和计数，由统一请求层反馈错误。

### 5.2 电脑统一待办

- 复用公共组织上下文判断设置默认范围及禁用状态。
- 分类名称由“已驳回”改为“退回修改”。
- 分类、来源、范围、关键词、页码和页大小组成可序列化查询状态。
- 用户触发查询、切换分类/来源/范围或翻页时，通过 `router.replace` 更新当前 URL；不新增浏览历史条目。
- 读取 URL 时只接受白名单值，非法值使用安全默认值。
- URL 同步和路由反向应用需要比较规范化结果，避免 watch/replace 循环和重复请求。
- 有活动筛选且结果为空时显示“清除筛选”；清除后恢复默认分类、来源、范围、关键词和第一页。
- 每条待办由 `<article>` 承载内容结构，内部只放一个覆盖整行的语义化 `<button>`；标题、元数据和可视“去处理”标签都属于这个按钮，避免在可点击卡片内嵌套第二个交互控件。按钮提供可读标签、原生 Enter/空格行为和 `:focus-visible` 样式，一次操作只导航一次。

### 5.3 手机统一待办

- 与电脑端共用 `category`、`source`、`scope`、`keyword` 四个筛选字段和白名单规则，但保留手机端增量加载模型；手机端不把已经增量加载的页数写入 URL。
- 筛选变化时重置列表、写入 URL，再发起第一页请求。
- 空结果提供“清除筛选”，错误状态保留“重试”。
- 分类芯片保留横向滚动，确保当前分类进入可视区域；文案使用“退回修改”。
- 卡片与电脑端一致，使用单一覆盖整卡的语义化按钮，不嵌套第二个按钮，并提供清晰的焦点样式。
- 返回、刷新、分类芯片、下拉框、关键词、查询和“去处理”等主要控件最小高度/宽度达到 44px；不改变现有颜色、圆角和布局语言。

## 6. 数据流

### 6.1 页面进入与筛选

1. 页面读取并白名单化路由查询。
2. 使用当前组织上下文归一化 `scopeMode`。
3. 将规范化筛选写入组件状态。
4. 请求 Todo Store 的 `refreshPage`。
5. Store 并行请求选中 Provider，并按现有规则聚合精确页、缓存页和未知来源。
6. 页面展示列表、总数语义和来源健康状态。

用户修改筛选时，先规范化并写入 URL，再以同一份规范化状态加载，保证返回页面、刷新和分享链接得到一致结果。

### 6.2 业务处理后的刷新

- 签约中心的手动“刷新数据”属于只读操作，调用 `refreshSummaries`。
- 签约任务详情中的业务动作成功后调用 `invalidateAfterMutation`。
- `invalidateAfterMutation` 失败不能覆盖业务动作已经成功的反馈；统一待办稍后仍可由轮询恢复。

## 7. 错误处理

- 系统服务启动测试必须在缺少真实推送凭证时也能通过；推送连接继续保持首次实际投递时才初始化。
- Todo Store 未知/缓存语义保持原样，不新增静默清零。
- URL 参数非法时忽略并回到安全默认值，不显示错误页。
- 路由同步失败不阻断当前列表查询，但测试环境必须能够观察失败路径。
- 公告全部已读失败时不做乐观清零。
- 待办导航继续复用 `todoNavigator` 的权限、路由和组织预检。

## 8. 测试设计

### 8.1 后端

- 新增 APNs 与 FCM 组件可由 Spring 通过 `PushNotificationProperties` 实例化的测试。
- 保留两类推送客户端现有网关、禁用配置和错误分类测试。
- 运行系统模块目标测试及既有统一待办后端目标测试。
- 使用最新源码构建 JAR，并以本机进程启动系统服务验证端口和健康接口。

### 8.2 前端

- HeaderNotice 不包含业务待办入口或 `todo/refresh`。
- 公告全部已读防重复、等待后端、权威重载、失败保留状态。
- 签约中心只读刷新使用 `refreshSummaries`；写操作使用 `invalidateAfterMutation`。
- 电脑和手机在无有效组织上下文时回退到全部授权组织。
- 手机分类数只汇总当前选中来源，未知/加载中时显示 `N+`、`?` 或 `…`。
- `returned` 在所有统一待办入口显示为“退回修改”。
- 电脑和手机的路由查询初始化、更新、非法值回退、返回恢复和无循环行为。
- 空状态清除筛选恢复默认值并只请求一次。
- 待办行/卡片使用单一语义化按钮，原生支持 Enter 和空格，且主要手机控件满足 44px。
- 运行全部统一待办专项测试、公告测试和生产构建；完整前端测试中的无关基线失败单独记录，不扩大本次范围。

### 8.3 真实界面回归

- 电脑首页仅显示一个业务待办入口，公告和个人消息保持独立。
- 电脑待办筛选后 URL 更新，进入业务页面再返回时状态恢复。
- 电脑和手机空结果均可一键清除筛选。
- 模拟一个 Provider 不可用，确认页面显示未知且分类数字不伪装为精确零。
- 使用键盘完成聚焦和打开待办；在 390px 宽手机视口检查触控尺寸和横向分类可用性。
- 不执行真实审批、签署或其他会改变生产业务数据的动作。

## 9. 验收标准

1. 最新源码构建的系统服务可以使用本机进程正常启动，APNs/FCM 缺少凭证时不阻断启动。
2. 前端源码中不存在 `todo/refresh` 调用，运行控制台不再报告未知 action。
3. 电脑顶部只有一个业务待办入口，并始终进入统一待办中心。
4. 公告全部已读只在后端成功并重新加载权威数据后更新未读数。
5. 电脑和手机使用同一组织范围保护，无有效上下文时不会请求“当前组织”。
6. 所有统一待办界面使用“退回修改”。
7. 来源未知或加载中时不显示无法证明的精确分类零。
8. 筛选可通过 URL 恢复，空结果可一键清除筛选。
9. 待办卡片可使用键盘操作，手机主要交互目标不小于 44px。
10. 统一待办、公告和系统模块目标测试通过，生产前端构建通过；真实界面回归符合上述行为。

## 10. 实施边界与顺序

实施计划应拆为以下可独立验证的批次：

1. 系统服务构造器注入及启动回归。
2. HeaderNotice、公告全部已读和废弃 action 清理。
3. 共享组织范围与分类/未知数量语义。
4. 电脑端 URL、空状态和键盘操作。
5. 手机端 URL、空状态、键盘操作和触控尺寸。
6. 目标测试、生产构建和本机真实界面回归。

每一批次先增加能够复现问题的失败测试，再实施最小修改使测试通过；不得覆盖工作区中与本设计无关的现有改动。
