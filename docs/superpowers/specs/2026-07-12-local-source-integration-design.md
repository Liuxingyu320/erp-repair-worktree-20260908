## 整合方案

### 1. 建立可审计的本地源码快照

在 `codex/local-source-integration-20260712` 上按上述范围选择性暂存。暂存后执行：

- 文件类型和目录统计；
- 排除项检查；
- `git diff --cached --check`；
- 明显凭据、私钥和硬编码口令检查；
- 源码快照提交。

快照提交只负责忠实保存本地源码状态，不在这一阶段处理 `7月12号` 的功能差异。

### 2. 合并前差距清单与人工批准门

创建源码快照后，在执行任何 `git merge` 前生成并展示以下信息：

- 本地快照新增或增强的功能，至少按库存通用商品、固定资产月度额度与批量报修、移动端渐进式重构、原生移动工程、部署与数据库脚本分组；
- `7月12号` 已有而本地快照可能缺少的功能，至少包括统一待办与 HR 人事能力；
- 目标侧尚未提交的 HR 入职改动及其状态，只读列示，不纳入本轮操作；
- 双方同时修改的文件和预计冲突点；
- 被排除的截图、JAR、字节码、本机配置和运行产物统计；
- 建议的逐组保留或组合策略。

展示清单后必须暂停。只有用户明确回复继续合并，才允许运行 `git merge`。沉默、超时或笼统状态询问都不视为批准。

### 3. 三方合并与冲突处理

目标侧在途 HR 改动必须先由其所有者提交、转移或明确处理，目标 worktree 恢复到可安全合并状态后才能继续。

正式整合使用 `git merge --no-ff --no-commit codex/local-source-integration-20260712`，禁止使用目录复制覆盖。冲突处理遵循以下规则：

- 保留 `7月12号` 的统一待办、HR 人事和目标侧已确认能力；
- 合入本地库存通用商品、固定资产、移动端、原生工程、脚本和文档能力；
- 路由、Store、服务、Mapper、SQL 与共享组件必须按功能组合，不允许整文件使用 `ours` 或 `theirs`；
- 出现业务语义不明确的冲突时，列出双方行为差异并再次询问用户，不自行选择；
- 合并过程中持续检查未解决冲突和空白错误。

### 4. 验证、提交与重跑

冲突全部解决后先运行与冲突模块对应的定向测试。定向验证通过后创建 `7月12号` 的合并提交，然后按用户要求在提交后重跑：

1. `mvn test`
2. `npm --prefix erp-ui run test`
3. `npm --prefix erp-ui run build:prod`

如果测试失败，先判断是合并引入、源码快照已有还是环境基线问题。只自动修复能够确认由本次合并引入且不需要新增业务决策的问题；其他失败保留证据并报告用户。
