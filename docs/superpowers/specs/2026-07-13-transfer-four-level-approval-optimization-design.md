# 调拨四级审批链优化设计

## 状态

- 设计日期：2026-07-13
- 设计状态：业务规则已确认，待文档复核
- 适用范围：库存调拨提交审批，不改变调拨发货、收货和库存记账规则

## 背景

当前调拨审批名义顺序为：

1. 四级负责人（店长/店长助理）
2. 三级负责人（店长上一级）
3. 运营总监
4. 总经理

业务确认继续保留这条四级审批链，不按金额或数量减少审批层级。需要优化的是审批人的解析边界、缺人时的向上收敛、自审跳级、固定高层节点的可靠性，以及配置页对真实候选人的可见性。

## 目标

- 所有审批人都以调拨目标门店为范围起点解析。
- 四级负责人优先匹配目标门店店长，无店长时由店长助理兜底。
- 三级负责人只允许来自“高于店长、低于运营总监和总经理”的岗位区间。
- 四级或三级缺失时允许向上收敛，不阻断调拨提交。
- 运营总监和总经理作为每个门店的固定必审高层，不允许静默缺失。
- 发起人命中某一审批层级时跳过本人所在层级，禁止自审。
- 已提交审批实例继续使用提交时快照，不受后续岗位和人员变化影响。

## 非目标

- 不按调拨金额、数量或调拨类型减少审批层级。
- 不改变调拨发货、分批发货、整批收货和库存增减规则。
- 不把调拨审批迁移到 Flowable 或其他 OA 流程引擎。
- 不重算或改写历史审批实例和历史任务。
- 不以人员姓名作为长期审批配置。

## 最终审批顺序

标准顺序固定为：

```text
四级负责人 -> 三级负责人 -> 运营总监 -> 总经理
```

四级、三级属于动态组织层；运营总监、总经理属于固定高层。最终生成的有效流程如下：

| 候选人解析结果 | 实际审批顺序 |
| --- | --- |
| 四级、三级均存在 | 四级负责人 -> 三级负责人 -> 运营总监 -> 总经理 |
| 四级缺失、三级存在 | 三级负责人 -> 运营总监 -> 总经理 |
| 四级存在、三级缺失 | 四级负责人 -> 运营总监 -> 总经理 |
| 四级、三级均缺失 | 运营总监 -> 总经理 |

运营总监和总经理不得因候选人解析失败而从流程中消失。

## 岗位排序语义

系统沿用现有岗位排序规则：`post_sort` 数字越小，岗位层级越高。

岗位边界必须从启用岗位实时读取，禁止在代码中写死具体排序值。当前数据可用于说明：

```text
运营总监/总经理：post_sort = 1
店长：post_sort = 5
三级负责人允许区间：1 < post_sort < 5
```

即使未来运营总监、总经理或店长的排序发生变化，也必须根据岗位编码重新计算上下边界。

## 候选人解析规则

### 目标门店

所有动态和固定候选人均以调拨单 `toDeptId` 指向的目标门店为业务范围，不使用发起人的归属门店替代目标门店。

目标门店必须存在、启用、未删除且组织类型为门店。目标门店无效时阻止提交，并提示修正调拨单组织信息。

### 四级负责人

四级负责人解析顺序如下：

1. 在目标门店的直接负责人员中查找启用的店长岗位 `dz`。
2. 找到一个或多个店长时，全部作为同一节点候选人，不再混入店长助理。
3. 完全没有店长时，查找启用的店长助理岗位 `dzzy`。
4. 同级多人使用或签，任意一人通过即可完成该节点。
5. 店长和店长助理均不存在时，四级节点记为缺失并向上进入三级节点。

四级候选人必须满足：

- 用户启用且未删除；
- 岗位启用；
- 员工状态不是离职；
- 用户归属目标门店，或在负责门店关系中直接分配到目标门店；
- 具备目标门店有效范围和调拨审批权限。

四级不继承集团、公司或区域的宽范围授权，避免公司级人员被误判为所有门店的店长。

### 三级负责人

三级负责人必须同时满足以下岗位边界：

```text
max(运营总监岗位排序, 总经理岗位排序)
    < 候选岗位排序
    < 店长岗位排序
```

解析步骤如下：

1. 读取启用店长岗位 `dz` 的排序作为下边界。
2. 读取启用运营总监岗位 `yyzj` 和总经理岗位 `zjl` 的排序。
3. 因数字越小层级越高，使用两者排序的较大值作为高层边界，确保候选人同时低于运营总监和总经理。
4. 从负责范围直接或通过祖先组织覆盖目标门店的有效用户中筛选候选岗位。
5. 只保留处于上述开区间内的岗位。
6. 在有效区间内按 `post_sort` 从大到小查找，取第一个存在有效候选人的岗位档位，即取最接近店长的一档。
7. 同一档位有多人时全部作为同一节点候选人，任意一人通过即可。
8. 区间内没有有效候选人时，三级节点记为缺失并直接进入运营总监。

三级候选查询必须显式排除：

- 店长 `dz`；
- 店长助理 `dzzy`；
- 运营总监 `yyzj`；
- 总经理 `zjl`；
- 已废弃的临时三级、四级岗位；
- 停用岗位、停用或删除用户、离职员工；
- 不具备目标门店负责范围或审批权限的用户。

### 运营总监

运营总监节点使用固定岗位编码 `yyzj`，根据目标门店的负责范围解析候选人，不绑定具体姓名。

该节点为必审节点：

- 必须有至少一名有效候选人；
- 多名候选人时使用或签；
- 无候选人时阻止提交，并提示“目标门店未配置有效运营总监”；
- 不能使用普通祖先岗位查询导致该节点被静默跳过。

### 总经理

总经理节点使用固定岗位编码 `zjl`，根据目标门店的负责范围解析候选人，不绑定具体姓名。

该节点为最终必审节点：

- 必须有至少一名有效候选人；
- 多名候选人时使用或签；
- 无候选人时阻止提交，并提示“目标门店未配置有效总经理”；
- 总经理审批通过后，调拨单才进入待发货状态。

运营总监和总经理当前可能具有相同 `post_sort`，因此两者顺序必须由稳定节点角色和固定节点顺序决定，不能依靠岗位排序自动推断。

## 自审与跳级规则

- 发起人命中四级候选集合时，不创建四级任务，从三级开始。
- 发起人命中三级候选集合时，不创建四级、三级任务，从运营总监开始。
- 发起人命中运营总监候选集合时，不创建运营总监任务，从总经理开始。
- 发起人命中总经理候选集合时，因为不存在更高审批层，阻止提交并提示“总经理不能发起需本人最终审批的调拨单”。
- 发起人同时命中多个层级时，以命中的最高层级执行跳级。
- 同级存在其他候选人时仍跳过整个本人层级，不要求同级其他人代审。
- 不允许管理员权限绕过任务候选人或自审限制。

跳级只针对发起人身份。普通的候选人缺失仍按“动态层可向上、固定高层必须存在”的规则处理。

## 审批实例与任务

提交调拨单时按以下顺序执行：

1. 校验目标门店和调拨明细。
2. 匹配启用的调拨审批规则。
3. 解析四级、三级、运营总监、总经理候选集合。
4. 根据发起人身份应用自审跳级。
5. 跳过缺失的四级、三级动态节点，并生成明确警告。
6. 校验运营总监、总经理固定节点均有有效候选人。
7. 按有效节点顺序创建审批实例和任务。
8. 将节点角色、节点顺序、岗位排序边界、候选用户 ID 和安全展示名写入审批快照。
9. 调拨单进入审核中状态。

审批实例整体使用顺序全部审批 `all_nodes`。每个节点使用同级候选人任意一人通过 `any_one`。不开放节点级“指定人数通过”或“所有岗位通过”配置。

一个节点审批通过后才能激活下一节点。任何当前节点候选人驳回，都立即结束本轮审批并按规则退回草稿。

## 缺失与错误处理

### 允许继续的情况

- 四级负责人缺失：记录警告，流程从三级开始。
- 三级负责人缺失：记录警告，流程进入运营总监。
- 四级、三级均缺失：合并记录警告，流程从运营总监开始。
- 发起人命中动态层：记录跳级原因，流程从更高层开始。

上述警告同时返回前端并写入调拨状态日志，不能只显示一次性提示。

### 必须阻止提交的情况

- 目标门店无效；
- 未匹配到启用审批规则；
- 运营总监无有效候选人；
- 总经理无有效候选人；
- 发起人为最终总经理候选人；
- 候选用户没有目标门店范围或没有调拨审批权限；
- 审批规则快照无法构造。

错误信息必须指出具体缺失层级和目标门店，不使用笼统的“审批规则未配置有效审批人”。

## 审批配置页

审批配置页将审批顺序展示为四个系统业务节点：

1. 四级负责人（店长优先、店长助理兜底）
2. 三级负责人（高于店长、低于运营总监和总经理）
3. 运营总监
4. 总经理

四个节点的业务角色和顺序由系统管理，不允许删除、拖动或修改为其他岗位。规则管理员仍可维护：

- 规则名称；
- 适用调拨类型；
- 适用组织范围；
- 驳回动作；
- 是否启用；
- 优先级和备注。

页面必须提供按目标门店的候选预览，显示：

- 四级候选人及店长助理兜底状态；
- 店长、高层边界和最终选中的三级岗位排序；
- 三级候选人；
- 运营总监候选人；
- 总经理候选人；
- 缺失层级、跳级结果和阻断原因。

节点名称只展示业务角色，候选人员另行展示，避免人员调整时修改规则。

## 服务边界

### 审批规则服务

- 维护规则的适用范围、状态和优先级；
- 保存时自动规范为四个固定业务节点；
- 禁止删除、重排或改变四个节点的稳定角色；
- 提供目标门店规则和候选人预览。

### 候选人解析服务

- 解析目标门店四级负责人；
- 计算三级岗位上下边界并解析候选人；
- 解析覆盖目标门店的运营总监和总经理；
- 过滤无效用户、岗位、员工状态、负责范围和审批权限；
- 返回候选集合、使用的岗位排序和缺失原因。

### 审批执行服务

- 根据候选解析结果和发起人身份生成有效节点链；
- 执行自审跳级；
- 校验固定必审节点；
- 创建实例、任务和规则快照；
- 推进审批、处理驳回并写入状态日志。

将候选人解析从审批执行服务中独立出来，避免组织查询、任务状态机和审批轨迹继续集中在同一个大型服务类中。

## 数据和兼容性

- 优先复用现有规则、节点、实例和任务表，不因本设计新增通用工作流表。
- 四个节点使用稳定角色标识：四级动态、三级区间、运营总监、总经理。
- 新提交调拨单使用新规则生成快照。
- 已提交实例继续使用原快照，不重新匹配候选人。
- 被驳回退回草稿的旧调拨单再次提交时，创建新实例并使用新规则。
- 数据迁移只调整当前规则节点定义，不修改历史实例和历史任务。
- 迁移前必须只读预览全部启用门店的四级、三级、运营总监和总经理覆盖情况。

## 权限与安全

- 查看调拨单仍受目标门店、来源门店和仓库范围限制。
- 审批接口继续要求 `inv:transfer:approve` 权限。
- 后端必须同时校验当前节点、任务状态、候选人快照、目标门店范围和自审规则。
- 管理员可以查看审批进度，但不是任务候选人时不能代替业务审批人。
- 候选人查询仅返回用户 ID 和安全展示名，不返回手机号等敏感字段。

## 审计与可观测性

状态日志至少记录：

- 命中的规则及规则版本；
- 目标门店；
- 四级、三级解析结果；
- 三级岗位上下边界和实际选中排序；
- 四级或三级缺失警告；
- 发起人跳过的层级及原因；
- 运营总监、总经理候选校验结果；
- 每次通过、驳回、退回草稿和最终完成动作。

审批详情和移动端待办继续读取同一实例和任务快照，保证桌面端、移动端口径一致。

## 验收标准

- 普通员工提交时，候选完整情况下依次生成四级、三级、运营总监、总经理任务。
- 无店长但有店长助理时，店长助理成为四级候选人。
- 四级缺失时从三级开始，三级缺失时进入运营总监。
- 四级、三级均缺失时仍生成运营总监、总经理两级任务。
- 三级候选人的岗位排序严格高于店长、低于运营总监和总经理。
- 三级区间存在多档岗位时，只选择最接近店长的有效档位。
- 运营总监和总经理不会因通用岗位解析失败而被跳过。
- 发起人命中某层时跳过该层并从更高层开始，且不能审批自己的任务。
- 总经理作为发起人时提交被阻止并得到明确提示。
- 同级多人时任意一人通过即可，其他人不能重复推进同一节点。
- 规则或组织信息变化不影响已提交实例的候选人快照。
- 审批警告、跳级原因和实际审批人可从状态日志与审批轨迹追溯。

## 实施验证策略

后续实施计划应覆盖但不限于：

- 候选解析单元验证：四级优先级、三级上下边界、同档多人、固定高层范围；
- 数据访问验证：启用状态、员工状态、岗位状态、目标门店直接范围和祖先覆盖范围；
- 审批服务验证：四种缺失组合、自审跳级、固定节点阻断、驳回重提和快照稳定性；
- 控制器权限验证：候选人、组织范围和 `inv:transfer:approve` 三重校验；
- 配置页验证：四节点只读顺序、门店候选预览和明确错误提示；
- 历史兼容验证：旧实例可继续查看和处理，新提交使用新规则；
- 上线前只读覆盖检查：所有启用门店必须存在运营总监和总经理候选人。

未经用户复核本设计文档，不进入代码实施。
