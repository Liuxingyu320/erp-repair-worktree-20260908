# 调拨审批自动匹配四级、三级最高领导设计

> 已由《调拨目标门店岗位链自动审批修订设计》取代。当前实现不再读取提交人的三级/四级档案文字字段，而是以调拨目标门店、店长/店长助理岗位、负责范围和岗位排序生成动态审批链。

## 目标

调拨单提交审批时，不再要求每个店铺手工选择四级门店负责人和三级部门负责人。系统根据提交人在用户管理中的组织层级自动定位四级门店、三级部门，并按岗位排序自动选出各层级最高领导作为前置审批人。

现有二级、一级审批配置保持原有解析方式和审批顺序，不改为动态组织领导。

## 已确认的业务规则

1. 岗位排序数字越小，岗位层级越高。
2. 同一组织存在多名并列最高岗位用户时，所有人都是候选审批人，其中任意一人审批即可。
3. 普通门店人员提交时，审批顺序是：四级门店最高领导、三级部门最高领导、现有二级审批、现有一级审批。
4. 四级门店最高领导提交时，跳过四级动态节点，从三级部门最高领导开始。
5. 三级部门最高领导提交时，跳过四级和三级动态节点，直接进入现有二级审批。
6. 四级或三级动态领导缺失时不阻止提交，跳过缺失节点并明确提醒。
7. 如果动态节点和现有二级、一级节点均无法产生任何有效审批人，保留当前安全约束，不允许单据在没有审批人的情况下直接通过。

## 方案选择

采用“系统自动生成动态前置节点”方案。

调拨审批规则不再要求管理员选择四级、三级负责人。系统在提交调拨单时自动解析这两个动态节点，再把现有二级、一级节点接在后面。

没有采用以下方案：

- 在每条审批规则中手工添加“自动四级领导”“自动三级领导”节点：仍然存在漏配风险。
- 只按单个部门名称或人员姓名匹配：部门重名、人员同名、组织改名时容易错误匹配。

## 组织与候选人解析

### 组织上下文

动态解析以当前提交人的用户档案为入口，读取以下组织字段：

- 所属公司
- 1 级部门
- 2 级部门
- 3 级部门
- 4 级门店

查询时使用完整组织上下文组合，而不是只用三级部门名称或四级门店名称，避免不同公司、不同区域存在同名组织时串人。

空字符串、仅空白和页面展示用的 `-` 统一视为未配置。

### 四级门店最高领导

当提交人档案存在四级门店时，系统查找同时满足以下条件的用户：

- 所属公司、1 级部门、2 级部门、3 级部门、4 级门店与提交人一致。
- 用户未删除、账号启用。
- 员工状态不是离职。
- 至少绑定一个启用岗位。

系统计算每个候选用户所绑定启用岗位的最小 `post_sort`，再取全体候选中的最小值。拥有该最小值的所有用户共同构成四级门店最高领导候选集合。

### 三级部门最高领导

当提交人档案存在三级部门时，系统查找同时满足以下条件的用户：

- 所属公司、1 级部门、2 级部门、3 级部门与提交人一致。
- 四级门店为空，表示该用户归属于三级部门本级，而不是某个具体门店。
- 用户未删除、账号启用。
- 员工状态不是离职。
- 至少绑定一个启用岗位。

最高岗位和并列候选人的计算方式与四级门店相同。

三级领导查询不把下属门店人员混入候选集合。三级部门本级无人时，该动态节点按缺失处理，不会选择其他门店的店长代替三级领导。

四级、三级动态候选人还必须具备调拨目标门店的有效授权范围（包含现有的祖先范围继承规则）。没有目标门店授权的用户不进入审批任务快照；若某层级最高领导全部因无授权被过滤，则该层级按动态领导缺失处理并提醒。

## 动态审批链

系统先解析四级、三级候选集合，再结合提交人的身份构造最终审批链。

### 普通员工

提交人既不属于四级最高领导候选集合，也不属于三级最高领导候选集合：

1. 四级门店最高领导。
2. 三级部门最高领导。
3. 现有二级审批节点。
4. 现有一级审批节点。

### 四级最高领导

提交人属于四级最高领导候选集合，但不属于三级最高领导候选集合：

1. 跳过四级节点，避免本人审批本人提交的单据。
2. 三级部门最高领导。
3. 现有二级审批节点。
4. 现有一级审批节点。

### 三级最高领导

提交人属于三级最高领导候选集合：

1. 跳过四级和三级动态节点。
2. 直接进入现有二级审批节点。
3. 再进入现有一级审批节点。

### 动态节点通过方式

四级、三级动态节点均使用“任一候选人通过”方式。并列最高领导中的任意一人审批后，该动态节点完成并进入下一节点。

## 现有规则兼容

现有审批规则的前两级原四级、三级配置升级为系统动态节点，不再使用原先手工选择的人员或岗位。

现有后两级二级、一级节点保持：

- 原配置内容不变。
- 原相对顺序不变。
- 原候选人解析方式不变。
- 原驳回动作、自审限制和审批快照规则不变。

审批配置页不再要求填写四级、三级负责人。新建规则时，页面显示两个系统管理的只读前置节点；管理员只维护后续二级、一级配置。

动态节点直接复用现有 `node_role` 字段作为稳定的候选来源标识：

- `level4_highest`：四级门店最高领导。
- `level3_highest`：三级部门最高领导。

部署迁移把每条现有规则按 `node_order` 排序后的前两级分别转换为上述动态类型，并清空这两级已不再使用的岗位选择信息。后续二级、一级节点不修改。新建或保存规则时，后端自动补齐这两个动态前置节点并校验其顺序，避免依赖节点名称猜测，也避免旧节点和新动态节点重复执行。

对少于两个节点的异常或历史规则，迁移不猜测现有节点的层级，也不覆盖其审批人：原节点整体后移并保留，系统在前面插入四级、三级动态节点。这样既保证迁移后结构完整，也避免单节点规则丢失原审批配置。

## 服务边界

新增独立的组织最高领导解析组件，职责包括：

- 规范化用户档案组织字段。
- 查询四级、三级组织候选用户。
- 按启用岗位的 `post_sort` 计算最高领导。
- 识别提交人是否属于动态最高领导候选集合。
- 返回动态审批节点、候选用户和缺失警告。

调拨审批服务负责：

- 调用组织最高领导解析组件。
- 按已确认规则合并动态节点与现有二级、一级节点。
- 创建审批实例和任务快照。
- 在没有任何有效审批人时保留现有阻断逻辑。

调拨提交服务和接口负责：

- 返回提交结果和动态审批警告。
- 把缺失或跳级信息写入调拨状态记录。

前端负责：

- 在审批规则配置页展示系统管理的四级、三级前置节点。
- 不再要求管理员选择这两级负责人。
- 提交成功后展示后端返回的警告。

## 返回结果与提醒

调拨提交成功响应增加非持久化的审批提醒列表，例如：

```json
{
  "approvalWarnings": [
    "未找到四级门店最高领导，本次审批从三级部门开始"
  ]
}
```

典型提醒：

- 缺少四级：`提交成功；未找到四级门店最高领导，本次审批从三级部门开始。`
- 缺少三级：`提交成功；未找到三级部门最高领导，本次审批跳过三级并继续进入已配置的二级审批。`
- 四级、三级都缺少：`提交成功；未找到四级、三级最高领导，本次审批直接从已配置的二级审批开始。`

提醒不能只在前端短暂显示。相同内容必须写入调拨状态记录，供后续审计和问题排查。

## 审批快照与数据变化

提交时把实际候选用户 ID、姓名、动态层级和当时使用的岗位排序写入审批任务或规则快照。

单据提交后：

- 用户调岗不改变已有任务候选人。
- 岗位排序变化不重新计算已有任务。
- 用户组织字段变化不重写已有审批链。
- 新提交的调拨单使用最新组织和岗位数据重新计算。

## 异常处理

以下情况不阻止提交，但生成警告并跳过对应动态节点：

- 提交人缺少四级门店字段。
- 提交人缺少三级部门字段。
- 对应组织没有有效用户。
- 对应组织用户均无启用岗位。
- 对应组织用户全部为离职或停用状态。

以下情况继续阻止提交：

- 未匹配到可用的调拨审批规则。
- 动态节点被跳过后，现有二级、一级配置也未产生任何有效审批人。
- 审批规则结构损坏，无法构造有效审批实例。

阻断错误必须说明是规则问题或没有任何有效审批人，不能把动态节点缺失误报成提交失败原因。

## 安全与一致性

- 候选查询只返回用户 ID 和审批展示所需的安全字段。
- 必须使用参数化 SQL，不拼接组织名称。
- 候选查询同时校验用户、员工状态和岗位状态。
- 最终审批权限继续以任务中的候选用户 ID 快照判断。
- 并列候选人按用户 ID 稳定排序，保证快照结果可重复。
- 完整组织上下文用于隔离同名公司、部门和门店。

## 测试设计

### 后端单元测试

- 普通门店员工生成四级、三级动态节点，后接现有二级、一级节点。
- 四级最高领导提交时跳过四级节点。
- 三级最高领导提交时跳过四级和三级节点。
- 同级多人拥有相同最小岗位排序时全部成为候选人。
- 一个用户绑定多个岗位时使用其启用岗位中的最小排序。
- 停用账号、离职员工、停用岗位不参与候选计算。
- 动态最高领导没有目标门店授权时不进入候选集合。
- 单节点旧规则迁移后保留原审批节点，并在前面补齐两个动态节点。
- 三级领导查询不选择下属四级门店人员代替。
- 完整组织路径不同但三级部门或门店名称相同时不会串人。
- 缺四级、缺三级、两级都缺时分别生成正确警告并继续提交。
- 所有动态节点缺失但现有二级、一级有效时从现有节点开始。
- 所有动态和现有节点都无候选人时继续阻止提交。
- 已提交任务在岗位或人员信息变化后候选快照不变。

### 数据访问测试

- 最高领导查询按 `post_sort` 升序计算。
- 并列最小排序返回全部有效用户。
- 查询包含用户启用、未删除、员工状态和岗位启用条件。
- 查询使用完整组织上下文，且把空白和 `-` 规范为未配置。

### 前端测试

- 审批配置页显示只读四级、三级自动节点。
- 四级、三级节点不再出现人员或岗位选择控件。
- 现有二级、一级节点仍可编辑且顺序不变。
- 新建规则自动展示动态前置节点。
- 提交成功无警告时显示普通成功提示。
- 提交成功有警告时显示成功状态和具体缺失层级，不误显示为失败。

### 兼容性测试

- 旧规则升级后只替换前两级，后两级配置内容和相对顺序不变。
- 旧审批实例、任务和历史快照仍可查询与审批。
- 同一调拨单不会同时执行旧四级、三级节点和新动态节点。

## 验收标准

- 店铺不需要手工选择四级、三级负责人也能提交调拨审批。
- 系统按用户管理的完整组织层级和岗位排序找到四级、三级最高领导。
- 岗位排序最小者为最高领导；并列最高者任意一人可以审批。
- 普通员工、四级最高领导、三级最高领导三种提交身份走正确的起始节点。
- 四级或三级领导缺失时提交成功，并在页面和状态记录中得到清晰提醒。
- 现有二级、一级审批配置不被改写。
- 没有任何有效审批人的单据不会无审批直接通过。
- 已提交审批任务保留候选人快照，不受后续人员和岗位调整影响。

## 非目标

- 不把二级、一级改为按组织最高领导动态计算。
- 不改造为 Flowable 或其他通用流程引擎。
- 不改变历史审批实例的候选人。
- 不允许动态节点缺失导致无审批自动通过。
