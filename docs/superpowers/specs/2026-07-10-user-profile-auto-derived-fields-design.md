# 用户档案字段自动匹配设计

## 背景

用户管理已经有“归属部门”、岗位关系和员工档案，但所属公司、1 级部门、2 级部门、3 级部门、4 级门店、职位、工龄和司龄仍作为普通文本字段编辑和保存。这会导致以下问题：

- 新增用户时已经选择归属部门和岗位，还需要重复输入组织层级和职位。
- 部门或门店改名、员工调岗后，档案里的重复文本不会自动更新。
- 列表、详情、导出和签约候选人可能读到不同来源的值。
- 组织路径异常时使用档案旧值兜底，会隐藏真实配置问题。

## 目标

以归属部门、岗位关系和相关日期为唯一可信数据源，由后端统一实时派生能够唯一计算的档案字段。前端只读展示派生结果，用户通过修改来源字段改变结果，不允许手工覆盖。

列表、详情、导出和后续业务接口必须获得一致的派生值。

## 方案选择

### 方案一：仅前端自动回填

选择部门或岗位后，前端把名称写入档案字段。该方案改动小，但无法保证导出、批量导入和其他后端调用者一致，也不能自动响应组织改名。

### 方案二：后端统一实时派生

由后端自动匹配器根据主部门路径、岗位关系和日期统一计算，所有读取入口复用同一套规则。该方案能够保持实时一致，并明确暴露组织配置异常。

### 方案三：保留冗余值并同步刷新

在组织、岗位或日期变化时回写档案字段。该方案查询简单，但需要覆盖所有变更入口，任何遗漏都会再次产生过期数据。

### 结论

采用方案二。原档案表中的重复列暂时保留，以兼容旧数据和历史导入，但停止将它们作为页面展示和业务判断的数据源。

## 字段分类

### 系统派生字段

| 字段 | 可信来源 | 规则 |
| --- | --- | --- |
| 所属公司 | `sys_user.dept_id -> sys_dept` 路径 | 取路径中距离员工归属部门最近的 `COMPANY` 节点。 |
| 1 级部门 | 组织路径 | 取公司节点之后第 1 个普通部门节点。 |
| 2 级部门 | 组织路径 | 取公司节点之后第 2 个普通部门节点。 |
| 3 级部门 | 组织路径 | 取公司节点之后第 3 个普通部门节点。 |
| 4 级门店 | 组织路径 | 取路径中距离员工归属部门最近的 `STORE` 节点。 |
| 职位 | `sys_user_post -> sys_post` | 按 `post_sort` 和 `post_name` 排序后使用顿号拼接。 |
| 部门主管 | `sys_dept.leader` | 从员工归属部门开始向上，取第一个已配置负责人的节点。 |
| 工龄 | `work_start_date` | 按起始日期到当前日期计算完整年月，显示为“X年Y个月”。 |
| 司龄 | `entry_date`、`leave_date` | 在职时计算到当前日期；已离职且离职日期有效时计算到离职日期。 |

普通部门节点指路径中不是 `GROUP`、`COMPANY`、`STORE` 或 `WAREHOUSE` 的节点。部门层级不足时，对应字段显示 `-`，不把后续层级向上填补。

仓库节点不作为门店。未标记为 `STORE` 的叶子节点也不按名称猜测为门店。

### 系统联动字段

- 员工状态修改为“离职”时，账号状态自动变为停用。
- 账号状态手工恢复为正常时，不自动更改员工状态，避免把离职员工恢复为在职。

### 保留人工维护的字段

以下字段在现有数据模型中没有唯一可信来源，不做猜测性自动填充：

- 直属主管
- 职级
- 法人单位
- 合同类型
- 社保类型
- 人员类别
- 试用期和计划转正日期
- 合同期限
- 工作地点、考勤方式和缴纳地

如果后续为这些字段建立了正式的岗位、法人主体、用工规则或组织配置表，再单独将对应字段转为派生值。

## 后端设计

### 自动匹配器

新增一个职责单一的用户档案派生服务，输入用户主部门、部门路径、岗位集合和档案日期，输出统一的派生字段和可选警告。

服务需同时支持单个用户和批量用户。列表和导出时应批量加载所需部门与岗位数据，禁止每行用户单独查询组织路径。

新增一个只读预览接口，输入 `deptId`、`postIds` 和计算年限所需的日期，直接复用自动匹配器返回派生值与警告。预览接口必须校验操作人对所选部门和岗位的数据权限，不写入任何数据。

### 写入边界

- 新增、修改和 HR 档案修改接口只使用归属部门、岗位和人工档案字段。
- 后端忽略请求中的所属公司、1–3 级部门、4 级门店、职位、部门主管、工龄和司龄值。
- 档案表原重复列不再由普通新增和修改流程回写。
- 批量导入可继续接收组织名称列，但这些列只用于唯一匹配 `dept_id`，不直接保存为派生值。

### 读取边界

以下入口在返回前统一应用自动匹配器：

- 用户管理列表
- 用户管理详情和编辑回显
- HR 人事工作台列表、详情和编辑回显
- Excel 导出
- 签约候选人和资料完整性判断

匹配结果覆盖响应对象中的同名档案展示值，但不回写数据库。

## 前端设计

- 所属公司、1–3 级部门、4 级门店、职位、部门主管、工龄和司龄改为禁用的只读控件。
- 只读控件附带“根据归属部门自动匹配”、“根据已选岗位自动匹配”或“根据日期自动计算”提示。
- 选择归属部门、岗位或修改相关日期后，新增/修改弹窗调用后端只读预览接口，用同一个自动匹配器立即更新预览，不在前端复制匹配规则。
- 预览请求应做防抖和旧请求结果丢弃，避免快速切换选项时旧结果覆盖新结果。保存成功后仍以正式查询接口返回的结果为准。
- 组织层级不足时显示 `-`；路径异常时显示“组织结构待修复”，不回显档案里的旧名称。

## 异常与兼容处理

### 组织异常

以下情况返回“组织结构待修复”警告：

- 用户归属部门不存在、已删除或不可用。
- `ancestors` 与 `parent_id` 无法构成一致路径。
- 路径中没有可识别的公司节点。
- 公司与门店之间超过 3 个普通部门层级。

异常警告用于提醒管理员修复组织数据，不阻断查询。新增或修改用户时，如果选择的归属部门本身不存在、已删除、已停用或越过操作人数据权限，则阻断保存并返回明确错误。

### 日期异常

- 起始日期为空时，对应年限显示 `-`。
- 起始日期晚于计算截止日期时，返回档案日期异常警告，不输出负数年限。
- 离职日期早于入职日期时，司龄显示 `-` 并返回日期异常警告。

### 历史数据

本次不对档案表里的旧派生文本做破坏性批量清空。上线后忽略这些旧值，同时提供只读审计查询，统计组织路径异常和旧值与实时派生值不一致的用户。

## 数据流

### 新增或修改用户

1. 前端提交基础账号字段、`deptId`、`postIds` 和人工档案字段。
2. 后端校验用户、部门、角色和岗位权限。
3. 后端写入 `sys_user`、岗位关系和人工档案字段，忽略请求中的派生值。
4. 查询响应时由自动匹配器重新计算派生字段。
5. 前端使用后端结果刷新列表和详情。

### 查询和导出

1. 先按现有数据权限获取用户集合。
2. 批量加载用户涉及的部门路径和岗位。
3. 批量计算派生字段和警告。
4. 列表、详情、导出和业务调用者使用同一结果。

## 测试与验收

### 后端单元测试

- 标准“集团 -> 公司 -> 1 级部门 -> 2 级部门 -> 3 级部门 -> 门店”路径能正确输出全部字段。
- 层级不足时仅缺失对应层级，不错位填补。
- 员工归属门店内部部门时，能从祖先路径识别门店。
- 仓库、未分类叶子节点不会被误判为门店。
- 部门负责人为空时向上寻找最近的已配置负责人节点。
- 多岗位按稳定顺序拼接，移除岗位后不再返回旧名称。
- 工龄、司龄在跨年、未满月、离职和异常日期情况下计算正确。
- 员工状态改为离职时账号自动停用。
- 请求伪造派生字段时，查询结果仍返回实时计算值。

### Mapper 和接口测试

- 列表批量派生不产生 N+1 查询。
- 列表、用户详情、HR 详情、导出和签约候选人对同一用户返回相同派生值。
- 组织改名或用户调部门后，无需修改档案即可查到新结果。
- 已删除、停用、断裂路径和越权部门的错误处理符合设计。

### 前端测试

- 派生字段为只读控件，不能手工修改。
- 修改归属部门和岗位时，自动预览立即更新。
- 快速连续修改选项时，旧预览请求不会覆盖最新选择的结果。
- 重新打开编辑页、详情页和 HR 工作台时，展示值与后端一致。
- 层级不足显示 `-`，路径异常显示“组织结构待修复”。

## 非目标

- 本次不新增法人主体、直属上级、用工规则或考勤配置数据模型。
- 不根据组织或姓名猜测职级、法人单位、合同、社保或人员类别。
- 不在本次开发中删除档案表的旧冗余列。
- 不改变现有部门、用户、角色和组织授权的数据权限边界。
