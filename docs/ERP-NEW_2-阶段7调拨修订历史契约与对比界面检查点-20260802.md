# ERP-NEW_2 阶段 7：调拨修订历史契约与对比界面检查点

## 1. 本检查点结论

阶段 6 已建立的不可变调拨业务修订现已具备按组织范围读取的强类型后端契约，以及新前端中的运行时校验、版本时间线和差异查看骨架。读取路径只返回解析后的业务字段，不泄露原始 JSON；服务端在返回前验证主单归属、连续版本号、唯一版本 ID、精确父链、已知状态和 SHA-256 快照哈希。

新前端默认查看最新版本，并优先把它的父版本作为差异基线。明细按物料、批次和来源库位的业务身份配对，不使用新草稿重新生成的数据库 `detail_id` 配对，因此能够正确显示“驳回后调整数量”而不是误判为一行删除加一行新增。

## 2. 后端只读边界

- 新增 `GET /inventory/transfer/{transferId}/revisions`。
- 权限集合与现有调拨详情读取保持一致，任一详情权限满足即可读取。
- 服务入口先调用现有 `assertAndGetScopedTransfer`，要求当前选择组织对调出/调入部门或仓库具有可见范围。
- 响应设置 `Cache-Control: no-store`，降低业务快照被中间缓存保留的风险。
- 返回抬头、明细、版本元数据和决策元数据的强类型 VO，不返回数据库中的原始快照字符串。
- 旧单尚无修订时返回空历史与空当前摘要，不猜测或伪造历史。

## 3. 完整性校验

服务端读取每条修订时执行以下失败即关闭检查：

1. 主单、修订和版本号均有效，版本号从 1 连续递增。
2. 修订 ID 在当前链中唯一；第一版父 ID 必须为空，后续版必须精确指向上一版。
3. 修订状态必须属于已知生命周期集合，`null` 状态安全地判为非法而不是触发 NPE。
4. 抬头快照、明细快照和哈希必须存在。
5. 对存储的规范化 JSON 重新计算 SHA-256，并与台账哈希逐字一致。
6. 解析后的抬头 `transferId` 必须等于受组织范围保护的主单 ID。
7. JSON 使用白名单 VO 解析；未知历史字段可忽略，但缺失或类型错误的必要字段由前端运行时契约继续拒绝。

## 4. 新前端契约与页面

- 新增 Zod 运行时契约，统一把后端安全整数 ID 转为字符串，避免浏览器数字精度风险。
- 客户端重复验证当前摘要、连续版本号、精确父链和抬头归属，异常响应不会进入页面状态。
- HTTP Reader 只接受正整数路径参数，使用同源 `/api` 基址、必需组织头和只读 GET；非法路径在调用 `fetch` 前拒绝。
- 调拨工作台新增“版本”入口和 `inventory/transfer/:transferId/history` 路由。
- 页面提供版本时间线、父版本基线、抬头变化、明细变化、摘要计数和快照哈希提示。
- 首次页面进入仅使用一次 200ms 的 `opacity + translateY(6px)`；版本切换即时完成，按键仅有轻微按压反馈，并支持 `prefers-reduced-motion`。
- 前端设计参考与采用门槛固化在 `docs/ERP-NEW_2-前端设计参考与动效规范-20260802.md`。
