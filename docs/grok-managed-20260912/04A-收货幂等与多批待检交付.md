## HTTP 与业务合同

`POST /inventory/purchase/receive/{orderId}` 保留 `inv:purchase:receive` 权限，新增必填 `X-Request-Id`，沿用现有 8–128 位格式。以 `PersistentCommand` 替换该入口原 30 秒短期防重；服务签名显式接收 requestId，没有无 ID 的写入旁路。

成功 `data` 为稳定 `InvPurchaseReceiveResult`，包含 requestId、purchaseOrderId、warehouseId、receiptBatchId、batchNo、arrivedTime、receivedQuantity。复用 `inv_quality_command`，命令类型为 `PURCHASE_RECEIVE`，保存首次原始结果。同 ID 回放经过当前仓库/权限核对及原单锁，早于订单状态和剩余量等可变条件；首批已检完、整单已 received、服务重新构造后仍返回原批次。

指纹冻结原单、仓库、到货时间、明细 ID/数量、供应商批次、送货单号和备注，并沿用执行器的操作者/组织/命令类型隔离。明细排序、数字刻度、文本首尾空白一致规范化；null/重复/缺失明细不能被丢弃后碰成原指纹。同 ID 改有效载荷、原单、操作者或仓库均拒绝。控制器不把全部 ServiceException 误标为“确定未执行”；历史结果回放失败仍按异常处理，客户端不得因此自动换新 ID 重收。

新 ID 可在前批仍待检时创建下一批，每批单独留存。原单/明细锁内校验当前剩余量；待检不增加可用库存，本次合格及原有受控让步数量才入库存，拒收只释放本次增量一次。收货不再删除历史无批次拒收记录。

逐批质检后，以原单范围的 `FOR UPDATE` 当前读取得全部批次明细及入库记录。只累计批次明细和历史无批次记录，避免同一事实重复计算；任意未检仍保持 submitted/pending。全部结束后的 qc/status 由整单累计决定，完成顺序不影响结论。混合合格/拒收沿用 concession 汇总枚举，不增加让步权限。损坏的批次/明细关联阻断事务，不自动修写历史数据。

旧 `/qc/{orderId}` 仅处理两个批次标识均为空的历史待检集合，不能自动接管新批次；存在新的 B 批时，针对旧 A 的整单确认也不能落到 B。旧成功质检命令仍优先回放。历史已接受、拒收事实参与最后整单结论。
