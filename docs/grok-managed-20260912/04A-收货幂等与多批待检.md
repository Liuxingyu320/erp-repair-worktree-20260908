## 阶段一：持久收货合同

1. 保持 URL 与 `inv:purchase:receive` 权限。控制器读取必填 `X-Request-Id`（8–128 位，采用现有持久命令格式），保留现有共享请求体。以 `PersistentCommand` 替换本入口的短期 `IdempotentSubmit`，不能让短期缓存阻断正确回放或合法的新批次。
2. service 接收显式 requestId 并返回 `InvPurchaseReceiveResult`。内部方法和接口签名同步调整；不得保留一个没有 requestId 却可实际写收货的旁路，不得在后端每次随机补 ID。原测试调用改用显式 ID。
3. 成功返回 AjaxResult 的 data 至少包含 requestId、purchaseOrderId、warehouseId、receiptBatchId、batchNo、arrivedTime、receivedQuantity。命令保存首次操作的原始结果；重试回放相同批次和数量，不重新查询并拼接可能已变化的待检状态。result 类型名需稳定，不随意更名破坏旧结果反序列化。
4. 锁序保持“当前仓库/权限核对 → 原采购单 FOR UPDATE → 命令唯一占用/回放 → 原单明细、批次/入库事实”。回放也必须通过当前操作者与仓库范围核对。把订单状态、剩余量、创建批次等可变条件放进新命令 action；否则首批完成甚至原单已 received 时仍会错误拒绝合法回放。
5. 指纹包含操作者、所选仓库、原单及完整冻结收货载荷（明细ID/数量、到货时间、供应商批次、送货单、备注），不引用之后变化的实体状态。同 ID 不同有效载荷拒绝。若对数量刻度、明细顺序、空白文本做规范化，必须在首次及回放一致应用并测试，不能让不同业务内容碰成相同指纹。
6. 命令、批次、批次明细、待检入库记录、采购累计和序号操作都在同一真实事务中，失败整体回滚。沿用执行器 MANDATORY，不使用独立提交命令占位或应用内缓存替代数据库约束。
7. 控制器可参照逐批质检返回 `receiveOutcome: REJECTED`，仅对 service 事务已回滚的明确业务拒绝返回。连接中断、未知服务异常、结果无法判定不能伪装成确定未执行，也不能返回成功。说明新前端需要以同 ID/同载荷核对未知结果。

## 阶段二：多批、累计事实与历史入口

1. 持久命令完整后才删除整单 QC_PENDING 对合法新 ID 的拦截。每次都在原单和明细锁内核对本次数量 ≤ 采购数量 − 当前有效 received_quantity；该数量包含所有待检、合格、受控让步数量，拒收按现有规则释放可重收到货量，且每次仅释放本次拒收增量一次。不能简单根据订单 qcStatus 推导剩余量。
2. 新到货只创建本批事实，不入可用库存，不清历史拒收记录，不重置其他批次。相同送货单号不作为全局唯一身份，允许合法不同 ID 的后批；原单、仓库、明细不属于当前范围或超过剩余量仍拒绝。
3. `/qc/batch/{orderId}` 保持 receiptBatchId 和所选 batchDetailId 约束，只处理本次提交的行和数量。未选择行仍待检；accepted+concession 仅本次增量入库，检验、附件、入库快照、库存、流水及拒收释放必须同事务；已有质检命令重复不二次生效。
4. 原单汇总从全部相关批次当前事实计算，不能只汇总最后一批，也不能使用 REPEATABLE READ 旧快照普通聚合。可在上述白名单 Mapper 增加明确的按 orderId 当前读方法（FOR UPDATE、按主键排序），锁后取全部 batch detail 与历史无批次 inbound 并汇总；不重复计算 batch-backed inbound 与 batch detail 的同一数量。任意批次/历史记录仍 pending，则原单仍 pending/submitted；已入库存保持。
5. 全部待检结束后，按整单累计 accepted/rejected/concession 复用现有 resolveQualityConclusion 规则，再根据采购明细有效收货量决定 submitted/received。混合合格/拒收在现有枚举中归 concession，不能把汇总枚举解释成新增让步授权。用相反完成顺序的测试证明最终数量和状态相同。
6. 旧 `/qc/{orderId}` 及内部 qualityCheck 必须停止“遍历所有新待检批次”路径。只剩 batch-backed 记录时，明确拒绝旧整单质检并提示选择具体批次；不能仅以当前 pending 批次数 > 1 为判断，因为确认 A 后 A 被他人处理、只剩新 B 时仍会误检 B。
7. 保留历史无批次记录的兼容入口：若存在 receiptBatchId/receiptBatchDetailId 均为空的历史 pending，旧入口只能处理该历史集合，绝不把同单新批次混入；完成后使用同一累计汇总规则，若新批仍待检，原单仍 pending。没有历史 pending 时拒绝，不能回退处理新批次。已有成功旧命令仍优先回放原结果，不因新限制失效。
8. 原收货清理方法目前仅删除无批次拒收记录，不应误报为会删除所有批次。本批取消收货时的该调用，保留拒收轨迹。累计时按 batch detail 事实与无批次旧记录区分，避免遗留记录重复计量；对不一致历史数据返回清楚的阻断/诊断，不自动修写历史金额或伪造批次。
