## 当前行为

- 员工选项支持按 100 人加载更多，表格按 20 人分页；搜索、翻页保留同店已勾选人员，切店清空选择。页面明确显示已加载、总可排班人数和含历史排班/草稿的展示人数。原无分页 API 调用仍返回原列表，不改变旧消费者。
- 勾选人员、日期并设置班次/地点后，只填写空白格；已有服务端排班、本地草稿及冲突格不被覆盖。新草稿仍通过原按门店/员工/日期的 draftEdits 和单调 stamp 保存。
- 复制上周同时读取来源周与目标周最新排班，只按相差 7 天的日期映射新草稿，不复制原 scheduleId、版本或已发布状态。显示来源、目标周及新增/跳过数量；停用班次/地点跳过。复制期间有新编辑或清除草稿则不应用旧读取；切店周、刷新或离页使旧复制失效。复制不触发保存、发布。
- 504 条保存/发布为 500+4；1001 条为 500+500+1。每批顺序执行，绑定原店周和操作代次；失败即停，页面显示本次已确认数量，不报告整周成功。成功批次逐项核对员工、日期、原 ID、班次、地点、版本精确推进与完整性，再按原 stamp 清理；期间新输入保留并接收对应服务端身份。
- 成功保存的未改变排班保留准确版本缓存，重试剩余批次不会重新提交已确认部分。失败或结果未知先读取原周权威数据；保留原本地意图，变化项沿用现有本地/远端比对和明确选择。回包缺项、业务内容错误不能清掉原草稿。
- 发布先保存完整冻结草稿，期间有新输入便停在草稿核对。每批发布传入冻结 ID 与逐条 rowVersion；后端在原事务和行锁内先核对整批，再发布。缺项、多余项、重复 ID、无效版本拒绝；任何版本变化使本批零写入。两批之间远端修改会保留本地/远端比对，重新确认后才能继续。
- 发布丢响应或部分失败后权威重读，后续确认只提交仍为草稿的 ID；权威读取失败时明确保留“待核对”状态。后续读到整个原集合都已发布，可以确认结果而不重复发送。

## R2 回执完整性复核

根项目经理发现发布成功回包为空时原页面会使用冻结行自行设为已发布，现已删除该兜底。发布完整回包必须覆盖本批所有且仅这些排班 ID，数量一致、无重复，员工/日期/门店/班次/地点与冻结快照相同，状态为 PUBLISHED，版本精确加一；否则作为未知结果停止后续批次并权威重读，不能提示整周成功。
