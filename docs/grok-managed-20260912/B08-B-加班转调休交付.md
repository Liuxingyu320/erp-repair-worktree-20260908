# B08-B 加班转调休来源闭环

2026-09-12，Codex 直接实施，按已批准33路径交付。ATT-U1 / D22 整项仍未完成：本段提供主管来源核定和撤销、真实余额入账与旧抵扣/工资用途互斥；C 的申请占用/审批结算及 D 的页面、角色、浏览器验收继续后续实施。本段没有页面、部署或线上验收结论。

## 实施结果

主管读取已日结来源后，提交来源日结 ID、精确版本、假种、核定分钟、原因和请求身份。服务在门店/月锁、日结行锁后重新核对来源员工、门店、日期、发布排班、已日结时间和版本；扣除旧早退抵扣和已转休分钟，按已匹配 COMPENSATORY / SOURCE_ONLY 规则入账。一分钟等于1000000内部单位，不使用浮点天数，也不自行设法律发放数额。核定身份和历史来源版本在新API以十进制字符串返回；原日结API的既有身份字段类型保持。

转休独立来源台账只追加 APPLY/REVERSE，额度分桶/流水/命令与来源同事务保存。请求重放先于新版本拒绝，相同请求和内容返回原核定，不同内容拒绝。撤销保留原公司、规则、分钟和审计身份；已占用、消费、到期或结转不能撤销后再次把来源用于工资/抵扣。来源失效会保留原事实、把可用余额标记待核对，不生成负数，也不假装已撤销。

原门店权限先于历史归属诊断。员工当前组织和法人必须匹配原来源门店；仅检查必要档案字段和调岗动作元数据。来源当日或之后已确认调岗、缺少生效日期都拒绝自动确认历史归属，不读取工资/证件的前后快照。规则/工作地缺失或多匹配不默认发额度。

旧抵扣新增和候选、两条日结投影及工资投影统一扣除净转休，失效来源不能继续分配。原工资 calculateSalary 的 LegacySalaryWriteGuard 保持禁写；只修其保留实现的月锁/日结锁和净加班聚合，未重新启用工资新增。

## 事务和迁移边界

来源写锁顺序：门店/月 → 日结 ID 升序 → 原核定（撤销）→ 员工/档案/规则/工作地 → 额度账户和分桶 → 追加来源和流水。日结重算用同一日结行锁串行，本段不反向锁排班。C 消费转休分桶时必须先锁原来源日结并核对已冻结版本，不能仅依赖本段的只读 sourceProblem 标记。

真实 MySQL 5.7 首轮发现默认 RR 中月锁前提示读取形成旧快照：双核定和等待工资提交各失败一次，16个事务场景中14通过。失败日志与 XML 保留在 review-b08b-overtime/mysql57-first。修正为5个写入口显式 READ_COMMITTED，并拒绝加入已有非明确 RC 事务。HTTP 调用经服务代理创建 RC；B 与额度桥沿同事务；已有 RR 外层不能借 REQUIRED 静默保留旧快照。工资锁等待回归使用生产 Mapper 与显式 RC 事务，保留工资服务单元测试模拟禁写守卫仅检验未启用的内部逻辑。

上线顺序必须先执行 A 额度表迁移，再执行 sql/erp_oa_attendance_overtime_transfer_20260912.sql，核验只新增来源表和 convert 按钮，然后部署接线版本。迁移不分配现有角色权限；授权由既有组织权限流程明确配置。B SQL 被旧抵扣/日结/工资查询引用，缺表会明确失败，不能跳过迁移。A 自动发放 Job 默认关闭开关保持，启用配置顺序沿 A 交付。回滚应用前必须保留来源表和全部台账；有真实转休记录后不能退回忽略净转休的旧业务版本，先停用相关功能并做审计核对。本次仅在隔离合成数据库重复迁移，无线上写入。
