# S06 / D13 停用角色后端交付

## 本批规则

- 停用角色保留已有成员；管理员可解除关联，解除后的成员不得再新增关联至停用角色。
- 普通用户资料保存时，提交中的原停用角色绑定保持原关系行；省略 `roleIds` 表示不改角色，显式 `[]` 才清空。
- 专门授权接口要求非 null 角色数组；`[]` 仍允许清空。不得先删除关系再判断哪些属于原绑定。
- 任意一个新增目标角色停用、删除或不存在，拒绝整组新增/替换；既有解绑与菜单、部门、账号权限检查不扩改。

## 实际入口与实现

- `SysUserController.add/edit/patch/insertAuthRole` 对应 `SysUserServiceImpl.insertUser/updateUser/insertUserAuth`。新增用户在写用户前锁定并检查全部角色；更新与授权先读原绑定、检查完整选择，再差量删除/新增，保留交集。
- 角色控制器的 `/authUser/selectAll` 对应 `SysRoleServiceImpl.insertAuthUsers`。所有目标用户先通过原数据范围检查，再按用户 ID 排序锁定；只新增原来不存在的启用角色关联。重复选择既有成员为成功无操作，不虚构新增绑定或会话失效。
- 单个/批量取消授权保持原入口与校验，允许停用角色解绑。
- `HrOnboardingConfirmationService` 只读核对：已按排序后的角色行锁检查启用且未删除，再锁用户，使用 `insertUserRoleIfAbsent` 的 SQL 状态条件；无需修改入职流程。
- 用户导入写用户、普通资料更新、注册入口本次核对未发现其他绕开服务层新增用户角色关系的入口。

## 事务与并发

`RoleAssignmentGuard` 仅在现有服务事务内部调用；沿用已有 `sys_sign_hr_state` 行锁，随后按角色 ID 排序锁角色、按用户 ID 排序锁用户，最后锁关联行。新增 `SysUserRoleMapper.lockUserForRoleAssignment` 仅锁未删除用户，避免生成孤立关联。与入职确认的“角色 → 用户 → 关联”顺序一致；入职不持有全局配置锁，同样通过角色行锁与本批序列化。

角色编辑和状态切换都使用同一角色行的事务 UPDATE。状态切换的受影响成员名单改为持有角色锁后读取，避免漏掉刚完成的入职授权。若授权先提交，再停用，则新成员已属于原成员并被保留；若停用先提交，随后新增授权读取停用状态并拒绝。没有将可重试的死锁当作成功，也未扩大为全局权限框架改造。
