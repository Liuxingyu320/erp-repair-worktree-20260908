# B04 库存后端分批验收准备

状态：**只读准备；本文件为项目管理说明，不代表已实施、已测试或已部署。**

准备日期：2026-09-12。实现目录限定为 `Grok实施工作副本_20260912`，原 R/M 副本继续保留。业务代码由 Grok 编写，Codex 派单、审核和独立验收。本文只记录当前源码核对、分批建议与本机运行环境观察，没有启动容器、连接数据库或读取实际凭据。

## 已确认的业务要求

同一采购单允许在前批待检时继续登记新的到货批次；每批分别登记、分别质检。未检与拒收数量不得计入可用库存；合格数量才按质检事实入库。现有“让步接收”是独立受控流程，后续派单必须明确其已有边界，不得改成默认合格或用来绕过逐批质检。

先完成持久收货幂等，再开放多批待检。不能简单删除 `QC_PENDING` 守卫后即宣称完成。

## 最小实施批次

| 批次 | 问题与范围 | 核心交付 |
|---|---|---|
| 04A | R03：收货未知结果重试 | 持久请求 ID、冻结载荷、事务内唯一结果、原批次回放；PC/H5 重试沿用原请求 |
| 04B | INV-U3：多批独立待检 | 并行待检批次、正确累计收货与原单结论、仅本次检验的合格数量入库；依赖 04A |
| 04C | R07：退货并发占用 | 原采购单统一锁序、锁后当前读、提交/确认/取消的并发一致性 |
| 04D | INV-F3：零库存残余成本 | 最后一次扣库结清剩余总成本，出库与流水共用精确金额 |

### 04A：收货持久幂等

候选文件：
- `erp-modules/erp-inventory/src/main/java/com/erp/inventory/controller/InvPurchaseController.java`
- `erp-modules/erp-inventory/src/main/java/com/erp/inventory/service/IInvPurchaseService.java`
- `erp-modules/erp-inventory/src/main/java/com/erp/inventory/service/impl/InvPurchaseServiceImpl.java`
- 收货 DTO 及必要的结果 DTO；PC/H5 收货 API 和请求恢复调用方另在派单时列出准确允许清单。

现状：收货仅有 30 秒 `IdempotentSubmit`，没有持久请求 ID；`receivePurchase` 每次都新建批次。可复用 `InvQualityCommandExecutor` 与 `InvQualityCommandMapper` 的请求占用、指纹、结果回放和 MANDATORY 事务约束，使用独立的收货命令类型。保持既有“原单锁 → 命令 → 批次/明细”顺序；权限和仓库范围校验不能因回放绕过。

冻结原单、仓库、操作者、明细、到货时间及送货单信息；结果必须能标识原批次。相同 ID 不同载荷拒绝，成功后再次提交原 ID 回放原结果；业务事实与命令结果同事务提交/回滚。不能把送货单号当作唯一请求身份，合法的下一次到货使用新的 ID。

验收必须在全新 MySQL 测试实例中运行：
1. 两个独立连接同时提交同 ID 收 20，仅一个批次、累计收货 20，两次结果指向同一批次。
2. 首次收 20 成功但客户端丢响应；完成首批真实质检后、越过短期重复窗口并重建服务，再重试仍回放首批，不变成累计 40。
3. 同 ID 改数量、仓库或原单均拒绝；另一合法新 ID 可以登记下一批。
4. 在批次/明细已写后注入事务失败，命令、批次、明细全部回滚；同 ID 后续可正常重试。
5. PC/H5 网络失败恢复不能换 ID、不能串原单或串仓库；明确永久拒绝与结果未知。

### 04B：多批独立待检

候选文件：`InvPurchaseServiceImpl.java`、`InvReceiptBatchMapper`、`InvReceiptBatchDetailMapper`、`InvInboundRecordMapper` 对应 Java/XML，以及必要的采购明细累计查询、批次选择调用方。既有批次表已存在，不应未经证明重复建设一套批次结构。

已发现的派单陷阱：
- 接收第二批时继续锁原单和明细，按当前累计收货核对剩余量，不能仅放开状态校验。
- 旧 `qualityCheck` 会遍历全部待检批次；开放多批后不得让一次旧请求顺便处理未确认的新批次。必须限制旧入口或绑定确认时的批次集合。
- 当前最后一个批次结束后，原单 `qcStatus` 主要使用“最后处理批次”的统计，应改为正确的原单累计事实。
- 当前拒收后再次收货有删除旧拒收入库记录的路径；应保留批次/质检追溯，避免把新批处理成旧批恢复。
- 尚有任一批待检时，原单仍应呈现待检，已合格库存不因此消失；拒收对可重收到货量的影响应保持可追踪、不可重复扣回。

数据库验收：
1. 收 20 待检，再收 30 待检：两个批次，可用库存 0。
2. 仅首批合格 20：库存 20，第二批待检 30；第二批部分检验只增加本次合格数量。
3. 两批以不同顺序完成，原单累计数量和结论一致；一批拒收后新到货仍保留原拒收证据。
4. 同时登记新到货与处理旧批质检：采购累计、批次待检量、检验事件、入库记录、库存流水一致；不超原单剩余量。
5. 重复质检命令无重复库存/检验事件；错误仓库、错误批次及超过待检数量被拒绝。

### 04C：退货并发占用

候选文件：`InvPurchaseReturnServiceImpl.java`、`InvPurchaseReturnDetailMapper.java/xml`，以及需要复用的采购原单锁入口。

所有提交、确认、取消统一“原采购单 → 退货单 → 明细 → 库存”锁序。当前只锁各自退货单，历史占用使用普通聚合查询，可能在 REPEATABLE READ 下读到旧快照。锁后必须使用当前事实，不能仅加锁却保持普通快照聚合。若草稿允许改关联原单，取锁后重新核对关联，不能锁 A 却处理已改关联 B 的草稿。

数据库验收必须使用两个真实连接与屏障控制，而非仅 Mockito/内存替身：
1. 原合格 10，两张各 7 同时提交：仅一张占用成功，另一张明确失败；成功者仍可确认。
2. 7＋3 同时提交并确认，总计 10。
3. 取消释放占用后另一张可重试；确认与取消并发只能一个终态。
4. 故意在第二事务先建立旧快照、再等待第一事务提交，验证锁后读取不会遗漏新占用。
5. 无重复扣库或流水，无由锁序新增的循环等待；事务失败不得残留 submitted 占用。

### 04D：零库存成本结清

候选文件：
- `InvDeliveryNoticeServiceImpl.java`
- `InvStockCheckAdjustmentService.java`
- `InvPurchaseReturnServiceImpl.java`
- `InvStockServiceImpl.java`
- 统一成本分摊工具与必要的 `InvStockMapper.java/xml`。

当前以上四类服务均调用 `deductInvStockWithCost`。最后一次消耗全部 `currentQuantity` 时，用锁定库存剩余 `totalCost` 结清；不是仅耗尽 availableQuantity 就清零。中间分批统一精度与舍入规则。库存扣减、出库记录、库存流水和发货通知精确成本使用同一金额。

不能只在 SQL 把零库存总成本强制归零：那会留下出库/流水金额不一致并影响销售退货。未知或非法成本不能擅自变成零。历史残差数据整理另建审查清单，不在功能修复中自动清理存量。

数据库验收：3 件/2.00/均价 0.67 与 3 件/1.00/均价 0.33，整批及分批耗尽后数量和总成本都为 0；重新入库均价正确；发货后全退成本净额为 0；并发版本冲突、可用量保护与晚失败回滚仍有效。

## 现有启动约定与环境变量

1. `scripts/configure-testcontainers-docker.sh` 提供 `erp_configure_testcontainers_docker`：从 Docker 当前上下文解析 `DOCKER_HOST`；非默认 Unix socket 场景补 `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock`。它不会创建测试数据库。
2. 根 Maven 的 `new-business-mysql-it` profile 用 Failsafe 跑 `*IT.java`，使用 compiler output 作为 classesDirectory。库存已有 `NewBusinessMigrationsMySqlIT` 通过 Testcontainers 新建 MySQL 5.7.44/8.0.36，Docker 不可用时不能跳过；会重复应用迁移验证重入性。
3. `InvQualityCommandNativeMysqlTest`、`InvPurchaseQualityCommandWiringMysqlTest`、`InvPurchaseFactsNativeMysqlTest` 当前硬编码 `127.0.0.1:3306`，自己创建随机临时 schema；它们不能靠 `ERP_IT_MYSQL_HOST/PORT` 自动改目标。
4. `ImageGalleryMySqlTest` 和 `InvSalesReturnCostMySqlTest` 使用 `IMAGE_GALLERY_TEST_JDBC_URL`，要求 URL 中 schema 匹配 `codex_image_gallery_` 前缀，否则会跳过。其测试连接认证目前是测试代码固定值，不支持另外配置认证变量。
5. `InvTransferSourceMySqlIntegrationTest` 由 `ERP_REPLENISHMENT_MYSQL_INTEGRATION=1` 启用，固定本机 3306，并会 DROP/CREATE 固定名的专用 schema。本批不要顺带启用它。
6. `scripts/run-native-mysql-integration-tests.sh` 是人事模块四个事务测试的启动脚本，不是库存 B04 启动器。其变量包括 `ERP_IT_MYSQL_HOST`、`ERP_IT_MYSQL_PORT`、`ERP_IT_MYSQL_USER`、`ERP_IT_MYSQL_PASSWORD`、`ERP_IT_EXPECTED_MYSQL_VERSION_PREFIX`、`ERP_IT_RUN_ID`，默认拒绝远程；`ERP_IT_ALLOW_REMOTE_NONPROD` 仅为已有脚本能力，本批不应使用远程目标。
7. Java 17 为项目要求；本机默认 Maven 曾选择 Java 25，执行前显式指定 Java 17，或使用已缓存的 Maven/Temurin 17 镜像。

以上是源码中的参数名和行为约定，没有读取用户现有环境变量值、数据库认证文件或容器 Env。
