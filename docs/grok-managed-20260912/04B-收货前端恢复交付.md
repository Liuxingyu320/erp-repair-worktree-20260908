## 改动及用户行为

PC/H5 收货共用 `utils/purchaseReceiveRecovery.js`。在第一次 POST 前，用 IndexedDB 一个 readwrite 事务原子保存完整冻结 requestId、载荷、登录用户、业务组织和采购单。正常请求、网络未知结果和重开恢复都显式传 `X-Request-Id`；API 拒绝缺参，并在 Axios 序列化前再次检查账号和组织。未将认证令牌、Cookie 或凭据写入恢复库。

页面提供不依赖采购状态、剩余量或当前详情行的“核对上一笔收货”入口，按原载荷回放并展示原 receiptBatchId/batchNo。恢复先于最新剩余数量读取；PC 在重试时也先核对原命令，再决定是否校验新输入。旧命令成功不会顺带提交新输入；新到货须重新打开收货窗口、检查最新剩余量后明确确认。

对话框打开时冻结账号/组织/单据和已见操作代次；最终确认前冻结仓库、到货时间、批号、送货单、备注及 detailId/数量。验证和确认期间互斥；切单、关闭、组织/账号变化和 keep-alive 失活均使旧窗口后续动作失效。手机现有 MobileActionDialog 保持只读，由父页面传入原 item 与原组织。

共同采购动作规则已解除“上一批待检则不能新收货”的封锁：submitted 且仍有余量可以登记下一批，PC/H5 同步生效。无余量和其他状态仍不能新收货；原质检优先级、权限与取消约束保留。

## 持久化与并发边界

数据库为同源浏览器 `erp-purchase-receive-v1`，`commands` 每个 actor/dept/order 一条记录。跨窗口 compare-and-set 由 IndexedDB readwrite 事务完成，未使用 localStorage 假锁或强制 Web Locks，因此不依赖安全上下文的 Web Locks 能力。

ACTIVE/SETTLED 是待核对记录；结果展示后标记 ACKED，并保留上一代完整记录。旧窗口迟到确认或旧 ack 无法把新一代覆盖/清空。只有重新打开并捕获最新已确认代次的明确新到货，才能替换为新 requestId。当前页面重复点击互斥；同用户/组织多个窗口可回放同 ID，后台 04A 的持久幂等负责使业务落库一次。

该协调仅覆盖同一浏览器配置、同一 origin 的 PC/H5。不同浏览器、不同设备、不同 origin 不共享 IndexedDB，无法自动识别为同一现场到货；不能将此实现宣称为跨设备重复收货识别。当前账号/组织或权限改变时停止后续发送/确认，已发出的 HTTP 请求仍由服务端权限与事务控制。清理浏览器站点数据会丢失本地恢复证据，未增加自动清理功能。

存储不可用、损坏或事务失败时停止发送新命令；保存结果失败时保留原 ACTIVE 记录，继续原 ID 核对。04A receive 控制器没有能证明事务回滚的 receiveOutcome=REJECTED 契约，任意 ServiceException、HTTP 业务错误、超时、未知 5xx 或格式/身份异常均保留原命令。没有把错误消息或普通 code 当作“未执行”的证明，也未增加丢弃未知命令按钮；遇到永久拒绝而无法证明回滚时仍须保留记录并人工核对。
