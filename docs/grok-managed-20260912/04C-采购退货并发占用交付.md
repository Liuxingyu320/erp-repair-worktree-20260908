# 04C / R07 采购退货并发占用

## 问题与本批行为

原证据是两张各退 7 件的草稿争用合格入库 10 件，可同时变成 submitted，随后两张确认都被 14 > 10 阻断；原探针没有证明已超退实物库存。此次修复提交阶段的占用一致性，保持现有仓库权限、原单/明细关联与可用库存保护。

- 保存、提交已存草稿、直接保存并提交、确认与取消都先锁关联原采购单。已存单据随后锁退货单并重新核对原单 ID 与仓库，最后处理明细和库存；不能锁 A 却处理已经关联 B 的退货单。
- 草稿原单仍不可修改。新草稿先锁原单读取原明细，再插入退货单；整次直接提交的失败会回滚草稿/明细/状态。
- 额度校验读取锁后的原采购明细、原始入库记录和原始已占用退货明细，在 Java 累计；列表展示仍使用原只读汇总。
- 原采购明细 SQL 的 `stockedQuantity` 含普通子查询，不能仅靠外层 FOR UPDATE 消除旧快照。本批使用现有 `InvInboundRecordMapper.selectByOrderIdForUpdate` 重算：新批次只计 accepted + concession，旧记录只计 passed/concession；未检、拒收不提供退货额度，重复商品旧记录沿用唯一明细匹配规则。
- 已提交与已退货均占用额度；取消释放占用。确认与取消只接受各自锁后的合法状态；没有新增自动重试或绕过库存版本/可用量限制。

## 索引迁移与发布条件

按 `--hidden --no-ignore` 搜索工作副本、源码及修复快照，现有 `scripts/fixtures/repair-purchase-facts-20260909.sql` 保存了 2026-09-09 **本地 MySQL 8.0.45** 结构，主表有 `idx_ipr_purchase(purchase_order_id)`，明细有 `idx_iprd_return(return_id)`。该文件头明确不是生产结构声明，本批没有连接现用数据库。

新增 `sql/erp_inventory_purchase_return_lock_indexes_20260912.sql` 在新后端前执行，复用上述名字；缺失时补非唯一索引，已有正确首列的 BTREE 索引保持不动，同名结构不兼容则明确失败并停止发布。DDL 使用 INPLACE / LOCK=NONE，不回填或清理业务行，不修改共享 Docker bootstrap 列表。

新的占用查询用 `STRAIGHT_JOIN` 固定原退货单→明细顺序，并分别 `FORCE INDEX` 上述名字，防止 RR 扫描锁扩散到不相关采购单。缺索引时新查询会失败并回滚，因此迁移核对是发布前门槛，不能只发布 Java/XML。

回滚时优先保留兼容的非唯一索引。若确需移除，只能在回退不再依赖 FORCE INDEX 的后端之后，且发布前证明确为本批新建时，才删除对应索引；不得删除原来已有的同名索引。失败在第一个索引完成、第二个未完成时可能留下已完成的结构，重新运行可继续，不应把 DDL 当作业务事务回滚。
