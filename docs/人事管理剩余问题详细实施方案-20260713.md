## 1. 实施结论

下一步不应直接打开人事主数据强制门禁，也不应直接在业务库批量补负责人或员工档案。项目目前需要先完成四个结构性收口，再进入人工数据治理：

1. 统一“谁属于员工”的权威口径，排除内置管理员账号，同时把其余缺失档案的真实员工明确暴露为 P0。
2. 将部门负责人从自由文本升级为“负责人用户 ID + 姓名快照”，解决同名、改名、离职及无法通知具体人员的问题。
3. 让 Java API、DBA readiness SQL 和页面汇总使用同一套规则，把“去重员工数”和“问题覆盖人次”分开，并把当前只展示的门禁参数真正接入资源级写入校验。
4. 补齐健康证受理开关、完整流程测试、迁移预检和发布顺序；健康证表必须先迁移，再部署引用该表的代码。

上述完成后，在隔离测试库完成发布演练，再由 HR 和组织管理员通过正常页面治理 P0。只有 P0 清零、口径对账一致且连续观察至少一个完整工作日，才允许单独启用主数据强制门禁。

本方案预计工程实施 6～8 个工作日；人工治理预计 1～3 个工作日并取决于负责人确认速度，之后至少再观察 1 个完整工作日。总周期预计 8～12 个工作日。它只收口当前剩余风险，不替代总方案中后续的批量补录、法人主体和持续指标阶段。

## 3. 当前项目证据基线

### 3.1 员工口径

隔离测试库当前有 155 个 `del_flag='0'` 的用户：

| 分类 | 数量 | 计划口径 |
|---|---:|---|
| 内置管理员用户 ID 1 | 1 | 排除，不再要求岗位或员工档案 |
| 已有 `sys_user_profile` 的非管理员 | 148 | 纳入员工集合 |
| 缺少 `sys_user_profile` 的非管理员 | 6 | 纳入员工集合，并产生 `EMPLOYEE_PROFILE_MISSING` P0 |
| 权威员工候选总数 | 154 | HR 列表、完整度、readiness 和员工选择器统一使用 |

补充说明：现有 46 个“未建档”展示值由 39 个“已有档案但员工状态为空”和 7 个“完全没有档案”组成；后者包含内置管理员 1 个，因此真正需要 HR 确认并建档的是 6 个账号。不能把“状态为空”和“档案不存在”继续混为一个概念。

`sys_user.user_type` 当前 155 条全部为 `00`，且项目 `SysUser` 领域对象未公开该字段，不能作为本期员工身份判断依据。首版本期只排除项目已经明确保护的内置管理员，即 `UserConstants.isAdmin(userId)`；未来如果引入独立账号类型，再通过兼容迁移扩展政策。

### 3.2 部门负责人

按当前 Java 组织派生规则，需要负责人身份的节点共有 31 个：

| 状态 | 数量 |
|---|---:|
| `leader` 为空 | 30 |
| `leader` 有文本但无法唯一匹配有效用户 | 1 |
| 可唯一匹配并安全自动回填 | 0 |

因此不得根据姓名自动写 `leader_user_id`。31 个节点都必须由有权限的组织管理员通过员工选择器人工确认。

### 3.3 当前观察快照

- 当前旧规则 P0 共 31 行：30 行 `DEPT_LEADER_MISSING`，1 行用户 ID 1 的 `POST_MISSING_OR_DISABLED`。
- 当前 P1 有 45 行 `POSITION_CONFIG_MISSING`，现有在职使用关系为 0，可在 P0 后按未来入职优先级处理。
- 9 条字典路由当前均就绪。
- Java 页面当前把各问题行影响数相加，组织上下级问题覆盖同一员工时会重复计算。
- 新规则上线后，管理员无岗位问题应消失；预计新增 6 行员工档案缺失问题、1 行负责人身份无法解析问题。准确行数和去重影响数必须以新规则重新扫描结果为准，不能直接用旧快照加减得出发布结论。

## 4. 本期权威决策

### 4.1 员工集合规则

员工口径分成两个嵌套集合，避免为了治理统计而把离职历史从员工档案中隐藏：

```text
HR 档案访问集合 = sys_user.del_flag = '0' AND user_id 不是内置管理员

在岗治理集合 = HR 档案访问集合
              AND sys_user_profile.employee_status 不等于“离职”
              （档案不存在或状态为空仍纳入）
```

- HR 档案列表、详情、历史导出及 HR 健康证历史访问使用“档案访问集合”，因此已离职员工仍可按数据范围查询。
- 完整度当前队列、主数据问题、负责人候选、新健康证受理和在用岗位检查使用“在岗治理集合”。
- 账号是否停用不自动移除档案历史；`待离职` 仍属于在岗治理集合，只有明确状态“离职”退出当前治理。
- 任何前端查询参数都不能包含内置管理员，也不能把“档案访问”请求伪装成“在岗治理”内部上下文。

### 4.2 缺失档案处理

- 新增稳定问题码 `EMPLOYEE_PROFILE_MISSING`，严重度 P0。
- 不在查询时自动建档，不执行批量 SQL 造档。
- 在员工档案页提供“建立员工档案”显式动作；HR 确认账号确属员工后调用幂等服务创建最小档案，再进入正常编辑流程补真实数据。
- 创建最小档案只写 `user_id` 和审计字段，不生成虚假工号、状态、岗位、合同或负责人。
- 员工本人现有资料补全流程仍可创建本人档案；两条路径必须依赖 `sys_user_profile.user_id` 唯一约束并处理并发重复。

### 4.3 部门负责人身份

- `sys_dept` 新增可空字段 `leader_user_id bigint(20)` 和普通索引。
- 保留现有 `leader` 字段作为姓名快照和旧接口兼容字段，不删除、不改含义。
- 选择负责人时，后端校验其属于当前操作者数据范围内的有效员工候选，并一次写入 `leader_user_id` 与最新 `nick_name` 快照。
- 不强制负责人必须与部门同节点，因为公司/区域负责人可能归属上级组织；但必须在操作者可管理范围内。
- 负责人账号停用、删除、离职、越出数据范围或只有文本没有 ID 时，readiness 输出 `DEPT_LEADER_UNRESOLVED` P0。
- 观察期允许未触碰的旧组织保持待治理状态；新增组织、重新启用组织或明确修改负责人时必须选择稳定身份。强制门禁开启后，所有受规则约束的启用节点都必须有有效 ID。

### 4.4 readiness 权威口径

- Java 纯评估器是在线 API 权威实现。
- DBA SQL 必须镜像同一员工集合、组织路径和负责人归属规则，不再使用“所有非 GROUP/STORE/WAREHOUSE 节点都必须有负责人”的近似规则。
- `affectedEmployeeCount` 改为所有过滤后问题覆盖员工 ID 的并集数量。
- 新增 `affectedOccurrenceCount` 表示各问题行影响人数之和，保留工作量视角。
- 页面分别显示“受影响员工（去重）”和“问题覆盖人次”，不能再用同一字段表达两种含义。
- 强制门禁使用资源级校验，不在每次保存时扫描并要求全租户 P0 同时清零；其他组织的历史问题不能阻断当前合法资源的修复。

### 4.5 健康证开关语义

按现有迁移备注，`feature.hr.health-certificate.enabled` 定义为“新受理入口开关”，不是删除历史数据或中断待审核流程的总停机开关：

| 能力 | 开关为 `false` | 原因 |
|---|---|---|
| 员工查看本人历史 | 允许 | 已有数据仍属于本人 |
| 新建/编辑草稿 | 禁止 | 停止新受理 |
| 提交审核 | 禁止 | 停止新增待审核量 |
| HR 列表、详情、附件 | 允许 | 需要处理已有业务 |
| HR 审核已有待办 | 允许 | 避免待审核记录被永久卡住 |
| 已审核证件到期提醒 | 继续 | 证件义务不因入口关闭而消失 |

能力接口必须返回明确的 `intakeEnabled` 和说明文案。配置缺失、空值或非法值按 `false` 处理。即使开关为 `false`，员工 Mapper 仍联表查询健康证状态，因此数据库迁移依旧是代码部署前的硬前置条件。

- 新增、修改、启用部门的负责人校验已在测试和试点组织验证。
- HR、组织管理员、测试和发布负责人共同签字。

任何一个条件不满足都继续观察，不允许通过修改问题严重度、写占位数据或直接删问题记录达到“清零”。

## 9. 目标环境发布顺序

业务目标环境必须按以下顺序执行；本方案编写阶段不对业务库执行任何写入：

1. 确认发布授权、维护窗口和回滚责任人。
2. 使用只读账号执行 `SELECT DATABASE(), VERSION()`，确认目标不是隔离测试库，也没有连错环境。
3. 备份 `sys_dept` 负责人字段、相关 `sys_config`、`sys_menu`、`sys_role_menu` 的发布前快照和表结构；备份文件受控保存。
4. 执行 `erp_hr_dept_leader_identity_20260713.sql`。
5. 执行 `erp_hr_health_certificate_20260713.sql`。这是部署当前员工 Mapper 代码前的硬前置。
6. 执行修正后的 `erp_hr_data_quality_20260713.sql`。
7. 运行两份 verify SQL 和 readiness SQL；任何表、列、索引或参数不符合即停止发布。
8. 明确核对两个运行开关。若环境历史值为 `true`，通过单独审批的配置变更将健康证受理和主数据强制门禁分别切为 `false`，不得通过重跑迁移完成该动作。
9. 部署后端，再部署前端；启动后先验证 capability、员工列表、部门详情和 readiness。
10. 保持健康证受理关闭、主数据强制门禁关闭，完成 HR-R5 人工治理。
11. 分别通过 Gate A 和 Gate B 后，再单独修改对应参数；每次只改一个开关并记录操作者、时间和前后值。

禁止在发布脚本中自动清空、删除或批量伪造员工、岗位、负责人及健康证数据。

## 10. 回滚方案

### 10.1 应用回滚

- 前端回滚到上一构建。
- 后端回滚到上一版本。
- 立即设置 `feature.hr.health-certificate.enabled=false`，停止新受理。
- 如果主数据门禁已开启，立即设置 `hr.master-data.enforce-on-enable=false`，恢复观察模式。

### 10.2 数据库回滚原则

- 不删除 `hr_employee_health_certificate` 表，不删除 `sys_dept.leader_user_id`，避免丢失已写入历史和负责人身份。
- 保留 `leader` 姓名快照，旧应用可继续读取。
- 新增字段、索引、参数和菜单默认保留；应用回滚后通过开关和菜单权限隔离新入口。
- 只有确认没有任何正式数据、备份完整且另行审批时，才允许制定单独的结构回退脚本；本方案不提供自动 DROP。

### 10.3 数据治理回滚

- 人工建立的员工档案和确认的负责人属于业务主数据，不能通过技术回滚批量删除。
- 误选负责人通过部门页面更正并保留操作日志。
- 误建档必须由 HR 复核账号身份后走受控更正，不执行直接 DELETE。

## 11. 主要风险与控制

| 风险 | 影响 | 控制 |
|---|---|---|
| 工作区已有大量并行改动 | 覆盖他人代码 | 只改清单文件，实施前后逐文件 diff，不做 reset/checkout |
| 员工口径变化影响 155 基线 | 报表数字变化 | 保留旧基线，新增 154 权威基线并解释差异 |
| 负责人无可自动匹配数据 | P0 治理量大 | 提供高效选择器，按影响面排序，禁止占位或猜测 |
| 姓名快照与 ID 不一致 | 页面误导 | ID 为权威，readiness 输出差异，保存时同步快照 |
| SQL 与 Java 再次漂移 | 发布判断失真 | 纯评估器、原生 parity 测试和同版本观察记录 |
| 开关误当成 schema 兜底 | 部署后员工查询缺表 | 明确迁移先于代码，verify SQL 作为硬门槛 |
| 迁移重跑改回配置 | 已启用能力被意外关闭 | 删除强制 UPDATE，只插入缺失默认值 |
| MySQL 8 通过但 5.7 失败 | 目标发布中断 | 禁用 8.0 专属语法；有 5.7 目标时必须在同版本测试实例演练 |
| 隔离库长期保留员工副本 | 隐私和存储风险 | 记录用途、限制访问、签字后删除 |
