## 1. 实际结果

已建立独立 V2 只读接口 `GET /transfer/shipments/{shipmentId}/receipt-planning`。接口要求调拨收货权限，响应强制 `Cache-Control: no-store`，服务事务标记为 `readOnly = true`，没有 `@PersistentCommand`，不会创建命令台账。

权威规划仅接受 V2 发货批次，并在一次批量读取中核验：

1. 发货批次、调拨单、来源仓快照与目标组织方向；
2. 目标仓明细库存模式、对账状态和对账批次；
3. 阶段 11 固化的来源分配、成本守恒与序列号发货审计；
4. 目标仓启用的正常存储库位与残损隔离库位；
5. 发货明细已发数量与来源分配数量守恒。

纯函数 Composer 对全部事实稳定排序并生成 `receipt-plan-v1` SHA-256 指纹。成本参与服务端指纹和守恒校验，但不会进入前端 VO。任何归属、模式、数量、批次、序列号或库位事实无法核验时都会 fail closed。

当前没有“每个来源分配已收数量”持久化事实，所以只要发货明细已有历史累计收货，本阶段会明确阻断，绝不把明细累计值猜分到各来源批次。该缺口留给阶段 12C 的专属收货明细事实解决。

前端新增浏览器安全的只读契约与 HTTP Reader，校验字符串 ID、十进制数量、目标库位边界、分配守恒、序列号唯一性和响应归属。Reader 没有注入默认 Gateway，也没有新增页面、按钮或写请求。
