# ERP-NEW_2 阶段 13O：差异裁决动作执行生命周期与惰性事件结构实施计划

> 日期：2026-08-03
>
> 分支：`codex/erp-new-2-rebuild`
>
> 基线：`43d23e17 feat: coordinate adjudication submission`
> 范围：五类裁决动作的纯执行状态机、效果分类、守恒校验和惰性事件结构；不执行库存、物流或财务 mutation，不开放接口，不启用运行 Gate

> 后续修正：阶段 13P2 审计确认异步动作必须在 `dispatch` 时绑定子调拨引用，并允许同一引用依次追加调度、完成两条事件。当前权威约束以阶段 13P2 计划和最新代码为准。

## 1. 结果目标

阶段 13N 已能安全创建并核验裁决计划，但计划头仍固定为 `adjudication_planned`，动作固定为 `pending`。正式方案要求补发、退回、报损、责任调整或运输损耗核销的真实效果完成后，差异事项才能进入 `resolved`。

阶段 13O 先冻结动作执行的可信领域边界：每个动作的效果归属、允许的状态转换、事项版本、数量金额守恒、执行权限和事件指纹必须可离线验证。后续事务只能消费该纯策略输出，不得在 Service、Mapper 或页面中自行推导状态。

本阶段不会把“已生成执行意图”误报为“物理效果已发生”。

## 2. 动作效果分类

服务端根据差异类型和动作类型唯一推导 `effectKind`，客户端不得提交或覆盖：

| 差异 | 动作 | 效果类型 | 生命周期 |
|---|---|---|---|
| `shortage` | `reship` | `reship_workflow` | 异步：`pending → in_progress → completed` |
| `damaged` | `return_to_source` | `return_workflow` | 异步：`pending → in_progress → completed` |
| `damaged` | `damage_write_off` | `quarantine_write_off_and_loss_ledger` | 原子：`pending → completed` |
| 两者 | `responsibility_adjustment` | `responsibility_ledger` | 原子：`pending → completed` |
| `shortage` | `transport_loss_write_off` | `shortage_loss_ledger` | 原子：`pending → completed` |
| `damaged` | `transport_loss_write_off` | `quarantine_write_off_and_loss_ledger` | 原子：`pending → completed` |

“原子完成”只表示未来执行事务必须把对应库存/责任/损失台账与状态变化放在同一事务中；纯策略本身不执行这些效果。

异步补发和退回只有在同一事务创建受约束的子工作流后才能进入 `in_progress`，并且只有子工作流的权威完成事实与引用核验成功后才能进入 `completed`。

## 3. 状态与版本不变量

动作状态仅允许：

- `pending`：尚未调度；
- `in_progress`：补发或退回子工作流已创建但未完成；
- `completed`：对应权威效果已经完成；
- 失败尝试不改变动作状态，依赖事务回滚和命令审计，不新增可被误解为完成的失败状态。

动作转换：

- `dispatch`：仅针对 `pending`；异步效果转 `in_progress`，原子效果转 `completed`；
- `complete`：仅针对异步效果的 `in_progress`，且必须携带格式受限的权威效果引用；
- 不允许回退、跳过异步完成证据、重复完成或对终态动作再次执行。

每次成功转换：

- `executionVersion` 精确加一；
- 差异事项 `caseVersion` 精确加一；
- 其他动作状态和版本保持不变；
- 当前及目标计划/事项状态由全部动作推导，不接受请求声明。

聚合状态：

- 全部 `pending`：`adjudication_planned`；
- 至少一个 `in_progress` 或 `completed`，但未全部完成：`adjudication_executing`；
- 全部 `completed`：`resolved`。

只有最后一个未完成动作成功完成时，计划和事项才同时进入 `resolved`。

## 4. 纯策略输入与输出

新增 `InvTransferReceiptDiscrepancyAdjudicationExecutionPolicy`：

- 输入 `Request`：请求 ID、事项/裁决/动作标识、预期事项版本、预期动作版本、命令和可选效果引用；
- 输入 `Boundary`：服务端锁定后的事项状态/版本、计划头、决定指纹和全部动作快照；
- 输入 `Actor`：用户、用户名和独立执行权限 `inv:transfer:discrepancy:execute`；
- 输出不可变 `PreparedExecution`：锚点、效果类型、前后状态/版本、数量金额责任、聚合状态、执行人时间和事件指纹；
- 列表必须防御性复制，输出不得包含 Mapper、HTTP、环境配置或可执行回调。

校验至少包括：

- 事项、计划和动作标识/版本完全匹配；
- 计划决定指纹为合法 SHA-256；
- 动作按 `sequence=1..N` 连续且标识唯一；
- 动作数量总和等于计划数量、金额总和等于计划金额；
- 动作类型与差异类型兼容，数量金额精度和责任方合法；
- 当前聚合状态与事项/计划状态一致；
- 请求 ID、权限、操作者、时间和效果引用合法；
- 事件指纹锚定请求、决定、动作、状态、版本、效果引用和执行人。

## 5. 惰性数据库结构

新增 `sql/erp_inventory_transfer_discrepancy_adjudication_execution_v2_20260803.sql`：

1. 使用 MySQL 5.7 可重复执行的列添加过程，为动作表增加 `execution_version bigint NOT NULL DEFAULT 0`；
2. 新增追加式 `inv_transfer_receipt_discrepancy_adjudication_execution_event`；
3. 事件保存请求幂等标识、事项/计划/动作锚点、决定指纹、命令、效果类型、前后状态与版本、数量金额、责任方、可选效果引用、事件指纹、权限和操作者；
4. `request_id` 唯一，动作/版本唯一，防止同一转换重复追加；
5. 只创建结构，不包含业务 `INSERT/UPDATE/DELETE`、数据库名、密码、种子、Gate 配置或 Docker 初始化复制。

该结构是未来事务的前置条件，不等于迁移已执行。
