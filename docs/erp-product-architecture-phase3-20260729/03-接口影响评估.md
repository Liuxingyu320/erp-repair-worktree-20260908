# ERP 第三阶段接口影响评估

> 文档版本：V1.0 评审稿
> 日期：2026-07-29
> 范围：PC Web、移动端、内部服务、审批回调、工作台/消息/待办聚合
> 约束：本文只冻结接口方向，不授权立即新增、删除或修改接口

## 1. 总体结论

1. PC 与移动端对同一业务对象调用同一业务服务和同一写接口。
2. 可以增加面向移动体验的只读聚合接口，但聚合层不得实现采购、库存、人事或审批写逻辑。
3. 库存采购申请新增独立接口；现有库存采购订单接口保留兼容。
4. 行政采购继续使用 `/oa/purchase/*`，不与库存采购请求合并。
5. 盘点增加“开始并冻结”和“冻结状态”接口；正常释放由业务流程驱动，紧急释放为 PC 专权。
6. 入职增加资料、签署、最终审批和激活状态接口；当前直接 `confirm` 创建员工的语义需要兼容迁移。
7. 审批动作统一进入 `/approval/*`；业务模块旧审批动作接口在切换期只作为兼容层。
8. 功能中心新增统一有效能力接口；客户端的按钮显隐不能替代服务端校验。
9. 当前不存在请假业务接口，不注册空壳审批接口。

## 2. 当前接口事实

| 领域 | 当前外部路径 | 当前事实 |
|---|---|---|
| 库存采购订单 | `/inventory/purchase/*` | PC 和移动共用；提交后直接进入订单执行，无独立申请审批 |
| 行政采购 | `/oa/purchase/*` | 与库存采购分离；已接统一审批 |
| 盘点 | `/inventory/stockCheck/*` | 创建即快照；提交时检测库存变化；仍有业务模块审批动作接口 |
| 入职 | `/system/hr/onboarding/*` | `ready → confirm` 后直接创建/关联员工和账号 |
| 电子签约 | `/oa/signPackage/*` | 移动签署/拒签使用当前登录用户所有权 |
| 统一审批 | `/approval/instances`、`/approval/tasks/*`、`/approval/todo/*` | 已具备实例、动作和待办 |
| 待办 | `/approval/todo`、`/inventory/todo`、`/oa/todo`、`/system/todo` | 前端当前按 Provider 聚合 |
| 公告/通知 | `/system/notice/*` | 公告、收件箱和已读；不是完整业务消息中心 |
| 功能能力 | 登录信息中的 `businessFeatures`、各模块 capabilities | 来源分散，主要为全局布尔值 |

当前 `erp-ui` 的 PC 和移动页面大多复用同一套 API 文件，这一方向正确，应保留。

## 3. 统一接口契约

### 3.1 业务详情响应

所有核心业务详情至少返回：

| 字段 | 说明 |
|---|---|
| `businessId` | 稳定业务主键 |
| `businessNo` | 用户可见编号 |
| `businessType` | 明确区分库存采购、行政采购、盘点、入职等 |
| `status` | 稳定状态码 |
| `statusLabel` | 服务端或统一字典生成的中文名称 |
| `version` | 当前业务行版本 |
| `allowedActions` | 当前用户、组织、功能开关和状态共同计算的动作 |
| `approvalInstanceId` | 存在审批时返回 |
| `approvalRound` | 当前或最近审批轮次 |
| `updatedAt` | 最近更新时间 |
| `traceRef` | 可选的脱敏追踪引用，不返回内部日志 |

PC 和移动获取同一业务 ID 时，上述字段必须一致。

### 3.2 写命令请求

所有创建、提交、审批、收发货、盘点调整、签署处置和激活动作至少使用：

- `requestId` 或 `Idempotency-Key`；
- `version`；
- 明确动作参数；
- 退回、拒绝、取消、关闭、作废、紧急释放的原因码和说明；
- 当前组织通过受控请求头/登录上下文传递，不接受正文随意覆盖；
- 附件只传统一 `fileId`，不传客户端本地路径。

同一幂等键和相同载荷重复请求返回首次业务结果；同一幂等键但不同载荷返回 `IDEMPOTENCY_CONFLICT`。

### 3.3 统一错误

| 错误码 | 场景 | 客户端行为 |
|---|---|---|
| `FEATURE_DISABLED` | 功能未开放 | 显示关闭原因，不展示假空数据 |
| `FEATURE_CONFIG_UNAVAILABLE` | 无法确认开关状态 | fail-closed，提示稍后重试 |
| `FORBIDDEN` | 无功能权限 | 不重试，不泄露对象详情 |
| `DATA_SCOPE_DENIED` | 超出数据范围 | 不重试 |
| `ORG_CONTEXT_MISMATCH` | 当前组织与业务对象不匹配 | 要求切换组织或返回 |
| `BUSINESS_STATE_CONFLICT` | 当前状态不允许动作 | 刷新详情与动作 |
| `VERSION_CONFLICT` | 并发版本变化 | 展示最新数据，禁止静默覆盖 |
| `IDEMPOTENCY_CONFLICT` | 幂等键被不同请求复用 | 生成新请求 ID 前先核对首次结果 |
| `APPROVAL_START_PENDING` | 业务已提交、审批发起待重试 | 显示“提交处理中”，不重复建单 |
| `APPROVAL_CALLBACK_PENDING` | 审批已决策、业务回写处理中 | 显示一致性处理中 |
| `INVENTORY_FROZEN` | 盘点冻结阻止库存写入 | 显示盘点编号和处理方式 |
| `INVENTORY_ADJUSTMENT_CONFLICT` | 盘点调整与库存版本冲突 | 禁止释放，进入补偿 |
| `SIGN_REMEDIATION_REQUIRED` | 已签合同需要处置 | 引导到整改/合同处置 |
| `ACTIVATION_PENDING` | 入职激活编排处理中 | 轮询或订阅结果，不重复激活 |
| `DEPENDENCY_UNAVAILABLE` | 下游服务不可用 | 保留业务中间态并可重试 |

HTTP 状态、业务错误码和用户文案应统一映射，不能所有失败都返回“操作失败”。

## 4. 库存采购接口

### 4.1 新增库存采购申请

建议外部接口：

| 方法与路径 | 用途 | 主要权限 |
|---|---|---|
| `GET /inventory/purchase-requests` | 管理范围列表 | `inv:purchaseRequest:list` |
| `GET /inventory/purchase-requests/my` | 本人申请 | 登录 + 所有权 |
| `GET /inventory/purchase-requests/{id}` | 详情、状态、动作和来源订单 | query/所有权/审批任务 |
| `POST /inventory/purchase-requests` | 创建草稿 | `inv:purchaseRequest:add` |
| `PUT /inventory/purchase-requests/{id}` | 编辑草稿或已退回申请 | `inv:purchaseRequest:edit` |
| `POST /inventory/purchase-requests/{id}/submit` | 提交统一审批 | `inv:purchaseRequest:submit` |
| `POST /inventory/purchase-requests/{id}/withdraw` | 撤回 | 所有权 + 状态规则 |
| `POST /inventory/purchase-requests/{id}/cancel` | 取消 | 所有权/专权 + 原因 |
| `POST /inventory/purchase-requests/{id}/close` | 关闭剩余需求 | `inv:purchaseRequest:close` |
| `POST /inventory/purchase-requests/conversions` | 合并/拆分生成订单 | `inv:purchaseRequest:convert` |
| `GET /inventory/purchase-requests/{id}/orders` | 查看转换关系 | query/所有权 |
| `POST /inventory/purchase-requests/export` | 导出 | `inv:purchaseRequest:export` |

移动端和 PC 端共用这些接口。移动只呈现适合本人申请、查看和审批的字段；PC 使用同一接口提供合并、拆分和批量管理。

### 4.2 现有采购订单接口

现有 `/inventory/purchase/*` 在 B01 保留，处理方式：

| 当前接口 | 处理 |
|---|---|
| `POST /save` | 保留兼容；新流程主要由申请转换创建订单 |
| `POST /submit` | 语义改为“确认订单可执行”前先提供新版本接口；不直接改坏旧客户端 |
| `GET /list`、`/my`、`/{orderId}` | 保留，详情新增来源申请关系和统一动作 |
| `POST /receive/{orderId}` | 保留，增加版本、幂等和冻结守卫 |
| `POST /qc/*` | 保留，质检过账前检查冻结 |
| `DELETE /delete/{orderId}` | 标记废弃；草稿删除与订单取消分开 |
| `DELETE /{orderId}` | 迁移为显式 `POST /{id}/cancel`，要求原因和版本 |

不在一个版本中直接移除旧接口。先发布新接口、前端切换、监控旧调用，最后再进入废弃期。

### 4.3 行政采购

`/oa/purchase/*` 路径保持稳定。调整点：

- 响应 `businessType=OA_ADMIN_PURCHASE`；
- 待办标题改为“行政采购审批”；
- `save`、`submit`、`withdraw`、`close` 使用独立权限；
- 审批动作仍进入统一 `/approval/tasks/*`；
- 不增加可以把行政申请转换成库存订单的接口。

## 5. 冻结盘点接口

### 5.1 目标接口

| 方法与路径 | 用途 | 说明 |
|---|---|---|
| `POST /inventory/stockCheck/create` | 创建盘点草稿 | 暂不冻结 |
| `POST /inventory/stockCheck/{id}/start` | 原子生成快照并冻结 | 新增；必须幂等 |
| `GET /inventory/stockCheck/{id}/freeze` | 查看冻结范围、状态和阻塞信息 | PC/移动共用 |
| `POST /inventory/stockCheck/input/{id}` | 录入实盘数量 | 仅活动冻结批次 |
| `POST /inventory/stockCheck/submit/{id}` | 提交差异审批或无差异完成 | 校验冻结 token |
| `POST /inventory/stockCheck/{id}/withdraw` | 撤回审批 | 按规则释放并使本轮失效 |
| `POST /inventory/stockCheck/cancel/{id}` | 取消并释放 | 要求原因和版本 |
| `POST /inventory/stockCheck/{id}/emergency-release` | 紧急释放 | PC 专权、双确认 |
| `GET /inventory/stockCheck/{id}/blocked-operations` | 查看被阻塞业务摘要 | 脱敏且分页 |

正常审批通过后的调整和释放由回调编排完成，不开放“先调整”“再释放”两个可任意调用的公共接口。

### 5.2 所有库存写接口的共同变化

以下类型在写入库存前调用同一冻结守卫：

- 采购质检入库；
- 销售/领用出库；
- 采购退货、销售退货；
- 调拨发货与收货；
- 手工调整；
- 盘点调整；
- 批次、库位和序列库存变化；
- 任何新增库存写入口。

守卫输入至少包含组织、仓库、物料、批次/库位、业务类型、业务 ID 和请求 ID。命中冻结时不做部分写入。

## 6. 入职与签约接口

### 6.1 当前兼容问题

当前：

```text
POST /system/hr/onboarding/{id}/ready
POST /system/hr/onboarding/{id}/confirm
```

`confirm` 会直接创建或关联用户和员工档案。目标流程增加资料预校验、签署、最终审批、激活和补偿后，不能继续让该接口同时表达“审批通过”和“全部激活完成”。

### 6.2 目标业务动作

建议逐步增加：

| 方法与路径 | 动作 |
|---|---|
| `POST /system/hr/onboarding/{id}/invite` | 创建/关联候选人身份并发送资料任务 |
| `GET /system/hr/onboarding/my/{id}` | 候选人查看本人入职任务 |
| `PUT /system/hr/onboarding/my/{id}/data` | 候选人分步保存本人资料 |
| `POST /system/hr/onboarding/{id}/data-review/pass` | HR 资料和合同关键字段预校验通过 |
| `POST /system/hr/onboarding/{id}/return` | 退回资料或签署后整改 |
| `POST /system/hr/onboarding/{id}/sign-package` | 幂等创建并关联签约包 |
| `GET /system/hr/onboarding/{id}/sign-packages` | 查看签约版本关系 |
| `POST /system/hr/onboarding/{id}/submit-activation-review` | 发起最终入职审批 |
| `POST /system/hr/onboarding/{id}/activate` | 系统/受控编排入口，不由普通客户端直接调用 |
| `POST /system/hr/onboarding/{id}/retry-activation` | PC 专权重试补偿 |
| `POST /system/hr/onboarding/{id}/start-termination` | 已签后终止入职并进入合同处置 |
| `POST /system/hr/onboarding/{id}/complete-remediation` | 完成整改后重新提交 |

候选人接口只允许访问当前登录身份关联的入职任务，不使用普通 HR 列表权限。

### 6.3 `confirm` 兼容策略

1. 新流程开关关闭时，旧 `confirm` 保持原语义；
2. 新流程开关开启时，旧接口只允许旧数据调用；
3. 新入职数据必须通过审批回调触发激活编排；
4. 前端切换后记录旧接口调用量；
5. 无调用且回退期结束后标记废弃；
6. 不把已签、待整改的数据强制映射回 `READY`。

### 6.4 签约接口

现有 `/oa/signPackage/mobile/{packageId}/sign`、`refuse`、`final-confirm` 继续使用。新增或扩展：

- 详情返回 `onboardingId` 或受控业务引用；
- 发送前校验签约包属于当前入职任务的当前版本；
- 完成签署后发布幂等业务事件；
- 已签后由入职域决定激活、整改或终止；
- 签约域负责签署证据和作废，不直接删除入职；
- 候选人仍通过登录身份和签约包所有权访问，不通过传入 employeeId 冒充。

## 7. 功能中心接口

### 7.1 当前用户有效能力

建议统一为：

`GET /system/features/effective`

返回：

- 功能编码；
- 有效状态：`ENABLED/DISABLED/UNAVAILABLE/NOT_INSTALLED/CLIENT_UPGRADE_REQUIRED`；
- 用户可见原因码和简短说明；
- 当前作用范围；
- 最低客户端版本；
- 是否只阻止新建；
- 依赖功能摘要；
- 结果版本/更新时间。

登录信息可继续返回精简能力快照，但客户端进入关键页面或执行写动作前应使用最新有效能力；服务端写接口始终重新判断。

### 7.2 管理接口

| 方法与路径 | 用途 |
|---|---|
| `GET /system/feature-center/features` | 功能目录 |
| `GET /system/feature-center/features/{code}` | 详情、依赖和当前发布 |
| `POST /system/feature-center/features/{code}/validate` | 发布前检查 |
| `POST /system/feature-center/features/{code}/changes` | 创建变更草稿 |
| `POST /system/feature-center/changes/{id}/approve` | 高风险变更复核 |
| `POST /system/feature-center/changes/{id}/publish` | 发布 |
| `POST /system/feature-center/changes/{id}/rollback` | 回退到上一个已知状态 |
| `GET /system/feature-center/features/{code}/history` | 变更审计 |

一期只开放全局运行时开关。部署开关只读，`NOT_INSTALLED` 模块不可发布为开启。

### 7.3 内部接口

服务间使用批量解析，避免每个请求逐键查询：

`POST /system/inner/features/evaluate`

输入功能编码、用户、组织、角色、客户端和业务上下文；输出签名/带版本的有效能力结果。调用失败必须 fail-closed。

现有 `/system/config/inner/configKey/{configKey}` 在迁移期保留。

## 8. 移动五入口聚合接口

移动聚合层只负责读模型和导航，不拥有业务状态机。

建议路径：

| 路径 | 返回 |
|---|---|
| `GET /system/mobile-shell/workbench` | 今日数据、待办计数、快捷入口、常用功能、业务提醒 |
| `GET /system/mobile-shell/messages` | 系统、审批、任务、库存异常、合同提醒 |
| `GET /system/mobile-shell/todos` | 待审批、待执行、已退回、风险和个人任务 |
| `GET /system/mobile-shell/applications` | 按角色、权限、组织、开关和客户端计算的应用目录 |
| `GET /system/mobile-shell/mine` | 本人信息、组织、设置和个人业务入口摘要 |

共同要求：

- 返回 `generatedAt`、当前组织和结果版本；
- Provider 部分失败时返回 `partial=true`、失败来源和重试信息，不用 0 掩盖失败；
- 计数与列表使用同一过滤条件；
- 深链包含业务类型和业务 ID，打开时重新鉴权；
- 快捷入口不缓存过期权限；
- 所有写动作跳转到统一业务接口或统一审批接口；
- PC 可以复用相同聚合数据，但不要求使用相同页面布局。

### 8.1 工作台

工作台结果按卡片返回：

- `cardCode`；
- `title`；
- `metric`、`unit`、`dataStatus`；
- `deepLink`；
- `requiredFeature`；
- `updatedAt`；
- `availableActions`。

接口失败、无权限、功能关闭和真实 0 必须为不同状态。

### 8.2 消息

消息统一字段：

- `messageId`、`messageType`；
- `title`、脱敏摘要；
- `businessType`、`businessId`；
- `read`、`createdAt`；
- `deepLink`；
- `sourceService`。

标记已读只改变消息状态，不完成业务待办。

### 8.3 待办

待办统一字段：

- `todoId`、`todoType`、`category`；
- `businessType`、`businessId`、`approvalInstanceId`；
- `title`、`status`、`priority`、`dueAt`；
- `availableActions`；
- `deepLink`；
- `provider`、`providerStatus`。

审批待办动作统一调用 `/approval/tasks/*`；库存异常等执行待办调用所属业务接口。

### 8.4 应用

应用目录由服务端返回：

- 一级模块、应用编码、名称和图标键；
- PC/移动支持情况；
- 当前是否可用及原因；
- 深链；
- 排序和常用标记；
- 所需功能、权限和组织类型。

前端不能用本地静态菜单独立决定业务可用性。

## 9. 统一审批接口

### 9.1 保留的统一入口

内部：

- `POST /approval/inner/approval/instances/start`
- `POST /approval/inner/approval/instances/withdraw`
- `GET /approval/inner/approval/instances/{id}`
- `GET /approval/inner/approval/status`

外部：

- `GET /approval/instances`
- `GET /approval/instances/{id}`
- `POST /approval/tasks/{id}/approve`
- `POST /approval/tasks/{id}/return`
- `POST /approval/tasks/{id}/reject`
- 受控转交、终止和回调重放接口
- `/approval/todo/*`

实际网关路径以现有路由为准；不得再为 PC 和移动各加一套动作端点。

### 9.2 业务模块提交

业务提交采用：

```text
业务事务写入 SUBMITTING
+ 本地审批发起 Outbox
→ 异步或可靠同步创建统一审批实例
→ 回写 approvalInstanceId
→ 业务进入 PENDING_APPROVAL
```

远程审批暂时不可用时，业务单据保留为 `SUBMITTING` 或明确失败状态，不回退成看似未提交的草稿，也不重复创建实例。

### 9.3 回调

回调必须包含：

- `eventKey`；
- `instanceId`、`businessCode`、`businessId`、`businessRound`；
- 决策动作；
- 操作人和时间；
- 原因；
- 业务快照摘要；
- 请求 ID。

业务消费成功后保存 `lastApprovalEventKey`。重复事件返回成功但不重复执行激活、库存调整、订单转换或归档。

### 9.4 旧审批接口

以下业务模块动作在原生切换后进入废弃期：

- `/inventory/stockCheck/approval/*`；
- 旧调拨审批动作；
- 任何业务模块自建的移动“同意/驳回”接口。

兼容层只能转发到统一审批服务，不能继续产生另一条审批记录。

## 10. 接口版本与废弃

### 10.1 兼容原则

- 新增字段保持客户端可忽略；
- 改变写语义时新增动作接口，不原地改变旧接口；
- 状态码先增加映射，不能直接替换历史值；
- 废弃接口返回 `Deprecation` 信息并记录调用方；
- 旧接口停用必须满足 PC、移动、自动任务和第三方调用均为 0；
- 不通过路由隐藏来假装接口已停用。

### 10.2 推荐时间顺序

```text
发布新契约
→ 服务端兼容
→ PC 切换
→ 移动切换
→ 监控旧调用
→ 灰度开关扩大
→ 一个稳定周期
→ 评审旧接口停用
```

## 11. 接口测试矩阵

每个核心写接口至少覆盖：

- 正常成功；
- 无功能权限；
- 超出数据范围；
- 当前组织不匹配；
- 功能关闭；
- 错误状态动作；
- 过期版本；
- 同幂等键相同载荷重放；
- 同幂等键不同载荷冲突；
- 两人并发；
- 下游超时；
- 回调重复、乱序和失败重试；
- PC 创建、移动处理、PC 查看；
- 移动创建、PC 处理、移动查看；
- 深链重新鉴权；
- 敏感字段不下发。

## 12. 接口验收门槛

- [ ] PC 和移动没有平行业务写接口；
- [ ] 新采购申请与行政采购路径、业务类型和待办标题可区分；
- [ ] 采购申请到订单关系可通过接口完整查询；
- [ ] 冻结盘点能阻止全部库存写路径；
- [ ] 签署后没有普通删除或直接驳回结束接口；
- [ ] 功能关闭时入口、API、待办和消息一致；
- [ ] 聚合接口能显式表达 Provider 失败，不返回假 0；
- [ ] 统一审批动作只有一套；
- [ ] 详情统一返回状态、版本和允许动作；
- [ ] 错误码、幂等和版本冲突已形成契约测试；
- [ ] 旧接口有调用监控、回退期和停用条件；
- [ ] 未为不存在的请假业务创建空壳接口。
