## 1. 本检查点结论

`erp-ui-next/` 已新增 `/oa/purchases` “我的采购申请”只读工作台，使用 `oa.purchase.view` 与 `oa:purchase:list` 双重门禁，只在店铺或仓库叶子上下文读取当前登录申请人的 ERP-NEW_2 隔离 Mock。页面覆盖标题和状态筛选、服务端分页、当前页审批状态指标，以及标题、金额、申请人、申请组织、审批轮次、创建时间和状态的桌面表格与移动卡片等价展示。

本切片没有提供详情、新建、编辑、保存、提交、撤回、关闭、审批轨迹、同意、退回、拒绝或导出入口，也没有把真实 OA 或统一审批闭环描述为已迁移。

## 2. 契约与隔离证据

- 列表端点：`GET /oa/purchase/my`。
- 入口权限：`oa:purchase:list`。
- 服务端强制使用当前登录用户作为申请人；Reader 只发送 `pageNum`、`pageSize`、`title`、`status` 和一个当前会话 `Dept-NumId`，不发送 `applicantId`、`shopDeptId`、`scopeDeptIds`、`dataScope` 或 CSRF。
- 请求前通过 `expectedOrganizationId` 拒绝组织漂移；解析后要求每行 `applicantId` 与会话用户一致、`shopDeptId` 与当前叶子组织精确一致，任一越界记录整页失败关闭。
- 公司上下文不发请求；店铺和仓库上下文均使用同一双重边界。
- 状态闭集为 `draft`、`submitting`、`pending`、`approved`、`returned`、`rejected`、`withdrawn`、`terminated`、`cancelled`；未知状态失败关闭。
- Java Long、可空非负十进制金额、非负安全审批轮次和有效本地创建时间由运行时契约校验。
- 审批实例 ID、行版本、审批事件键、内部操作人和原始数据范围字段均被丢弃。
- 默认 Provider 仍只注入 ERP-NEW_2 隔离 Mock；真实 HTTP Reader 未接入应用启动流程。
- 后端列表响应没有显式 `Cache-Control: no-store` 证明，这是生产注入阻断项。
