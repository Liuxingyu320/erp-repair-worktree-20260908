# ERP-NEW_2 阶段 12C：明细库存收货持久化实施计划

> 日期：2026-08-02
> 基线：`d7c3f9b1 feat: add authoritative transfer receipt planning`
> 范围：只修改 ERP-NEW_2 隔离工作树；不使用 Docker、不启动服务、不连接数据库、不执行迁移

## 1. 目标与安全边界

阶段 12C 为 V2 发货批次增加多次部分收货所需的独立持久化事实、固定锁序和库存写事务。最终写服务必须在同一事务内锁定并重新计算阶段 12B 的 `receiptPlanVersion`，然后按现场分类结果写入合格、残损和显式短缺事实。

本阶段分三个独立检查点，任何一步失败都不能提前接线下一步：

1. **12C1：结构骨架**。新增加法迁移源码、领域写记录、固定锁序 Mapper 契约及源码测试。收货服务仍然只注入 Gate，并在 Gate 后硬拒绝；不执行任何 Mapper。
2. **12C2：事务内权威校验**。注入只读/锁定 Mapper，完成组织、版本、数量、目标库位、序列号、幂等和规划指纹校验；仍不调用库存写方法。
3. **12C3：原子写入**。按固定锁序补建目标汇总库存、派生批次和余额，写不可变收货审计、明细流水、序列号位置、累计进度与生命周期；补故障注入和整单回滚测试。

两个 Gate 在 12C1—12C3 全程保持默认 `false`。源码完成不代表可以启用；只有专属非 Docker 数据库验证、并发与排他路由审计完成后，才进入 12D 启用检查点。

## 2. 12C1 加法数据模型

新增迁移 `sql/erp_inventory_transfer_receipt_v2_20260802.sql`，只允许 roll-forward：

- `inv_transfer_shipment_allocation` 增加累计合格、累计残损、累计显式短缺和 `receipt_version`。更新 SQL必须同时约束旧版本及三类累计量不超过 `allocated_quantity`。
- `inv_transfer_shipment_receipt` 保存一次命令的不可变头、请求指纹、收货规划版本、来源/目标对账批次、分类总量、完成标识、状态及操作者；`command_request_id` 全局唯一。
- `inv_transfer_shipment_receipt_allocation` 每个收货头和来源发货分配唯一一行，同时保存正常和隔离目标位置、变更前后版本、三类数量和成本快照。
- `inv_transfer_shipment_receipt_serial` 逐件保存处置、来源审计关联、目标位置和状态前后值；同一收货头内序列号唯一。
- `inv_inventory_lot` 增加 `source_lot_id` 与 `receipt_disposition`，以目标仓、物料、来源批次、处置唯一映射合格或残损派生批次。旧批次两列为空，不与 V2 派生批次混用。
- `inv_stock` 与 `inv_stock_balance_detail` 均增加默认零的 `quarantine_quantity`；V2 更新必须在汇总层和明细层都保持 `current = available + locked + quarantine`。12D 启用前还必须把专属环境的对账规则升级为相同公式。
- `inv_stock_ledger_detail` 增加 `receipt_allocation_id` 与 `receipt_disposition`，每个收货分配的 accepted/damaged 处置各最多一条不可变流水。

MySQL 5.7 不可靠执行 `CHECK`，所以数据库列默认值、唯一键和带谓词版本更新共同承担硬约束；Java 层仍必须在写前后重复校验守恒。

## 3. 固定锁序与 Mapper 契约

12C1 Mapper 方法按以下顺序命名并在 XML 中稳定排序：

1. 发货批次（复用 `InvTransferShipmentMapper.selectByIdForUpdate`）与调拨单（复用 `InvTransferOrderMapper.selectInvTransferOrderByIdForUpdate`）；
2. 调拨明细、发货明细、来源发货分配；
3. 目标仓库存模式；
4. 全部物料履约策略；
5. 全部目标汇总库存；
6. 全部来源批次；
7. 全部目标库位；
8. 已存在目标派生批次；
9. 已存在目标明细余额；
10. 全部发货关联序列号。

集合参数必须非空、去重、升序后传入 Mapper；SQL 再使用相同键排序并 `FOR UPDATE`。缺失汇总库存只能在全部第 4 级锁持有后补建；缺失派生批次/余额只能在全部汇总库存锁持有后补建。唯一键冲突必须让事务整体回滚并返回可重试错误，不能捕获后继续。

12C1 可以声明插入和条件更新 SQL，但服务不得持有该 Mapper。结构测试必须证明：

- 每个接口方法都有可解析绑定；
- 所有锁查询含稳定 `ORDER BY ... FOR UPDATE`；
- 所有数量写入含正数、版本、归属和非负/守恒谓词；
- 不存在无条件库存更新；
- Gate 没有 `true` 配置，收货服务仍只有 Gate 一个字段。

## 4. 数量与成本约束

每个来源发货分配的当前剩余量为：

`allocated - accepted_received - damaged_received - shortage_reported`

本次三类数量合计必须大于零且不超过当前剩余。`finalizeShipment=true` 时提交后剩余必须为零；为 `false` 时剩余继续在途。显式短缺只写审计累计，不增加目标库存。

合格和残损金额分别使用阶段 11 不可变来源分配的 `cost_price × quantity`，六位小数。目标汇总库存的成本只增加实际入库的合格与残损金额；合格增加 `current + available`，残损增加 `current + quarantine`。两种处置分别写独立明细余额与流水。

serial 跟踪下三类数量必须为整数并分别等于序列号数；每个序列号必须属于该发货分配且当前仍为来源位置的 `shipped`。合格序列号更新为目标位置 `available`，残损更新为 `quarantine`，短缺保留无目标位置的差异事实，是否脱离来源位置留给后续差异裁决规则明确，12C3 前不得猜测。

## 5. 幂等、生命周期与返回

- 命令台账仍以 `X-Request-Id`、命令类型和资源键做第一层幂等；收货头 `command_request_id` 做业务层唯一约束。
- 收货头另存规范化请求 SHA-256。重复 request ID 且请求指纹相同可重放原强类型结果；不同则拒绝。
- 任一残损/短缺产生开放差异，发货与调拨进入 `discrepancy`；仍有在途且无差异时进入/保持部分收货；全部合格完成时才进入 `received`。
- `inv_transfer_shipment_detail.received_quantity` 只累计合格数量，不能混入残损或短缺。
- 旧 `inv_transfer_discrepancy` 处理器不得接管 V2；12C 的收货分配先作为不可变差异证据，后续必须建立 V2 专属裁决边界后才能启用写 Gate。
- 12C3 完成前返回仍为明确拒绝，不制造“写入成功”的模拟结果。

## 7. 验证与停止条件

每个子检查点运行库存模块定向及完整离线 Reactor、`erp-ui-next npm run verify`、`git diff --check`、秘密/连接串/受保护路径和 Gate 配置审计。

发现任何共享数据库/服务配置、迁移被复制进初始化目录、无版本库存更新、先逐物料写后再锁下一物料、短缺被错误计入库存、成本从当前售价重算、序列号脱离权威来源、服务在 12C1 可执行 Mapper，或需要触碰受保护原项目时立即停止。
