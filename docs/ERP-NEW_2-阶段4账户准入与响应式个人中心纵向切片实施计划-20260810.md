## 一、预期结果

把旧桌面端“个人中心”、独立“必须修改密码”页和移动端“我的资料”归并为 `erp-ui-next/` 的一套响应式账户体验，并补齐登录后的两类准入闭环：

1. `TEMPORARY` / `CHANGE_REQUIRED` 凭据只能进入强制改密页；
2. 凭据正常但 15 项入职资料不完整的用户只能进入资料补全页；
3. 两项均通过后，才读取授权组织树并建立可访问业务功能的完整会话；
4. 正常登录用户可从应用外壳进入账户中心，维护基础资料、头像和密码；
5. 桌面与移动端使用相同路由、领域模型和后端契约，不复制两套页面。

本切片不启动服务、不连接数据库或中间件；真实 HTTP 适配器通过自动化契约测试验证，默认运行继续使用 ERP-NEW_2 隔离 Mock。

## 二、现状问题

- 新前端会话目前并发读取 `/system/user/getInfo` 与 `/system/dept/shop-tree`。
- 临时凭据用户访问组织树会被 `CredentialStateInterceptor` 拒绝；资料不完整用户访问组织树会收到 `PROFILE_COMPLETION_REQUIRED`。
- 因组织树失败，现有 bootstrap 把整个会话标记为 unavailable，用户无法到达后端明确允许的改密或补资料接口。
- 当前 `SessionSnapshot` 只表达“已有完整组织上下文”，不能诚实表达“已认证但尚未通过准入”的状态。
- 个人资料读写、资料补全、改密和头像接口尚未统一声明禁止缓存；持久化命令也没有统一的幂等边界。
- 改密接口使用任意 `Map<String, String>`，不能拒绝多余字段。

## 三、方案选择

### 采用：受限准入会话与完整业务会话分型

- 先读取浏览器 Cookie 会话和 `/system/user/getInfo`。
- 若凭据受限，生成只含身份、CSRF、密码策略和凭据限制的受限会话，不请求组织树。
- 若资料不完整，生成只含身份、CSRF、密码策略和缺失字段的受限会话，不请求组织树。
- 只有准入条件都通过时才读取组织树，并生成现有完整 `SessionSnapshot`。
- 受限会话不包含组织，不把用户默认部门伪装成已经授权的操作组织。
- 受限模式只安装账户准入 HTTP Gateway；库存、审批、OA 等业务 Gateway 继续 unavailable。
- 改密或补资料成功后重新运行完整 bootstrap，由服务端重新判定下一道准入门禁。

### 不采用的方案

- **伪造占位组织**：会把未经组织树证明的部门写入业务请求头，破坏组织失败关闭边界。
- **忽略组织树 409 并继续完整会话**：资料门禁只存在于页面层，业务 Gateway 仍可能被误用。
- **让旧页面继续承担强制改密或移动资料**：会形成双前端、双状态和不一致的安全行为。

## 四、状态与路由设计

### 会话状态

- `ready`：完整业务会话，必须有当前组织且它存在于授权组织列表。
- `restricted`：已认证但未完成准入；业务快照为空，仅保留受限会话。
- `loading`、`anonymous`、`expired`、`unavailable`：保留既有含义。

受限原因严格为：

- `credential-change`：状态为 `TEMPORARY` 或 `CHANGE_REQUIRED`，同时保留可选失效时间；
- `profile-completion`：保留后端返回的缺失字段键与中文标签。

### 路由

- `/credential/change-password`：全屏响应式强制改密页；不能跳过，允许安全退出。
- `/complete-profile`：全屏响应式 15 项资料补全页；已完整敏感字段按后端投影只读展示。
- `/account`：完整会话内的响应式账户中心；无需伪造功能码或用户管理权限，只要求登录。

全局路由守卫规则：

1. 匿名或过期会话进入登录页；
2. `restricted` 只允许与当前限制匹配的准入页，其他目标统一重定向；
3. `ready` 才执行现有 feature / permission 校验；
4. 已解除限制后访问准入页，重定向到 `/account`；
5. 登录成功的安全返回路径只有在完整会话建立后才生效。

## 五、后端边界

- 新增固定字段 `SysSelfPasswordUpdateRequest`，只接受 `oldPassword`、`newPassword`，拒绝未知字段；明文密码不进入操作日志。
- 个人资料读取、资料补全读取以及所有写响应设置 `Cache-Control: no-store, max-age=0` 和 `Pragma: no-cache`。
- 资料更新、资料补全、改密和头像上传增加 `@IdempotentSubmit(timeout = 30)`。
- 资料补全请求增加未知字段拒绝，继续由现有服务执行 15 项业务校验和原子事务。
- 头像继续走现有专属文件服务；前端只接受后端既有图片白名单中的 JPEG/PNG 且限制 5 MiB，后端保留扩展名白名单并增加非空/大小边界。
- 所有账户写请求省略组织头，但必须携带 CSRF、稳定 `X-Request-Id` 与同值 `Idempotency-Key`；同一次失败重试复用标识，表单内容变化后生成新标识。

## 六、前端领域与交互

新增 `domains/account/`：

- 固定 Zod 契约：会话准入、本人资料、资料完整度、基础资料更新、改密和头像上传；
- `AccountGateway`：读取资料/完整度，保存资料/完整度，改密和上传头像；
- HTTP 适配器：验证 legacy envelope、`no-store`、Long 字符串、同源头像路径及命令头；
- Mock Gateway：仅修改隔离内存，模拟准入完成、资料更新、密码清空与头像更新；
- 密码策略工具：与后端 `chrtype=0..4`、8–20 字符规则同源测试。

页面原则：

- 继续遵循《ERP-NEW_2 前端设计参考与使用约束》：吸收 UI Prompt Library 与 21st.dev 的后台信息层级、Motion Primitives 的状态连续性；React Bits、Magic UI、Uiverse 与 MotionSites 仅用于校验局部质感，不复制第三方代码、品牌、素材或付费提示词。
- 账户中心使用概览、基本资料、安全与头像四个清晰区域；移动端改为单列，不隐藏动作。
- 强制改密页面不展示“稍后处理”；临时凭据失效时只允许退出并联系管理员。
- 密码从不写入 URL、Storage、Cookie、调试状态或持久化 Mock；提交完成和组件卸载时清空三个密码字段。
- 资料补全只提交允许的 15 项；只读 HR 摘要不进入命令。
- 银行卡与证件号只在当前短生命周期表单中存在；响应和页面均不得缓存。
- 头像使用本地对象 URL 预览并及时释放；不引入裁剪依赖，不把 base64 写入状态仓库。
- 动效采用克制的状态反馈，并遵循 `prefers-reduced-motion`；不引入装饰性持续动画。
