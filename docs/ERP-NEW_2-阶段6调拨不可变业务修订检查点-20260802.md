# ERP-NEW_2 阶段 6：调拨不可变业务修订检查点

> 日期：2026-08-02
> 分支：`codex/erp-new-2-rebuild`
> 基线提交：`b4c69c65 feat: add persistent transfer command boundary`

## 1. 本检查点结论

调拨主单继续使用稳定的 `transfer_id`，发货、收货、差异和库存预留等既有外键关系不复制、不替换。新的 `inv_transfer_revision` 台账单独保存业务内容版本：当前草稿可修改，提交时原子封存；审批结果只追加决策状态和审计信息，不覆盖已提交的抬头、明细或 SHA-256 快照。

驳回、退回或撤回需要回到草稿时，系统先永久保留原审批版本，再创建以该版本为父节点的新草稿。新草稿后续修改不会改变旧版本。审批通过、拒绝结案、终止关闭、取消和系统直发均只结束当前版本，不生成可编辑草稿。

## 2. 版本事务不变量

1. 一个调拨主单按 `(transfer_id, revision_no)` 形成单调递增版本链，主单标识和物流事实外键保持稳定。
2. 同一审批轮次最多对应一个业务修订，`(transfer_id, approval_round)` 使用数据库唯一键防止重复封存。
3. 只有 `DRAFT` 版本可更新业务快照；所有其他状态均没有更新快照的 Mapper 入口。
4. 提交在现有业务事务中把草稿封存为 `SUBMITTED`，自动审批则直接封存为 `APPROVED`。
5. 审批结果只从预期的 `SUBMITTED` 条件更新，写入决策动作、原因、操作人、实例和时间。
6. 回到草稿的结果追加子版本，子版本的 `parent_revision_id` 永久指向被驳回、退回或撤回的封存版本。
7. 业务快照使用显式白名单字段、确定性明细排序和规范化小数；不包含累计发货量、累计收货量等后续物流事实。
8. `snapshot_hash` 是规范化抬头 JSON 与明细 JSON 的 SHA-256；相同业务内容不因明细传入顺序或小数尾零而产生不同哈希。
9. 只要主单存在任意非草稿修订，就永久禁止物理删除；取消后的单据也不再通过删除覆盖历史。
10. 修订服务使用 `Propagation.MANDATORY`，不能脱离草稿、提交、审批、取消或直发的外层事务单独落账。

## 3. 接入路径

| 业务路径 | 修订行为 |
| --- | --- |
| 新建/编辑草稿 | 新建或同步唯一当前 `DRAFT` |
| 提交旧审批 | 封存当前草稿并绑定旧审批实例与新轮次 |
| 提交统一审批 | 封存当前草稿并绑定新轮次，最终回调补齐实例 |
| 自动审批 | 提交时直接封存为 `APPROVED` |
| 旧审批通过 | `SUBMITTED -> APPROVED` |
| 旧审批驳回到草稿 | `SUBMITTED -> REJECTED`，追加子 `DRAFT` |
| 统一审批退回 | `SUBMITTED -> RETURNED`，追加子 `DRAFT` |
| 统一审批撤回 | `SUBMITTED -> WITHDRAWN`，追加子 `DRAFT` |
| 拒绝/终止结案 | `SUBMITTED -> REJECTED/CLOSED`，不新建草稿 |
| 草稿或旧审批单取消 | 当前版本转为 `CANCELLED` |
| 销售跨店系统直发 | 当前草稿直接封存为 `DELIVERED` |
| 物理删除草稿 | 仅无任何封存历史时删除当前草稿版本和主单 |

## 4. 数据结构

增量脚本：`sql/erp_inventory_transfer_revision_20260802.sql`

新增表：`inv_transfer_revision`

关键字段包括：

- 版本号、父版本、审批轮次和审批实例；
- `DRAFT / SUBMITTED / APPROVED / REJECTED / RETURNED / WITHDRAWN / CLOSED / CANCELLED / DELIVERED` 生命周期；
- 规范化抬头与明细 JSON、SHA-256 快照哈希；
- 决策动作、原因、操作人、决策时间和封存时间；
- 创建、更新时间和操作人审计字段。

脚本不包含 `USE`、数据库名、账号、密码、种子数据或环境地址。本检查点没有执行该脚本。

## 5. 向后兼容

已经处于审批中的旧调拨单如果尚无业务修订，在下一次有效审批结果到达时，会按当前审批轮次和当前业务内容补录一个封存提交版本，再应用审批结果。该兼容逻辑不会猜测或重建无法证明的更早历史，也不会批量迁移现有数据库。

旧审批引擎和统一审批引擎继续保留各自的规则/流程快照；业务内容快照不再塞入 `rule_snapshot`，避免把审批路由与商品、数量、组织和业务原因混为一个可变对象。
