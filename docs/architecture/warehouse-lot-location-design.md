# 仓库批次、库位与序列号库存设计

> 决策日期：2026-07-13
> 状态：增量数据模型已定稿；生产权威读切换未启用
> 适用范围：采购入库、销售出库、调拨、退货、盘点、调整
> 约束：本地 MySQL 完成回填演练和连续对账前，不得将任何仓库切到 `detail` 权威读模式。

## 1. 决策

采用“明细事实 + 兼容汇总”两层模型：

1. `inv_stock_balance_detail` 是“物料 + 仓库 + 批次 + 库位”的明细余额。
2. `inv_inventory_serial` 是单件序列号的位置和状态事实，不把多个序列号塞进余额文本字段。
3. `inv_stock` 在兼容期继续作为仓库级汇总，不删表、不改现有唯一键。
4. 所有库存变动最终由一个统一变动服务在同一事务内更新明细余额、汇总余额和不可变流水。
5. `inv_warehouse_stock_mode` 按仓库控制读写模式，新增记录默认 `legacy/legacy`，脚本不会自动切换。

不采用“直接把批次和库位加进 `inv_stock` 唯一键”：该做法需同版改写全部入出库路径，且会破坏旧页面和报表对“一物料一仓库一行”的假设。

## 2. 核心不变式

任何写入提交前后都必须满足：

- 明细余额：`current_quantity - locked_quantity = available_quantity`。
- 所有数量、锁定量和可用量均不小于 0。
- 仓库级：同物料全部明细余额合计 = `inv_stock` 汇总余额。
- 明细总成本合计 = `inv_stock.total_cost`，金额差异容忍上限为 0.01。
- 流水：`before_quantity + change_quantity = after_quantity`。
- 序列号物料的每个在库序列号只能有一个仓库、一个批次和一个库位。
- 序列号余额只允许 0/1；非序列号物料不强制整数。
- 批次、库位、序列号和业务单据必须属于同一仓库上下文。
- 已完成的流水和质检事实不允许覆盖，纠错使用反向流水。

## 3. 数据对象

| 对象 | 作用 | 关键约束 |
|---|---|---|
| `inv_warehouse_zone` | 库区主数据 | 仓库内编码唯一 |
| `inv_warehouse_location` | 库位主数据 | 仓库内编码唯一；包含“未分配库位”虚拟位 |
| `inv_inventory_lot` | 物料批次/效期 | 仓库+物料+批次号唯一 |
| `inv_stock_balance_detail` | 批次库位明细余额 | 仓库+物料+批次+库位唯一 |
| `inv_inventory_serial` | 序列号单件事实 | 物料类型+序列号唯一 |
| `inv_stock_ledger_detail` | 不可变明细流水 | `request_id` 唯一，用于幂等 |
| `inv_warehouse_task` | 上架/移库/拣货/复核任务 | 业务来源+任务类型+幂等键唯一 |
| `inv_warehouse_task_detail` | 作业数量与来源/目标维度 | 已处理量不得超过计划量 |
| `inv_warehouse_stock_mode` | 逐仓灰度开关 | 默认 `legacy/legacy`；切换前必须有对账签字 |

收货事实继续由 `inv_receipt_batch` 和 `inv_receipt_batch_detail` 表达；质检结论由 `inv_quality_inspection` 表达。批次主数据通过 `receipt_batch_id` 反查采购和质检来源。

## 4. 写入协议

### 4.1 锁顺序

所有业务遵守固定锁顺序，禁止反向获锁：

1. 业务主单。
2. 业务明细/作业任务。
3. `inv_inventory_lot`。
4. `inv_stock_balance_detail`，按 `balance_id` 升序。
5. `inv_inventory_serial`，按 `serial_id` 升序。
6. `inv_stock` 汇总行。
7. 插入明细流水和现有汇总流水。

锁冲突重试最多 2 次，每次使用新的事务；不在已标记回滚的事务内重试。

### 4.2 幂等

- 入口接受 `requestId`，同一仓库内全局唯一。
- 先检查 `inv_stock_ledger_detail.request_id`；已存在则返回原结果，不再变动余额。
- 业务单据幂等注解只是第一层，数据库唯一键是最终保护。

### 4.3 双写模式

| `write_mode` | 行为 |
|---|---|
| `legacy` | 只更新现有 `inv_stock`/汇总流水，用于未回填仓库 |
| `dual` | 同事务更新明细余额、`inv_stock`、两类流水；任一失败整体回滚 |

不设置“只写明细”模式，直到所有旧消费者下线。

## 5. 读取协议

| `read_mode` | 用途 |
|---|---|
| `legacy` | 库存总览、报表和旧 API 继续读 `inv_stock` |
| `shadow` | 对外仍返回旧读，后台同步执行新读并记录差异 |
| `detail` | 新页面以明细余额为权威，库存总数仍与 `inv_stock` 对账 |

切换 `detail` 必须同时满足：

- 本机回填演练通过；
- 目标仓库全量对账 0 差异；
- `dual + shadow` 连续 7 天 0 差异；
- 入库、出库、退货、调拨、盘点和并发回归全部通过；
- 有仓库负责人和技术负责人的对账签字。

## 6. 批次、效期和出库分配

- 采购质检合格/让步数量创建或关联 `inv_inventory_lot`。
- 无供应商批次时使用系统批次号，不使用空值代替批次。
- 待上架数量先进“待上架”虚拟库位，完成上架任务后移到物理库位。
- 默认出库按 FEFO：有效期的先按到期日升序，再按入库时间升序；无效期的按 FIFO。
- 过期、隔离、待检、冻结和禁用批次不参与自动分配。
- 人工改批次必须持有独立权限并记录原因。

## 7. 序列号

- 序列号状态：`pending_qc` → `available` → `allocated` → `picked` → `shipped`；退货可进入 `quarantine` 后重新检验。
- 序列号的移库、锁定和出库必须逐个扫描或导入，不允许只填数量。
- 同一序列号再次入库必须是明确退货/返修业务，普通采购拒绝重复。

## 8. 作业任务

任务类型包含 `putaway` 上架、`move` 移库、`pick` 拣货、`review` 复核、`ship` 发货和 `count` 盘点。

- 任务是作业计划，不是库存流水。
- 扫码每成功一次只提交一个幂等请求，不在前端先改余额。
- 任务可部分完成；已处理量超过计划量时后端拒绝。
- 取消任务只释放未处理的预留，不撤销已完成的库存事实。

## 9. 迁移和回滚

1. 执行 `erp_inventory_lot_location_schema_20260713.sql`，仅增表/字段，模式默认为 legacy。
2. 执行回填脚本 dry-run，处理负数、余额公式、非单件序列号等阻断项。
3. 在本机独立 MySQL 测试库开启回填；业务库必须先备份且取得签字。
4. 运行对账脚本，所有阻断项为 0。
5. 单仓开启 `dual + shadow`，连续观察 7 天。
6. 评审后切到 `dual + detail`；其他仓库不受影响。

回滚只把目标仓库改回 `legacy/legacy`，不删除批次、库位、流水和序列号事实。如果双写期已有新业务，删除新事实会破坏审计链，因此明确禁止。

## 10. 发布阻断项

- 新老余额任一数量/成本差异。
- 明细余额负数或数量公式错误。
- 孤儿批次、库位、序列号或流水。
- 重复 `request_id`、重复序列号。
- 不可用批次被自动分配。
- 任何写入路径在 `dual` 模式下只改了一层余额。
- 无对账签字或紧急回退演练未通过。

## 11. 验证矩阵

- 采购：同单两批、混合质检、让步、拒收重收、上架。
- 出库：FEFO、手工改批次、部分拣货、复核差异、取消预留。
- 调拨：源批次/库位扣减，目标仓历史保持，在途数量对平。
- 退货：采购批次退出、销售序列号退回隔离区。
- 盘点：按库位/批次快照，盲盘、复盘、并发出库冲突。
- 并发：同余额 20 并发扣减、重复 requestId、死锁重试、回滚无半笔流水。
- 性能：10 万余额、100 万流水下列表 P95 < 1.5s，单笔变动 P95 < 300ms。

## 12. 本次提交的边界

本次提交完成数据模型、安全回填、对账和回滚脚本，但不启用任何仓库的 `dual` 或 `detail` 模式。统一库存变动服务及扫码作业页面必须在本设计通过数据演练后单独发布，不与首次建表同版强切。
