# ERP-NEW_2 阶段 13B：收货差异双方事实确认契约实施计划

> 日期：2026-08-02
> 分支：`codex/erp-new-2-rebuild`
> 基线：`09e922d9 feat: add immutable transfer discrepancy cases`
> 范围：V2 差异事项权威只读投影、追加式双方确认事件结构和纯命令契约；不开放接口、不执行迁移、不写确认事件、不进入裁决

## 1. 结果目标

阶段 13A 已在 V2 收货事务中生成不可变残损、短缺事项。阶段 13B 为这些事项建立双方看到同一事实、确认同一版本和同一指纹的权威契约，并使“可以交给独立差异角色裁决”成为可验证的服务端推导结果，而不是前端按钮或单方状态更新。

本阶段不复用旧 `inv_transfer_discrepancy`，不让旧 `InvTransferDiscrepancyProcessor` 读取或处理 V2 事项，不实现补发、退回、报损、责任调整或运输损耗核销。

## 2. 追加式确认事件

新增独立惰性迁移源码 `sql/erp_inventory_transfer_discrepancy_confirmation_v2_20260802.sql`，只创建 `inv_transfer_receipt_discrepancy_confirmation_event`：

- 每个事件保存全局幂等 `request_id`、事项标识、事项版本和事实指纹。
- `party_role` 只能为 `source` 或 `target`，并保存该次确认对应的组织标识。
- `decision` 只能为 `confirmed` 或 `disputed`；质疑必须有说明，确认说明可为空。
- 事件只追加，不覆盖历史；双方当前意见由各自最大事件标识推导。
- 索引支持按 `discrepancy_case_id + party_role + confirmation_event_id` 获取双方最新事件。
- 迁移不执行、不插入种子、不修改 13A 事项、不复制到 Docker 初始化目录。

## 3. 权威只读边界

新增 V2 专属只读 Mapper 与服务，按事项标识和当前选择组织读取：

1. SQL 必须从 13A 事项出发，内连接不可变收货分配、收货、V2 发货分配、发货明细、发货批次和调拨单，逐层核验 receipt、shipment、transfer、allocation 归属。
2. 当前选择组织必须严格等于调出库存组织或调入库存组织之一；不能仅依赖宽泛上下级数据范围。
3. 服务仍先校验用户对当前选择组织的权限，且拒绝来源与目标解析为同一组织的事项，避免一人一组织兼任双方。
4. 只返回双方各自最新追加事件；不存在事件时返回空确认槽位。
5. Mapper 或服务发现空标识、非法类型、非正数量、金额不一致、非法指纹、未知状态或事件角色与组织不一致时 fail closed。

## 4. 双方确认状态投影

投影只接受当前事项的 `case_version + fact_fingerprint`：

- 双方都没有当前有效意见：`awaiting_confirmation`。
- 仅一方当前有效意见为 `confirmed`：`awaiting_counterparty`。
- 任一方当前有效意见为 `disputed`：`disputed`。
- 双方当前有效意见都为 `confirmed`：`ready_for_adjudication`，并且只有此状态 `readyForAdjudication=true`。
- 指纹或版本陈旧的事件保留在只读结果中用于审计，但不计入当前状态。

该投影不更新 13A 事项的 `status` 或 `case_version`。后续独立裁决事务必须重新锁定事项和双方最新事件，并重复验证同一条件，不能信任本阶段只读结果。

## 5. 纯确认命令契约

新增尚未接入 Controller 或 Mapper 写方法的纯策略：

- 请求必须携带幂等标识、事项标识、事项版本、事实指纹、决定和说明。
- 服务端根据当前选择组织推导 `source|target`，客户端不得声明自身角色。
- 当前组织必须精确匹配且双方组织必须不同；事项必须仍为 `awaiting_confirmation`。
- 请求版本和指纹必须与权威事项完全一致。
- `confirmed` 允许空说明；`disputed` 必须提供非空说明。
- 策略只生成不可变准备事件和“假设追加后”的投影，不执行 DML、不关闭事项。
