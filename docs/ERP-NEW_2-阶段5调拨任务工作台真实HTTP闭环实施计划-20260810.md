# ERP-NEW_2 阶段 5 调拨任务工作台真实 HTTP 闭环实施计划

## 1. 结果与范围

本切片把 `erp-ui-next/` 的库存调拨任务工作台从 Mock-only 聚合视图升级为真实、组织隔离、失败关闭的只读 HTTP 工作台。完成后，页面通过当前会话明确选择的组织读取调拨分页列表与运营摘要，展示服务端真实状态、审批等待对象、下一步动作、明细行数和更新时间；不再显示 Mock 文案，不再把跨单位数量伪装成“件”汇总，也不再使用调拨单 ID 拼装并不存在的收货任务链接。

本切片不启动 Docker、前后端服务、MySQL、Redis 或 Nacos，不连接任何数据库或中间件，不安装依赖，不启用当前默认关闭的调拨写适配器，不删除旧前端，不修改或访问受保护原项目，也不执行 push、merge 或跨工作树操作。

## 2. 约束与假设

- 唯一可写目录为 `/Users/liuxingyu/.codex/worktrees/353b/ERP-NEW`，分支固定为 `codex/erp-new-2-rebuild`。
- 后端继续使用现有 `inv_transfer_order`、`inv_transfer_detail`、审批摘要和组织范围服务；本轮仅增加只读响应字段、低基数汇总和缓存保护，不改变调拨状态机或持久化语义。
- 列表筛选使用服务端已有的精确单号、状态和调拨类型条件；页码和页大小由前端冻结契约限制，固定按服务端创建时间倒序。
- 每一行必须证明当前组织是调出方或调入方；运营摘要必须回显其组织标识。任一不一致均由前端适配器失败关闭。
- 业务数量仍以十进制字符串解析，但工作台列表不展示跨单位总量；数量必须在详情页按明细单位核对。
- 当前列表没有权威 shipment/task/case 标识，因此只暴露能由 transferId 准确定位的详情、版本和发货规划入口；收货与差异动作不伪造深链。
- 视觉继续遵循 `docs/ERP-NEW_2-前端设计参考与使用约束.md`：采用克制、专业的后台信息层级和必要反馈，不为本读取切片增加装饰性动效。

## 4. 实施步骤

1. 为调拨列表补充 `detailLineCount`，为运营摘要补充待审批、待发货、待收货计数及当前组织标识；所有统计复用同一组织范围条件。
2. 为 `/inventory/transfer/list`、`/processing`、`/ops-summary` 增加 `Cache-Control: no-store, max-age=0` 与 `Pragma: no-cache`，并用源码/绑定测试固定只读权限、组织参数和缓存边界。
3. 建立严格 Zod 契约：验证 Long 标识、状态枚举、非负计数、时间、审批摘要、分页结构和组织归属；只输出页面需要的白名单字段。
4. 建立真实 HTTP reader：并行读取 `/inventory/transfer/list` 与 `/inventory/transfer/ops-summary`，要求单一明确组织请求头、无 CSRF、no-store 响应和可取消请求。
5. 将 Gateway、真实组合器和 Mock Gateway 迁移到带查询与组织上下文的签名；真实运行时不再把 `loadDashboard` 留在 unavailable 实现。
6. 重构任务工作台为服务端筛选和分页：显式“查询”动作、保留上次成功结果、组织切换自动取消旧请求并重载、准确的总数/页数与空状态。
7. 用状态展示矩阵生成“当前阶段、等待对象、下一步动作”；删除 Mock、伪截止时间、跨单位总量和虚假收货链接，桌面与移动端保持相同事实。
8. 更新迁移覆盖证据和本切片检查点，但仍将完整调拨页面保持为“部分实现”，因为真实导出、规则配置及其余写闭环尚未全部完成。

## 6. 风险与回滚

- 风险：列表审批摘要是分页后的第二次读取。保持 PageHelper 只包围订单 Mapper 的首个查询，并以测试固定分页总数不被摘要查询破坏。
- 风险：旧接口消费者可能依赖现有字段。只增加字段和响应头，不删除旧字段、不更改已有状态值。
- 风险：组织切换时旧响应覆盖新组织。使用 AbortController 与组织上下文回显双重校验，失败时保留最近一次同组织成功结果或清空跨组织结果。
- 风险：明细单位混杂导致总量误导。工作台只展示行数和“逐行核对单位数量”，不展示订单总数量。
- 回滚：本切片保持为独立本地提交；如验证失败，修正当前分支中的相关文件。不会用破坏性 reset、checkout 或清理命令，也不会触碰其他工作树。
