# ERP-NEW_2 阶段 12：明细库存收货事务实施计划

> 日期：2026-08-02
> 基线：`b85efd58 feat: add guarded transfer shipment write skeleton`
> 范围：只修改 ERP-NEW_2 隔离工作树；不启动服务、不连接数据库、不执行迁移

## 1. 目标与本轮边界

阶段 12 为 `inventory_write_version=V2_DETAIL` 的发货批次建立独立收货边界，最终支持同一发货批次多次部分收货，并把合格、残损和显式短缺分别落入可核验的业务事实。目标链路必须同时维护目标仓汇总库存、批次库位明细库存、序列号位置、不可变流水、收货批次审计、调拨累计量和生命周期。

本轮先交付“默认硬关闭的 API/DTO/命令/结果/Gate 骨架 + 完整事务设计”，不写半成品库存 SQL。骨架即使被误接线也必须在进入命令台账和业务锁之前失败。后续实现持久化、离线测试与迁移源码测试后，仍不启用任何 Gate，不执行 SQL。

## 2. 旧收货链不能复用

现有 `POST /transfer/shipment/receive/{shipmentId}` 只适用于 `LEGACY`：

1. 一次请求必须覆盖当前批次全部待收明细；未分类余量会立即变成短缺，无法表达“本次只到一部分，剩余仍在途”。
2. 它只增加目标 `inv_stock`，不创建或移动目标批次、库位余额及序列号事实。
3. 它使用发货明细加权成本，无法逐来源发货分配继承实际批次成本。
4. 它直接终结发货批次为 `received/discrepancy`，没有不可变的多次收货批次和逐分配累计量。
5. 它通过目标汇总库存不存在时捕获唯一键冲突重试，不能单独证明与 V2 明细库存写入的固定锁序兼容。

因此 V2 新增 `POST /transfer/shipments/{shipmentId}/receipts`，旧入口继续明确拒绝 `V2_DETAIL`，两个写链不共享请求 DTO、命令类型或持久化服务。

## 3. 请求与部分收货语义

请求头继续强制 `X-Request-Id`。正文只允许服务端收货规划的回传：

- `receiptPlanVersion`：64 位小写 SHA-256；
- `basis=server-recommendation`；
- `arrivedTime` 和可选备注；
- `finalizeShipment`：`false` 表示未分类余量继续在途，`true` 要求本次提交后全部余量已分类；
- 逐来源发货分配的 `shipmentAllocationId`；
- 合格数量与目标正常收货库位；
- 残损数量与目标隔离库位；
- 显式短缺数量；
- 序列号物料分别回传合格、残损、短缺序列号 ID；
- 残损或短缺必须同时提供说明和附件引用。

客户端不能提交物料、仓库、批次、成本、目标批次号、余额 ID、操作者或状态。事务内必须重新读取并锁定发货事实，重新计算相同 `receiptPlanVersion`；客户端引用的来源分配、目标库位和序列号必须全部位于服务端允许边界，分类数量必须在剩余量内守恒。服务端默认建议全部合格收货，但操作者必须能够按现场实物改成部分、残损或显式短缺，写服务不得要求实际分类与默认建议逐字相同。

未出现在本次请求中的剩余量或 `finalizeShipment=false` 下未分类的数量继续计入在途，不自动创建短缺。显式短缺进入未裁决差异；只有差异裁决后才进入“已裁决短缺”。

## 4. 不可变收货模型

加法迁移计划新建：

1. `inv_transfer_shipment_receipt`：一次命令一条不可变收货头；`command_request_id` 唯一，保存收货规划版本、目标仓模式对账批次、总分类量和完成状态。
2. `inv_transfer_shipment_receipt_allocation`：逐来源发货分配保存合格/残损/短缺数量、来源批次库位成本、目标批次库位余额、变更前后版本及汇总日志关联。
3. `inv_transfer_shipment_receipt_serial`：逐件保存来源发货序列号、收货处置、目标位置以及 `shipped → available/quarantine` 状态变化。
4. `inv_transfer_shipment_allocation` 增加累计合格、累计残损、累计显式短缺与版本；每次更新必须满足三类累计量不超过发货分配数量。
5. `inv_inventory_lot` 增加 `source_lot_id` 与 `receipt_disposition`，以“目标仓 + 物料 + 来源批次 + 处置”唯一映射；合格批次沿用来源质量/效期，残损批次固定为隔离状态。
6. `inv_stock_ledger_detail` 增加收货分配关联，逐目标余额写唯一 `transfer_in` 或 `transfer_damage_in` 明细流水。
7. `inv_stock` 增加默认值为零的 `quarantine_quantity`；V2 仓汇总守恒扩展为 `current_quantity = available_quantity + locked_quantity + quarantine_quantity`，避免把残损伪装成可用或预留库存。

迁移只存放在 `sql/`，不复制到 Docker 初始化目录、不执行、不切模式、不写业务种子。

## 5. 目标位置与建行规则

- 合格数量只允许进入目标仓启用、非虚拟、非 `receiving/quarantine/shipping/virtual` 的正常存储库位。
- 残损数量只允许进入目标仓启用、非虚拟的 `quarantine` 库位。
- 目标仓必须为 `dual + detail + reconcile passed` 且有非空对账批次；来源发货快照和目标仓当前对账批次都写入收货头。
- 每个物料必须存在启用的履约策略行；它同时充当 V2 首次建行前的稳定物料级互斥事实。
- 在物料策略和目标汇总库存锁持有期间，才允许按唯一维度补建目标汇总库存、派生批次和明细余额。唯一键冲突必须转成整单回滚重试提示，不能在同一事务内吞异常后继续。
- V2 运行前的排他路由清单必须证明其他库存写入者遵守同一汇总库存前置锁；不能证明时保持 Gate 关闭。

## 6. 固定锁序

所有既有行锁在第一次库存变更前完成，集合均去重升序：

0. 命令台账（只在两个 V2 Gate 通过后进入 Executor）。
1. 发货批次，再锁调拨单。
2. 调拨明细、发货明细、来源发货分配。
3. 目标仓 `inv_warehouse_stock_mode`。
4. 物料履约策略，按 `item_type,item_id`。
5. 目标 `inv_stock` 汇总库存，按 `stock_id`；缺行只能在第 4 级互斥下补建并立即锁定。
6. 来源批次快照，按 `source_lot_id`。
7. 客户端规划引用的目标库位，按 `location_id`。
8. 已存在的目标派生批次，按 `lot_id`；缺行只能在第 4、5 级锁持有时补建。
9. 已存在的目标明细余额，按 `balance_id`；缺行只能在目标批次和库位均已锁定后补建。
10. 发货关联序列号，按 `serial_id`。

同一事务涉及多个物料时，必须先取得全部第 4 级锁，再取得全部第 5 级锁，之后才能进入批次/库位/余额阶段，禁止逐物料完成整条链。Stage 11 的出库写入已先锁汇总库存再锁明细事实；V2 首次入库的批次/余额补建是唯一例外路径，并由物料策略、全部汇总库存锁和唯一维度约束共同串行化。

## 7. 数量、成本与序列号守恒

对每条来源发货分配：

`allocated = accepted + damaged + adjudicatedShortage + returned + inTransitOrUnresolved`

其中：

- 本次 `accepted + damaged + explicitShortage` 必须大于零且不超过当前剩余；
- `explicitShortage` 在裁决前仍属于 `inTransitOrUnresolved`，不得增加目标库存；
- 合格数量同时增加目标汇总当前/可用数量和正常明细余额；
- 残损数量同时增加目标汇总当前/隔离数量和隔离明细余额，不增加可用或预留数量；
- 每条目标明细余额金额严格使用来源发货分配 `cost_price × quantity`，六位小数，不读取当前售价或目标仓现价；
- 目标汇总库存增加成本必须等于所有合格与残损分配金额之和；
- 目标汇总当前数量必须等于正常与隔离明细余额合计，汇总隔离数量必须等于隔离明细余额合计；
- serial 策略下三类数量分别等于对应序列号条数，ID 必须来自该发货分配且当前状态为 `shipped`；
- lot 策略不允许提交任何序列号；
- `received_quantity` 只累计合格数量；残损、短缺和在途由 V2 审计表独立计算，不能混入旧字段伪装完成。

## 8. 生命周期与差异

- 提交后仍有未分类在途且无差异：发货批次保持 `pending_receive`，调拨单进入或保持 `partial_received`。
- 全部数量已分类且无残损/短缺：发货批次为 `received`。
- 出现残损或显式短缺：创建不可变差异明细，发货批次和调拨单进入 `discrepancy`；短缺不得自动裁决。
- 同一发货批次在无开放差异时可继续多次部分收货；开放差异时先由后续 V2 差异裁决边界处理，旧差异处理器不得直接改写 V2 明细库存。
- 调拨单只有全部已发数量完成合格收货或差异已按守恒式裁决后才能归档。

## 9. 幂等、Gate 与失败策略

- 新命令类型：`TRANSFER_SHIPMENT_RECEIPT_CREATE_V2`。
- 资源键：`transfer-shipment:{shipmentId}`。
- 成功返回强类型 `InvTransferShipmentReceiptCreationVo`。
- `command_request_id` 在收货头唯一；重复请求同指纹重放原结果，不同指纹拒绝。
- 新 Gate 默认均为 `false`：
  - `erp.inventory.transfer-receipt-v2.write-enabled`
  - `erp.inventory.transfer-receipt-v2.persistence-ready`
- 命令服务在调用 Executor 前检查 Gate，持久化服务再次检查，避免默认关闭时写入命令台账。
- 本轮骨架在 Gate 后仍显式拒绝“持久化边界未实现”；仓库中不提供任何启用配置。
- 任一影响行数、版本、归属、数量、成本、序列号、模式或规划校验失败，抛错并由单一数据库事务整单回滚；不写补偿 SQL。

Stage 11 的 `receipt-boundary-ready` 仍保持未配置/`false`。只有 Stage 12 持久化、专属数据库迁移、并发与故障注入、排他路由和启用清单全部通过后，才能进入单独启用检查点。
