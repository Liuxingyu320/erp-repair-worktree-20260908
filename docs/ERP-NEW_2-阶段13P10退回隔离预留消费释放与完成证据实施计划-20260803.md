# ERP-NEW_2 阶段 13P10：退回隔离预留消费、释放与完成证据实施计划

> 日期：2026-08-03
>
> 分支：`codex/erp-new-2-rebuild`
>
> 基线：`0a97eab9 feat: reserve adjudication return quarantine`
>
> 范围：实现未接线的隔离预留生命周期所有者和权威完成证据；不接入发货或审批入口，不启动运行环境

## 1. 审计结论

普通 V2 发货与普通调拨预留不能直接处理差异退回子调拨：

1. `InvTransferShipmentCreationMapper.selectEligibleCandidateFacts` 明确排除 `quarantine` 库位，只允许合格或让步库存参与普通发货规划；
2. `InvTransferReservationService` 只读写 `inv_transfer_reservation`，而阶段 13P9 的退回子调拨只拥有 `inv_transfer_quarantine_reservation`；
3. 普通发货消费明细余额的 `available_quantity`，退回发货必须消费已经从 `quarantine_quantity` 转入 `locked_quantity` 的精确受损余额；
4. 普通审批驳回、原生审批退回/撤回/终止及取消逻辑只会释放普通预留，不能直接用于退回子调拨；
5. P7 当前完成证据只证明“曾经预留”，没有证明该预留已全部消费且从未释放；
6. P9 序列号绑定只保存初始 `quarantine -> quarantine_reserved` 证据，尚无消费、释放、版本和事件归属。

因此 P10 建立独立的隔离预留生命周期边界；普通预留、普通规划和普通发货行为保持不变。

## 2. 生命周期与数量守恒

主预留状态固定为：

- `ACTIVE`：全部数量仍冻结；
- `PARTIAL`：一部分已消费，仍有冻结余量；
- `CONSUMED`：全部数量进入合法 V2 发货；
- `RELEASED`：未发货且全部退回原隔离库存；
- `CLOSED`：部分已消费，其余全部释放。

任意时刻必须满足：

```text
reserved = consumed + released + remaining
remaining >= 0
```

消费 `q` 的物理变换：

```text
current_after    = current_before - q
available_after  = available_before
locked_after     = locked_before - q
quarantine_after = quarantine_before
total_cost_after = total_cost_before - q * source_cost_price
version_after    = version_before + 1
```

释放全部剩余量 `r` 的物理变换：

```text
current_after    = current_before
available_after  = available_before
locked_after     = locked_before - r
quarantine_after = quarantine_before + r
total_cost_after = total_cost_before
version_after    = version_before + 1
```

汇总库存和精确受损批次库位余额必须执行同一数量变换。任一版本、成本、数量、批次、库位、收货分配或序列号事实漂移均失败关闭。

## 3. 不可变事件证据

新增两张惰性事件表：

- `inv_transfer_quarantine_reservation_consumption`：每个命令请求和 V2 发货明细只允许一条消费事件，保存发货批次、数量、金额及汇总/明细库存版本前后值；
- `inv_transfer_quarantine_reservation_release`：每个释放命令只允许一条事件，保存释放原因、数量及版本前后值。

序列号绑定表加法增加生命周期状态、版本、消费事件/释放事件归属、发货批次和更新时间。初始绑定仍不可修改；只允许：

- `ACTIVE + quarantine_reserved -> CONSUMED + shipped`；
- `ACTIVE + quarantine_reserved -> RELEASED + quarantine`。

序列号消费按 `receipt_serial_id, serial_id` 稳定选择，数量必须为整数；批次物料不得出现序列号绑定。

## 4. 固定锁序与事务所有者

新增 `InvTransferReceiptDiscrepancyReturnReservationLifecycleService`，所有写方法使用 `Propagation.MANDATORY`，只能加入未来已有外层命令事务：

1. 校验请求 ID、退回子调拨、唯一明细、操作人和命令上下文；
2. 锁定隔离预留头，并验证 P7 工作流关系和当前审批轮次；
3. 按 `stock_id` 锁定汇总库存；
4. 按 `balance_id` 锁定精确受损余额；
5. 按 `receipt_serial_id, serial_id` 锁定全部序列号绑定及当前序列号；
6. 纯策略一次性验证全部事实并生成消费或释放变换；
7. 条件更新汇总库存、明细余额和序列号；
8. 追加不可变事件；
9. 条件更新主预留累计量、状态和版本；
10. 回读并返回权威结果，供未来发货/审批适配器使用。

所有锁在第一次数量变更前取得。任何 DML 影响行数不为一、事件唯一冲突或回读不一致均抛错，由外层事务整体回滚；不写补偿 SQL。

## 5. 完成证据加强

扩展 P7 子调拨事实，实时读取实际预留：

- `reservationStatus`；
- `reservedQuantity`；
- `consumedQuantity`；
- `releasedQuantity`。

创建关系时要求预留为 `ACTIVE` 且消费、释放均为零。完成证明除现有 `received + V2 发货 + V2 收货 + 零开放差异` 外，还必须要求：

```text
reservationStatus = CONSUMED
consumedQuantity = reservedQuantity = actionQuantity
releasedQuantity = 0
```

普通补发工作流也改为从普通预留台账实时读取相同证据，避免只依赖 P7 关系中的历史快照。

## 6. 本阶段接线边界

- 新生命周期 Service 在生产主代码中保持零调用点；
- 不修改 `InvTransferShipmentCreationService`、`InvTransferCommandService`、Controller 或前端 Writer；
- 不修改原生/旧审批回调、取消和撤回入口；
- 不改变普通 `InvTransferReservationService`；
- 不启用 V2 发货/收货 Gate；
- 不把阶段 13P9 退回 owner 接入阶段 13P6 执行事务。

后续阶段必须用专属退回发货规划/创建适配器调用消费方法，并由审批/取消适配器调用释放方法；在这些接线完成前，退回子调拨仍不可运行。
