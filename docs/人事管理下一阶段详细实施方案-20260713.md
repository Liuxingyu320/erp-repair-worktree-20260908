# 人事管理下一阶段详细实施方案

> 方案日期：2026-07-13
> 文档状态：第一批 `HR-N0-01`～`HR-N1-04` 已实现，`HR-N1-05` 已于 2026-07-13 进入 P0 观察
> 依据：[人事管理功能检查与优化方案](./人事管理功能检查与优化方案-20260713.md)
> 项目约束：兼容当前 Java 17、Spring Boot 4、Spring Cloud、Vue 2、Element UI、MyBatis 和 MySQL 5.7；不使用虚拟机、Docker 或 Testcontainers；数据库验证使用本机独立测试库，不接触业务库。

## 1. 建设结论

下一阶段不能直接把 155 名员工的全部缺失字段批量填上，也不能继续只改页面。当前项目更需要按以下顺序推进：

1. **先校准完整度口径**：现有 `HrEmployeeFieldRegistry` 将几乎全部 68 个员工档案字段计入完整度，其中包含血型、政治面貌、办公电话、部分学历字段等不一定属于业务阻断项。必须把“业务必填完成率”和“资料覆盖率”拆开，否则 0 人完整、平均 32% 会持续误导治理优先级。
2. **再建立组织主数据健康队列和启用门禁**：部门负责人来自 `sys_dept.leader`，公司、部门层级和门店来自组织树实时派生；组织路径或负责人缺失会直接阻断入职。问题必须在组织启用和入职创建之前被发现。
3. **然后按责任人治理员工档案**：员工本人、组织管理员、HR、合同社保专员分别处理自己能负责的字段；系统派生字段不能要求 HR 手工填占位值。
4. **完成安全的批量补录能力**：替换当前正式员工“直接导入”的过渡能力，采用“模板—预检—逐行确认—结果—可回滚”的批次流程。
5. **最后统一法人主体和日常效率**：当前员工档案已经保存法人主体 ID、编码、名称，但项目没有统一法人主体主数据来源，调岗仍要求手填三项。应建立主数据选择器，由服务端生成一致快照。

推荐把工作拆成 5 个可独立发布的阶段。单人顺序实施预计 6～8 周；后端、前端、数据治理和测试可并行时预计 4～5 周。

## 2. 当前项目基线

### 2.1 已确认的数据基线

- 员工总数：155 人。
- 按现有 68 字段口径，完整档案：0 人。
- 待补资料：155 人。
- 平均完整度：32%。
- 账号配置风险：1 人。
- 已发现真实入职阻塞：目标组织未配置部门负责人。

上述数值作为“旧口径基线”保留。阶段 0 上线后必须同时输出新的“业务必填完成率”和“资料覆盖率”，不能覆盖旧基线后失去对照。

### 2.2 可以直接复用的能力

- `HrEmployeeFieldRegistry`：68 字段唯一注册表，已经包含字段所属存储、可编辑性、分组和脱敏类型。
- `HrEmployeeCompletenessEvaluator`：员工档案完整度统一计算入口。
- `SysUserProfileCompletionServiceImpl`：员工本人可填写 15 项个人、身份、联系和银行卡资料。
- `SysUserProfileDerivationService`：从 `sys_dept`、岗位和日期实时派生公司、部门、门店、岗位、部门负责人和年限。
- `HrOnboardingRuleService`：入职缺失字段、阻塞码和允许动作的后端权威规则。
- `HrCompletenessController`、`HrCompletenessService`：已有员工、部门、账号风险队列。
- `HrOnboardingImportBatchCoordinator` 等：已有入职预览导入、逐行处理、幂等和批次结果模式。
- `SysTodoServiceImpl`：已有 `HR_PROFILE_INCOMPLETE`、入职确认、合同到期和离职账号待办。
- `hr_onboarding_operation_log`、`sys_hr_lifecycle_action`：已有可用于流程指标的操作事实和不可变生命周期动作。
- 敏感字段查看、敏感导出和 `hr_sensitive_access_log`：已有数据范围、脱敏和审计边界。

### 2.3 当前结构性缺口

1. 完整度只有一个百分比，没有区分必填、条件必填和建议补充。
2. 完整度字段没有责任人、截止阶段和风险等级元数据。
3. 组织结构异常只以派生警告或单据阻塞形式出现，没有集中治理队列。
4. `sys_dept`、`sys_post` 启用时没有统一的人事可用性门禁。
5. 正式员工旧导入接口 `/system/hr/employee/importData` 会直接写数据，没有新的预览批次、逐行确认和回滚链路。
6. `sys_user_profile` 已有 `legal_entity_id/legal_entity_code/legal_entity`，但没有权威法人主体表和组织映射。
7. `hr_onboarding` 只有法人主体名称，没有稳定 ID 和编码。
8. 部门汇总只有人数和平均百分比，没有缺失字段排名、责任人和可直接处理的员工队列。

## 3. 范围与非目标

### 3.1 本计划包含

- 员工档案完整度口径重构。
- 组织、岗位、入职配置和法人主体主数据健康检查。
- 主数据问题集中队列和启用门禁。
- 按字段、组织、责任人汇总资料缺口。
- 正式员工非敏感资料的安全批量补录。
- 法人主体主数据、组织映射和调岗/入职选择器。
- 桌面端和移动端高频操作简化。
- 人事数据质量及流程效率指标。
- 权限、数据范围、审计、测试、灰度和回滚。

### 3.2 本计划暂不包含

- 薪资核算、个税、考勤和排班系统重建。
- 招聘 ATS、面试流程和人才库。
- 组织架构的大规模业务重组。
- 修改 OA 电子签约状态机或合同模板业务规则。
- 批量导入身份证号、银行卡号、地址、手机号等敏感值。
- 自动猜测部门负责人、法人主体或组织关系并直接写入业务库。

敏感资料继续由员工本人补全页或具备权限的 HR 单人编辑流程处理。批量治理首版只允许 `MaskingClass.NONE` 且非派生字段。

## 4. 实施原则

1. **后端规则唯一**：完整度、主数据阻塞、字段责任和允许动作都由后端返回，前端只负责呈现。
2. **口径双轨过渡**：旧 `profileCompletionPercent` 保持兼容；新增业务必填和覆盖率字段，新页面切换后再评估是否废弃旧字段。
3. **派生字段不手填**：公司、组织层级、门店、岗位、部门负责人等继续从主数据派生，不允许通过员工档案导入写占位值。
4. **数据范围优先**：所有员工、组织、负责人和法人主体选项必须经过现有 `@DataScope` 或等价服务端校验。
5. **迁移先加后减**：只新增表、字段、索引、权限和兼容接口；至少一个正式版本后再下线旧导入入口。
6. **修复先 dry-run**：所有数据脚本默认只读，输出数量、冲突和样本；没有人工确认不得执行写入。
7. **批量操作可解释、可重放、可回滚**：预检批次固定源文件摘要、逐行结果、修改字段和非敏感前后值。
8. **不使用虚拟机或容器**：本机原生 Java、Node、MySQL、Redis 完成验证；集成测试使用独立测试库。
9. **不污染现有改动**：实施只修改本方案列出的 HR、系统主数据和必要 OA 回归文件，不覆盖 OA、库存、云盘等其他已有变更。

## 7. 阶段 0：完整度口径校准

### 7.1 新口径

为 `HrEmployeeFieldRegistry.FieldDefinition` 增加以下治理元数据：

- `requirementTier`：`REQUIRED/CONDITIONAL/OPTIONAL`。
- `responsibility`：`EMPLOYEE/ORG_ADMIN/HR/CONTRACT_SOCIAL/SYSTEM`。
- `dueStage`：`PRE_ENTRY/POST_ENTRY_7D/LIFECYCLE/NONE`。
- `riskLevel`：`BLOCKING/IMPORTANT/NORMAL`。

首版建议口径：

| 责任方 | 首版字段范围 | 处理入口 |
|---|---|---|
| 员工本人 | 现有登录补全页的 15 项：姓名、手机号、性别、出生日期、证件、地址、婚姻、民族、紧急联系人、银行资料 | `/profile-completion` |
| 组织管理员 | 所属公司、组织层级、门店、岗位、部门负责人 | 系统管理的部门、岗位页面 |
| HR | 工号、职级、员工状态、人员类别、入职日期、直属主管、工作地、招聘渠道等 | 员工档案 |
| 合同社保专员 | 合同起止、合同类型、法人主体、社保类型与缴纳地、公积金缴纳地 | 员工档案/合同流程 |
| 系统派生 | 工龄、司龄、合同期限、组织名称、岗位名称 | 无手工入口，只显示来源问题 |

血型、政治面貌、办公电话、部分教育经历等首版列为 `OPTIONAL`，计入资料覆盖率但不阻断“业务资料完整”。试用期、转正日、离职日、国籍/民族、门店和合同字段继续按员工状态、人员类别及合同适用性条件计算。

### 7.2 返回模型兼容策略

`HrEmployeeCompletenessSnapshot`、列表 VO 和汇总 VO 新增：

- `requiredCompletionPercent`；
- `requiredCompletedFieldCount`；
- `requiredApplicableFieldCount`；
- `missingRequiredFields`；
- `coveragePercent`；
- `missingOptionalFields`；
- `missingByResponsibility`。

兼容规则：

1. `profileCompletionPercent` 在至少一个正式版本内继续返回当前算法结果。
2. 新页面明确显示“业务必填完成率”和“资料覆盖率”，不再只写“完整度”。
3. `SysTodoServiceImpl` 的 `HR_PROFILE_INCOMPLETE` 改用 `requiredCompletionPercent < 100`。
4. 旧客户端仍可读取原字段，不因新口径立即失效。

## 8. 阶段 1：主数据健康队列与启用门禁

### 8.1 主数据问题码

计划新增稳定问题码，不再依赖“组织结构待修复”等中文字符串判断：

| 问题码 | 严重度 | 权威来源 | 处理入口 |
|---|---|---|---|
| `ORG_PATH_INVALID` | P0 | `sys_dept.parent_id/ancestors/status` | 部门管理 |
| `COMPANY_NODE_MISSING` | P0 | `GROUP` 后的公司层级 | 部门管理 |
| `STORE_MAPPING_MISSING` | P1 | 组织树的 `STORE` 节点 | 部门管理 |
| `DEPT_LEADER_MISSING` | P0 | `sys_dept.leader` | 部门管理 |
| `POST_MISSING_OR_DISABLED` | P0 | `sys_post` | 岗位管理 |
| `POSITION_CONFIG_MISSING` | P1 | `hr_onboarding_position_config` | 岗位入职配置 |
| `POSITION_CONFIG_ROLE_MISSING` | P1 | 配置默认角色 | 岗位入职配置 |
| `DICTIONARY_ROUTE_MISSING` | P1 | `sys_config/sys_dict_*` | 参数/字典管理 |
| `LEGAL_ENTITY_MAPPING_MISSING` | P0 | 阶段 3 法人主体映射 | 法人主体管理 |

当前 `HrOnboardingRuleService` 已公开的 `DERIVED_*` 阻塞码保持兼容，由新的主数据问题码映射到现有入职页面文案。

### 8.2 后端能力

计划新增：

- `HrMasterDataIssueCodes.java`：稳定问题码和严重度。
- `HrMasterDataReadinessService.java`：按数据范围计算组织、岗位、配置和受影响人数/入职单数。
- `HrMasterDataIssueVo.java`：问题资源、影响范围、处理地址和安全摘要。
- `HrMasterDataSummaryVo.java`：P0/P1 数量、受影响员工、受影响入职单。

扩展现有接口：

| 网关接口 | 用途 | 权限 |
|---|---|---|
| `GET /system/hr/completeness/master-data/summary` | 主数据健康摘要 | `hr:completeness:list` |
| `GET /system/hr/completeness/master-data/issues` | 分页问题队列 | `hr:masterData:list` |
| `GET /system/hr/completeness/master-data/issues/export` | 导出非敏感问题清单 | `hr:masterData:export` |

问题行只返回资源名称、问题码、影响数量和处理链接，不返回身份证、手机号、银行卡等员工资料。

### 8.4 启用门禁

新增系统参数：

- `hr.master-data.readiness.enabled=true`：开启只读检测。
- `hr.master-data.enforce-on-enable=false`：初始只观察，不拦截。

清理完现有 P0 后，将第二项切为 `true`。门禁只作用于以下动作：

1. 新组织或岗位从停用切为启用。
2. 修改组织父级、类型或负责人后保存。
3. 岗位入职配置启用。
4. 入职单标记就绪或确认入职。

既有异常记录不会被自动停用。失败提示必须列出具体问题和处理入口，不能只返回“校验失败”。

计划新增幂等迁移：

输出：

1. 组织路径断裂、停用祖先、公司层级缺失。
2. 在用组织未配置负责人。
3. 员工无岗位、停用岗位、无目标门店。
4. 在用岗位 × 在用人员类别缺少入职配置或默认角色。
5. 现有入职单受每类问题影响的数量。
6. 法人主体 ID、编码、名称不完整或互相冲突的数量。

脚本只允许 `SELECT`，不包含自动修复语句。

### 8.6 阶段验收

- 当前已知“目标组织未配置部门负责人”能同时在入职详情和主数据队列出现。
- 主数据问题受 `@DataScope` 限制，普通 HR 看不到范围外组织。

#### 匹配和安全规则

1. 只允许通过明确 `userId` 或唯一工号匹配，不按姓名模糊匹配。
2. 不创建账号、不修改用户名、密码、角色或数据范围。

4. 确认时重新锁定并校验员工数据范围。
5. 预检后员工发生变化时，比较非敏感源状态哈希，当前行标记 `STALE`，不覆盖新数据。
6. 每行独立结果，但批次确认使用明确幂等键；重复提交不重复更新。
7. 回滚仅允许在当前值仍等于该批次写入结果时执行，避免覆盖后续人工修改。

### 9.4 治理批次执行方式

1. 先选一个组织、10～20 名员工试点。
2. 导出该组织非敏感缺口模板。
3. HR 和组织负责人共同确认字段来源。
4. 上传预检，只处理 `UPDATE`，先解决全部 `ERROR/STALE`。
5. 确认后核对员工详情、完整度和操作结果。
6. 观察 1 个工作日后再扩大到下一组织。
7. 敏感字段由员工本人完成，不在 Excel 中流转。

### 9.5 阶段验收

- 预览不会写员工数据。
- 同一文件重复确认不重复修改。
- 范围外员工、敏感列、派生列、未知列全部被拒绝。
- 冲突或过期行不覆盖人工新修改。
- 回滚不会覆盖批次之后的合法变更。

### 14.2 应用回滚

- 每阶段独立发布，不把完整度、批量导入和法人主体切换绑在同一个版本。
- 使用系统参数关闭主数据门禁、批量导入入口或法人主体选择器。
- 旧字段、旧读取接口和历史快照继续保留。
- 回滚应用不删除新表或新列，防止已产生的数据丢失。

建议功能参数：

- `hr.completeness.policy.v2.enabled`
- `hr.master-data.readiness.enabled`
- `hr.master-data.enforce-on-enable`
- `hr.employee.profile-import.enabled`
- `hr.legal-entity.master.enabled`

### 14.3 数据回滚

- 主数据清理不提供自动“猜测并修复”，所以只需按人工变更审计逐条撤销。
- 批量员工补录通过批次行保存的非敏感前值执行条件回滚。
- 法人主体表和映射采用逻辑停用，不物理删除历史主体。
- `hr_onboarding` 和生命周期动作中的主体名称继续作为历史快照，不随主数据改名回写。

## 16. 最终完成标准

本计划完成不以“页面上线”作为标准，必须同时满足：

1. 业务必填完成率与资料覆盖率口径清晰、可对账。
2. 在用组织和岗位 P0 主数据问题为 0。
3. 新问题在组织或岗位启用时被阻断，而不是等入职单报错。
4. 员工、组织管理员、HR 和合同社保专员只收到自己可处理的缺口。
5. 正式员工批量补录有预检、幂等、逐行结果、数据范围校验和条件回滚。
6. 敏感字段不通过批量 Excel 治理链路流转。
7. 入职和调岗不再手填法人主体三元组。
8. HR 生命周期动作和 OA 签约快照保持一致。
9. 前后端测试、原生 MySQL 迁移验证、生产构建、桌面与移动视觉回归全部通过。
10. 全程不使用虚拟机或容器，且不修改范围外业务数据。
