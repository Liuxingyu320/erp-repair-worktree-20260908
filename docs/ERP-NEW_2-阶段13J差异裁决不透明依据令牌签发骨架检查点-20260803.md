## 1. 已完成结果

- 新增不依赖 JWT、Redis 或共享缓存的差异裁决依据令牌策略。
- 生产签发器使用 `SecureRandom` 生成 32 字节随机值，编码为带版本前缀的 256 位 Base64URL bearer token。
- 原始令牌只存在于一次性签发结果；持久化意图、Mapper 和数据库结构只接收带用途域分离的 SHA-256 摘要。
- 令牌有效期固定为 5 分钟，Java 策略和条件 SQL 同时核验精确时长。
- 令牌绑定：精确权限、裁决人、所选组织、规范化组织范围摘要、事项、版本、事实指纹、来源确认事件和目标确认事件。
- 纯核验策略统一拒绝篡改、过期、未来签发、已消费、跨用户、跨组织、跨范围、跨事项、跨版本和事实变化。
- 新增无 Controller 的唯一签发事务服务；权限验证发生在组织解析和数据库访问之前。
- 新增加法表、窄 Mapper 和浏览器安全签发 VO；VO 和内部持久化意图的 `toString()` 均脱敏令牌及内部摘要。

## 2. 组织隔离与信息隐藏

- `ShopScopeService` 返回的范围必须非空、不超过 10000 项、全部为正数，并规范化去重。
- 所选组织必须属于当前范围，且事项的调出或调入组织至少一方属于该范围。
- 范围被下推至 `SELECT ... FOR UPDATE`，范围外事项不会被锁定。
- 条件 `INSERT ... SELECT` 再次核对所选组织、组织范围、双方最新确认和独立裁决职责。
- 不存在、范围外、事实或确认边界不可核验使用同一失败结果，不泄露事项是否存在。

聚焦自审曾发现初版签发服务复用了无组织过滤的旧事项锁查询。该问题已在提交前修复：旧裁决写服务继续显式传入 `null` 保持现有关闭行为，签发服务必须传入有限组织范围；阶段 13E 原子事务回归已通过。

## 3. 持久化边界

新增表 `inv_transfer_receipt_discrepancy_adjudication_basis` 只保存服务端绑定：

- `token_hash`，没有原始 token 列；
- 事项、版本、事实和双方确认事件锚点；
- 所选组织与完整范围摘要；
- 裁决人和精确权限快照；
- `issued_at`、`expires_at` 与 `issued/consumed` 状态；
- 为后续同事务消费预留 `consumed_at`、`consumed_request_id` 和 `consumed_adjudication_id`。

当前 Mapper 只有一条条件插入，没有 UPDATE、DELETE、裁决计划写入、事项推进或库存/物流/财务写入。DDL 仅为 ERP-NEW_2 专属数据库的未来 roll-forward 源码，本阶段未执行。

## 6. 下一安全阶段

阶段 13K 应把以下步骤纳入阶段 13E 的同一个数据库事务和固定锁序：

1. 锁定事项；
2. 锁定幂等请求；
3. 按原始令牌摘要锁定 basis 记录；
4. 重新解析并核对当前组织范围、用户、权限、事项事实和双方确认；
5. 写入裁决头及动作并条件推进事项；
6. 条件标记 basis 为已消费，绑定相同 `requestId` 和裁决主键；
7. 任一步失败则全部回滚；相同请求的重放必须精确核对同一 basis 和同一裁决结果。

在该同事务消费闭环完成前，不新增 HTTP 写入口。本检查点不宣称真实裁决提交或长期目标完成。
