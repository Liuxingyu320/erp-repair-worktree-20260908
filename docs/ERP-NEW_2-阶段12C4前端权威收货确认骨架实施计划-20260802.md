# ERP-NEW_2 阶段 12C4：前端权威收货确认骨架实施计划

> 日期：2026-08-02
> 分支：`codex/erp-new-2-rebuild`
> 基线：`9bc4d1dd feat: execute atomic transfer receipts`
> 范围：ERP-NEW_2 新前端、V2 新回执十进制字符串契约和对应离线测试；默认 Mock，不启用后端 Gate，不发真实写请求

## 1. 结果与范围

本阶段把既有只读收货规划契约扩展为可核验的前端收货命令边界，并让移动收货页基于同一份服务端权威规划完成合格、残损、短缺和序列号分类。本阶段只在浏览器隔离 Mock 中演练命令；真实 HTTP Writer 仅作为未注入适配器存在，不进入应用启动组合。

页面不得自行读取或计算库存余额、批次成本、状态机或可收上限。所有可选 allocation、目标正常/隔离库位、待收 serial 和 `receiptPlanVersion` 均来自规划响应；前端只负责分类、局部守恒校验、证据门禁、请求标识和二次确认。

## 2. 交互与设计约束

- 这是高频企业移动任务，采用 Emil Kowalski 的克制与速度作为主原则、Jakub Krehel 的生产级细节作为次原则。
- 数量和 serial 分类立即更新，不增加装饰性动画；只有低频二次确认和成功回执允许 180ms 内的轻微透明度/位移动效。
- 所有动效必须支持 `prefers-reduced-motion`，不得使用循环、弹跳、缩放、视差或大面积模糊。
- 信息结构继续遵循 UI Prompt Library 的“摘要 + 主清单 + 确认区”，并参考 Motion Primitives 的状态连续性；21st.dev、React Bits、Magic UI、Uiverse 与 MotionSites 只作为视觉和提示词灵感，不复制 React/Tailwind 源码或引入运行时依赖。
- 页面保留唯一主操作；提交前明确显示合格、残损、短缺、仍在途数量和是否完成本批。

## 3. 契约与纯逻辑

扩展 `erp-ui-next/src/domains/inventory/transfer/transfer-receipt.contract.ts`：

1. 新增严格的收货分类 Draft、V2 创建命令、创建结果和 Mock 演练结果类型。
2. 数量继续使用十进制字符串与 Decimal 校验，最多四位小数；禁止 JavaScript 浮点数承担守恒判断。
3. 纯命令构造器必须校验规划可执行、plan version、allocation 归属、目标库位候选、单 allocation 分类上限、全局 serial 唯一性和逐件数量守恒。
4. `finalizeShipment` 由权威规划总剩余量减去本次分类总量得出，前端不得让用户提交矛盾布尔值。
5. 残损或短缺必须同时具备说明与附件引用；零数量不得夹带库位或 serial。
6. blocked/complete allocation 不得进入命令；全部零分类不得形成请求。

## 4. HTTP 与运行时边界

扩展 `transfer-receipt.http.ts`，新增独立 `TransferReceiptWriter`：

- `POST /inventory/transfer/shipments/{shipmentId}/receipts`；
- `X-Request-Id`、组织头和 CSRF 均由统一 HTTP Client 负责；
- body 只发送后端 DTO 字段，不发送前端显示数据；
- 路径及所有服务端 Long 标识必须为正整数；Mock/local-only 附件引用不得进入真实 Writer；
- 响应必须回显相同 shipment、plan version，并满足分类总量和剩余量一致，否则失败关闭。

`AppGateways.transfer` 仍只注入 Mock `loadReceiptPlanning` 和 `simulateReceiptConfirmation`。应用在 mocks 关闭时继续使用 unavailable Gateway；本阶段不创建真实运行时组合，不修改环境变量或 Gate。

## 5. 移动收货页

重构 `ReceivingPage.vue`：

1. 从 Gateway 加载并再次解析权威规划，不再使用旧的扁平 `ReceivingTask`。
2. lot allocation 提供合格、残损、短缺十进制分类；serial allocation 逐件选择三类处置并由选择结果生成数量。
3. 目标正常/隔离库位只允许选择规划候选；无对应数量时不携带库位。
4. 有残损/短缺时显示说明和本地证据门禁；本地证据只生成显式 `local-only:` Mock 引用，真实 Writer 必须拒绝。
5. 首次主操作只打开可聚焦的确认面板；确认后调用 Mock simulator，并保留同一请求标识，防止用户重试时产生两个命令。
6. 规划变化、输入非法、提交失败均保持已填内容并提供刷新/重试；Mock 成功回执明确说明没有写库存或数据库。

## 7. 验证与停止条件

先运行 receipt 契约、HTTP 和页面定向测试，再运行 `npm --prefix erp-ui-next run verify`；随后运行库存模块完整离线测试和后端全 Reactor，确认前端契约未漂移。最后执行 `git diff --check`、Gate、共享连接串、秘密、受保护路径和运行时注入审计。

发现需要启用 Gate、发送真实 POST、上传到现有文件服务、连接数据库/中间件、使用 Docker、引用旧前端源码、访问受保护原项目或把 `local-only:` 引用交给真实 Writer 时立即停止。真实写联调、证据上传和数据库验证必须在 ERP-NEW_2 专属非 Docker 环境中另立检查点。
