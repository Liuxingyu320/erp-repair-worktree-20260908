## 1. 执行结论

下一阶段按以下顺序执行，不允许跳过前置门禁：

```text
HR-R5-0 隔离人事发布范围
    ↓
HR-R5-1 原生 MySQL 5.7 迁移双跑与原生测试
    ↓
HR-R5-2 非业务测试环境完整发布演练
    ↓
HR-R5-3 正式库结构与应用发布（两个开关保持 false）
    ↓
HR-R5-4 P0 数据治理，P1 建立责任清单
    ↓
HR-R5-5 P0=0 后观察至少一个完整工作日
    ↓
HR-R6-A 单独开启健康证新受理
    ↓
HR-R6-B 单独开启主数据强制门禁
```

当前不具备直接开启功能的条件。干净发布范围已经通过工程与原生 MySQL 5.7.31 家族级门禁，可以进入非业务环境完整发布演练；但业务库仍缺健康证表，数据快照仍有 P0。正式目标如果是其他 5.7 小版本，仍需在同版本非业务环境复跑。

## 2. 目标、范围与非目标

### 2.1 目标

1. 形成不夹带 OA、库存、云盘等无关修改的人事发布边界和文件清单。
2. 在不使用虚拟机和容器的前提下，获得原生 MySQL 5.7 迁移、幂等、回滚和 Java/SQL 对账证据。
3. 先以开关关闭状态发布表结构和应用，再通过正常页面治理真实 P0 数据。
4. 达到 P0=0、Java/API 与 DBA SQL 对账一致、观察满一个完整工作日。
5. 先开启健康证新受理，稳定后再开启主数据强制门禁，两次变更可独立回退。

### 2.2 本阶段范围

- `sys_dept.leader_user_id` 负责人稳定身份和组织路径治理。
- `sys_user_profile` 缺档员工显式初始化和真实资料补齐。
- `hr_employee_health_certificate` 迁移、权限、附件、审核、提醒和新受理开关。
- 人事主数据 readiness、影响人数口径、问题跳转与资源级写入门禁。
- 当前 45 个岗位×员工类别 P1 的责任化治理。

### 2.3 非目标

- 不根据姓名自动猜测或批量回填负责人 ID。
- 不批量生成虚假员工档案、工号、岗位、合同或入职配置。
- 不删除新表、新字段或已受理的健康证历史作为常规回滚方式。
- 不在本阶段同时解决前端入口包 1.69 MiB 的性能警告；该项单独进入性能优化待办。
- 不混入当前工作区中 OA、库存、云盘、移动通用组件等其他业务改动。

## 4. 不可突破的执行原则

1. **不写错库**：原生测试 URL 只允许指向库名包含 `test`、`_it_` 或 `rehearsal` 的隔离库；测试中已有硬保护，不得绕过。
2. **不把敏感信息写入命令或文档**：数据库口令使用本地受控登录文件或环境变量，不放入 Git、命令历史和测试输出。
3. **不自动治理业务语义**：组织、员工、负责人和岗位配置仅通过已有页面和服务入口处理，不直接执行批量 `UPDATE`。
4. **不并发跑菜单初始化**：三份迁移中的 `MAX(menu_id)+1` 段必须在维护窗口单会话、单执行人运行。
5. **结构先于应用**：`hr_employee_health_certificate` 表和 21 个预期列未就绪前，禁止部署当前后端，因为员工 Mapper 已联表该表。
6. **开关分离**：健康证新受理和主数据写入门禁不允许同时开启，两次开启之间必须有独立验证和回退点。
7. **每个阶段先满足停止条件**：出现结构不一致、双跑增量、对账差异、越权、敏感数据泄漏或非预期 5xx 时立即停止，不带病进入下一阶段。

### 5.2 HR-R5-1：原生 MySQL 5.7 复验

2026-07-14 进展：当前混合工作区与 HR-R5-0 干净发布范围均在不使用虚拟机、Docker 或 Testcontainers 的条件下，通过 Oracle 官方原生 MySQL 5.7.31 完成迁移双跑、预检、Java/SQL 对账和 3 个实际执行的原生测试，证据见 `docs/人事MySQL57原生复验记录-20260714.md` 和 `docs/人事HR-R5-0干净发布范围验证记录-20260714.md`。MySQL 5.7 家族语法、流程和干净范围依赖风险已关闭；已知正式目标小版本若不是 5.7.31，仍须做同版本验证。

#### 环境准备

1. 使用本机原生 MySQL 5.7.44 进程，或一台受控的非业务 MySQL 5.7 测试服务器。
2. 禁止使用 Docker、Colima、Testcontainers、虚拟机或容器镜像。
3. 创建一个可丢弃隔离库，库名必须包含 `test`、`_it_` 或 `rehearsal`。
4. 测试账号只获授隔离库需要的 DDL/DML 权限，不授权业务库。
5. 使用经批准的非生产基线数据。如需使用真实快照，必须先完成脱敏、访问授权和销毁方案。

#### 迁移顺序

```text
1. sql/erp_hr_dept_leader_identity_20260713.sql
2. sql/erp_hr_health_certificate_20260713.sql
3. sql/erp_hr_data_quality_20260713.sql
```

三份迁移在同一隔离库按顺序连续执行两遍。第二遍不得新增字段、索引、菜单、配置、权限或角色授权。

#### 预检和对账

```text

scripts/verify-hr-health-certificate-migration.sql
scripts/hr-master-data-readiness.sql
```

必须核对：

- `hr_employee_health_certificate` 表存在且 21 个预期列齐全。
- `uk_hr_health_user_current(user_id,current_flag)` 是唯一索引，没有每员工多条 `current_flag='Y'`。
- `sys_dept.leader_user_id` 和 `idx_sys_dept_leader_user_id` 存在。
- 每个配置 key 只有一条，每个权限字符串只有一个菜单记录，角色授权无重复。
- `feature.hr.health-certificate.enabled` 和 `hr.master-data.enforce-on-enable` 的原有值在迁移双跑后未被覆盖。
- Java 评估器与 DBA SQL 的问题键、严重度和行级影响人数完全一致。

### 5.3 HR-R5-2：非业务测试环境完整发布演练

### 5.4 HR-R5-3：正式结构与应用发布

本工作包只能在获得正式变更授权、维护窗口、备份责任人和回退责任人后执行。本方案本身不授权立即写业务库。

#### 发布前

1. 使用只读账号确认 `SELECT DATABASE(), VERSION()`，并核对变更工单中的目标库。
2. 备份或快照以下对象：
   - `sys_dept` 结构和负责人字段；
   - `sys_config` 中人事相关 key；
   - `sys_menu`、`sys_role_menu` 中人事权限；
   - `sys_user_profile`、`sys_user_post`、入职岗位配置的治理前基线。
3. 执行两份只读预检。健康证表尚未存在时，预检结果必须与变更计划一致，不能是连错库。
4. 显式核对并必要时先关闭两个运行开关。

#### 发布顺序

1. 执行 `erp_hr_dept_leader_identity_20260713.sql`。
2. 执行 `erp_hr_health_certificate_20260713.sql`。
3. 执行 `erp_hr_data_quality_20260713.sql`。
4. 立即执行两份 verify SQL，确认表、列、索引、配置、权限和授权。
5. 再次确认两个运行开关为 `false`。
6. 部署后端，验证启动、员工列表、capability 和 readiness。
7. 部署前端，验证桌面/移动菜单、权限和页面跳转。

#### 发布后立即检查

- 健康证 capability 返回关闭状态和正确说明。
- 员工 Mapper 不再出现缺 `hr_employee_health_certificate` 表。
- readiness 可查询，但 `observationMode=true`、`enforcementEnabled=false`。
- 新健康证草稿/提交被开关拒绝；历史查询和已有审核仍可用。
- 未出现权限重复、菜单重复、附件越权或员工敏感信息出现在负责人选项中。

#### 回退

- 立即确认两个运行开关为 `false`。
- 回退前端和后端应用版本。
- 保留 `hr_employee_health_certificate`、`leader_user_id`、索引、菜单和权限，不执行破坏性 DROP。
- 使用发布前快照对账配置和权限；仅在确认没有任何新业务数据且另行审批时才制定结构回退脚本。

### 5.5 HR-R5-4：P0/P1 数据治理

治理只使用已有应用页面和服务入口，每批最多处理 5 个资源，每批完成后立即重跑 readiness 并核对是否产生新问题。

#### 第 1 批：组织路径 P0

目标：`COMPANY_NODE_MISSING=0`。

1. 从 readiness 页面的“去处理”进入 `/system/dept?deptId=<id>`。
2. 由组织管理员确认该节点的真实业务归属，判断应调整父节点、节点类型还是停用无效组织。
3. 通过部门服务修改，让系统同步更新 `parent_id` 和 `ancestors`，不直接 SQL 改祖级路径。
4. 复核受影响子节点、门店、仓库和员工归属。

停止条件：组织管理员无法确认真实公司归属，或调整会改变门店/仓库权限边界且尚未完成影响评估。

#### 第 2 批：员工缺档 P0

目标：`EMPLOYEE_PROFILE_MISSING=0`。

1. 由 HR 逐一确认缺档账号是否真实员工。
2. 对确认为员工的账号，通过 `/hr/employee?userId=<id>&action=initializeProfile` 执行显式建档。
3. 建档后补齐真实的员工状态、员工类别、组织、岗位和必填资料。
4. 重复点击建档应返回同一份档案，不产生唯一键错误或重复行。
5. 如果账号不是员工，禁止为了清零直接伪造档案或标记离职；必须新建“非员工账号类型”政策的独立评审任务。

停止条件：账号身份无法确认，或真实岗位/组织/员工类别尚无责任人确认。

#### 第 3 批：负责人 P0 和历史文本

目标：`DEPT_LEADER_MISSING=0`、`DEPT_LEADER_UNRESOLVED=0`，历史姓名未绑定 ID 的节点均经人工复核。

1. 从 readiness 动作链接进入部门编辑页。
2. 通过“姓名 / 工号 / 组织”选择器选择真实负责人，同名员工必须使用工号和组织区分。
3. 后端以 `leader_user_id` 为唯一可信身份，姓名仅作快照。
4. 管理员、已删除、停用、离职或越出当前数据范围的员工不得作为负责人。
5. 修改后复核姓名快照与当前员工主数据一致。

停止条件：真实负责人尚未组织任命，或候选人账号处于停用/离职/越权状态。

#### 第 4 批：岗位配置 P1

目标：不为清零数字制造虚假配置，对 45 个 `POSITION_CONFIG_MISSING` 建立可审计处理结论。

1. 优先处理未来 30 天内有实际入职需求的岗位×员工类别。
2. 通过 `/hr/position-config?postId=<id>&employeeCategory=<value>` 配置真实必填字段、默认角色和字典路由。
3. 对无入职计划的组合，记录业务责任人、处理日期和暂不配置理由，不写空配置。
4. 如果 P1 对当前在职员工的影响人数从 0 变为大于 0，提升为当日处理任务。

#### 每批验证

- readiness 页面问题行按预期减少，没有新增其他 P0。
- `affectedEmployeeCount` 仍是去重员工数，`affectedOccurrenceCount` 仍是问题覆盖人次。
- 只读 DBA SQL 与 Java 结果一致。
- 操作日志不包含证件号、银行卡、手机、附件内容等敏感信息。

### 5.6 HR-R5-5：观察期

观察从第一次完整扫描确认 P0=0 后开始，至少覆盖一个完整工作日，并覆盖一次 02:35（Asia/Shanghai）健康证提醒调度周期。

#### 观察快照

工作日至少保存三次低敏摘要：上班后、中间时点、下班前。每次记录：

- 代码版本、数据库版本、扫描时间和时区。
- P0/P1/P2 行数、去重受影响员工、问题覆盖人次。
- Java/SQL 对账是否完全一致。
- 健康证待审核、有效、30 天内到期、已过期、最老待审核时长和提醒失败数。
- 员工列表、部门保存、建档、健康证查询/审核相关的非预期 4xx/5xx 和 SQL 错误数。
- 操作责任人、复核人和结论，不记录员工敏感字段。

`reminderFailureCount` 是当前应用实例内计数。如果正式环境有多个 `erp-system` 实例，不能只看单页面当前实例计数，还必须聚合所有实例的提醒日志。持久化、集群级提醒指标可作为后续运维优化，不在本次开关启用前直接扩展业务表。

#### 完成标准

- 三次快照和观察期结束复核均为 P0=0。
- Java/SQL 每次对账一致，无新增永久性误报。
- 观察期内不存在缺表、缺列、负责人误清空、越权附件、重复当前健康证等问题。
- 至少一个 02:35 提醒扫描周期无未解释失败。
- 尚未清理的 P1 都有业务负责人、原因和完成日期。

### 5.7 HR-R6-A：单独开启健康证新受理

#### 前置门禁

- MySQL 5.7 复验已完成。
- 正式健康证表、21 列、唯一索引、6 个权限和角色授权预检通过。
- P0=0，观察期通过。
- 附件验证、本人/数据范围访问、草稿、提交、审核、驳回、续证和提醒均有通过证据。
- 当前待审核队列、最老待审核时长和提醒失败计数已由 HR 确认。
- HR 负责人、测试负责人和发布负责人签字。

#### 执行

1. 在维护窗口只修改 `feature.hr.health-certificate.enabled=true`。
2. 如需灰度，使用已有菜单/角色权限对试点组织开放，不新增第二个含义重叠的功能开关。
3. 验证 capability 立即返回 `intakeEnabled=true`。
4. 使用真实、已授权的业务记录完成一次受理闭环；禁止为了冒烟在正式环境伪造员工或证件。
5. 开启后密切观察新草稿、待审核、审核成功、附件失败、乐观锁冲突和当前证件唯一性。

#### 回退

出现附件越权、重复当前证件、连续非预期 5xx 或严重流程卡死时，立即设置 `feature.hr.health-certificate.enabled=false`。关闭后仍允许查询历史、处理已有待审核和执行已审核当前证件的提醒；不删除已受理数据。

### 5.8 HR-R6-B：单独开启主数据强制门禁

#### 前置门禁

- Gate A 开启后运行稳定，健康证问题不影响主数据变更。
- readiness 中所有 P0 持续为 0。
- Java/SQL 问题键、严重度和影响人数完全一致。
- P0 清零后已观察至少一个完整工作日。
- 非业务环境已证明开关为 `true` 时，会拒绝无效组织路径、缺负责人的受管启用节点和停用/删除在用岗位。
- 非业务环境已证明开关不会因其他组织历史问题拒绝当前合法修复。
- HR、组织管理员、测试和发布负责人共同签字。

#### 执行

1. 只修改 `hr.master-data.enforce-on-enable=true`。
2. 读取 readiness summary，确认 `observationMode=false`、`enforcementEnabled=true`。
3. 不在正式环境故意制造无效数据。通过正常的部门修改、启用和岗位变更观察是否有误拦截。
4. 开启后每次门禁拒绝都必须包含稳定问题码和处理入口，无法解释的拒绝立即升级。

#### 回退

出现合法部门无法保存、合法岗位无法变更、其他组织问题误伤当前资源或错误码不稳定时，立即设置 `hr.master-data.enforce-on-enable=false`，恢复只读观察模式。不回滚已正确治理的组织、员工和负责人数据。
