## 2. 实际交付

### 2.1 一次性提交协调器

新增 `transfer-discrepancy-adjudication-submit.ts`：

1. 解析本地草案并重读服务端权威规划；
2. 将草案与当前事项、版本、差异类型和数量重新绑定；
3. 读取当前组织并签发一次性 basis；
4. 生成一个请求 ID，并在内存中构造严格提交信封；
5. 仅对 `ErpApiError.retryable=true` 且未取消的提交，用同一信封和同一请求 ID 重试一次；
6. 写入函数返回后立即结束其函数栈，使 basis 和信封离开作用域；
7. 重新读取服务端规划，核对事项、裁决 ID 和动作数量；
8. 无法核验时返回 `reload-required`，不再次发送写命令。

协调器实例只保存依赖和单个 `inFlight` 布尔值，不保存草案、basis、token、信封或写入结果。

### 2.2 页面和草案面板骨架

- 草案面板新增 `submissionEnabled`、`submitting` 和 `confirmed-draft` 边界；
- 未注入协调器时，原有 Mock 草案演练和关闭 Gate 文案保持不变；
- 显式注入协调器时，页面要求草案检查和二次确认后才调用一次协调器；
- 提交期间禁用输入和重复确认；
- 服务端规划核验成功后切换为只读计划视图；
- 写响应已返回但投影未核验，或提交结果未知时，锁定草案提交，只保留“重新读取计划状态”；
- 页面切换事项或卸载时取消当前请求；
- 页面只依赖提交端口类型，不直接 import HTTP Writer factory。

### 2.3 HTTP 边界类型收紧

Reader/Writer 接口增加 `this: void`，明确这些传输能力不依赖对象绑定状态，允许协调器安全组合和测试，同时未改变任何 HTTP 路径、请求头、正文或默认注入关系。

## 3. 安全与失败语义

- 同一协调器存在 in-flight 提交时，在任何第二次网络调用前抛出 `ADJUDICATION_SUBMISSION_BUSY`；
- basis 签发永不自动重试；
- 非 retryable 错误和 Abort 永不自动重试；
- 第二次提交仍失败时直接结束，不进行第三次尝试；
- 提交成功后的投影读取失败、事项不一致、裁决 ID 不一致或动作数量不一致均只返回 `reload-required`；
- 结果、页面状态、阶段回调和错误提示均不含 basis token；
- 未使用 localStorage、sessionStorage、IndexedDB、Pinia、Cookie、URL、日志或遥测保存 token；
- 未把真实 Writer 加入 `TransferGateway`、providers、Mock、bootstrap 或路由 props。
