# ERP-NEW_2 阶段 5：调拨持久化命令检查点

> 日期：2026-08-02
> 分支：`codex/erp-new-2-rebuild`
> 基线提交：`147e32e5 feat: add transfer stock reservation skeleton`

## 1. 本检查点结论

调拨保存、提交、审批、发货、收货、批次收货、差异处理、草稿删除、取消和撤回现已统一经过持久化命令门面。每个 HTTP 写请求必须携带 `X-Request-Id`，命令台账与业务变更位于同一个数据库事务中。

这取代了调拨入口原先仅依赖 Redis 短时锁的防重方式。重复请求不再被简单拒绝，而是在请求身份和内容完全一致时返回首次持久化结果，不会重复冻结、扣减、入库、创建批次或推进状态。

## 2. 命令事务不变量

1. `request_id` 使用全局唯一键和 ASCII 二进制排序，大小写不同的标识不会被数据库折叠。
2. 请求指纹覆盖命令类型、登录用户、操作组织、目标资源和规范化请求内容。
3. 相同请求标识只能由同一用户、同一组织、同一命令和同一内容重放；任何不一致都默认拒绝。
4. 首次请求通过唯一键原子抢占 `PENDING` 行，业务成功后才在同一事务写入 `SUCCEEDED` 和首次结果。
5. 业务异常、结果保存冲突或事务提交失败会同时回滚命令行与业务变化，不留下“命令成功但库存失败”或相反状态。
6. 并发重复请求由 InnoDB 唯一键和锁等待串行化；首笔提交后重放结果，首笔回滚后允许另一笔重新抢占。
7. 命令执行器使用 `Propagation.MANDATORY`，禁止脱离外层业务事务单独写入台账。
8. 持久化结果只允许从 `PENDING` 完成一次，普通业务没有覆盖或删除历史结果的入口。

## 3. 接入范围

| 命令 | 类型 |
| --- | --- |
| 草稿保存 | `TRANSFER_DRAFT_SAVE` |
| 提交审批 | `TRANSFER_SUBMIT` |
| 审批处理 | `TRANSFER_APPROVE` |
| 分批发货 | `TRANSFER_DELIVER` |
| 整单兼容收货 | `TRANSFER_RECEIVE` |
| 发货批次收货 | `TRANSFER_SHIPMENT_RECEIVE` |
| 差异裁决 | `TRANSFER_DISCREPANCY_RESOLVE` |
| 草稿删除 | `TRANSFER_DRAFT_DELETE` |
| 调拨取消 | `TRANSFER_CANCEL` |
| 审批撤回 | `TRANSFER_WITHDRAW` |

控制器使用 `@PersistentCommand` 标记这些入口，并强制读取 `X-Request-Id`。原来的 `@IdempotentSubmit` 已从这些入口移除，避免 Redis 在持久化结果重放之前先返回“重复提交”。

新前端 HTTP 客户端继续默认生成随机 `X-Request-Id`，并新增显式 `requestId` 参数。调用方在网络超时或响应丢失后可以复用同一个标识安全重试；不符合 8～128 位安全字符约束的标识会在发出网络请求前被拒绝。

## 4. 数据结构

增量脚本：`sql/erp_inventory_transfer_command_20260802.sql`

新增表：`inv_transfer_command`

关键字段包括：

- 全局唯一请求标识、稳定命令类型和 SHA-256 请求指纹；
- 登录用户、操作组织和目标资源审计维度；
- `PENDING` / `SUCCEEDED` 状态；
- 首次结果 Java 类型、JSON 结果和完成时间。

脚本不包含 `USE`、数据库名、账号、密码、种子数据或环境地址。本检查点没有执行该脚本。
