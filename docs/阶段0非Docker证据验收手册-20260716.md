# 阶段 0 非 Docker 证据验收手册（2026-07-16）

## 1. 适用范围与安全边界

本手册只用于阶段 0 的非 Docker 技术证据采集和离线验收，完全不执行 Docker、Docker Compose 或 ECS 操作，不拉取镜像、不启停容器、不改动远程服务。数据库采集器 `scripts/stage0_db_evidence.py` 只允许固定的聚合查询，在单个 MySQL 连接中显式设置 `REPEATABLE READ`、只读事务和一致性快照；它不执行迁移、DML 或结构变更。

合并或复核不包含 Docker 发布镜像的候选时，先运行签署源码静态门禁：

```bash
bash scripts/verify-sign-final-confirmation-cutover.sh --source-only-static
```

该模式仍校验源码 SQL、manifest/list、SHA-256、遗留任务迁移语义和已退役接口，但明确不校验 `docker/` 下的发布镜像或 bootstrap 清单。默认 `--static` 和 `--preflight` 保持失败关闭，不会在 Docker 发布物缺失时自动降级；源码门禁通过不能替代发布镜像一致性、目标库预检或生产上线批准。

这是技术证据门禁，不是上线授权。即使下述命令全部返回 0，也不得宣称生产就绪，更不能代替变更审批、备份恢复演练、真实业务验收和人工签字。

## 2. MySQL 只读证据前置条件

1. 先取得目标库和采集时间窗的明确批准，再由凭据系统下发仅有读权限的 MySQL 账号。
2. MySQL client options 文件必须位于代码仓库之外，路径必须是绝对路径，不得为符号链接，必须由当前用户或 `root` 所有，权限必须精确为 `0600`。
3. 不得在命令行、环境变量、证据 JSON、Shell 历史或发布摘要中保存密码。不得使用 `--password` 或 `MYSQL_PWD`。
4. 采集器要求候选仓库是已提交的干净工作树；运行 `git status --short` 必须没有输出。这是为了使证据能绑定唯一候选提交。
5. 变更审批中必须先确定一个非敏感、稳定且唯一的目标标签，例如 `prod-cn-primary`。采集与验证都要显式传入同一个 `--target-label`；它用于把证据绑定到审批上下文，但不是数据库实例的密码学身份证明。
6. `collect` 必须显式传入批准的 `--host`、`--port`、`--user`；client options 文件中的同名值不能代替这三个 CLI 目标参数。采集子进程会禁用隐藏的 `.mylogin.cnf`，避免 login-path 把连接改到另一实例。

配置文件只允许一个 `[client]` 分组及连接、认证、TLS 白名单选项；`!include` / `!includedir`、其他分组、重复选项和 `execute` / `init-command` / `pager` / `tee` 等执行型选项都会失败关闭。建议只把密码和 TLS 材料留在文件中；下面只是占位符：

```ini
[client]
password=<delivered-by-credential-system>
ssl-mode=VERIFY_IDENTITY
ssl-ca=/secure/mysql/approved-ca.pem
```

由凭据系统写入仓库外的受控路径后，再独立确认权限：

```bash
chmod 600 /secure/mysql/stage0-readonly.cnf
git status --short
```

## 3. 证据档位与时效

| 档位 | 用途 | 最长有效期 |
| --- | --- | --- |
| `pre-maintenance` | 维护窗开始前的只读前置条件检查 | 24 小时 |
| `release-ready` | 候选发布决策前的更严格只读检查 | 2 小时 |

有效期从证据的 `collectedAt` 开始计算。过期证据必须在同一候选提交上重新采集，不得修改时间戳。`release-ready` 不能由较旧的 `pre-maintenance` 证据代替。

## 4. `pre-maintenance` 采集与离线验证

先在受控的仓库外目录中准备证据文件：

```bash
mkdir -p /secure/stage0-evidence
chmod 700 /secure/stage0-evidence

python3 scripts/stage0_db_evidence.py collect \
  --profile pre-maintenance \
  --defaults-file /secure/mysql/stage0-readonly.cnf \
  --host readonly-db.example.internal \
  --port 3306 \
  --user evidence_reader \
  --database erp_business \
  --target-label prod-cn-primary \
  --output /secure/stage0-evidence/pre-maintenance.json
```

`erp_business` 是非敏感示例名，实际执行时必须换成已批准的明确目标库名。默认拒绝覆盖已有 JSON 或 `.sha256` 伴随文件；只有在变更记录已明确要求重采时，才可审慎加上 `--overwrite`。

验证命令不连接 MySQL，但会使用当前仓库的提交和契约重新校验证据：

```bash
python3 scripts/stage0_db_evidence.py verify \
  --profile pre-maintenance \
  --database erp_business \
  --target-label prod-cn-primary \
  --evidence /secure/stage0-evidence/pre-maintenance.json
```

## 5. `release-ready` 采集与离线验证

`release-ready` 必须独立采集，不得改名或复用另一档位的文件；除共同前置条件外，它还要求新业务 manifest 声明的 13 张创建表都是基础表、7 个灰度开关各只有一条且为显式 false，并执行签署 seal/角色当前态、统一审批、OA legacy 与库存安全开关等发布后检查：

```bash
python3 scripts/stage0_db_evidence.py collect \
  --profile release-ready \
  --defaults-file /secure/mysql/stage0-readonly.cnf \
  --host readonly-db.example.internal \
  --port 3306 \
  --user evidence_reader \
  --database erp_business \
  --target-label prod-cn-primary \
  --output /secure/stage0-evidence/release-ready.json

python3 scripts/stage0_db_evidence.py verify \
  --profile release-ready \
  --database erp_business \
  --target-label prod-cn-primary \
  --evidence /secure/stage0-evidence/release-ready.json
```

## 6. 返回码与证据绑定

| 返回码 | 含义 | 验收处置 |
| --- | --- | --- |
| `0` | 采集完整且所有检查通过，或离线验证通过 | 仅表示本技术门禁通过 |
| `1` | 证据结构、哈希和契约有效，但至少一项业务检查为 `blocked` | 失败关闭，不得继续 |
| `2` | 采集、MySQL 协议、输出、时效、权限或离线验证失败 | 不得将其解释为通过；查询中断不会产生合格通过证据 |

每份证据绑定以下候选状态：

- 完整 Git 候选提交 SHA；
- 采集器 `scripts/stage0_db_evidence.py` 的 SHA-256；
- 由档位、固定检查集、预期值和每条查询 SHA-256 生成的查询契约 SHA-256；
- 四份发布 manifest 的 SHA-256：新业务、统一审批扩展、签署最终确认和库存原生审批关闭契约。

采集器会创建 `<name>.json` 和 `<name>.json.sha256` 两个普通文件，两者权限均必须精确为 `0600`，所有者必须是当前用户或 `root`，且不得为符号链接。发布证据对时使用同目录排他锁；无 `--overwrite` 时不会覆盖并发或迟到文件，显式覆盖的第二步失败会回滚旧 pair。若进程被强杀或主机断电，可能留下 `.lock` 或不匹配 pair，离线验证会失败；必须先确认没有采集器仍在运行并保留现场，再由授权人员处理，不能把残留当成通过证据。离线验证会重算伴随文件、提交、采集器、查询契约和四份 manifest 的哈希，并逐项复算检查结果。

## 7. Prometheus 规则与实际加载证据

先在候选仓库中用已安装的 `promtool` 执行严格检查；缺少 `promtool` 时必须失败：

```bash
PATH=/path/to/promtool:$PATH bash scripts/verify-new-business-monitoring.sh --require-promtool
```

该命令验证本地规则文件中的 10 条唯一告警及其表达式，但不证明生产 Prometheus 已加载这些规则。实际加载证据必须来自已批准 Prometheus 实例的 `/api/v1/rules?type=alert` 响应体，并满足：

- API 顶层 `status` 为 `success`；
- 存在且只存在一个 `erp-new-business-20260714` 组，`interval` 为 60 秒；
- 目标组按固定顺序恰好包含候选契约中的 10 个唯一告警名；
- 每条规则都是 `type=alerting`、`health=ok` 且 `state=inactive`；
- 每条 API `query` 去除首尾空白后必须与固定候选 `expr` 一致，`duration`、`severity` 与 `release` 也必须匹配固定发布契约。

仅保存响应体的最小脱敏 JSON：`status`、目标组 `name` / `interval`，以及各规则的 `name` / `type` / `health` / `state` / `query` / `duration` 和静态 `severity` / `release` 路由标签。认证应由受控代理、mTLS 或组织批准的凭据注入机制完成。不得保存 Authorization 头、Cookie、Token、请求/响应头、活动告警实例、注释、值、其他标签、`curl --trace` 输出、浏览器 HAR、Prometheus 配置或投影前的原始响应。下面的失败关闭示例不包含凭据：

```bash
(
  set -euo pipefail
  mkdir -p output/gray
  umask 077
  target=output/gray/prometheus-rules-alerts.json
  temporary="${target}.tmp"
  trap 'rm -f "$temporary"' EXIT
  rm -f "$temporary"
  curl --fail --silent --show-error --get \
    "${PROMETHEUS_URL:?set the approved endpoint outside this command}/api/v1/rules" \
    --data-urlencode 'type=alert' \
    | jq --arg group 'erp-new-business-20260714' \
      '{status, data: {groups: [.data.groups[]
        | select(.name == $group)
        | {name, interval, rules: [.rules[]
          | {name, type, health, state, query, duration,
             labels: {severity: .labels.severity, release: .labels.release}}]}]}}' \
      > "$temporary"
  chmod 600 "$temporary"
  mv "$temporary" "$target"
  shasum -a 256 "$target"
)
```

不得用页面截图、`promtool` 文本输出、手写声明或仓库中的 YAML 代替 Rules API JSON。该 JSON 应按 [`20260714-new-business-gray-operations-runbook.md`](releases/20260714-new-business-gray-operations-runbook.md) 纳入灰度证据，并由灰度门禁校验本地候选 SHA 以及 API 返回的 10 条必需运行语义。`candidateRulesSha256` 不是服务端 SHA 证明；Rules API 不提供源文件 SHA，投影又为避免泄露而丢弃注释与其他标签，所以字节级部署一致性必须另由监控主机的部署日志/变更记录闭合。

灰度门禁还会固定整份 `scripts/new-business-daily-reconciliation.sql` 的 SHA-256，并把它与前后 summary 中的 `reconciliationSqlSha256`、19 个 issue code 逐项对齐；查询被注释、追加恒假条件、空 `issues` 、缺任一 code、布尔值冒充数字、复用同一 artifact 或前后时间倒置都会失败。七次开关审计 ID 必须唯一，开关、两阶段灰度、后对账、回滚演练与签字时间必须按操作顺序递增。

## 8. 证据局限与外部闭合项

必须按以下边界解读证据：

- 数据库证据中的计数、表名和列名契约不是目标库的完整列类型、`default`、符号性（signedness）或全量 schema 指纹。JSON 中的 `schemaFingerprintSha256` 只是选定聚合指标与目标标识的哈希，不得扩大解读。
- 当前状态检查不证明历史迁移曾按顺序执行，不证明备份可恢复，不证明采集者/操作者身份，不证明目标环境已批准，也不证明签署 2026-07-11 至 2026-07-14 的完整前置链已执行。`targetLabel` 只是审批上下文标签；同名标签仍需由外部审批和运行审计确认指向正确实例。
- JSON 伴随文件的 SHA-256 只能提供完整性检查，不是数字签名、时间戳认证或真实性证明。操作审计、变更单和独立存证仍需外部系统承担。
- 本地 `promtool` 通过只证明候选 YAML 可被解析且满足本地契约，不证明生产 Prometheus 已加载或正在评估这些规则。Rules API 最小投影通过也只证明 10 条必需运行语义，不证明服务端文件与候选 YAML 字节级相同。

以下项目仍必须由外部证据闭合，任何一项缺失都不得批准生产上线：

1. 已批准的目标库、数据库名、读取窗口和最小权限只读账号；
2. 带来源、时间、哈希、MySQL 版本和成功恢复演练记录的可恢复备份；
3. 库存 2026-07-10 前置结构的独立证据；
4. OA legacy 记录数为 0 的目标库证据；
5. 签署 2026-07-11 至 2026-07-14 完整前置链、在途任务处置和人工切换变更单；
6. 真实角色 UAT、两阶段灰度、灰度前后零异常对账、关闭入口后的在途业务回滚演练和业务/运维/发布多方签字；
7. 实际生产 Prometheus Rules API 返回的 10 条告警加载、健康、非活动状态与固定运行语义匹配证据，以及监控主机部署日志/变更记录中的候选文件 SHA 追溯。

## 9. 验收结论记录

验收记录应同时标注候选提交、目标环境审批号、`target-label`、两份数据库证据路径与 SHA-256、Prometheus Rules API 证据路径与 SHA-256、返回码、执行时间和独立复核人。仅当本手册技术门禁和上述所有外部闭合项均有可复核证据时，才能由授权人员另行作出上线决策。
